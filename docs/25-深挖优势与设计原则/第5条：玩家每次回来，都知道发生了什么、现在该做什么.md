
这条差异化不应该只是：

> “AI 自动生成上次剧情摘要。”

普通摘要只能回答：

```text
上次大概讲了什么
```

但玩家真正需要的是：

```text
我现在在哪里？
现在是什么时间？
我的角色当前怎么样？
我离开后发生了什么？
哪些事情已经确认？
哪些只是证词或玩家猜测？
我有哪些私人信息还没分享？
队伍上次决定了什么？
哪些计划已经过期？
现在有没有必须立刻处理的事情？
接下来有哪些合理方向可以选择？
```

我建议把这套能力命名为：

# **Campaign Continuity / 战役连续性系统**

玩家端产品可以叫：

# **继续战役**

一句产品定义：

> **AI-Keeper 将当前状态、上次会话、玩家已知信息、未完成行动和队伍计划编译成一份按视角生成的“续团简报”，让玩家在一分钟内恢复情境，但不利用隐藏真相替玩家决定下一步。**

---

# 一、它解决的不是“忘记剧情”，而是四种断层

玩家回来时，可能面对四种不同问题。

## 1. 事实断层

玩家忘了：

```text
谁死了
谁还活着
门开没开
钥匙在谁手上
队伍现在在哪
当前 HP / SAN 是多少
```

这部分必须来自权威状态和事件，不允许 AI 凭记忆补全。

---

## 2. 认知断层

玩家不知道：

```text
这件事自己角色是否知道
这是队伍公开信息还是他人私密信息
某条线索是否已经分享
自己缺席期间发生的事，角色是否在场
```

这部分需要“玩家知道”和“角色知道”分开。

---

## 3. 推理断层

玩家忘了：

```text
队伍怀疑谁
为什么怀疑
有哪些开放问题
哪些假说已经被否定
哪些线索还没整理
```

这部分来自调查工作台，不能由 AI 直接给出真相。

---

## 4. 行动断层

玩家不知道：

```text
现在轮到我了吗
我上次行动是否已提交
是否有一个 Luck 消耗等待确认
队伍是否已经决定去某个地点
我答应 NPC 的事是否到期
下一场什么时候开始
```

这部分需要 Transaction、Schedule、语义合同和承诺账本。

---

# 二、不能只有一种“回来”

必须区分不同的返回场景，否则很容易重复开局、重复播放或给出错误摘要。

|返回类型|场景|系统应该做什么|
|---|---|---|
|`reconnect`|同一场游戏断线几分钟|同步状态和漏掉的可见事件|
|`short_return`|切后台、离开半小时|显示“你离开后发生了什么”|
|`next_session`|下一次正常开团|显示上局总结和本局开场状态|
|`missed_session`|玩家缺席了一整局|区分玩家可知与角色可知的缺席补课包|
|`long_return`|数周或数月后回来|完整续团简报和人物、目标、线索回顾|
|`late_join`|战役中途新加入|只展示 Host 允许的入场背景|
|`checkpoint_restore`|房间从检查点恢复|显示当前分支变化，不把旧分支当当前事实|

因此不能简单地：

```text
每次打开页面都生成完整上局摘要
```

断线两分钟的玩家只需要：

```text
你的状态已同步
漏掉了 3 条可见事件
当前轮到玩家 B
```

而一个月没来的玩家才需要完整恢复包。

---

# 三、这项能力的核心对象：Continuity Packet

建议定义：

# **Continuity Packet / 续团包**

它不是一段 AI 文本，而是一组有来源的结构化视图。

```json
{
  "continuityPacketId": "cpk_xxx",
  "roomId": "room_xxx",
  "characterId": "char_a",
  "returnType": "next_session",
  "generatedAt": "2026-07-11T18:30:00Z",
  "baseSequence": 812,
  "currentSequence": 1047,
  "stateVersion": 87,
  "currentSituation": {},
  "sinceLastSeen": [],
  "characterChanges": [],
  "partyUpdates": [],
  "privateUpdates": [],
  "openThreads": [],
  "pendingDecisions": [],
  "commitments": [],
  "agreedPlans": [],
  "availableDirections": [],
  "nextSession": {},
  "sourceRefs": []
}
```

玩家界面只展示人能看懂的卡片，但底层必须结构化。

# 四、续团包首先回答三个问题

## 1. 我现在处于什么状态？

```text
当前位置
当前游戏内时间
当前场景
当前在场人物
当前可见威胁
当前角色 HP / SAN / MP / Luck
当前状态效果
当前装备和关键物品
当前回合或行动状态
```

## 2. 从我上次看到以后，发生了什么？

```text
Party 公开事件
本人私密事件
状态变化
获得或失去的物品
新分享的线索
NPC 状态变化
地图变化
计划变化
```

## 3. 现在有哪些事情需要我关注？

```text
立即需要处理的决策
上次未完成的行动
队伍已约定计划
开放问题
本人承诺
即将到期的事件
下一场时间
```

---

# 五、“发生了什么”不能只是一段总结

建议拆成五类变化。

## 1. 世界变化

来自 State：

```text
当前场景已切换
某扇门已经打开
某 NPC 已离开
地图区域已揭示
游戏时间推进
```

这些是当前权威状态。

---

## 2. 行动结果

来自 Transaction / Rule：

```text
谁做了什么
是否结算成功
是否消耗资源
状态如何变化
是否还在等待复核
```

---

## 3. 信息变化

来自 Clue / Projection：

```text
获得了新线索
谁分享了什么
某条私密信息变成 Party 已知
某条证词被补充
```

---

## 4. 调查变化

来自 Investigation：

```text
新增开放问题
新增假说
假说被证伪
出现新的证词矛盾
队伍给某线索加了标签
```

注意：

```text
新增假说 ≠ 新增事实
```

---

## 5. 社交与承诺变化

例如：

```text
答应 NPC 明晚前交付药品
队伍决定先去档案馆
某 NPC 表示愿意提供帮助
某角色欠下人情
```

这些不是 HP 或线索，但对长期连续性非常重要。

---

# 六、每条摘要都必须有状态标签

不能把所有信息写成同一种肯定句。

建议至少显示：

```text
已确认
亲眼观察
NPC 证词
队伍共享
本人私密
玩家假说
存在争议
已证伪
已过期
待复核
```

例如：

> **已确认**  
> 队伍已经进入医院地下档案室。  
> 来源：场景切换事件 #1031。
> 
> **NPC 证词**  
> 护士声称教授昨晚没有进入地下室。  
> 来源：事件 #998。
> 
> **存在争议**  
> 该证词与玩家 A 的目击记录冲突。
> 
> **尚未知**  
> 教授进入地下室的目的。

这比：

> “护士撒谎，教授去过地下室。”

安全得多，也更尊重玩家推理。

---

# 七、必须区分“玩家知道”和“角色知道”

这是你们非常有辨识度的一项能力。

玩家可能缺席了一局，但其他玩家会告诉他：

```text
OOC 上发生了什么
```

他的角色可能并不在场，也没有被告知。

因此续团包可以有两个视图。

## 玩家补课视图

用于让现实中的玩家跟上游戏：

```text
上局 Party 公开剧情摘要
队伍做了哪些决定
当前游戏状态
```

## 角色认知视图

用于避免元游戏：

```text
你的角色实际知道什么
谁向你分享了什么
哪些事情你的角色不在场
哪些信息需要由队友在游戏中告知
```

示例：

> **玩家补课**  
> 上局队伍在地下室发现了一间密室。
> 
> **你的角色认知**  
> 你的角色当时不在场，目前尚未在游戏内获知密室的存在。
> 
> **可选操作**  
> 请求队友在角色内向你说明。

房间可以设置：

```text
full_player_recap
character_only
hybrid
```

但无论采用哪一种，系统都必须明确区分 OOC 知识与角色知识。

---

# 八、不能复用 player_sequences 表示“玩家理解到哪里”

你们已有的 `player_sequences` 更接近：

```text
投递游标
```

它表示服务端已经处理到哪个事件边界，并不表示：

```text
玩家认真读过
玩家理解了
玩家记住了
玩家确认摘要
```

建议新增：

# `PlayerContinuityCursor`

```json
{
  "roomId": "room_xxx",
  "characterId": "char_a",
  "lastDeliveredSequence": 1047,
  "lastOpenedSequence": 1020,
  "lastAcknowledgedRecapSequence": 980,
  "lastAcknowledgedStateVersion": 84,
  "lastSessionId": "session_12",
  "updatedAt": "..."
}
```

需要区分：

```text
服务器发到了哪里
玩家打开到了哪里
玩家确认看完哪次续团包
```

否则系统会把“已发送”误当成“玩家已经知道”。

---

# 九、还需要 Session Handoff：离开时就为下次回来做准备

不能等玩家回来后再让 AI临时总结几百条事件。

每次 Session 结束时，系统应生成：

# **Session Handoff / 会话交接包**

它包含：

```text
本局最终状态
本局确认的新事实
本局获得的新线索
本局角色和物品变化
本局产生的新矛盾
未完成行动
队伍约定的计划
玩家承诺
下一场时间
```

它是有来源的结构化快照。

下次回来时：

```text
上次 Handoff
+
玩家离开后的安全 Delta
+
当前状态
=
Continuity Packet
```

这样更稳定，也更便宜。

---

# 十、Session Handoff 不能自动决定队伍计划

Session 结束时可以让玩家确认：

> **队伍下次计划**
> 
> 目前记录为：
> 
> 1. 先去医院档案室；
>     
> 2. 查找 B-17 的旧建筑图；
>     
> 3. 询问护士长值班记录。
>     
> 
> [确认] [修改] [暂不确定]

这条计划来自玩家确认。

AI 可以根据讨论提出候选，但不能把一句：

> “也许可以去档案馆看看。”

自动写成：

```text
队伍下次一定去档案馆
```

建议计划对象：

```json
{
  "planId": "plan_xxx",
  "scope": "party",
  "statement": "下一步前往医院档案室",
  "status": "agreed",
  "createdBy": "party_confirmation",
  "sourceRefs": [],
  "validity": "current",
  "blockedReason": null
}
```

---

# 十一、“现在该做什么”不能变成 AI 代替玩家决策

这部分最容易走偏。

不应该显示：

> **AI 推荐：立刻去北仓库。**

因为这可能：

- 利用隐藏真相；
    
- 暗示正确路线；
    
- 把玩家变成执行器；
    
- 破坏开放世界探索。
    

应该把“下一步”分成四类。

---

## 1. 现在必须处理

这些是系统义务，不是剧情建议：

```text
确认是否花费 Luck
回应一个协同行动邀请
等待 Host 复核
重新同步状态
确认是否分享私密线索
选择下一回合动作
```

标题可以是：

# **需要你处理**

---

## 2. 队伍已约定计划

由玩家确认过：

```text
去医院档案室
与记者会面
把处方交给医生检查
```

标题：

# **队伍上次决定**

---

## 3. 尚未解决的问题

来自调查工作台：

```text
教授为什么进入地下室？
B-17 对应哪扇门？
护士证词为何矛盾？
```

标题：

# **仍未解决**

---

## 4. 当前可以尝试的方向

只基于当前可见场景和已知信息：

```text
与当前在场 NPC 对话
检查当前可见物体
查看已共享线索
移动到已知相邻地点
继续某个开放问题
```

标题：

# **当前可做**

不要称为：

```text
正确下一步
推荐路线
最优行动
```

---

# 十二、availableDirections 必须是“能力提示”，不是“答案提示”

例如玩家当前在档案室：

```text
可见实体：
旧书架
登记台
管理员
锁着的后门
```

系统可以显示：

```text
与管理员交谈
查看登记台
检查旧书架
询问关于 B-17 的记录
移动到已知出口
```

这是当前场景的可交互能力。

系统不能利用隐藏模组知道：

```text
关键线索藏在第三排书架
```

然后把“检查旧书架”高亮为最重要。

排序只能依据：

```text
玩家置顶
最近讨论
队伍计划
当前可见
尚未处理
```

不能依据：

```text
真相相关度
结局相关度
隐藏 Trigger 权重
```

---

# 十三、计划和方向会过期，必须检测陈旧状态

例如上次队伍决定：

> 去档案馆找管理员。

但玩家回来时：

```text
档案馆已失火
管理员已离开
地图入口已封锁
```

不能继续显示：

```text
下一步：去档案馆找管理员
```

应显示：

> **原计划已受阻**  
> 队伍原本计划前往档案馆，但档案馆目前已关闭。  
> 来源：事件 #1040。
> 
> **需要重新决定方向**

这叫：

# **Plan Validity / 计划有效性**

状态可以是：

```text
current
completed
blocked
stale
cancelled
superseded
```

AI 只能根据当前已知状态判断计划是否仍可执行，不能替玩家选新计划。

---

# 十四、承诺、债务和期限必须进入续团包

长团经常遗忘：

```text
答应明晚前把药送给医生
欠记者一个人情
NPC 约定凌晨两点见面
三天后仪式开始
租来的汽车明天要归还
```

建议定义：

# `Commitment`

```json
{
  "commitmentId": "commit_xxx",
  "actorRef": "char_a",
  "beneficiaryRef": "npc_doctor",
  "statement": "在午夜前送回药品",
  "dueGameTime": "1926-11-15T00:00:00",
  "status": "open",
  "sourceRefs": [
    {
      "type": "event",
      "sequence": 912
    }
  ]
}
```

续团时显示：

> **即将到期**  
> 你答应医生在午夜前归还药品。  
> 当前时间：23:20。  
> 剩余游戏内时间：40 分钟。

这是真正会影响玩家“现在该做什么”的信息。

---

# 十五、还要显示 Pending Decision，而不仅是 Pending Action

玩家回来时可能不是要提交新行动，而是要完成之前中断的决策。

例如：

```text
是否花费 4 点 Luck
是否接受 Push Roll
是否公开某条私密线索
是否接收一件重要物品
是否参与联合行动
是否接受 Host 的规则复核结果
```

定义：

```text
PendingDecision
```

它必须比开放问题优先展示。

界面顺序建议：

```text
1. 必须处理
2. 当前危险或回合状态
3. 队伍已约定计划
4. 未解决问题
5. 当前可做
```

---

# 十六、续团摘要必须按玩家影响排序，而不是按剧情重要性排序

AI 不能读取 Host 真相后决定：

```text
这条信息最重要
```

推荐排序依据：

```text
直接改变当前角色状态
影响当前场景
与未完成行动相关
与玩家已知线索相关
被玩家置顶
属于 Party 已约定计划
存在期限
最近发生
```

禁止依据：

```text
最终真相相关度
隐藏结局权重
模组关键线索标签
未公开 Trigger 重要度
```

---

# 十七、摘要生成必须“先结构化，后叙述”

错误流程：

```text
把过去 300 条事件交给 AI
→ 请总结
```

正确流程：

```text
1. 读取当前 State Snapshot
2. 读取玩家 continuity cursor
3. 查询 cursor 之后的 viewer-safe events
4. 读取角色变化
5. 读取物品变化
6. 读取 Clue / Investigation Diff
7. 读取 pending actions / decisions
8. 读取 Party plan / commitments
9. 确定性生成结构化 Continuity Packet
10. AI 只负责把已允许字段改写成易读语言
11. 对摘要中的每个 Claim 做 sourceRef 覆盖检查
12. Safety 最终过滤
```

AI 不能向 Continuity Packet 增加新事实。

---

# 十八、续团包必须支持不同详细程度

玩家可以选择：

## 30 秒

```text
现在在哪里
当前角色状态
最重要的三项变化
当前必须处理
队伍上次计划
```

## 2 分钟

```text
本局/上局摘要
新增线索
人物变化
开放问题
计划与承诺
```

## 完整回顾

```text
按时间线查看
每项带来源
角色与物品完整变化
调查工作台 Diff
全部 Party 已知事件
```

这比强迫所有玩家阅读一篇长 AI 总结更实用。

# 十九、玩家界面建议

玩家进入房间后，先看到：

# **继续战役**

---

## 卡片一：你现在在哪里

```text
圣玛丽医院 · 地下档案室
游戏时间：1926 年 11 月 14 日 23:20
当前在场：陈教授、安娜、你
```

角色状态：

```text
HP 8 / 12
SAN 54
Luck 31
状态：轻伤
```

---

## 卡片二：从你上次离开后

> **已确认**
> 
> - 队伍进入了地下档案室。
>     
> - 安娜打开了北侧铁门。
>     
> 
> **队伍共享**
> 
> - 玩家 A 分享了“烧焦处方与医院高层有关”的摘要。
>     
> 
> **存在争议**
> 
> - 护士的证词与教授的行动记录发生冲突。
>     

按钮：

```text
查看来源
查看完整时间线
```

---

# 二十、一个完整场景示例

玩家 A 两周没有上线。

在他离开后发生：

```text
1. 队伍进入地下档案室。
2. 玩家 B 找到旧建筑平面图。
3. 玩家 C 私下发现院长签名，但没有分享。
4. 队伍决定下一步检查 B-17。
5. 角色 A 的急救包被队友使用了一次。
6. NPC 医生提醒午夜前归还药品。
```

玩家 A 回来时：

## 玩家 A 应该看到

> ## 欢迎回来
> 
> **当前地点**  
> 圣玛丽医院地下档案室。
> 
> **你离开后发生了什么**
> 
> - 队伍进入了地下档案室。

>

>     
> - 你的急救包被使用了一次，剩余 1 次。
>     
> 
> **即将到期**
>

>     
>

# 二十一、缺席角色的回归包

如果角色 A 在剧情里也缺席，续团包应额外提示：

> **玩家补课信息**  
> 队伍已经进入地下档案室。
> 
> **角色实际已知**  
> 你的角色尚未在游戏内获知地下档案室中的发现。
> 
> **建议的角色内衔接**
> 
> - 让队友向你的角色说明；
>     
> - 由 Host 选择一个合理的角色回归场景；
>     
> - 保持部分信息未知。
>     

注意这里“建议”是衔接方式，不是调查答案。

# 二十二、玩家每次回来，也应该知道“什么没有发生”

这是一项很细但很有用的能力。

例如：

```text
你的上一条行动没有成功提交
你没有消耗 Luck
你的物品没有被转移
你的私人线索没有被分享
你没有错过角色专属事件
```

尤其在网络异常后，系统可以明确说：

> 上次的行动未进入结算，没有消耗行动或资源，可以重新提交。

这会显著减少玩家的不安和重复点击。

# 二十三、Host 不在线时也能生成续团包

因为续团包来自：

```text
State
Journal
Timeline
Clue
Investigation
Character
Item
Transaction
Schedule
```

而不是依赖 Host 手工总结，所以：

```text
Host 不在线
AI provider 暂时不可用
```

玩家仍然可以看到结构化版本：

```text
当前状态
上次变化
待处理事项
队伍计划
开放问题
下一场时间
```

AI 不可用时只是没有自然语言润色，核心数据仍然存在。

这也是你们这条差异化的关键：

> **连续性来自可重建的数据链，不来自某个 Host 或某次 AI 总结的记忆。**

# 二十四、建议新增独立模块

我认为这一条值得新增一个明确模块：

# **27-Continuity 战役连续性与续团系统**

```text

                    ↓

                    ↓

                    ↓
        AI Language Renderer（可选）
                    ↓
            Player Continue UI
```

# 二十九、工程验收最关键的测试

```text
1. 玩家 A 的续团包不包含玩家 B 私密事件。
2. Host-only 真相不进入任何 Player continuity packet。
3. 玩家缺席时，玩家补课视图和角色认知视图不同。
4. reconnect 不会触发完整 next-session recap。
5. 同一 ContinuityCursor 重复生成结果稳定。
6. 当前状态来自 State，不从 AI 摘要推导。
7. SinceLastSeen 只包含 cursor 之后的可见事件。
8. Party plan 必须来自玩家确认，而不是 AI 自动决定。
9. 已失效计划能标记 blocked/stale。
10. PendingDecision 比开放问题优先显示。
11. Commitment 能按游戏内时间提示到期。
12. AI 不会根据隐藏真相排序“最重要”内容。
13. AvailableDirection 只使用当前可见实体和已知信息。
14. 不显示隐藏线索数量或不可见事件数量。
15. AI 生成的摘要每条关键 Claim 有 SourceRef。
16. AI 不可用时结构化续团包仍可展示。
17. Session Handoff 不把玩家假说写成确认事实。
18. Player A 和 Player B 同时回来，看到不同但正确的续团包。
19. Checkpoint restore 后只显示当前分支状态。
20. 玩家角色库后续编辑不改变历史 Continuity Packet。
```

最关键的一条：

> **同一房间、同一时刻，玩家 A、玩家 B 和 Host 打开“继续战役”，看到的内容不同，但当前状态、来源和权限全部正确。**

# 三十、衡量是否成功

|指标|目标方向|
|---|---|
|玩家回来后理解当前局面的时间|控制在 60 秒内|
|Session 开始时重复解释时间|显著下降|
|“上次发生了什么”询问次数|显著下降|
|玩家重复提交旧行动|接近 0|
|玩家错过 pending decision|接近 0|
|私密信息进入错误 recap|必须为 0|
|Host-only 真相泄露|必须为 0|
|计划陈旧但未提示|持续下降|
|Continuity Packet SourceRef 覆盖率|接近 100%|
|玩家打开后直接进入行动的比例|提升|
|长期团回流率|提升|
|间隔一个月后的回归成功率|提升|
|Host 手工 recap 时间|显著下降|

最直接的产品目标可以是：

> **玩家间隔一个月回来，在 60 秒内知道自己在哪里、角色发生了什么、队伍掌握了什么、哪些问题还没解决、现在有哪些事情需要自己处理。**

# 最终收敛

这条能力真正的壁垒不是：

```text
AI 能写一篇漂亮的剧情总结
```

而是：

```text
知道玩家上次看到哪里
知道玩家和角色分别知道什么
知道当前世界状态
知道哪些行动还没完成
知道队伍真正确认过什么计划
知道哪些计划已经失效
知道哪些承诺即将到期
知道哪些方向当前可行
知道哪些内容绝不能透露
```

最终产品定义可以写成：

> **AI-Keeper 的续团系统会从权威状态、事件日志、角色和物品变化、调查工作台、待处理决策和队伍确认计划中，为每个玩家编译一份按视角隔离、带来源的 Continuity Packet；它帮助玩家迅速恢复上下文和行动能力，但不利用隐藏真相替玩家选择下一步。**
