

这一块如果处理得好，会成为你们继“可信记忆、透明裁决、调查工作台、模组编译器”之后的又一条核心差异化。

先给结论：

> **角色卡不只是数值表，而是玩家身份、规则能力、当前状态、认知边界和成长历史的组合。**  
> **物品也不只是背包里的一行文字，而是有来源、所有权、持有者、状态、能力、可见性和变化历史的世界资产。**

建议把这套能力定义为：

# **角色运行体 + 物品资产账本**

英文可以叫：

```text
Character Runtime & Asset Ledger
Living Character System
Character and Inventory Ledger
```

一句产品定义：

> **玩家可以导入各种旧角色卡，系统自动映射到对应规则；当前状态、技能来源和物品效果始终可解释，AI 可以理解玩家如何使用物品，但不能伪造数值、凭空创造物品或直接修改角色状态。**

---

# 一、先把角色卡拆成六层

目前最危险的设计，是把所有内容都塞在：

```text
characters.xlsx_data
```

然后：

```text
角色背景从这里读
技能从这里读
当前 HP 也从这里读
物品也从这里读
状态修改又写回这里
```

这会造成：

- 角色卡基线和当前状态混乱；
    
- 导入格式绑死业务逻辑；
    
- AI 能看到不该看到的私密背景；
    
- 当前 HP、SAN 与 Host HUD 不一致；
    
- 房间内变化污染玩家原始角色；
    
- 角色跨战役时无法判断哪些变化应保留；
    
- 规则系统升级后难以迁移。
    

建议拆成六层。

## L0：原始来源 `CharacterSource`

保存玩家导入的原始角色卡：

```text
PDF
扫描图片
XLSX
CSV
JSON
YAML
其他平台导出
手工创建表单
模组预设角色
```

这一层用于：

```text
来源追踪
重新解析
人工核对
导入失败回退
```

它不能直接作为当前游戏状态。

---

## L1：规则模板 `CharacterSchema`

由规则包定义：

```text
有哪些属性
有哪些技能
字段类型是什么
字段范围是什么
哪些值是基础值
哪些值是派生值
如何计算 HP / MP / SAN
哪些动作可以点击
角色卡如何展示
如何从旧版本迁移
```

例如 CoC 7e：

```text
STR
CON
SIZ
DEX
APP
INT
POW
EDU

HP
MP
SAN
Luck

Spot Hidden
Library Use
Psychology
Listen
...
```

D&D、PF2e 或其他系统则有完全不同的 Schema。

所以正确设计不是做一个“万能超大角色卡”，而是：

```text
通用角色核心
+
规则系统扩展 Schema
```

---

## L2：角色档案 `CharacterProfile`

保存相对稳定的角色身份：

```text
角色姓名
公开昵称
头像
代词
职业
年龄
外貌
背景
关系
长期特质
玩家公开说明
私密背景
与 Host 分享的秘密
```

这一层不是当前战斗或场景状态。

---

## L3：房间角色实例 `RoomCharacterInstance`

玩家把角色带入房间时，创建一个房间快照。

```text
Character Library Profile
        ↓ 加入房间时复制
RoomCharacterInstance
```

必须避免：

```text
运行中的房间实时引用玩家角色库原件
```

否则玩家在外面编辑角色卡，会直接改变进行中的战役。

建议：

```text
characterLibraryId
roomCharacterId
sourceCharacterRevision
roomId
moduleVersionId
rulesetVersion
createdAt
```

房间实例创建后固定基线。

---

## L4：运行态 `CharacterRuntimeState`

保存当前房间里的即时状态：

```text
currentHP
currentSAN
currentMP
currentLuck
conditions
temporaryModifiers
injuries
equippedItems
currentLocation
combatStatus
temporaryResources
```

这是当前权威状态。

必须由：

```text
Rule
Transaction
StateService
```

受控写入。

不能由：

```text
玩家前端
AI
角色卡文件
自然语言中的自报数值
```

直接修改。

---

## L5：成长与变化账本 `CharacterProgressionLedger`

记录长期变化：

```text
技能成长
永久属性变化
新能力
伤疤
精神症状
关系变化
头衔
长期物品
角色死亡或退役
```

不是直接覆盖角色原始文件，而是形成事件账本。

例如：

```text
Session 4：
Psychology 45 -> 50
来源：成长检定
事件：evt_818
事务：tx_204
```

# 二、角色卡最重要的边界：基线、当前值、派生值

每个字段必须明确属于哪一类。

|字段类型|示例|谁负责|
|---|---|---|
|基础字段|STR 60、心理学 45|角色档案 / 规则模板|
|当前运行值|HP 8/12、SAN 54|Runtime State|
|派生字段|HP 最大值、伤害加值|Rule Package 计算|
|临时修正|黑暗惩罚、受伤减值|Runtime Modifier|
|玩家笔记|“我害怕地下室”|Player-owned Note|
|已知信息|知道教授进入地下室|Knowledge / Projection|
|Host 私密内容|隐藏背景真相|Host-only，不进普通角色 DTO|

玩家端可以显示：

```text
心理学：45
来源：角色卡基线

当前心理学：35
修正：
- 重伤：-10
```

并支持按钮：

```text
为什么是 35？
```

展开后显示来源。

这会让角色卡本身也具备透明性。

# 三、各种角色卡格式怎么自动导入

这里可以复用前面讨论的 Module Intake Router 思路，但建立一个：

# **Character Sheet Compiler**

流程：

```text
角色卡文件
    ↓
格式识别
    ↓
版式识别
    ↓
规则系统识别
    ↓
字段候选提取
    ↓
映射到 CharacterSchema
    ↓
公式和范围校验
    ↓
风险分级
    ↓
生成角色草稿
    ↓
玩家确认公开信息
    ↓
创建 RoomCharacterInstance
```

---

## 1. 不同格式分别处理

|格式|处理方式|
|---|---|
|XLSX / CSV|读取 Sheet、标题、字段和值|
|数字 PDF|读取文本块、字段位置、勾选框|
|扫描 PDF / 图片|OCR + 视觉表单识别|
|JSON / YAML|Schema mapping|
|DOCX|标题、表格、表单字段|
|其他平台导出|专门 Adapter|
|无法识别|原文件保留 + Reference-only|

---

## 2. 如何识别规则系统

综合判断：

```text
属性名称
技能名称
字段顺序
骰子表达
HP/SAN/AC 等资源名称
角色卡标题
文件元数据
模板布局
```

例如看到：

```text
STR CON SIZ DEX APP INT POW EDU
SAN Luck
Spot Hidden
```

可以较高置信度判断为：

```text
CoC 7e
```

如果同时存在多个可能规则包，最多询问一个非剧透问题：

> 这张角色卡使用的是 CoC 6e 还是 CoC 7e？

---

## 3. 字段候选不能直接成为权威值

例如 OCR 识别：

```text
心理学：85
```

但原图可能实际是：

```text
心理学：35
```

因此导入字段要带：

```text
sourceRef
parseConfidence
mappingConfidence
validationStatus
```

```json
{
  "fieldId": "skill.psychology",
  "rawLabel": "心理学",
  "rawValue": "35",
  "normalizedValue": 35,
  "sourceRef": {
    "page": 1,
    "bbox": [120, 420, 260, 455]
  },
  "parseConfidence": 0.94,
  "mappingConfidence": 0.99,
  "validationStatus": "valid"
}
```

---

## 4. 自动校验规则

系统可以自动检查：

```text
属性是否在允许范围
当前 HP 是否超过最大 HP
技能是否重复
当前值和最大值是否倒置
Luck / SAN 是否与规则版本兼容
派生值是否符合公式
武器伤害表达是否合法
技能名称是否属于当前 Ruleset
```

高置信度且合法的字段自动接受。

低置信度字段：

```text
保留原始来源
不用于权威结算
进入 unmappedFields
```

而不是强迫玩家逐项校对全部角色卡。

---

## 5. 导入时只问少量问题

建议最多询问：

```text
规则系统 / 版本
哪个数字是当前值，哪个是最大值
是否将未识别字段保留为自定义资料
```

其他不确定内容采用安全默认：

```text
不参与规则结算
保留在原始角色附件
允许以后修正
```

# 四、角色卡私密信息也要分层

不能只有：

```text
public / private
```

建议最少支持：

```text
public
party
private:self
shared_with_host
host_only
admin_audit
```

例如：

|字段|默认可见性|
|---|---|
|角色姓名、头像|party|
|公开职业|party|
|当前 HP 是否精确公开|房间规则决定|
|私人背景|private:self|
|交给 Host 的秘密|shared_with_host|
|私人笔记|private:self|
|角色隐藏身份|host_only 或 shared_with_host|
|管理审计|admin_audit|

需要强调：

> **Host 能管理房间，不代表自动拥有玩家全部私人笔记。**

玩家必须主动选择：

```text
只给自己
允许 AI 整理
分享给 Host
分享给 Party
```

# 五、物品不能只是角色卡里的字符串数组

错误设计：

```json
{
  "inventory": [
    "手枪",
    "钥匙",
    "信件",
    "急救包"
  ]
}
```

这无法回答：

```text
是哪把手枪？
还有多少弹药？
钥匙开哪扇门？
信件内容谁知道？
急救包还剩几次？
物品现在谁拿着？
它来自哪里？
是否已经损坏？
是否被藏起来？
```

建议把物品拆成：

# **ItemTemplate + ItemInstance + ItemKnowledge**

---

# 六、ItemTemplate：物品定义

它来自：

```text
规则系统
模组
Host 自建
导入角色卡
插件内容包
```

示例：

```json
{
  "itemTemplateId": "item_template:first_aid_kit",
  "rulesetId": "coc7e",
  "name": "急救包",
  "kind": "tool",
  "stackable": false,
  "defaultCharges": 3,
  "capabilities": [
    {
      "type": "assist_check",
      "skillId": "first_aid",
      "modifier": 20
    },
    {
      "type": "consume_charge",
      "amount": 1
    }
  ],
  "visibility": "public",
  "sourceRefs": []
}
```

ItemTemplate 定义：

```text
它是什么
允许做什么
规则能力是什么
默认状态是什么
```

但不表示某个房间中已经存在这个物品。

---

# 七、ItemInstance：实际存在的物品

```json
{
  "itemInstanceId": "item_782",
  "templateId": "item_template:first_aid_kit",
  "roomId": "room_xxx",
  "ownerCharacterId": "char_a",
  "custodianCharacterId": "char_a",
  "locationRef": null,
  "quantity": 1,
  "charges": 2,
  "condition": "used",
  "equipped": false,
  "containerId": "bag_01",
  "visibility": "private:self",
  "stateVersion": 43,
  "sourceRefs": [
    {
      "type": "event",
      "sequence": 812
    }
  ]
}
```

它表示：

```text
房间中具体存在的这一件物品
```

即使两把武器名称相同，也可能有不同：

```text
损坏程度
弹药数量
来源
所有者
序列号
隐藏属性
```

---

# 八、ItemKnowledge：玩家知道什么

这是特别适合 TRPG 的一层。

同一物品可能存在：

```text
物理对象
已知名称
已知用途
隐藏功能
已发现内容
玩家推测
```

例如一枚戒指：

```text
Host 真相：
可以打开密室，并带有诅咒。

玩家 A：
知道它是一枚旧戒指。

玩家 B：
只知道 A 拿到了一件金属物品。

Party：
还不知道它能开门。
```

所以物品定义不能直接全部暴露给持有者。

建议：

```json
{
  "itemKnowledgeId": "ik_102",
  "itemInstanceId": "item_782",
  "viewerCharacterId": "char_a",
  "knownName": "旧银戒指",
  "knownProperties": [
    "刻有医院徽章"
  ],
  "revealedCapabilityIds": [],
  "sourceRefs": [
    {
      "type": "inspection",
      "eventSequence": 915
    }
  ]
}
```

# 九、物品和线索必须分开，但允许关联

这是特别重要的设计。

> **物品是世界中的对象；线索是玩家获得的信息。**

一封信可以同时是：

```text
ItemInstance：烧焦的信件
Asset：信件图片
Clue：信中提到地下室第二扇门
Knowledge：谁知道这段内容
```

拿到物品不一定等于看懂所有信息。

例如：

```text
角色拿到密封信
```

系统只创建：

```text
拥有信件物品
知道信件存在
```

只有玩家执行：

```text
打开信
阅读信
翻译信
检查水印
```

才可能分别获得不同 Clue。

同样：

```text
把信的内容告诉队伍
```

只是分享 Clue，不一定转移物品。

而：

```text
把信交给安娜
```

才是转移 ItemInstance。

# 十、玩家自然语言使用物品时，要生成“物品行动合同”

玩家说：

> “我用急救包给自己处理伤口。”

AI 可以解析成：

```json
{
  "actionType": "use_item",
  "itemInstanceId": "item_first_aid_02",
  "targetCharacterId": "char_self",
  "capability": "assist_check:first_aid",
  "quantity": 1,
  "constraints": [],
  "requiresConfirmation": true
}
```

玩家看到：

> **使用物品：**急救包  
> **目标：**自己  
> **预计消耗：**1 次使用次数  
> **相关检定：**急救  
> **当前剩余：**2 次

按钮：

```text
确认使用
修改目标
取消
```

确认后才进入：

```text
RuleExecutor
→ StateService
→ Inventory mutation
→ Resolution Receipt
```

AI 不能仅凭一句叙事：

> “你熟练地用急救包包扎伤口。”

就自动扣次数、恢复 HP。

# 十一、建议统一物品动作类型

```text
inspect
use
equip
unequip
consume
transfer
drop
pick_up
store
remove_from_container
split_stack
merge_stack
load
unload
repair
combine
destroy
share_information
reveal
```

每种动作有不同规则。

例如：

## `inspect`

```text
可能揭示 ItemKnowledge 或 Clue
不改变所有权
```

## `transfer`

```text
改变 custodian / owner
不自动分享所有已知 Clue
```

## `share_information`

```text
分享 Clue 或安全摘要
不移动 ItemInstance
```

## `consume`

```text
扣 quantity / charges
可能应用 Rule Effect
```

## `destroy`

```text
不可逆或高风险
必须确认
可能触发 Clue / Trigger / Audit
```

---

# 十二、物品所有权、持有和位置必须分开

需要区分：

```text
owner
custodian
location
container
```

例如：

```text
所有者：博物馆
当前持有人：玩家 A
实际位置：玩家 A 的背包
```

或者：

```text
所有者：队伍公共资产
持有人：玩家 B
位置：汽车后备箱
```

如果只有 `character_id`，很多剧情就表达不了。

---

# 十三、需要队伍公共仓库和世界物品位置

建议至少支持：

```text
个人背包
已装备
队伍仓库
车辆
场景地面
容器
NPC 持有
隐藏位置
已销毁
已消耗
```

物品转移链：

```text
场景桌面
→ 玩家 A 拾取
→ 玩家 A 放入背包
→ 转交玩家 B
→ 玩家 B 存入队伍汽车
```

每一步都写 ItemEvent。

---

# 十四、重要物品转移建议采用双向确认

普通低价值物品可以直接转移。

但这些物品建议需要接收者确认或 Host 规则：

```text
重要剧情物品
武器
大量金钱
玩家私密物品
绑定角色的物品
被诅咒物品
```

流程：

```text
玩家 A 提议转交
→ 玩家 B 接受
→ Transaction 提交
```

如果是：

```text
偷窃
抢夺
强制夺取
```

则不是普通 transfer，而是：

```text
Player Intent
→ Rule
→ Transaction
→ Item ownership/custody change
```

不能通过背包 UI 直接拖走别人的物品。

---

# 十五、物品能力不能直接从描述文本中执行

例如模组写：

> 这把刀似乎能割开任何东西。

AI 不能自动编译成：

```text
ignore_all_armor = true
```

物品描述可以生成：

```text
ItemCapabilityCandidate
```

但只有通过规则 Schema 校验和人工/机器高风险验证后，才能成为可执行 capability。

未确认时：

```text
只显示描述
不自动执行规则效果
```

# 十七、装备和背包要遵循规则包，而不是平台写死

不同系统对装备的规则不同：

```text
有无负重
装备槽
武器装填
弹药
耐久
手持限制
防具
法术位
消费品
```

建议由 `RulePackage` 提供：

```text
InventoryPolicy
EquipmentSlotPolicy
EncumbrancePolicy
StackPolicy
WeaponPolicy
AmmoPolicy
```

平台核心只处理：

```text
物品实例
所有权
状态
版本
事务
可见性
```

不要把 D&D 式装备槽写死到所有 TRPG。

# 十八、物品导入也需要分级自动化

从角色卡提取到：

```text
左轮手枪
子弹 18 发
急救包
怀表
旧照片
```

系统应尝试映射：

|原始文本|处理|
|---|---|
|左轮手枪|匹配规则包标准 ItemTemplate|
|子弹 18 发|创建 ammo stack|
|急救包|匹配 tool template|
|怀表|创建 generic unique item|
|旧照片|创建 reference item，可能绑定 Asset|
|无法识别的描述|创建 text-only reference item|

安全原则：

```text
能识别规则能力的才自动执行
不能识别的仍可正常展示和使用叙事
但不自动产生数值效果
```

# 十九、物品别名和重复检测

玩家角色卡中可能写：

```text
左轮
.38 Revolver
手枪
Webley
```

不能只按名称合并。

需要结合：

```text
规则系统
伤害表达
弹药类型
来源字段
数量
唯一标识
```

如果不确定，保持分开。

错误合并物品会导致：

```text
弹药数量错乱
独特剧情物品消失
装备状态丢失
```

# 二十、物品变化必须有事务回执

例如玩家使用急救包：

> **物品操作结果**  
> 急救包使用成功。  
> 剩余次数：2 → 1。  
> 相关检定：急救 60，掷骰 42，成功。  
> HP：5 → 7。
> 
> 来源：  
> 行动 `act_319`  
> 事务 `tx_319`  
> 状态版本 `state_84`

如果 State 写入失败：

> 操作未提交，急救包次数未扣除。

不能出现：

```text
HP 恢复成功
但急救包没有扣次数
```

或者：

```text
次数扣了
但 HP 没变
```

应在同一事务或补偿链中完成。

# 二十一、角色成长不能自动回写角色库

一个房间中的永久变化，可能不应该自动影响另一个战役。

建议流程：

```text
战役结束
→ 生成 Character Progression Summary
→ 玩家查看变化
→ Host / Rule 确认
→ 玩家选择：
   1. 保存为角色库新版本
   2. 仅保留在当前战役
   3. 创建角色分支
```

例如：

```text
原角色：陈默 v3
战役后：
- 心理学 +5
- 获得长期伤疤
- 得到古董怀表
```

生成：

```text
陈默 v4 - 圣玛丽医院结局
```

而不是直接覆盖 v3。

# 二十五、AI 在角色卡和物品系统中可以做什么

AI 可以：

```text
识别导入字段
建议字段映射
解释当前数值来源
根据自然语言选择候选技能
根据自然语言识别物品使用意图
总结本局角色变化
提醒资源不足
整理背包分类
发现重复或冲突字段
```

AI 不可以：

```text
直接修改 HP/SAN/Luck
凭空增加技能
凭空创建物品
自动消耗资源
自动转移他人物品
把私密角色背景分享给 Party
从隐藏模组真相推断物品真正用途并告诉玩家
把描述文本直接编译成高权限能力
```

# 二十六、AI 获取的角色上下文必须是任务专用视图

不要把完整角色卡和全部私密笔记塞给 AI。

建议：

## `CharacterActionView`

用于行动理解：

```text
可用技能
当前公开状态
当前装备
允许使用的物品能力
当前场景相关修正
```

## `CharacterNarrativeView`

用于叙事：

```text
公开外貌
玩家允许 AI 使用的性格标签
当前可见状态
```

## `CharacterPrivateAssistantView`

仅本人授权：

```text
私人笔记
个人目标
私人线索
```

## `CharacterHostReviewView`

Host 复核需要的规则字段，但不自动包括玩家私人笔记。

## `CharacterPublicView`

只包含公开身份和玩家显式公开内容。

# 二十七、一个完整案例：烧焦处方

房间里存在：

```text
ItemInstance：
烧焦处方原件

Asset：
处方图片

Clue A：
处方属于医院

Clue B：
签名是院长

Clue C：
背面写着地下室第二扇门
```

玩家 A 拿到物品，但只看了正面。

因此：

```text
玩家 A：
拥有 ItemInstance
知道 Clue A
知道 Clue B
不知道 Clue C

玩家 B：
只知道 A 捡到了一张烧焦纸片

Party：
尚无共享内容
```

玩家 A 说：

> “我把处方给安娜看，但先把背面盖住。”

系统不能简单理解为：

```text
transfer item
```

它应该生成意图确认：

> 你希望：
> 
> - 让安娜查看处方正面；
>     
> - 不转移物品所有权；
>     
> - 不展示背面内容。
>     
> 
> 将分享：医院来源、院长签名。  
> 不会分享：背面内容。

这同时涉及：

```text
Item
Clue
Visibility
Projection
Transaction
```

这是你们比普通“背包系统”更有差异化的地方。

# 二十八、另一个案例：左轮手枪

```text
ItemTemplate：
.38 左轮手枪

ItemInstance：
item_revolver_01
状态：已装备
弹仓：3 / 6
备弹：12
状况：正常
所有者：角色 A
```

玩家说：

> “我朝门锁开一枪。”

系统解析：

```text
use_item
item = revolver
target = door_lock
resource = 1 ammo
action = ranged_attack / object_damage
```

结算前显示：

```text
将消耗 1 发弹药
会产生巨大噪音
可能触发场景公开事件
```

确认后：

```text
RuleExecutor 结算
弹药 3 -> 2
门锁状态更新
噪音事件产生
Journal 写证据链
```

AI 只能理解和叙事，不能自行决定门锁一定被打坏。

# 三十四、工程验收最关键的测试

```text
1. 导入角色卡后原文件仍保留。
2. 当前 HP/SAN 来自 Runtime State，不来自 xlsx_data。
3. 玩家文本中的伪造技能值不会被采用。
4. 派生值由 Rule Package 计算。
5. 低置信度导入字段不会进入权威结算。
6. active room 角色不受角色库后续编辑影响。
7. 玩家 A 私人背景不会进入玩家 B 或 Party DTO。
8. Host 不自动看到玩家私人笔记。
9. 同名物品不会未经验证自动合并。
10. 物品使用失败不会消耗次数。
11. 物品次数扣除和状态效果在同一事务完成。
12. 物品转移不会自动分享 Clue。
13. 分享 Clue 不会自动转移物品。
14. 持有密封信不等于知道信件内容。
15. Player A 物品不会出现在 Player B 背包。
16. 断线重连不会重复生成物品。
17. AI 不能凭空创造 ItemInstance。
18. AI 不能直接改变 Item owner。
19. 高影响物品操作未经确认不执行。
20. 物品效果必须来自已验证 ItemCapability。
21. Item receipt 可以追到 actionId、transactionId、stateVersion。
22. 战役成长不会静默覆盖角色库原版本。
```

# 三十五、这套能力最终的竞争壁垒

普通平台的角色卡是：

```text
一个表单
```

普通平台的物品栏是：

```text
一组名称和数量
```

你们应该做到：

```text
角色字段从哪里来
为什么当前值发生变化
这个技能由哪个规则包解释
这个物品是谁带来的
现在由谁持有
谁知道它的真实用途
它还剩多少次数
用它会触发什么规则
使用后改变了什么
这次改变能追溯到哪个行动和事务
```

这会形成：

# **可解释的角色运行体与世界资产系统**

最终产品定义可以收敛为：

> **AI-Keeper 将各种格式的角色卡编译成规则可验证、状态可追踪的角色实例，并把物品建模为有来源、能力、所有权、认知范围和事务历史的世界资产；AI 可以帮助导入、理解和操作，但所有数值、消耗、转移和效果都必须由规则、状态和事务链确认。**
