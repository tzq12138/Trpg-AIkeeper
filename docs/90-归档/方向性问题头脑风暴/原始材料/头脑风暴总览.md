## 总判断

**有前后矛盾，有过度设计，也有明显漏设计。**

但三者不是均匀分布的：

- **矛盾主要集中在产品根部**：产品模式、Host 角色、AI/Engine 权威、演出与业务状态的关系。
    
- **过度设计主要集中在中下层**：24 个模块、数百个 DTO/状态机、32 个 P0 页面模式，以及尚未验证就准备独立成系统的 Semantic、Combat、Continuity、Investigation 等。
    
- **漏设计主要发生在产品层**：目标用户、核心场景、验证假设、成功指标、统一用户旅程、事实与认知模型、纠错申诉、内容供给与版权隐私。
    

换句话说，现在这套文档更像：

> **一个高度防御性的 AI 跑团平台架构大全，尚未完全收敛成围绕单一用户价值的产品设计。**

我把 `90-归档` 视为历史资料，把测试报告和工程回执视为实现证据，主要以总览、核心架构、24 个模块 PRD、前端设计和设计哲学作为现行产品审阅对象。

# 一、自顶向下看，第一层问题是：产品到底是什么

目前文档实际上同时在做三种产品。

### 方向 A：AI 独立替代 KP

前端设计里，AI-Keeper 是唯一掌握幕后真相的真正 KP；房主不看剧透；桌务只处理连接、暂停和安全问题；Shared Stage 只是全桌共同观看的大屏。

这是一个很清楚的产品命题：

> 几个玩家即使找不到真人 KP，也可以直接开一个调查团。

### 方向 B：AI 辅助人类 KP

另一些文档又允许 Host：

- 查询剧本知识；
    
- 查看完整时间线；
    
- 恢复 checkpoint；
    
- 处理遭遇；
    
- 复核重大剧情；
    
- 决定新 Canon、核心揭示和 Retcon。
    

这实际上意味着存在一个知道真相、拥有剧情权力的人类 KP。

### 方向 C：AI 长期维持战役

设计哲学又进一步讨论：

- 长期可信记忆；
    
- CampaignPromise；
    
- StoryThread；
    
- NPC Agenda；
    
- WorldClock；
    
- Host 缺席自治；
    
- Continuity Packet；
    
- Session Handoff；
    
- 战役方向控制器。
    

这已经不是“能跑一局”，而是在设计一个能够自主维护长期战役的 AI 运行时。

这三种方向都可以成立，但它们对应的 MVP 完全不同。现在文档把它们叠在了一起，导致几乎所有模块都能被解释为 P0。

## 我的建议

首版先锁定一个最可验证、也最符合当前文档差异化的命题：

> **2–4 名玩家无需真人 KP，使用一个经过验证的 COC 短模组，通过文字行动完成一场可解释、可恢复、不剧透的调查游戏；每名玩家使用私人终端，Shared Stage 是可选公共镜像。**

这优先验证最核心的不确定性：

1. AI 是否能正确理解玩家行动；
    
2. 规则与状态是否可信；
    
3. 公共和私密信息是否公平；
    
4. 没有真人 KP 时故事能否持续推进；
    
5. 整场体验是否真的比“先找一个人当 KP”容易启动。
    

长团、真人 KP 模式、复杂地图和模组编辑器都可以后续增加，但不能同时作为第一个版本的主命题。

# 二、第二层问题是：角色模型前后冲突

目前 `Host` 至少表示三种不同事物：

1. 公共大屏或公共舞台；
    
2. 房主、桌务、房间管理员；
    
3. 有剧情裁决和复核权的人类主持人。
    

这是当前最危险的概念污染之一。

前端文档已经明确说：

- Host 页面不是房主后台；
    
- Shared Stage 是公共显示设备；
    
- Room Owner 负责建房和成员管理；
    
- Table Steward 负责故障、安全和暂停；
    
- AI-Keeper 是唯一真正的 KP。
    

但 `17-Host-Client` PRD 又把同一个 Host Client 定义成“公共舞台和房主控制台”，并让 Host 创建房间、开局、看日志、恢复 checkpoint、做 full export、处理遭遇。

这会直接影响：

- token 和会话设计；
    
- 谁能看玩家私密内容；
    
- 谁能看真相；
    
- 谁能恢复历史；
    
- 谁能复核 AI；
    
- Shared Stage 断线时是否影响游戏；
    
- 前端到底需要几套页面。
    

## 建议彻底拆开设备与人

|概念|建议名称|真相权限|主要职责|
|---|---|--:|---|
|公共显示设备|`SharedStage`|无|只读展示 party-safe 内容|
|创建房间的人|`RoomOwner`|默认无|建房、邀请、成员与配置|
|现场管理员|`TableSteward`|无|暂停、安全工具、故障恢复|
|人类主持人|`HumanKeeper`|有|只在真人 KP 模式中存在|
|AI 主持服务|`AIKeeper`|受控读取|理解、建议、叙事|
|权威执行服务|`Engine`|必要事实|唯一状态写入|

`Host` 应从产品规范中逐步退出，只作为旧代码兼容名。

尤其需要做一个明确裁决：

> 如果 RoomOwner 永远不看真相，他就不能负责复核“核心剧情是否正确”；如果他需要复核核心剧情，他实际上就是 HumanKeeper，必须有独立模式和幕后界面。

不能一边规定 AI 独占幕后真相，一边又要求无剧透房主决定新 Canon 和核心揭示。

# 三、第三层问题是：核心行动链路有 S0 级矛盾

现行核心架构和 AI V2.1 PRD 的原则是正确的：

```text
玩家意图
→ 身份与资产校验
→ AI 机制建议
→ RuleExecutor 权威结算
→ State 权威提交
→ AI 根据已确定结果生成叙事
→ 安全投影和日志
```

也就是说：

- AI 不能直接写状态；
    
- AI 不能决定骰值和成功等级；
    
- AI 不能在结果产生之前宣布结果；
    
- Engine 是唯一权威写入口。
    

但 `KP_MCP_Design.md` v0.1 给出的流程却是：

```text
kp_resolve_turn
→ narrative 先直接推送
→ rollRequests 再掷骰
→ stateMutations 再写入
```

它还允许 `direct` mutation，后端“不校验直接写”，包括：

- `scene_transition`；
    
- `npc_reaction`；
    
- `add_status_tag`；
    
- 恐惧、重伤、昏迷等标签。
    

这是原则级冲突，不是接口风格差异。

它可能导致：

- AI 先叙述检定成功，后端随后掷出失败；
    
- AI 直接把角色写成昏迷；
    
- AI 把 NPC 态度或场景切换变成权威事实；
    
- `keeperNotes` 在后续上下文中逐渐被误当作事实；
    
- 重试、回滚和审计无法重建真正发生了什么。
    

另外，`soul.md` 仍允许玩家自行掷骰并把结果告诉 AI，也允许 AI 直接代骰，这同样与服务器权威骰值冲突。

## 应当立即裁决

`KP_MCP_Design.md` 应标记为 **Deprecated / 非规范文档**。MCP 只能是 provider 的传输或工具调用层，不能重新定义业务结算顺序。

唯一主链建议固化为：

```text
Player Intent
→ 身份、拥有权、可见性校验
→ 语义/机制编译
→ 模糊或高影响动作由玩家确认
→ Rule 权威结算
→ State 原子提交
→ 生成 Reveal Plan
→ AI 基于已提交结果生成 public/private narrative
→ Projection
→ Receipt + Journal
```

这里还应增加一个目前尚未被主链正式吸收的关键环节：

> **AI 理解结果不确定或会产生重大不可逆后果时，必须先让玩家确认“系统理解的是不是这个意思”。**

这是 AI 主持产品的信任基础。

# 四、第四层问题是：业务权威被公共舞台的表现进度绑住了

Transaction PRD 规定：

- 玩家私密 `state_patch`；
    
- `private_notice`；
    
- `action_completed`
    

需要进入 `ReleaseGate`，等 Host 发出 `host_step_complete` ACK 后才能下发。

这个设计是为了避免玩家手机提前看到结果，破坏大屏上的公共演出。动机是合理的，但当前边界有问题。

因为其他文档同时又规定：

- Host 可以不在线；
    
- Shared Stage 只是公共显示设备；
    
- 玩家手机必须支持无大屏 fallback；
    
- 远程文字团不应依赖公共屏幕。
    

于是会出现：

> 大屏断线或根本不存在，玩家行动就一直卡在 resolving。

## 建议拆成三个独立概念

### 1. 权威完成

State 成功提交后，业务上即完成，不等待任何 UI。

### 2. 信息揭示顺序

由服务端 `RevealPolicy` 控制哪些内容先公开、哪些私密结果稍后释放。

### 3. 视觉播放状态

Shared Stage ACK 只用于：

- 防止动画重复播放；
    
- 恢复播放位置；
    
- 跳过或重播表现。
    

它不能决定行动是否完成，更不能无限阻塞玩家。

安全做法可以是：

```text
State committed
→ 公共 reveal 事件已发布
→ 私密结果可以释放
```

或设置服务端超时 fallback，而不是依赖某一块屏幕确认“已经播完”。

# 五、第五层问题是：MVP 与 P0 已经失去约束力

路线文档的 MVP 原本很克制：

- 房间和身份；
    
- 文字意图；
    
- COC 检定；
    
- Engine 权威状态；
    
- 公共/私密投影；
    
- 线索和防剧透；
    
- 重连；
    
- 日志。
    

同时明确后置：

- 语音视频；
    
- 社区；
    
- 复杂日程；
    
- 动态光照；
    
- 完整插件；
    
- AI 地图；
    
- 直播；
    
- 完整素材 CDN。
    

但 UI 文档的 P0 已经包含大约 32 个页面或模式：

- 公共桌面 8 项；
    
- 玩家手机 11 项；
    
- 桌务 7 项；
    
- 战役准备 6 项。
    

里面包括：

- 公共地图；
    
- 调查工作台；
    
- 继续战役；
    
- 模组导入；
    
- 自动编译；
    
- 无剧透质量报告；
    
- AI 状态；
    
- 安全工具；
    
- Session 总结。
    

模块文档中，Asset、Module、Voice、Safety、Schedule、Community 等也都不同程度使用了 P0。

文本扫描中，现行产品和架构文档里的 `P0` 大约出现了 577 次，分布在 131 个文件中。它现在同时表示：

- MVP 必须能力；
    
- 严重安全问题；
    
- 文档必须先定义；
    
- 已有代码要修；
    
- 未来设计的前置条件。
    

因此 P0 已经无法用于做范围决策。

## 应拆成三个维度

|维度|建议|
|---|---|
|发布范围|`M0 / M1 / M2 / Later`|
|风险严重度|`S0 / S1 / S2 / S3`|
|成熟状态|`Idea / Draft / Reviewed / Normative / Implemented / Verified / Production-ready`|

相应地，回执中的状态也必须拆开：

- 设计评审通过；
    
- 实现完成；
    
- 测试验证；
    
- 生产安全就绪。
    

不能再把“设计稿完成但没有代码”称为工程验收通过，也不能把“测试存在错误但与本模块无关”直接写成无条件通过。

# 六、过度设计主要在哪里

## 合理的复杂度

以下复杂度是产品的核心竞争力，不建议削弱：

- Engine 唯一权威写入；
    
- Rule 与 AI 分离；
    
- 公共、队伍、角色私密投影；
    
- 状态版本；
    
- 幂等、重连和事件追溯；
    
- 线索证据链；
    
- AI 上下文最小化；
    
- 防剧透和输出校验。
    

这些不是过度设计，而是 AI 跑团产品成立的基础。

## 应当降级的复杂度

### 1. 大量未来系统被提前做成正式模块

设计哲学已经提出：

- `25-Investigation`；
    
- `26-Combat`；
    
- `26-Semantic`；
    
- 两个不同的 `27-Continuity`；
    
- 独立 Item/Inventory；
    
- Narrative Governor；
    
- Host Delegation；
    
- Campaign Direction；
    
- Module Compiler。
    

甚至模块编号已经发生碰撞，说明这些仍然是探索方案，不应被视为现行施工图。

### 2. 过早建立精确 DTO 和状态机

在目标用户、主运行模式和 Campaign 生命周期尚未锁定时，很多未来系统已经有非常细的：

- DTO；
    
- 枚举；  
    -状态机；
    
- 事件名；
    
- 审计字段；
    
- API；
    
- 多层数据模型。
    

这会产生维护成本，也会让后续产品裁决被既有文档反向绑架。

### 3. Shared Stage 表现系统过深

Cue 队列、演出 ACK、BGM 挂起、字幕阻塞、紧急清屏、恢复播放都可以进入后续沉浸版本，但核心循环必须先证明：

> 没有大屏、动画、声音和导演系统，游戏仍然完整成立。

### 4. 后验物品主张过深

职业—物品标签矩阵、编辑距离、baseline access、自动把物品加入背包、Luck/Know 分支已经设计得很详细，但物品权威目前仍分散在 Character、Clue 和 State 中。

应先完成最小 Item 权威模型，再决定这项机制是否值得进入产品。

# 七、真正漏掉的设计

## 1. 目标用户和 JTBD

目前没有明确回答：

- 是已有 COC 玩家，还是没有跑团经验的新玩家？
    
- 是找不到 KP 的固定朋友群，还是临时组队用户？
    
- 是线下面对面，还是远程文字团？
    
- 是一次性短团，还是长期战役？
    
- 用户为什么不用真人 KP、Discord Bot、现有 VTT 或普通聊天模型？
    

这是所有模块之前应该存在的产品定义。

## 2. 可验证的产品假设和指标

文档没有形成明确的：

- MVP 假设；
    
- 北极星指标；
    
- 激活指标；
    
- 首场完成率；
    
- 行动误解率；
    
- 规则争议率；
    
- 剧透事故率；
    
- 第二场继续率；
    
- 玩家信任度；
    
- 每玩家小时成本。
    

目前的验收主要是“接口是否存在、测试是否通过”，不足以判断产品是否真的好用。

## 3. Campaign、Room、Session 的统一生命周期

建议至少明确：

```text
ModuleDefinition / ModuleVersion
→ Campaign
→ Room / Table
→ Session
→ Scene / Encounter
→ Turn
→ PlayerAction
→ ResolutionTransaction
→ StateChange + Event + Projection
```

不一定要按这个名字最终落地，但必须有一份唯一规范。

现在 Campaign 在 UI、Journal 和设计哲学中大量存在，却没有成为 24 模块领域模型中的正式聚合；Room 又同时承担房间容器和当前一场 Session 的职责。

## 4. 事实、观察、证词和推测的统一模型

目前各模块都在谈反幻觉，但缺少跨模块统一模型。

建议至少区分：

- `CanonicalFact`：客观事实；
    
- `Observation`：某角色实际感知；
    
- `Evidence/Clue`：有来源的证据；
    
- `Testimony`：NPC 或文档的陈述，可能不真实；
    
- `Hypothesis`：玩家或 AI 推测；
    
- `Summary`：对已有内容的压缩；
    
- `KeeperPlan/Note`：AI 的计划，不是事实。
    

尤其 `keeperNotes` 必须明确为 `non_canonical`，带来源、有效期和置信状态，不能因为反复进入上下文就逐渐“事实化”。

## 5. AI 误解与玩家申诉

产品必须明确：

- 哪些动作自动解释；
    
- 哪些动作必须确认；
    
- 玩家怎么说“你理解错了”；
    
- 是否允许撤回；
    
- 规则争议由谁处理；
    
- 如何重算或 Retcon；
    
- 修正结果如何通知全桌；
    
- 修正前后的事件如何审计。
    

这是核心体验，不是边缘异常。

## 6. 首版内容供给策略

需要决定首版究竟是：

- 使用少量人工校验的短模组；
    
- 允许任意 PDF 自动导入；
    
- 或两者并存。
    

我建议 M0 使用可控短模组。任意 PDF 导入会把 OCR、版权、结构化质量、缺失线索和叙事完整性问题一起带进来，反而无法判断 AI 主持本身是否成立。

## 7. 内容权利、数据保留和模型使用

仍需统一回答：

- 用户是否有权上传模组；
    
- PDF、图片、音频是否发送给第三方模型；
    
- 是否用于产品改进或训练；
    
- 原文件、解析文本、向量和 AI 日志保存多久；
    
- 删除 Campaign 或账号后，备份如何删除；
    
- 语音录入是否需要全桌同意；
    
- 战报和生成内容的权利归属。
    

## 8. 可访问性和低带宽基线

虽然前端零散提到了字幕、减少动画和无大屏 fallback，但还应成为统一验收要求：

- 屏幕阅读器；
    
- 键盘操作；
    
- 对比度和色觉；
    
- 减少动画；
    
- 所有视觉和音频 Cue 的文字替代；
    
- 小屏；
    
- 弱网；
    
- 断线恢复；
    
- 中英文术语策略。

# 八、建议的 M0

### 必须进入

1. 一个经过验证的短 COC 模组；
    
2. 建房、邀请、加入和角色绑定；
    
3. 最小 Session 0：内容提示、边界、暂停/X-card；
    
4. 文字行动；
    
5. 模糊或高影响动作确认；
    
6. 核心技能检定和 SAN；
    
7. Engine 唯一状态写入；
    
8. 公共与角色私密叙事；
    
9. 私密线索、分享和公共摘要；
    
10. 无 Shared Stage 也能完整游戏；
    
11. 断线恢复；
    
12. 可解释的行动回执；
    
13. Session 结束摘要。

# 九、文档体系建议重建成六份顶层规范
