# AI-Keeper 产品设计文档顶层审计

**审阅日期：** 2026-07-12  
**审阅范围：** `docs.zip` 中 292 个文件，其中 249 份 Markdown。对现行产品、架构、24 个模块 PRD、前端设计和设计哲学做横向交叉审阅；开发任务、测试报告和工程回执只作为状态证据；`90-归档` 只用于追溯历史，不作为现行规范。

---

## 一、结论先行

这套文档不是“设计得不够”，而是相反：**底层和中层已经设计得很深，但最顶层的产品选择尚未统一。**

当前最需要解决的不是再补一个模块、DTO 或页面，而是先锁死下面五件事：

1. **产品到底是哪一种：AI 独立做 KP、AI 辅助人类 KP，还是 AI 维持长期战役。**现有文档三种模式并存。
2. **Host 到底是什么：公共大屏、房主/桌务，还是有剧情裁决权的人类主持。**现有文档至少有三种互斥定义。
3. **一次玩家行动的唯一合法链路是什么。**现行核心架构要求“先规则与状态，后叙事”，但 MCP v0.1 允许先推叙事、后掷骰，并允许 AI `direct` 写状态。
4. **MVP 到底验证什么。**路线文档主张极窄文字主链路，UI 和模块文档却把地图、调查工作台、模组导入、安全工具、连续性、语音等大量能力列为 P0。
5. **长期领域骨架是什么。**文档大量使用 Campaign、Room、Session、Scene、Turn、Encounter、Action、Transaction，但没有一份现行文档给出它们的唯一层级、生命周期和权威归属。

如果这五项不先裁决，继续补模块会让文档越来越完整，但产品越来越难以收敛。

---

## 二、审阅中采用的文档权威顺序

目前仓库没有正式的文档裁决规则。为避免把历史版本误判成现行矛盾，本次暂时按以下顺序判断：

1. `10-总览与路线`：产品范围和阶段边界；
2. `20-核心架构/AI-Keeper核心链路架构.md`：核心安全与权威链路；
3. `30-平台子系统/*/PRD.md` 中的 V2.1：模块现行边界；
4. `40-前端设计`：产品体验提案；
5. `50-设计哲学`：北星和探索性方案；
6. 工程回执、测试报告：实现证据，不决定产品定义；
7. `90-归档`：历史参考，不具有裁决权。

即使采用这套偏保守的顺序，仍然存在多处 S0 级矛盾，说明问题不是单纯的新旧文档并存。

# 三、前后矛盾

## S0-01：权威裁决链路自相矛盾

### 现行原则

核心架构明确规定：

```text
资产校验 -> 机制编译 -> RuleExecutor 权威结算 -> AI 根据权威结果叙事
```

并规定 Engine 是唯一状态写入口，AI 只能提出建议。

证据：

- `20-核心架构/AI-Keeper核心链路架构.md:21-46`
- `10-总览与路线/平台能力分层与MVP边界.md:28-39`
- `30-平台子系统/12-AI-Keeper核心系统/PRD.md:22-55`

### 冲突设计

`KP_MCP_Design.md` v0.1 设计为：

```text
kp_resolve_turn
-> narrative 直接推送
-> rollRequests 再掷骰
-> stateMutations 再写入
```

并定义 `direct` 为“后端直接写，不校验”，允许直接写 `scene_transition`、`npc_reaction`、`add_status_tag` 等状态。

证据：

- `20-核心架构/KP_MCP_Design.md:341-389`
- `20-核心架构/KP_MCP_Design.md:393-442`

### 后果

- 叙事可能先宣布成功，之后骰子却失败；
- AI 可以把“恐惧、重伤、昏迷”等标签直接写成事实；
- 线索、场景和 NPC 状态可能绕过 Rule/State/Clue 服务；
- 防幻觉、回放、审计和重试都失去统一事实来源。

### 裁决建议

`KP_MCP_Design.md` 应立即标为 **Deprecated / 非规范**，MCP 只保留为 provider 传输层。它不得重新定义结算顺序，也不得拥有任何 `direct` 状态写入。

唯一合法链路应为：

```text
Player Intent
-> 身份、拥有权、可见性校验
-> 机制建议/语义编译
-> 必要时玩家确认
-> Rule 权威结算
-> State 原子提交
-> 安全投影计划
-> AI 基于已提交结果生成公共/私密叙事
-> Journal/Receipt
```

## S0-02：AI 行为准则与规则权威冲突

`soul.md` 允许“让玩家自行掷骰并提供结果”，也允许 AI “直接代骰”。这与服务器端 RuleExecutor 产生权威骰值的原则不一致。

证据：`20-核心架构/soul.md:303-333`

### 裁决建议

`soul.md` 必须从“通用聊天 KP Prompt”改成“平台内受约束的 Narrative Policy”：

- AI 可以建议需要什么检定；
- AI 不得接受玩家口述骰值作为权威结果；
- AI 不得自行产生权威骰值；
- AI 只能消费 `RuleResult`；
- 所有“结果”措辞必须引用已提交的规则与状态结果。

## S0-03：Host 同时被定义成设备、房主和主持人

前端产品文档明确指出：

- Host 页面其实是所有人共同观看的 `Shared Stage`；
- Room Owner 只负责建房和成员管理，不看剧透；
- Table Steward 只处理暂停、故障和无剧透操作；
- AI-Keeper 是唯一掌握幕后真相的 KP。

证据：`40-前端设计/哪些UI页面出来，分别给谁用.md:1-38`

但现行 `17-Host-Client` PRD 又把 Host Client 定义为“公共舞台和房主控制台”，让同一个 Host 创建房间、开局、看完整时间线、恢复 checkpoint、导出 full、处理遭遇。

证据：`30-平台子系统/17-Host-Client公共舞台端/PRD.md:1-63`

核心架构中的 Host 则是只能消费公共事件、不能查看完整 KP-only 真相的舞台角色。

证据：`20-核心架构/AI-Keeper核心链路架构.md:21-35`

### 后果

- 权限模型无法稳定；
- 同一 `owner_token` 可能同时控制公共大屏和私密管理能力；
- 无法判断 Host timeline 是否可见玩家私密事件；
- 产品页面、API、审计和离线模式会继续各说各话。

### 裁决建议

把“设备”和“人类角色”彻底拆开：

| 类型 | 建议名称 | 是否是人 | 是否看真相 | 权限 |
|---|---|---:|---:|---|
| 公共显示设备 | `SharedStage` | 否 | 否 | 只读 party-safe 投影 |
| 房间创建者 | `RoomOwner` | 是 | 否，默认 | 成员、房间、账务/配置 |
| 桌面管理员 | `TableSteward` | 是 | 否 | 暂停、恢复连接、安全工具、故障处理 |
| 人类 KP | `HumanKeeper` | 是 | 是 | 仅在明确支持的人类 KP 模式存在 |
| AI 主持运行时 | `AIKeeper` | 否 | 受控读取 | 建议与叙事，不写权威状态 |
| 权威执行者 | `Engine` | 否 | 读取必要事实 | 唯一权威写入 |

`Host` 这个词应从规范层退出，最多保留为旧代码兼容名。

## S0-04：“AI 独占真相”与“人类 Host 复核重大剧情”无法同时成立

UI 文档写死：普通产品不应存在完整模组真相、未发现线索、NPC 真实动机、隐藏地图、AI 内部计划和直接世界状态编辑器；AI-KP 独占幕后真相。

证据：`40-前端设计/哪些UI页面出来，分别给谁用.md:1012-1029`

但“Host 不在线”设计又把以下决定定义为 `host_owned`：

- 新 Canon；
- 重大方向；
- 核心揭示；
- Retcon；
- 异常裁决。

证据：`50-设计哲学/第4条：Host 不在线时仍能继续，但重要结果必须可复核.md:74-83`

### 矛盾本质

一个完全不看真相的人，无法有意义地复核“核心揭示是否正确”。他最多能批准“是否现在发生一个高风险变化”，不能判断内容本身是否符合模组真相。

### 必须二选一或显式支持双模式

- **AI-only 模式：** 新 Canon 原则上禁止；核心揭示只能来自预编译 Module/RevealGate；RoomOwner/Steward 不复核剧情真相。
- **Human-Keeper 模式：** 人类 KP 有独立幕后视图和真相权限；AI 是助手。
- 若两种都支持，必须成为房间创建时不可含糊的 `runMode`，使用不同权限表和 UI，而不是共用 Host 概念。

## S0-05：Shared Stage 可选，与 Host ACK 阻塞玩家结果冲突

Transaction PRD 规定，玩家私密 patch、通知和 action completed 进入 `ReleaseGate`，等 Host 发 `host_step_complete` ACK 后才释放。

证据：`30-平台子系统/14-Transaction事务系统/PRD.md:396-412`

但其他文档同时要求：

- Host 可以不在线；
- 手机端有“无大屏 fallback”；
- Shared Stage 是公共显示设备而非权威角色。

### 风险

- 大屏断线会让玩家永远卡在 resolving；
- 没有大屏的远程或纯手机团无法完成行动；
- 表现层反向成为业务状态的可用性依赖。

### 裁决建议

区分三件事：

1. **权威提交：** State 成功即完成，不等待任何 UI；
2. **信息揭示顺序：** 由服务端 `RevealPolicy` 和事件依赖控制；
3. **视觉播放确认：** Shared Stage ACK 只用于避免重复动画，不控制业务完成。

私密结果可以延迟到公共揭示事件已发布或服务端超时，但绝不能无限等待某块屏幕的 ACK。

## S0-06：产品主命题未统一

当前文档同时描述三种产品：

### A. AI 独立主持短团

- AI-Keeper 是唯一 KP；
- 房主不看剧透；
- Shared Stage + Player Companion；
- 重点是无主持人也能开团。

### B. AI 辅助人类 KP

- Host 查询剧本知识；
- Host 复核重大剧情；
- Host 看完整时间线、恢复、处理遭遇；
- Safety 文档多处用“AI 辅助 KP”。

### C. AI 自主维持长期战役

- 长期可信记忆；
- 战役方向控制器；
- Host 缺席续行；
- Session Handoff 与 Continuity；
- NPC Agenda、WorldClock、RevealGate。

三者都可以成立，但对应的 MVP、权限、内容准备、质量指标和 UI 完全不同。当前文档试图同时完成三者，是范围膨胀的根源。

## S1-07：MVP 路线与 UI P0 不一致

路线文档要求第一轮只验证窄主链：房间、身份、文字意图、规则、状态、投影、线索、防剧透、重连和日志，并明确把语音视频、复杂日程、社区、动态光照等后置。

证据：`10-总览与路线/平台能力分层与MVP边界.md:28-65`

但 UI 文档的 P0 包含 32 个页面/模式：

- 公共桌面 8 项；
- 玩家手机 11 项；
- 桌务 7 项；
- 战役准备 6 项。

其中包括公共地图、调查工作台、继续战役、模组导入、自动编译、质量报告、安全工具等。

证据：`40-前端设计/哪些UI页面出来，分别给谁用.md:1121-1173`

### 裁决建议

把“完整产品信息架构”与“首个可验证版本”分开。P0 不应是一张长期愿望清单。

## S1-08：跑团内容安全被同时定义为 P0 和阶段 5

`工程安全运营护栏` 把内容分级、禁区、X-Card、私密反馈、淡出和 AI 内容限制全部放到阶段 5。

证据：`10-总览与路线/工程安全运营护栏.md:45-54`

但 Safety V2.1 又将安全定义为 P0 主链路，并把 X-card、fade、private feedback 放入 v1 产品边界。

证据：`30-平台子系统/21-Safety跑团安全边界系统/PRD.md:3-8, 67-80`

### 裁决建议

拆成两层：

- **M0 必须有：** 内容提醒、玩家边界、全局暂停/X-card、淡出、私密反馈、AI 尊重边界；
- **上线前补强：** 举报、审核看板、组织策略、合规报表、复杂治理。

对 AI 主持的恐怖游戏而言，最小桌面安全不是运营增强，而是核心交互的一部分。

## S1-09：Host 的“完整日志”与玩家私密边界冲突

工程护栏规定，角色私密信息默认只对角色拥有者和必要的 Engine 可见，Host 不默认拥有完整 KP 视角。

证据：`10-总览与路线/工程安全运营护栏.md:19-30`

但 Journal PRD 规定 Host/Owner 可以查看房间完整 Journal 事件，并导出 full。

证据：`30-平台子系统/11-Journal日志与回放系统/PRD.md:43-83, 161-183`

### 裁决建议

“可审计”不等于“能看原文”。Steward 应看到：

- 某次私密事件发生；
- 事件类型、状态、来源和失败原因；
- 必要的脱敏摘要；

而不是默认看到其他玩家私密线索、私密行动文本或敏感反馈。只有 HumanKeeper 模式或平台合规角色才能按明确授权查看更深内容。

## S1-11：P0、验收和完成的语义被混用

文本扫描中，现行产品/架构文档里 `P0` 出现约 577 次，分布在 131 个文件。它被用于表示：

- 当前 MVP 用户价值；
- 安全漏洞严重度；
- 文档必须先定义；
- 已有代码需要修复；
- 未来系统的前置设计。

工程回执也把不同状态混为“工程验收通过”：

- Room 回执报告 409 passed、12 errors，同时给出“P0 无剩余”；
- AI 回执写“本轮工程验收通过”，但明确“生产安全完成未达到”；
- Community 没有代码改动，仅完成设计，却写“本轮工程验收通过”。

证据：

- `30-平台子系统/01-Room团房间系统/回执-2026-07-06.md:3-5, 87-119`
- `30-平台子系统/12-AI-Keeper核心系统/回执-2026-07-06.md:89-131`
- `30-平台子系统/23-Community社区生态系统/回执-2026-07-08.md:8-38`

### 裁决建议

分成三个正交维度：

| 维度 | 建议枚举 |
|---|---|
| 发布范围 | `M0 / M1 / M2 / Later` |
| 风险严重度 | `S0 / S1 / S2 / S3` |
| 成熟度 | `Idea / Draft / Reviewed / Normative / Implemented / Verified / Production-ready` |

“设计通过”“实现完成”“测试验证”“生产就绪”必须分别给结论。

# 四、过度设计

## 1. 在产品假设之前完成了平台级分解

排除归档、开发执行和测试报告后，现行产品/架构文档约 157 份、5.6 万行；平台已拆成 24 个模块，每个模块又包含 PRD、功能列表、计划、回执和验收。

问题不在文档多，而在于尚未明确：

- 第一目标用户是谁；
- 最重要的使用场景是什么；
- AI-only 和 Human-Keeper 哪个是主模式；
- 一次性短团还是长期战役优先；
- 首版成功如何衡量。

因此，很多精确 DTO、状态机和模块边界是在未锁定产品前提下建立的，容易形成“伪精确”。

## 2. UI P0 过宽

首版同时要求公共舞台、玩家端、桌务端、战役准备台四套完整体验，且包含地图、调查、连续性、模组导入和安全控制。即便不少是同一路由的不同模式，产品、设计、测试和异常状态仍然是 32 套用户状态。

## 3. 未来能力被提前固化成系统

以下方向有长期价值，但不应在当前阶段都被当作规范模块：

- 完整 Semantic Interaction Protocol；
- 可插拔 Combat/Encounter Runtime；
- Narrative Governor、CampaignPromise、StoryThread、WorldClock；
- Trusted Memory / Fact、Cognition、Hypothesis 多账本；
- Host Delegation / ReviewBacklog；
- Continuity Packet；
- 独立 Item/Inventory；
- 多 provider、MCP、Agent、A/B 叙事、流式输出；
- 社区、插件、市场、复杂 Ops。

应先把它们降为能力提案，并明确它们解决的已验证问题。

## 4. 表现层协议过早进入核心可靠性

ReleaseGate、Host ACK、Cue 去重、BGM 挂起、演出恢复都可能是优秀的舞台设计；但把 Shared Stage 的播放进度接入玩家行动完成，会让沉浸层污染业务权威层。

正确边界应是：**核心循环在没有 Shared Stage、没有声音、没有动画时仍然完全成立。**

## 5. “后验物品主张”设计深度远超基础库存模型成熟度

现有数据流已经为职业—物品标签矩阵、编辑距离、baseline access、自动注入背包和 Luck/Know 分支设计了较深机制。但当前 Character、Clue、State 中物品权威仍分散，独立 Item 边界尚未决定。

应先建立最小物品权威与证据链，再决定是否值得支持复杂的追溯主张。

# 五、漏设计

## 1. 缺产品定义与验证假设

对 157 份现行产品/架构 Markdown 做文本扫描，没有找到明确的：

- 目标用户；
- 用户画像；
- 用户研究/访谈；
- JTBD；
- 北极星指标；
- 成功指标；
- MVP 假设；
- 可用性测试计划。

这是当前最大的漏项。技术北星很清楚，但产品北星没有被写成可验证命题。

建议至少回答：

> 对哪一类玩家，在什么场景下，AI-Keeper 替代了什么现有做法，带来什么可测量改善？

## 2. 缺主运行模式

需要在建房时明确：

- `ai_only`；
- `human_keeper_assisted`；
- 将来是否支持 `hybrid`。

并为每种模式定义真相可见、复核、暂停、Retcon、导出和故障恢复权限。

## 3. 缺完整领域生命周期

建议统一为：

```text
ModuleDefinition / ModuleVersion
-> Campaign（一次长期游玩实例）
-> Room/Table（成员与实时接入容器）
-> Session（一次实际聚会）
-> Scene / Encounter
-> Turn（如规则需要）
-> PlayerAction
-> ResolutionTransaction
-> StateChange + Event + Projection
```

是否最终采用这些名称可以讨论，但必须有一份唯一规范。特别是 Campaign 当前大量出现在 UI、Journal 和设计哲学中，却没有成为 24 模块施工图里的明确领域聚合。

## 4. 缺统一的“认知与事实模型”

反幻觉不能只靠 Prompt 和可见性字段。需要跨 WorldBook、Clue、Journal、AI、Continuity 统一定义：

| 类型 | 含义 | 能否改写 Canon |
|---|---|---:|
| `CanonicalFact` | 模组或 Engine 确认的客观事实 | 是，受控 |
| `Observation` | 某角色实际感知到的内容 | 否 |
| `Evidence/Clue` | 有来源的可引用证据 | 否，支持推断 |
| `Testimony` | NPC/文档声称的内容 | 否 |
| `Hypothesis` | 玩家或 AI 的推测 | 否 |
| `Summary` | 对已有事实的派生压缩 | 否 |
| `KeeperPlan/Note` | AI 的计划或候选方向 | 否 |

尤其 `keeperNotes` 不能因为被保存并用于后续 context，就逐步变成事实。它必须带类型、来源、置信度、有效期和 `non_canonical` 标记。

## 5. 缺一条唯一的端到端用户旅程

现有文档有很多页面和局部流程，但缺少一份从用户视角贯穿全程的主旅程：

```text
发现产品/试玩
-> 创建 Campaign
-> 选择或导入 Module
-> 质量检查与失败兜底
-> 邀请玩家
-> 角色绑定
-> Session 0 与安全设置
-> 开局
-> 行动—澄清—结算—叙事—回执循环
-> 争议/暂停/重连/故障
-> Session 结束
-> Handoff / 下次继续
-> 归档、导出、删除
```

每一步都需要：入口、角色、前置条件、权威状态变化、失败分支和用户可见反馈。

## 6. 缺“AI 误解与玩家申诉”产品机制

设计哲学提到了 Intent Contract 和 Review Transaction，但现行 MVP 没有统一回答：

- 什么情况下系统自动解释；
- 什么情况下必须让玩家确认；
- 玩家如何说“你理解错了”；
- 规则结果争议由谁处理；
- 是否允许重掷、撤回、Retcon；
- 修正后如何通知全桌并保留审计。

这是 AI 主持产品的核心信任机制，不应只是异常处理。

## 7. 缺首版内容供给策略

需要决定首版验证使用：

- 官方/自制的预编译短模组；
- 用户上传任意 PDF；
- 或两者并存。

如果一开始就支持任意 PDF，导入质量、版权、OCR、结构化失败和剧情完整性会掩盖核心主持体验。更稳妥的验证方式是先用少量可控短模组证明主持闭环，再开放导入。

## 8. 缺内容权利与数据使用政策

社区文档设计了公开素材许可，但私人模组导入仍需要明确：

- 用户是否有权上传该 PDF/图片/音频；
- 内容是否发送给第三方模型提供商；
- 是否用于产品或模型改进；
- 原文件、解析文本和 embedding 保存多久；
- 删除账号/战役后，备份中的删除语义；
- 生成内容和战报的权利归属；
- 语音录入是否需要全桌知情与同意。

## 9. 缺可访问性、设备和低带宽基线

前端设计零散提到字幕、减少动画和手机 fallback，但还需要统一验收：

- 屏幕阅读器与键盘操作；
- 色觉与对比度；
- 减少动画；
- 纯文字替代所有音频/视觉 Cue；
- 低带宽与断网恢复；
- 小屏可用；
- 中英文/术语本地化策略。

## 10. 缺 AI 质量、成本和可复现性指标

日志字段很多，但产品层还需要定义：

- 一次行动允许的端到端延迟；
- 澄清率和误解率；
- fallback 触发率；
- 剧透拦截率与误杀率；
- 规则争议和 Retcon 率；
- 每房间/每小时成本；
- provider、model、prompt、schema 版本如何绑定到一次结果；
- 模型升级如何做回归和灰度。

# 六、建议先做的产品裁决

## 推荐主命题

从现有文档最有差异化、也最一致的部分看，建议首版锁定为：

> **2–4 名玩家无需人类 KP，使用一个经过验证的 COC 短模组，通过文字行动完成一场可解释、可恢复、不剧透的调查游戏；每名玩家使用私人终端，Shared Stage 只是可选的公共镜像。**

这不是永久放弃长期战役、人类 KP、语音或模组编辑器，而是先验证最核心的不确定性：

1. AI 是否能正确理解玩家行动；
2. 规则与状态是否可信；
3. 公共/私密信息是否让玩家感到公平；
4. 没有人类 KP 时，故事是否能持续推进；
5. 一整场体验是否比“找人当 KP”更容易开始。

## 三种产品命题的优先级差异

| 主命题 | 必须最先做 | 可以后置 |
|---|---|---|
| AI 独立跑短团 | 可控模组、意图确认、Rule/State、线索、节奏、安全、无主持故障恢复 | 长期记忆、社区、复杂地图、Human-Keeper 控制台 |
| AI 辅助人类 KP | HumanKeeper 后台、真相检索、准备工具、复核与导演控制 | Host 缺席自治、AI-only 无剧透房主模式 |
| AI 维持长期战役 | Campaign/Session、可信记忆、Continuity、方向控制、版本与迁移 | 华丽舞台、社区、插件、复杂 VTT |

在没有选定其中一个作为主命题前，不应继续扩模块。

# 七、建议的 M0 范围

## 必须有

1. 一个经过验证的短 COC 模组；
2. 创建房间、邀请、加入、角色选择/绑定；
3. 最小 Session 0：内容提示、边界设置、X-card/暂停；
4. 文字行动输入；
5. 对模糊或高影响行动进行一次明确确认；
6. COC 核心技能检定、SAN 和最小状态变化；
7. Engine 唯一权威写入；
8. 公共叙事与角色私密叙事；
9. 私密线索、主动分享、公开摘要；
10. 无 Shared Stage 也能完整运行；
11. 断线重连；
12. 可解释回执：理解了什么、为何检定、结果是什么、状态怎么变；
13. Session 结束摘要和安全退出。

## 明确后置

- 任意 PDF 的完全自动编译；
- 模组可视化编辑器；
- 复杂地图、Token、动态光照；
- 语音、TTS、BGM 和多媒体 Cue；
- 完整调查工作台；
- 可插拔战斗运行时；
- 长期 Campaign Governor；
- Host 缺席授权与 ReviewBacklog；
- 独立 Semantic、Item、Continuity 大模块；
- Schedule、Community、Plugin、Market；
- 多模型 A/B 叙事与自主 Agent。

# 八、M0 建议指标

以下是应进入产品文档的指标类别，具体目标值应通过试跑校准：

## 激活

- 从创建房间到所有玩家 ready 的时间；
- 首次用户成功开始第一幕的比例；
- 因模组、角色或连接问题无法开局的比例。

## 核心体验

- 完成一场/一个短模组的团队比例；
- 一次行动无需人工干预完成结算的比例；
- 平均澄清轮数；
- 玩家认为“系统正确理解了我的行动”的比例；
- 玩家能解释检定原因和结果的比例。

## 信任与安全

- 未授权状态写入数；
- 剧透事故数；
- 规则争议率；
- Retcon/回滚率；
- 安全暂停后的正确处理率。

## 性能与成本

- 行动端到端 P50/P95 延迟；
- provider fallback 率；
- 每玩家小时模型成本；
- 断线恢复成功率。

## 留存

- 完成首场后愿意再开一场的团队比例；
- 长团方向确定后，再加入第二 Session 继续率。

# 十、文档治理规则

每份现行文档顶部增加统一元数据：

```yaml
status: normative | candidate | exploratory | deprecated | archived
version: 2.2
doc_owner: Product / Architecture / Module owner
effective_date: YYYY-MM-DD
supersedes: []
depends_on: []
release_scope: M0 | M1 | M2 | Later
last_validated: YYYY-MM-DD
```

并执行以下规则：

1. 全局概念只能在六份顶层规范中定义；模块 PRD 只能引用，不能重定义 Host、State、Visibility、P0 等概念。

3. 工程回执必须分别报告：设计、实现、测试、生产就绪。
4. 旧版文档必须写 `superseded_by`，不能仅靠目录位置推断。
5. 每次目录迁移跑一次 Markdown link check；当前 5 个现行文档链接应先修复。

# 十一、建议的处理顺序

## 第一步：冻结新增模块

暂时不新增 25/26/27，也不继续细化 Community、Plugin、Combat、Semantic、Continuity。

## 第二步：一周内只裁决 8 个问题

2. AI-only 与 Human-Keeper 是否双模式；
3. Host 名称与角色拆分；

每个 P0 只回答一句：

> 没有它，能否用一个可控短模组让 2–4 名玩家完成一次无真人 KP 的可信调查？

任何模块都必须说明它在这条路径中的位置，否则不进入 M0。

# 十二、最终判断

## 前后矛盾：有，而且有数个会破坏产品根基的 S0 矛盾

最严重的是：AI/Engine 权威、Host 定义、真相复核、Shared Stage ACK 和产品主模式。

## 过度设计：有，主要表现为“中下层精确，上层未裁决”

状态、投影、审计和反剧透的深度是有价值的；过度之处在于把大量长期能力同时固化为 P0、模块和精细协议。

## 漏设计：有，且漏的是产品层而不是功能层

缺的是目标用户、主场景、验证假设、成功指标、运行模式、统一领域生命周期、事实/认知模型、申诉纠错、内容供给、版权隐私和可访问性。

一句话总结：

> **这套文档现在更像“一个高度防御性的 AI 跑团平台架构大全”，还不是“一份围绕单一用户价值收敛的产品设计”。下一步应该做减法和裁决，而不是继续补系统。**
