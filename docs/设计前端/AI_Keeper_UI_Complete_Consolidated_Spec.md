# 1. 当前有效设计基线

## 1.1 终端分工

| 终端 | 核心问题 | 主要职责 |
|---|---|---|
| 公共大屏 | 现在发生了什么？ | 场景、公共叙事、公开行动、冲突、公开结果、队伍概况 |
| 玩家手机“当前” | 现在需要我做什么？ | 当前事项、行动声明、决定、个人结果、最近发生 |
| 玩家手机“调查” | 我们知道什么、还在查什么？ | 线索、人物、地点、开放问题、假说、私人发现 |
| 玩家手机“角色” | 我现在是什么状态、能使用什么？ | HP、SAN、Luck、技能、物品、异常、历史 |
| 桌务端 | 流程出问题时如何继续？ | 无剧透的连接、缺席、安全与恢复控制 |

## 1.2 公共大屏基础结构

```text
顶部：场景名称 · 游戏时间 · AI-KP 状态
中部左：场景主视觉 / 地图 / Handout / 当前冲突
中部右：队伍目标 · 公开时钟 · 固定顺序角色状态
底部：当前叙事 + 最近 3—5 条公共事件
```

核心约束：

- 场景与 AI-KP 公共叙事是默认第一焦点；
- 大屏不提供推进剧情、掷骰、修改 HP、添加单位等操作；
- 角色状态只显示简化 HP/SAN 条与公开状态词；
- P0 支持最多 6 名玩家，成员位置固定；
- 私密内容不存在任何占位、数量或提示；
- 普通结果进入底部记录，重要结果短暂占据中央焦点；
- 线索、Handout、投票和桌面裁定属于持续内容。

## 1.3 玩家手机基础导航

```text
[当前] [调查] [角色] [更多]
```

“当前”页采用：

```text
一件最高优先级主事项
+
待处理数量
+
统一输入框
```

输入模式：

```text
行动 / 本轮行动
角色发言或角色喊话
队伍讨论
规则提问
私人笔记
```

## 1.4 行动确认

采用渐进式确认：

- 低风险且理解清楚：短暂显示安全摘要，可撤销后自动提交；
- 高影响、资源消耗、多个目标或重大公开影响：完整确认；
- 核心语义存在歧义：只追问一个必要问题；
- 非执行类输入不直接进入角色行动事务。

## 1.5 调查系统

调查首页默认显示：

```text
搜索
私人新发现提醒
当前调查目标
最近新增 / 开放问题（动态排序）
队伍置顶
分类入口
```

资料详情统一为：

```text
摘要
当前已知
相关资料
玩家笔记
```

假说：

- 默认仅自己可见；
- 分享后生成独立队伍版本；
- 其他玩家只补充支持、矛盾、相关资料和评论；
- 状态仅有“讨论中 / 已证伪 / 已搁置”；
- AI 只能提出状态建议，不能自动判断真假。

## 1.6 角色、技能与物品

角色首页常驻：

```text
HP / SAN / Luck
当前异常
技能摘要
物品摘要
成长摘要
更多数值
```

技能点击后只将技能作为行动辅助标签，不直接掷骰。

物品点击后打开简洁物品卡；使用物品时将物品标签带回行动输入，不直接消耗。

物品转交：

```text
发送者发起
→ 接收者确认
→ 服务端原子修改持有人与位置
```

可选择公开或私下递交；私下递交可能进入规则裁决，但不会在公共大屏暴露事务存在。

## 1.7 战斗整轮模型

最终战斗流程：

```text
公开本轮局势
→ 全体玩家分别声明
→ 处理缺席声明
→ 锁定全部声明
→ 公开可观察准备动作
→ AI-KP 生成 RoundResolutionPlan
→ 按规则权威顺序逐步提交事实
→ 按 ResolutionCluster 编排连贯叙事
→ 生成轮末局势总结
→ 手机立即开放下一轮声明
```

核心规则：

- 声明阶段不掷骰、不扣资源、不改状态；
- 大屏在锁定前只显示“已声明 / 思考中”；
- 锁定后不允许补行动、修改声明或插入角色喊话；
- AI-KP 以“场景冲突”而不是单个角色回合作为展示焦点；
- 规则层保持全局正确顺序，展示层可在不颠倒事实的前提下组织镜头；
- 每轮必须生成公开局势总结；
- 总结展示期间，玩家手机可同时填写下一轮声明。

## 1.8 缺席与重连

缺席策略只有：

```text
本轮暂不主动行动
维持已经成立的持续行为
```

禁止 AI 或桌务替玩家选择新目标、战术、Luck、Push、额外 MP 或一次性物品。

重大离线选择节点必须记录：

> 该节点曾存在可选资源或规则选择，但玩家当时离线且无有效预声明，因此按未选择处理。

不允许事后补选或局部重算。

整轮锁定后重新上线，只能观看、讨论和查看状态；下一轮通过紧凑“重新加入局势”卡恢复声明。

## 1.9 预备动作

预备动作最终定义：

> 放弃本轮普通主动行动，锁定一项只在本轮有效的完整主要动作；当明确、可观察且尚未发生的条件首次有效满足时，按规则时序自动执行。

硬规则：

- 占用本轮主动行动；
- 触发条件具体、可观察；
- 动作、目标、方式、工具与未触发结果必须完整；
- 锁定后不可修改或主动取消；
- 不能追溯触发；
- 本轮未触发不返还行动；
- 触发后自动执行，不二次确认；
- 动作或成立基础中途失效后立即关闭，不自动恢复；
- 只能有一个主要动作；
- 仅允许规则认定的必要附带位移；
- 具体实体或确定性目标选择器均可；
- 多个预备动作按规则优先级、敏捷、平手规则和稳定 Rank 排序；
- 连续动作在触发阈值处形成权威中间状态，结算预备动作后重新校验并继续；
- 最多两个明确感知依据，使用 OR；
- 玩家端只看自然语言确认摘要。

## 1.10 预备动作的资源规则

- 锁定时必须当前具备最低执行条件；
- 锁定时不冻结武器、不预留资源；
- 触发和每个阶段开始前重新校验；
- 资源只在规则定义的实际消耗节点扣除；
- 已发生的准备成本不自动退款；
- 资源不足不自动降级、换版本或改投入量；
- 玩家自由选择的投入必须提前锁定具体数值；
- 规则客观计算型成本可以锁定“公式 + 目标上限 + 资源上限”；
- 资源不足后的处理必须来自规则包，而不是前端或 AI-KP 临时决定。

# 附录 1：AI_Keeper_UI_Brainstorm_Round1

# AI-Keeper UI 头脑风暴第一轮总结

**日期：2026-07-18**  
**范围：公共实时舞台（Shared Stage Live）与玩家手机端（Player Companion）**  
**目标：让玩家无需学习复杂系统，也能一眼看懂当前局面，并立即知道自己该做什么。**

---

## 1. 核心产品原则

### 1.1 公共大屏与玩家手机分工

| 终端 | 核心职责 |
|---|---|
| 公共大屏 | 展示全桌共同看到的场景、叙事、行动焦点、公开结果与队伍概况 |
| 玩家手机 | 处理个人行动、确认、私密信息、角色、物品、调查资料与待处理事项 |
| 桌务端 | 后续单独设计，只负责流程、安全和无剧透异常处理 |

公共大屏负责“看懂现在”；玩家手机负责“我现在要做什么”。

### 1.2 每个主页面只回答一个问题

- 公共大屏：**现在发生了什么？**
- 玩家手机首页：**现在需要我处理什么？**
- 调查页：**刚获得了什么、还在调查什么？**
- 角色页：**我现在状态如何、还能使用什么？**

### 1.3 公共大屏不是控制台

公共大屏不常驻：

- 系统设置和管理菜单；
- 主动掷骰、推进剧情、添加单位；
- 完整角色卡和精确资源；
- 完整日志和后台状态；
- 玩家私人信息；
- AI-KP 幕后信息。

# 2. 公共实时舞台

## 2.1 默认焦点

默认采用：

> **场景氛围 + AI-KP 公共叙事。**

场景视觉占据主要区域；行动、骰点、线索、决定等内容只在发生时临时进入焦点，结束后回到场景。

## 2.2 基础结构

```text
┌────────────────────────────────────────────────────┐
│ 场景名称 · 游戏时间                   AI-KP 状态   │
├─────────────────────────────────┬──────────────────┤
│                                 │ 当前目标         │
│                                 │ 公开时钟         │
│          场景主视觉             ├──────────────────┤
│                                 │ 队伍成员         │
│                                 │ 简化 HP / SAN    │
│                                 │ 当前行动状态     │
├─────────────────────────────────┴──────────────────┤
│ 当前叙事                                           │
│ 最近 3—5 条公共事件                                │
└────────────────────────────────────────────────────┘
```

建议比例：

- 顶部状态栏：7%—9%；
- 中部舞台：66%—70%；
- 底部叙事栏：22%—25%；
- 右侧栏：中部宽度的 20%—24%。

## 2.3 右侧信息栏

固定顺序：

1. 当前队伍目标；
2. 公开游戏时钟或倒计时；
3. 所有玩家角色。

队伍目标只能来自玩家已经确认的计划，不能由 AI 根据模组真相推荐。

没有明确目标时显示“自由调查”；没有时间压力时显示游戏内时间，不制造虚假倒计时。

## 2.4 角色状态显示

公共大屏显示简化状态条，不显示精确数值。

```text
[头像] 陈默           轻伤
HP   ███████░░░
SAN  █████░░░░░
```

规则：

- 不显示 `8/12`、`54/70` 等精确值；
- 必须同时显示文字状态，不能只依赖颜色；
- Luck、MP、弹药和私人状态不常驻；
- 已公开的重伤、疯狂、昏迷等可以突出；
- 状态变化仅使用短暂轻量动画。

## 2.5 成员排列

- 所有队伍成员始终显示；
- 按固定座位顺序排列；
- 当前在场、离场、断线、行动中等只改变样式，不改变位置；
- 当前行动角色只高亮对应角色卡；
- 3—4 人使用中型卡；
- 5—6 人使用紧凑卡；
- P0 最多支持 6 名玩家；
- 不使用分页、轮播或滚动角色列表。

## 2.6 底部叙事记录

采用固定底部叙事栏，显示当前叙事和最近 3—5 条公共事件。

规则：

- 最新内容最大、最醒目；
- 历史内容逐级缩小和降低对比度；
- 超出数量后最旧内容淡出；
- 不使用聊天气泡；
- 不显示完整玩家原始输入；
- 不显示私密行动；
- 不显示复杂规则过程；
- 不使用逐字打字效果。

## 2.7 当前行动表现

公开行动在以下流程完成后才进入大屏：

```text
玩家输入
→ 确认或撤销窗口
→ 服务端验证
→ 正式接收行动
→ 生成公共安全摘要
```

大屏显示：

```text
陈默正在观察教授的反应……
```

同时高亮陈默的角色卡并标记“行动中”。

该摘要一直保留到裁决结果产生。

以下内容不会进入大屏：

- 行动草稿；
- 尚未消除的歧义；
- 已撤销行动；
- 无效目标；
- 未通过权限验证的行动；
- 秘密行动；
- 玩家完整原话和私人限制。

## 2.8 等待玩家决定

行动进入 Luck、Push、反击等阶段时，根据可见范围显示。

公开决定：

```text
陈默可以花费 Luck 修改这次结果
等待陈默决定……
```

私人决定：

```text
等待陈默完成一项个人决定……
```

完成后显示安全摘要：

- 公开资源或公开动作：显示“陈默决定花费 Luck 修改结果”；
- 私密机制：显示“陈默完成了一项个人决定”。

不显示精确剩余资源、隐藏风险或未选择的选项。

## 2.9 公共骰点和重要结果

采用两级展示。

### 普通结果

- 高亮对应角色卡；
- 写入底部叙事记录；
- 不遮挡主场景。

### 重要结果

以下内容可以进入中央结果卡：

- 大成功、大失败；
- 重伤、昏迷、临时疯狂；
- 关键公开线索；
- 敌对单位被击败；
- 重大桌面裁定。

展示时场景保留并轻微压暗，不完全切走。

## 2.10 瞬时结果与持续内容

### 瞬时结果

大成功、大失败、受伤、疯狂、击败等：

- 约 4 秒自动收起；
- 随后写入底部记录；
- 返回场景。

### 持续内容

新线索、Handout、全桌决定、桌面裁定、安全提示等：

- 按内容类型决定何时收起；
- 右侧角色栏继续保留；
- 底部叙事栏临时收缩成一行；
- 主视觉扩大用于资料展示。

| 内容 | 结束条件 |
|---|---|
| 线索、Handout | 满足最低展示时间，AI-KP 继续叙事时收起 |
| 全桌决定 | 投票或决定完成 |
| 桌面裁定 | 在线玩家确认，桌务必要时可继续 |
| 安全提示 | 必须明确确认 |

# 3. 公共大屏与手机联动

## 3.1 新线索通知

大屏展示线索时，玩家手机收到非打断式通知：

```text
队伍获得新线索
旧建筑平面图

[查看]
```

规则：

- 不自动跳转；
- 不覆盖正在编辑的行动；
- 通知收起后进入待处理入口；
- 私密线索只通知有权限的玩家；
- 其他玩家不知道私密线索是否存在。

## 3.2 线索详情打开方式

根据内容类型自适应：

- 简短线索、人物摘要、地点信息：底部抽屉；
- 地图、照片、信件、长文档：全屏查看器；
- 关闭后返回原页面；
- 行动草稿、滚动位置和当前事项不丢失。

## 3.3 分享内容的公共展示

普通文字发现：

- 进入底部公共记录；
- 分享者角色卡短暂高亮；
- 不抢占主视觉。

图片、地图、信件、证物等内容：

- 系统可以根据公开形式建议“重点展示”；
- 玩家最终确认；
- 重点展示进入公共主视觉；
- 所有玩家手机收到通知。

系统不能依据“是否接近真相”判断重要程度。


## 4.2 事项优先级

```text
> 协同行动邀请

> 新公共线索
> 自由行动
```

## 4.3 一件主事项 + 待处理数量

首页一次只展开最高优先级的一项，下面显示：

```text

协同行动邀请 ×1
新线索 ×1
```

不把首页做成任务列表。

## 4.4 统一底部抽屉

点击摘要后打开：

### 待处理

- Luck、Push；
- 协同行动；
- 物品接收；

### 最近发生

- 公共裁决；
- 私人结果；
- 线索；
- 状态变化；
- 物品变化；
- 桌面裁定。

抽屉最多占屏幕约 70%，保留当前页面上下文。

# 5. 玩家行动输入

## 5.1 一个输入框 + 明确模式

```text
[行动 ▾]  描述你想做什么……  [发送]
```

模式：

- 行动；
- 角色发言；
- 队伍讨论；
- 规则提问；
- 私人笔记。

规则：

- 当前模式始终可见；
- 切换模式不清空输入；
- 不依赖 AI 猜测输入类型；
- 进入新场景或处理完强制事项后默认回到“行动”；
- 非行动模式不会自动执行角色行动。

## 5.2 渐进式确认

### 低风险且理解明确

```text
将执行：查看北侧铁门是否能够打开
[撤销]
```

显示约 2 秒后自动提交。

### 高影响行动

必须完整确认目标、方式、资源消耗和公开影响。

### 关键歧义

不提交，只追问一个必要问题。

## 5.3 行动等待状态

```text
你的行动

观察教授听到“B-17”时的反应

正在裁决……
```

此时：

- 不能再提交新的正式行动；
- 可以继续角色发言、队伍讨论、规则提问和私人笔记；
- AI 响应较慢时显示“行动已保存”；
- Luck、Push 等决定自动成为首页主事项。

# 6. 玩家结果与历史

## 6.1 分层结果卡

```text
结果：普通成功

[全桌可见]
教授听到“B-17”时短暂停顿。

[仅你可见]
教授随后看向了北侧书架。

[加入笔记]
[分享给队伍]
[查看判定依据]
```

规则：

- 公共结果与大屏一致；
- 私人结果明确标记；
- 其他玩家不知道私人补充是否存在；
- 规则过程默认折叠；
- 没有私人结果时不显示空区域。

## 6.2 结果收起规则

### 普通结果

普通成功、失败、常规伤害：

- 满足最低阅读时间后自动收起；
- 玩家开始下一行动或切换页面时收起；
- 永久进入“最近发生”。

### 重要结果

私密线索、重伤、疯狂、关键物品变化：

- 持续停留；
- 玩家阅读、确认或完成后续操作后收起。

### 后续决定

直接转为新的最高优先级事项。

## 6.3 最近发生

公共和私人内容按真实时间混合排列：

```text
23:20 [仅你] 教授看向北侧书架
23:19 [全桌] 心理学普通成功
23:18 [队伍] 获得旧建筑平面图
```

同一次行动合并成一张卡，不拆成碎片事件。

展开后显示：

- 行动；
- 最终裁决；
- 公共结果；
- 私人结果；
- 资源变化；
- 复核或桌面裁定。

```text
公开范围：全体队伍
```

规则：

- 不默认分享原始完整内容；
- 不附带私人笔记、假说和判定依据；
- 分享后生成队伍版本；
- 私人原始记录继续保留；
- 队伍版本标记“由某玩家分享”；
- 玩家观察不会自动升级为系统确认事实。

|---|---|

| 角色 | 状态、技能、物品、成长、更多数值 |

# 9. 调查首页

## 9.1 调查总览

```text
调查

[搜索线索、人物、地点……]

当前调查目标
最近新增
开放问题
队伍置顶

[线索] [人物] [地点] [时间线] [假说]
```

## 9.2 动态排序

- 有未读资料：最近新增置顶；
- 全部读完：开放问题置顶；
- 不在玩家阅读过程中突然重排；
- 重新进入或主动刷新时更新顺序。

## 9.3 队伍资料与私人资料

默认主体为队伍公开资料。

存在新的私人发现时，在顶部单独提醒：

```text
仅你可见的新发现 1

教授看向了北侧书架。

[查看]
[分享给队伍]
```

读完后进入对应资料分类，并保留“仅你可见”标签。

# 10. 调查资料详情

## 10.1 统一四段式

人物、地点、物品和线索全部使用：

1. 摘要；
2. 当前已知；
3. 相关资料；
4. 玩家笔记。

摘要默认展开，其余折叠，并显示数量。

```text
摘要                         已展开
当前已知                     3 条
相关资料                     4 项
玩家笔记                     2 条
```

“当前已知”必须使用认知标签：

- 亲眼观察；
- NPC 证词；
- 玩家推测；
- 存在争议；
- 已确认；
- 已证伪。

不显示关键程度、完成度和隐藏线索数量。

## 10.2 底部操作

最多显示两个主要操作和一个更多菜单。

示例：

- 私人发现：加入笔记、分享给队伍；
- 队伍资料：加入笔记、置顶；
- 开放问题：补充发现、提出假说；
- 玩家假说：关联资料、更新状态。

---

# 11. 玩家假说

## 11.1 创建方式

采用“一句话假说 + 可选关联资料”。

```text
我认为：
陈教授知道 B-17 的真实用途。

可能相关：
☑ 教授听到 B-17 时停顿
☑ 护士关于教授行踪的证词

[保存假说]
```

规则：

- 只要求一句话；
- 关联资料可跳过；
- 从资料详情创建时自动关联当前资料；
- 系统只能推荐近期公开资料，不能推荐“正确证据”；
- 假说明确标记为玩家推测。

## 11.2 默认可见范围

默认仅自己可见。

分享后生成独立的队伍版本；之后修改私人原稿不会偷偷修改队伍版本。

## 11.3 共享假说协作

其他玩家不投票，只能：

- 补充支持资料；
- 补充矛盾资料；
- 补充相关资料；
- 写评论。

## 11.4 状态

只保留：

- 讨论中；
- 已证伪；
- 已搁置。

AI 可以依据新的已确认事实提出“可能证伪”建议，但不能自动修改状态。

任意玩家确认后立即生效，并提供 10 秒撤销。

状态变化只进入公共大屏底部记录，不抢占场景。

---

# 12. 开放问题

## 12.1 状态

- 待调查；
- 已有解释；
- 已关闭。

规则：

- 关联队伍假说后可建议改为“已有解释”；
- 已有解释被证伪后可建议恢复“待调查”；
- AI 不能自动关闭；
- 已关闭不代表答案绝对正确；
- 可以重新打开。

## 12.2 关闭流程

任意玩家可以发起关闭。

确认时显示仍有关联的假说和争议资料，并说明关闭不会删除资料。

关闭后提供 10 秒撤销。

## 12.3 首页展示数量

调查首页最多显示 3 条开放问题。

排序：

```text
队伍置顶
→ 最近更新
```

AI 不按幕后重要程度排序。

# 13. 角色页

## 13.1 页面结构

正常时显示精简总览；存在异常时，顶部增加当前状态卡。

```text
陈默 · 私家侦探

当前状态
轻伤 · 右手活动受限
[查看影响] [使用急救包]

HP      8 / 12

物品
装备 2 · 背包 6 · 重要物品 1

成长
待处理 1 项

更多数值
```

## 13.2 常驻核心数值

只常驻：

- HP；
- SAN；
- Luck。

MP、MOV、体格、伤害加值等进入“更多数值”。

## 13.3 异常卡

- 只显示当前实际影响；
- 最紧急的一项展开，其余折叠；
- 可处理时显示一个主要操作；
- 私密异常不会公开到大屏；
- 解除后自动消失，但保留历史。

# 14. 技能页

## 14.1 页面组织

- 顶部搜索；
- 常用技能；
- 完整技能按调查、社交、战斗、知识、其他分类。

常用技能来源：

```text
玩家手动置顶
+
最近使用补足
```

AI 不能根据隐藏场景推荐正确技能。

## 14.2 技能使用

点击技能不会直接掷骰，而是将技能作为辅助标签带入行动输入：

```text
[行动 · 侦查]

描述你想怎样使用侦查……
```

玩家仍需描述目标和方法。

技能标签是玩家建议，不强制 AI-KP 使用该技能。

## 15.1 页面组织

```text

随身携带
容器内
不在身上
```

提供统一搜索。

规则：

- 物品位置必须真实；
- 容器默认只展开一层；
- 搜索结果仍显示当前位置；
- 当前无法使用时显示原因；
- 私人物品不会公开。

## 15.2 简洁物品卡

```text
急救包
随身携带 · 剩余 1 次
[仅你持有]

已知用途
可以处理常规外伤。

[使用物品]
[转交]
[…]
```

点击“使用物品”后，将物品标签带入行动输入，而不是直接消耗。

# 16. 物品转交

## 16.1 接收确认

转交采用请求—确认流程。

```text
发送者发起
→ 接收者确认
→ 服务端原子更新持有人和位置
```

接收前物品仍属于发送者。

请求期间同一物品不能再次转交或消耗。

## 16.2 公开与私下递交

发起时选择：

- 公开递交；
- 私下递交。

公开递交成功后进入公共记录。

私下递交只通知双方；其他玩家不知道该事务存在。

## 16.3 私下递交风险

如果环境不适合隐蔽，不禁止，也不自动改为公开，而是作为隐蔽行动裁决。

风险只显示定性等级：

- 较低；
- 一般；
- 较高；
- 无法判断。

风险提示只能依据玩家已知的公开环境，不能泄露隐藏观察者和隐藏警觉数值。

## 16.4 接收者信息

接收者看到：

- 发送者；
- 物品；
- 递交方式；
- 定性风险；
- 是否可能占用行动。

不显示发送者私人备注和隐藏难度。

## 16.5 是否占用行动

由当前情境和规则决定。

自由调查中通常是轻量互动；战斗、追逐、潜行或高压场景中可能占用动作、反应或注意力。

如果会占用行动，必须提前明确确认。

## 16.6 接收者正在行动

新递交请求不会打断当前正式行动，而是排入待处理队列。

当前行动结束后重新验证：

- 双方是否仍在同一场景；
- 物品是否仍由发送者持有；
- 当前行动阶段是否允许；
- 风险和行动成本是否变化。

## 16.7 条件暂时不满足

转成“暂存意图”，不继续占据待处理队列，也不锁定物品。

```text
暂存请求

准备将“旧钥匙”交给安娜
当前无法完成：双方不在同一场景

[条件满足时提醒]
[取消]
```

发送者仍可以正常使用、丢弃或转交物品。

条件重新满足后，不自动执行，只提醒发送者：

```text
你现在可以把“旧钥匙”交给安娜了。

[重新发起]
[忽略]
```

只有重新发起后，接收者才会收到请求。

# 17. 本轮简化策略汇总

| 复杂问题 | 采用的简化方式 |
|---|---|
| 公共大屏信息过载 | 场景为主，右侧轻量概况，底部有限历史 |
| 玩家不知道该做什么 | 手机首页始终突出一个当前事项 |
| 多个通知同时出现 | 一件主事项 + 待处理数量 |
| 行动误执行 | 渐进式确认 |
| AI 裁决等待 | 正式行动锁定，讨论与笔记继续 |
| 私密与公共混淆 | 明确文字标签，不只靠颜色 |
| 历史事件碎片化 | 同一次行动合并为一张记录 |
| 调查页面过于复杂 | 总览首页 + 统一四段式详情 |
| 玩家不敢提出猜测 | 假说默认私人 |
| 推理变成投票 | 只补充支持、矛盾和评论 |
| 角色卡数字太多 | 首页只显示 HP、SAN、Luck |
| 技能按钮变成自动过关 | 技能只作为行动标签 |
| 物品误消耗 | 使用物品必须进入行动确认 |
| 转交状态不一致 | 接收确认 + 原子事务 |
| 暂时无法递交 | 保存意图、不锁物品、不自动执行 |

## 1. 战斗主模型

本轮最终否决“轮到某人后再输入并立即结算”的传统电子游戏式流程。

最终模型：

```text
公开本轮局势
→ 全体玩家分别声明
→ 处理未声明或缺席玩家
→ 锁定全部声明
→ 公开可观察的准备动作
→ AI-KP 生成整轮结算计划
→ 按规则顺序逐步提交结果
→ 将相关结果编排成连贯场景
→ 生成轮末局势总结
→ 开放下一轮声明
```

核心原则：

- 玩家负责声明自己的意图；
- 规则系统负责顺序、检定、资源和状态；
- AI-KP 负责综合所有行动、处理相互影响并组织叙事；
- 公共大屏负责共同理解；
- 玩家手机负责个人声明、结果和规则决定。

## 10. AI-KP 整轮结算计划

AI-KP 综合：

```text
全部玩家声明
NPC 与敌对单位意图
锁定前已发生的角色喊话
当前场景状态
位置、距离、遮挡
敏捷与规则顺序
预备动作和触发条件
持续行为
上一轮遗留影响
```

建议结构：

```text
RoundResolutionPlan
├─ ResolutionStep
│  ├─ globalOrder
│  ├─ clusterId
│  ├─ involvedEntities
│  ├─ dependsOn
│  ├─ ruleBinding
│  ├─ visibility
│  └─ stateTransaction
└─ PresentationCluster
   ├─ publicTitle
   ├─ publicParticipants
   ├─ completedPublicFacts
   └─ currentNarration
```

顺序不能按提交先后，必须综合规则、敏捷、预备动作、触发条件、位置和行动依赖。

## 12. 多冲突与全局顺序

采用：

> 规则层保持全局正确顺序；展示层在不改变事实先后的前提下，尽量合并为连贯场景。

内部顺序可能跨多个冲突。公共叙事可以自然切镜头，但不能颠倒已经提交的事实。

每个关键状态必须逐步提交，不能先生成整轮故事再一次性修改世界状态。

## 18. 缺席策略

只保留两种固定策略。

### 本轮暂不主动行动 `idle`

不生成新的攻击、移动、交互、交流、目标或资源消耗。角色仍在场景中，并正常承受外部影响。

它不是自动闪避、自动防御或 AI 托管。

### 维持既有持续行为 `maintain_existing`

只维持已经成立且规则支持的持续行为，例如：

```text
继续抵住铁门
继续维持已生效仪式
继续抓住已控制对象
```

不能表达：

```text
继续保护安娜
继续攻击最近敌人
有危险就躲
看情况花 Luck
```

## 19. 缺席期间的固定成本和可选资源

采用：

> 确定性的规则成本和强制检定继续执行；需要玩家选择的资源或策略决定不代选。

可自动执行：

```text
固定每轮扣资源
固定每轮检定
固定持续时长
固定失败后果
```

不能代选：

```text

Push
追加 MP
牺牲 HP
使用一次性物品
改变目标
接受额外风险
```

玩家回来后不能事后补选，也不局部回滚或重算。

## 25. 最终确认：两阶段影响提示

本轮最后确认采用：

> 选择目标、技能、武器或物品时先显示一行轻量提示；点击“提交声明”后再做完整校验。自然语言输入过程中不持续刷新和跳动。

### 第一阶段：轻量提示

```text
右手受伤可能影响手枪使用
该物品当前不在你身上
该目标已经离开你的视线
```

特点：

- 一行提示；
- 不阻止继续输入；
- 不展开复杂规则；
- 不按每个字实时刷新；
- 不清空草稿。

### 第二阶段：提交时完整校验

统一检查：

```text
目标是否有效
物品是否可用
资源是否足够
角色是否具备行动能力
当前阶段是否允许
状态是否影响行动
是否存在明确资源消耗
```

结果：

```text
可以提交
可以尝试但有影响
当前无法执行
部分条件将在整轮结算时确定
```

不采用全文实时分析，是为了避免页面频繁跳动、干扰自然语言表达和提前制造错误的“系统已经理解完成”印象。

```text
结算中自由插入角色喊话
为喊话创造规则外 ReactionDecision
AI-KP 替离线玩家选择战术
桌务替玩家消耗资源
离线玩家回来后事后补选
整轮中途重新上线后补行动
玩家输入过程中持续实时全文校验
```

---

## 30. 本轮最终设计原则

| 主题 | 最终结论 |
|---|---|
| 战斗输入 | 所有人先声明，后统一结算 |
| 结算顺序 | 规则、预备动作与现场关系决定 |
| AI-KP | 综合排序、逐步提交、连贯叙事 |
| 公共大屏 | 展示冲突和结果，不做控制台 |
| 隐藏敌人 | 完全不显示存在性 |
| 多阶段行动 | 同一声明内分阶段结算 |
| 后续阶段 | 由 AI-KP 根据新局势编排 |
| 多冲突 | 规则层全局排序，展示层连贯切镜 |
| 结算中输入 | 默认锁定，只开放规则真实决定 |
| 队伍讨论 | 桌外协调 |
| 角色喊话 | 仅声明锁定前有效 |
| 缺席 | 暂不行动 / 维持既有行为 |
| 资源代选 | AI 与桌务均禁止 |
| 重大离线后果 | 明确记录，不事后补选 |
| 重连 | 当前轮只观看，下一轮恢复 |
| 影响提示 | 轻量预提示 + 提交时完整校验 |

---

## 31. 本轮最终定义

> **战斗中的玩家只负责声明自己的意图；规则系统维护顺序、检定、资源与状态；AI-KP 综合所有玩家、NPC、敌人、预备动作和场景关系，将整轮行动按规则逐步结算，并编排成连贯公共叙事。公共大屏让全桌看懂冲突如何发展，玩家手机让每个人看懂自己声明了什么、受到了什么影响，以及当前是否需要处理规则真实存在的决定。**

# 附录 3：AI_Keeper_UI_Brainstorm_Round3_Prepared_Actions

# AI-Keeper UI 头脑风暴第三轮总结：预备动作

**日期：2026-07-19**  
**承接文档：`AI_Keeper_UI_Brainstorm_Round2_Combat.md`**  
**范围：预备动作的声明、锁定、触发、感知依据、目标绑定、同时触发排序、连续动作中断、失败处理、审计，以及公共大屏与玩家手机表现。**

---

# 1. 最终定义

> **预备动作是玩家放弃本轮普通主动行动，预先锁定一个完整动作；当本轮内一个明确、具体、可观察且尚未发生的条件首次有效满足时，系统按照规则时序自动执行该动作。**

预备动作不是：

- 免费反应；
- 普通行动之外的额外动作；
- 看到结果后再决定是否执行的期权；
- 由 AI-KP 自动寻找最佳时机、最佳目标或最佳感知方式的战术托管；
- 对已经完成的事件进行追溯补救；
- 跨轮自动延续的永久待机动作。

基础流程：

```text
玩家自然语言声明条件式动作
→ 系统识别为预备动作候选
→ 补齐必要信息
→ 校验触发条件、阈值与感知依据
→ 校验目标、武器、技能和未触发处理
→ 玩家确认
→ 占用本轮主动行动
→ 声明锁定
→ 等待本轮首次有效触发
→ 自动执行或因不合法而失效
→ 本轮结束后终止
```

---

# 2. 功能启用边界

只有规则包明确支持以下机制时，界面才提供预备动作：

```text
预备
延迟行动
待机动作
触发式行动
规则定义的类似机制
```

产品层不能为了 UI 顺滑自行发明预备机制。

若规则包不支持，玩家输入：

```text
如果敌人进门，我就开枪。
```

系统只能将其作为普通条件式意图交给 AI-KP 理解，不能自动授予中断时序。

---

# 3. 自然语言声明方式

玩家仍使用自然语言：

```text
如果人影越过翻倒的推车，我就用左轮向它开枪。
```

系统识别后转为确认卡，而不是直接提交：

```text
系统理解为预备动作

触发条件
走廊中的人影越过翻倒的推车

执行动作
使用左轮手枪向该人影射击

本轮未触发
动作不执行，本轮主动行动仍然消耗

[确认预备]
[改为普通行动]
[修改]
```

若信息不完整，只询问缺少的必要内容。

例如：

```text
如果门开了，我就行动。
```

系统只追问：

```text
门打开后，你准备执行什么动作？
```

不要求玩家填写复杂表单，但后台结构必须完整。

---

# 4. 预备动作消耗本轮主动行动

这是硬规则：

```text
声明预备动作
→ 本轮普通主动行动被占用
→ 角色本轮不再进行另一项普通主动行动
```

禁止：

```text
我先搜索房间；
如果怪物冲进来，我再开枪。
```

否则预备动作会变成免费反应。

手机确认卡必须明确提示：

```text
预备动作将占用你的本轮主动行动。

触发前：
你不会执行其他普通主动行动。
```

内部字段：

```text
consumesRoundAction = true
```

---

# 5. 触发条件必须具体、可观察

## 5.1 允许的条件

```text
人影越过翻倒的推车
北侧铁门开始打开
邪教徒进入安娜的近距离范围
怪物越过房间门槛
护士从口袋中拿出一件物品
目标离开公开掩体区域
```

这些条件必须具备：

- 明确对象；
- 明确事件或状态变化；
- 明确边界或阈值；
- 能够被权威事件系统判断；
- 角色能够通过锁定的感知依据确认。

## 5.2 不允许的条件

```text
如果它有敌意
如果它想攻击我
如果它是神话生物
如果它准备背叛我们
如果这是最危险的目标
如果现在是最佳射击时机
如果情况不对
```

这些条件依赖隐藏意图、未公开身份、战术最优判断或模糊主观感受。

系统提示：

```text
无法锁定该触发条件

“如果它有敌意”不能直接观察。

请改为可以实际看到或听到的事件，例如：
· 如果它举枪指向我们
· 如果它向安娜冲过去
```

---

# 6. 准备动作必须完整

锁定前必须明确：

```text
触发事件
触发阈值
触发依据
执行什么动作
具体目标或区域
使用什么武器、物品、技能或方式
本轮未触发时如何处理
有效时间
```

建议结构：

```text
PreparedActionDeclaration
├─ triggerEvent
├─ triggerThreshold
├─ perceptionBasis
├─ actionType
├─ targetBinding
├─ method
├─ toolOrSkill
├─ noTriggerOutcome
├─ validRoundId
└─ consumesRoundAction
```

完整确认卡：

```text
确认预备动作

触发条件
走廊中的人影越过翻倒的推车

触发依据
直接看见该人影越过推车

执行动作
使用左轮手枪向目标射击

目标
触发该条件的单位

可能消耗
弹药 1

本轮未触发
动作不执行，本轮主动行动仍然消耗

有效时间
仅当前战斗轮

[确认预备]
[修改]
[改为普通行动]
```

缺少关键内容时不能锁定。

---

# 7. 声明锁定后不可修改

以下内容在锁定后固定：

```text
触发事件
触发阈值
感知依据
目标或目标选择器
动作内容
武器、物品或技能
有效轮次
未触发处理
```

触发时不能：

```text
改打后面的目标
更换武器
改成其他动作
改变触发条件
改用另一种感知方式
```

系统也不能自动换目标、换武器、优化行动或使用隐藏信息修正声明。

---

# 8. 禁止追溯触发

预备动作只能响应声明锁定之后发生的新事件。

合法：

```text
门开始打开
→ 检查预备条件
→ 满足后插入预备动作
→ 结算预备动作
→ 继续后续事件
```

非法：

```text
门已经撞开
→ 敌人已经进入
→ 攻击已经完成
→ 伤害已经结算
→ 玩家提出“刚才应该触发”
```

一旦相关事实和后续动作已提交：

```text
不能倒带
不能补触发
不能局部重算
不能事后更换条件
```

---

# 9. 本轮未触发时

```text
本轮结束
→ 触发条件未发生
→ 预备动作失效
→ 本轮主动行动不返还
→ 下一轮如需继续必须重新声明
```

手机记录：

```text
预备动作未触发

触发条件：
走廊中的人影越过翻倒的推车

本轮结果：
条件未发生，预备动作未执行。
本轮主动行动已经消耗。
```

不允许备用动作、退还行动、自动跨轮保留或自动改写条件。

---

# 10. 触发后自动执行

```text
触发事件提交
→ 匹配锁定条件
→ 校验动作当前合法性
→ 自动进入规则结算
```

不再次询问：

```text
是否执行
是否放弃
是否换目标
是否换武器
```

玩家在声明锁定时已经完成最终授权。

手机：

```text
预备动作已触发

人影已经越过翻倒的推车。
正在结算射击……
```

公共大屏：

```text
人影刚越过推车，
陈默已经扣下扳机。
```

---

# 11. 触发成立但动作无法执行

若触发发生时动作已经不合法：

```text
触发条件满足
→ 动作合法性校验失败
→ 不执行
→ 不换目标
→ 不换武器
→ 不生成替代动作
→ 本轮行动仍然消耗
```

示例：

```text
预备：
人影越过推车时用左轮射击。

触发时：
左轮此前已经被打落。
```

手机记录：

```text
预备动作无法执行

触发条件已经满足：
人影越过了翻倒的推车。

无法执行原因：
左轮手枪当前不在你手中。

结果：
预备动作未执行；
本轮主动行动不返还。
```

---

# 12. 同一事件触发多个预备动作

```text
触发事件发生
→ 找出全部匹配动作
→ 校验每项当前合法性
→ 按规则优先级排序
→ 按敏捷、速度或规则指定属性排序
→ 使用规则包既有平手规则
→ 仍完全相同时使用本场稳定平手顺序
→ 逐项结算并提交状态
```

禁止按声明提交时间、网络到达时间、点击确认时间、大屏顺序或 AI-KP 叙事偏好排序。

---

# 13. 每项预备动作独立提交事务

正确链路：

```text
PreparedActionTrigger
→ RuleResolution
→ ResourceTransaction
→ StateCommit
→ RevalidateRemainingPreparedActions
```

不能先完成所有骰点再统一写入状态。

前一个动作可能导致后续动作目标倒地、离开、失效或被遮挡，因此剩余动作必须基于最新状态重新校验。

---

# 14. 本场稳定平手顺序

若规则优先级、敏捷及规则包平手条件全部相同，使用战斗开始时生成的固定顺序。

```text
战斗开始
→ 根据战斗实例与随机种子生成 stableTieBreakerRank
→ 写入 CombatOrderSnapshot
→ 整场战斗保持稳定
```

不能依据提交顺序、网络延迟、每轮重新随机或 AI-KP 判断。

新单位加入时：

- 已有单位相对顺序不变；
- 新实体获得独立 Rank；
- 离场后重回保留原 Rank；
- 断线不改变 Rank；
- 名称变化不生成新 Rank。

---

# 15. 平手顺序的 UI 可见性

默认不主动占用公共界面。

实际发生平手时，手机规则依据显示：

```text
结算顺序依据

· 动作优先级相同
· 敏捷相同
· 规则包没有其他平手条件

使用本场固定平手顺序：
陈默先于林海
```

玩家可在“更多 → 规则依据 → 本场平手顺序”查看公开参与者的安全版本。

不能泄露隐藏敌人、隐藏单位空缺、未公开 NPC 或隐藏参与者数量。

---

# 16. 同一条件一轮内出现多次

预备动作只响应本轮内第一次有效触发：

```text
进入等待
→ 第一次有效满足
→ 消费预备动作
→ 自动执行或因不合法失效
→ 后续相同事件不再触发
```

即使第一次触发时无法执行，也不能等待第二次更有利机会。

若第一次事件无法通过锁定感知依据确认，则不算有效触发，预备动作可以继续等待本轮后续有效事件。

---

# 17. 锁定时条件已经成立

若锁定时条件已经成立，不能作为预备动作。

例如人影已经在房间内：

```text
无效：
如果人影进入房间，我就开枪。
```

系统提示：

```text
该条件当前已经成立，
不能作为未来的预备触发条件。

你可以：
· 改为本轮普通射击行动
· 改为“如果人影越过北侧门槛”
· 改为“如果人影继续靠近安娜”
```

系统不能自动理解成“再次进入”。

---

# 18. 状态与事件必须区分

```text
当前状态：门已经打开
未来事件：门从关闭变为打开

当前状态：敌人在房间内
未来事件：敌人越过门槛

当前状态：邪教徒正在靠近
未来事件：邪教徒进入明确距离范围
```

预备动作必须绑定未来事件或状态跃迁，而不是当前已成立的静态状态。

---

# 19. 触发阈值必须明确

模糊条件需要规范化为明确节点。

“门被打开”需要明确为：

```text
门开始移动
门打开到足以看见门后
门完全打开
```

“邪教徒靠近安娜”需要明确为：

```text
开始朝安娜移动
进入安娜近距离范围
到达安娜身边
```

通用阈值类型：

```text
状态开始变化
越过明确边界
进入明确范围
动作完成
```

锁定后不能修改阈值，AI-KP 不能为了故事效果提前或延后触发。

---

# 20. 连续动作在触发节点暂停

若预备条件是“怪物越过门槛时开枪”：

```text
怪物从走廊开始移动
→ 到达门槛
→ 提交门槛中间位置
→ 暂停剩余移动
→ 触发预备射击
→ 提交射击结果
→ 重新校验怪物剩余移动
```

不能先把怪物移动到房间中央，再补算门槛射击。

连续动作需支持中间状态：

```text
MovementStep
├─ startPosition
├─ triggerBoundary
├─ intermediatePosition
├─ remainingPath
└─ continuationStatus
```

---

# 21. 预备动作后原连续动作自动继续

预备动作完成后：

```text
提交预备动作结果
→ 重新校验被暂停的原连续动作
```

若仍合法，从触发节点继续剩余部分。

不能重新从起点执行、再次询问行动者、由 AI-KP 改变目标，或把剩余动作视为新行动。

若角色失能、路径封闭、目标不存在或规则条件失效，则按新状态终止或改变。

---

# 22. 目标绑定方式

允许两类目标绑定。

## 22.1 具体实体

```text
目标：邪教徒 A
```

底层绑定 `entityId`，名称变化不视为换目标。

## 22.2 可观察的确定性选择器

```text
第一个越过北侧门槛的可见单位
第一个进入安娜近距离范围的公开敌对单位
第一个从门后出现并举起武器的人
```

建议结构：

```text
TargetSelector
├─ eventType
├─ areaOrBoundary
├─ observableFilters
├─ ordinal
├─ visibilityRequirement
└─ resolveOnce
```

---

# 23. 允许与禁止的选择器

允许：

```text
越过指定门槛
进入公开区域
进入明确距离
从指定方向出现
拿出可见武器
打开指定的门
第一个满足条件的单位
```

若使用“敌对单位”，敌对关系必须已经公开成立。

禁止：

```text
最危险的敌人
最适合攻击的目标
幕后主使
HP 最低的敌人
准备攻击我的人
对安娜威胁最大的人
神话生物
隐藏身份为邪教徒的人
```

这些依赖隐藏属性、战术优化或未公开身份。

---

# 24. 选择器只解析一次

触发时：

```text
匹配触发事件
→ 按锁定选择器解析唯一目标
→ 绑定具体 entityId
→ 消费预备动作
→ 不再重新选择
```

后续出现更危险或更适合的单位，也不能换目标。

---

# 25. 触发条件与目标解析必须区分

例如：

```text
门打开时，射击门后第一个可见单位。
```

门打开但门后无人：

```text
触发条件已满足
目标选择器解析失败
预备动作被消费
动作无法执行
本轮行动不返还
```

若声明是：

```text
第一个单位越过门槛时射击该单位。
```

则没有单位越过时，触发条件尚未满足。

---

# 26. 同时多个候选满足选择器

```text
匹配全部候选
→ 先比较权威事件顺序
→ 若规则上完全同时
→ 使用 stableTieBreakerRank
→ 解析唯一目标
```

不能由 AI-KP 选更危险、更近或 HP 更低的目标，也不能在触发后让玩家选择，或同时攻击多个目标。

---

# 27. 触发时无法感知

若事件发生，但角色无法通过锁定依据感知：

```text
事件发生
→ 感知校验失败
→ 不构成有效触发
→ 预备动作继续等待
```

不消耗预备动作，也不事后补触发。

角色后来看到目标已在房间内，也不能倒带触发。

---

# 28. 本轮后续仍可等待下一次有效触发

第一次相关事件不可观察时，不算有效触发。

若本轮稍后再次出现符合全部条件、并能通过锁定依据感知的事件，可以正常触发。

若声明绑定具体实体，则其他实体不能替代。

---

# 29. 感知判断使用触发时点状态

必须在事件实际发生的规则时点判断：

```text
视线
照明
遮挡
距离
听觉条件
触觉条件
有效感知能力
设备状态
角色当前状态
```

例如：

```text
触发前能看见，触发时灯熄灭 → 不触发
触发时看不见，随后灯亮 → 不补触发
触发时通过有效设备看见 → 可以触发
触发时角色昏迷 → 不触发
```

AI-KP 不能事后认定角色“应该注意到了”。

---

# 30. 安全记录不能泄露隐藏事件

若角色无权知道事件发生过，记录不能写：

```text
邪教徒曾越过门槛，但你没有看见。
```

只能写：

```text
本轮没有出现你能够观察到的有效触发事件。
```

只有角色之后合法得知相关事件时，才可以显示具体未触发原因。

---

# 31. 触发依据必须锁定

触发事件描述外部发生了什么；触发依据描述角色凭什么确认事件发生。

例如：

```text
触发事件：
北侧铁门开始向内移动

触发依据：
听见北侧铁门门轴转动的声音
```

或：

```text
触发事件：
邪教徒越过北侧门槛

触发依据：
通过走廊尽头的镜面观察
```

两者必须分开保存。

---

# 32. 允许的触发依据

只允许声明锁定时已经成立、且能够具体描述的感知渠道：

```text
直接视觉
直接听觉
直接触觉
已启用设备
明确的反射或观察媒介
事先约定的公开信号
```

示例：

```text
看见门开始移动
听见门轴转动声
感觉手中的绳索被拉紧
通过已开启的摄像头看到门口
通过镜面看到目标越过门槛
听见安娜喊出约定口令
```

---

# 33. 不允许的触发依据

```text
感觉情况不对
察觉到敌意
AI-KP 判断我应该发现
队友可能会提醒我
任何可用感官
如果有人注意到了
系统认为时机合适
```

系统应要求玩家说明具体感知方式。

---

# 34. 触发时严格使用锁定依据

例如锁定依据是门轴声音，但爆炸声完全掩盖门轴声：

```text
门开始移动
→ 听觉依据无效
→ 不触发
```

即使角色能看见门，也不能自动改用视觉，除非视觉已作为第二依据锁定。

若摄像设备断电，也不能改成“角色碰巧听见”。

---

# 35. 设备感知必须已经成立

合法：

```text
已经开启并对准北侧门的摄像机
```

不合法：

```text
我身上带着摄像机
```

设备依据至少要明确：

```text
设备是什么
是否已经启用
正在观察哪个区域
角色如何接收信息
```

若设备需要本轮拿出、启动或部署，这本身可能需要行动，不能默认与预备动作同时完成。

---

# 36. 约定信号的边界

例如：

```text
触发事件：
安娜喊出约定口令“灯灭了”

触发依据：
直接听见安娜的喊声
```

它只能证明角色听见了约定口令，不能自动证明门后有敌人、安娜看见了神话生物或当前目标有敌意。

信号可能基于误判、欺骗或错误信息。

---

# 37. 最多两个明确触发依据，使用 OR

最终采用：

> **一份预备动作最多锁定两个明确、具体的触发依据，并使用 OR 关系。任一依据在触发时点有效，即满足感知条件。**

例如：

```text
触发事件
北侧铁门开始移动

触发依据之一
直接看见铁门开始向内移动

或

触发依据之二
听见北侧铁门门轴转动的声音
```

内部表达：

```text
perceptionLogic = OR
perceptionBases = [
  direct_vision:north_door,
  direct_hearing:north_door_hinge
]
```

---

# 38. 两个触发依据的硬边界

允许：

```text
直接看见门开始移动
或
听见门轴转动声
```

允许：

```text
通过已开启摄像机看到门口
或
听见约定口令
```

不允许：

```text
任何一种我能察觉的方式
视觉、听觉、直觉或其他感官
系统找到任何可用渠道
队友或设备可能通知我
```

两个依据必须：

- 在锁定时完整列出；
- 各自具体；
- 各自已经成立或准备完成；
- 不依赖隐藏信息；
- 触发时不能增加第三种依据；
- 不能从 OR 改成 AND；
- 不能事后替换失效依据。

---

# 39. 两个依据的触发判定

```text
检查依据 A
→ 有效则触发

否则检查依据 B
→ 有效则触发

两者均无效
→ 本次不构成有效触发
→ 预备动作继续等待
```

只触发一次。

若两个依据同时有效，也只生成一次触发事务。

建议统一去重键：

```text
prepared:{preparedActionId}:trigger:{sourceEventId}
```

---

# 46. 最终设计原则

| 主题 | 最终决定 |
|---|---|
| 行动成本 | 消耗本轮普通主动行动 |
| 有效时间 | 仅当前战斗轮 |
| 未触发 | 失效且不返还行动 |
| 触发后 | 自动执行，不二次确认 |
| 条件 | 具体、可观察、可结构化判断 |
| 阈值 | 有歧义必须明确 |
| 当前已成立条件 | 不能锁定 |
| 修改 | 锁定后不可修改 |
| 追溯 | 禁止 |
| 多次事件 | 第一次有效触发后消费 |
| 动作失效 | 不自动换目标、武器或动作 |
| 同时触发 | 规则顺序、规则平手、稳定 Rank |
| 连续动作 | 在触发节点暂停，结算后重新校验并继续 |
| 目标 | 具体实体或确定性选择器 |
| 多候选 | 事件顺序 + stableTieBreakerRank |
| 感知 | 必须在触发时点有效 |
| 感知依据 | 锁定时明确 |
| 多感知 | 最多两个，OR |
| 隐藏信息 | 不通过条件、记录或 UI 泄露 |
| 公共大屏 | 只显示可观察姿态与结果 |
| 手机 | 显示完整声明、触发来源和规则依据 |

# 47. 本轮最终产品表达

**日期：2026-07-21**

**本轮范围：预备动作的自然语言交互、歧义追问、确认摘要编辑、普通行动与预备动作互转、备用动作限制、单次生命周期、锁定后取消限制、动作复杂度、附带位移、工具与资源校验、内部准备阶段、资源消耗节点、分阶段资源不足、效果降级与可变投入。**

# 1. 本轮核心修正

第三轮已经确定了预备动作的权威结构、可观察触发、目标绑定、触发依据和时序。本轮进一步明确：

> **玩家端始终使用自然语言，不展示条件树、触发器编辑器、AND/OR 表单或资源执行脚本。结构化规则只存在于后台。**

同时，预备动作采用严格的单次生命周期：

```text
玩家确认并锁定
→ 等待触发
→ 首次有效触发后执行
或
→ 条件/执行基础失效后结束
或
→ 本轮结束时未触发而结束
```

旧预备动作一旦结束，不会自动恢复。玩家如需继续，只能在新的声明阶段重新声明。

---

# 2. 玩家端只使用自然语言描述

玩家可以直接输入：

```text
如果北侧门打开后出现一个拿着武器的人，
我就用左轮向他开枪。
```

系统应生成自然语言确认摘要：

```text
确认预备动作

当北侧门打开，并且你看见门后出现持械者时，
你会使用左轮向该持械者射击。

如果本轮没有出现这种情况，
动作不会执行，本轮主动行动仍然消耗。

[确认预备]
[修改描述]
[改为普通行动]
```

玩家不需要看到：

```text
主要事件
附加条件
AND / OR
条件树
事件类型
TargetSelector
perceptionLogic
```

这些内容只能作为服务端内部结构存在。

---

# 3. 只询问影响核心语义的歧义

系统只在歧义会改变以下内容时追问：

```text
触发时点
触发对象
执行目标
具体动作
使用的武器、物品、技能或方式
```

必须追问的例子：

```text
“门打开时开枪”
→ 门刚开始移动，还是打开到可以看见门后？

“有人靠近就攻击”
→ 靠近谁？进入什么范围才算靠近？
```

不需要追问：

```text
举枪姿势
动作修饰
语气
不影响规则的叙事细节
```

这些细节由 AI-KP 按通常语义叙述，并通过最终摘要供玩家检查。

---

# 4. 每份候选声明最多追问一次

流程：

```text
提交自然语言候选
→ 检查核心歧义
→ 无歧义：生成确认摘要
→ 有歧义：只追问一个最关键问题
→ 根据回答重新解析
→ 仍不明确：拒绝锁定
```

拒绝时：

```text
这项预备动作仍无法确定触发时机或目标，
因此不能锁定。

你可以：
· 修改完整描述
· 改为普通行动
· 取消本轮声明
```

固定规则：

- 一次只追问一个最关键歧义；
- 不把玩家带入连续问卷；
- 追问后仍不明确时，AI-KP不能自行补全；
- 候选解析失败不消耗本轮行动；
- 原始草稿完整保留。

---

# 5. 每次重新提交都重新获得一次追问机会

玩家修改描述后，新文本视为新的声明候选：

```text
旧候选解析失败
→ 玩家修改完整描述
→ 重新提交
→ 重新获得一次关键歧义追问机会
```

不限制玩家在声明锁定前的修改次数。

规则：

- 未锁定候选不占用本轮行动；
- 每次解析都以最新完整文本为准；
- 不能偷偷继承旧候选中已被删除的目标、条件或工具；
- 前一次追问结果如果仍适用，应体现在新的确认摘要中；
- 只有最终确认后才占用本轮主动行动。

---

# 6. 玩家可以直接编辑系统确认摘要

系统生成摘要后，玩家可以直接修改自然语言：

```text
原摘要：
当北侧门打开到能够看见门后，
你会用左轮射击第一个越过门槛的可见持械者。

玩家修改：
当北侧门打开到能够看见门后，
并且第一个可见人员举起武器时，
我才用左轮向他射击。
```

修改后的摘要必须作为**新的自然语言候选**重新解析：

```text
编辑确认摘要
→ 保存为新候选
→ 重新进行语义解析
→ 必要时追问一次
→ 重新生成确认摘要
→ 玩家最终确认
```

不能只修改显示文本而继续使用旧后台结构。

# 7. 行动类型可以自动互转

## 7.1 预备动作改成普通行动

玩家将：

```text
如果门打开，我就射击门口的人。
```

改为：

```text
我不等门打开了，现在就向门口射击。
```

系统应提示：

```text
行动类型已改变

修改后的内容不再包含未来触发条件，
将按本轮普通行动处理：

现在使用左轮向北侧门口射击。

[确认普通行动]
[继续修改]
[取消]
```

转换时必须清除：

```text
触发事件
触发阈值
触发依据
等待状态
未触发处理
预备动作排序信息
```

## 7.2 普通行动改成预备动作

玩家将：

```text
我向门口的人影射击。
```

改为：

```text
如果他越过推车，我再向他射击。
```

系统应提示：

```text
行动类型已改变

修改后的内容包含未来触发条件，
将按预备动作处理。

预备动作会占用你的本轮主动行动。
若本轮未触发，行动不会返还。

[继续确认预备动作]
[继续修改]
[取消]
```

随后重新执行完整预备动作校验。

## 7.3 类型转换的原则

- 页面标签和后台结构必须同时转换；
- 旧类型的规则校验结果不得沿用；
- 新文本中仍明确存在的目标、工具可重新解析保留；
- 新文本已经删除的内容不得偷偷继承；
- 编辑阶段不消耗行动；
- 最终确认后才锁定。

---

# 8. “否则”不能包含备用主动行动

不允许：

```text
如果人影越过推车，我就开枪；
否则我去帮助安娜。
```

它实际包含：

```text
触发时执行射击
+
未触发时执行另一项主动行动
```

这会让预备动作变成无成本保险。

系统提示：

```text
这项声明包含两个备选主动行动：

· 条件满足时射击
· 条件未触发时帮助安娜

预备动作未触发时，
本轮主动行动仍然消耗，
不能自动执行另一项主动行动。
```

允许的“否则”内容仅限不产生新机制效果的等待描述：

```text
否则继续保持瞄准，直到本轮结束。
否则本轮什么也不做。
```

不能产生：

```text
新检定
新移动
新目标
物品使用
状态修改
额外资源消耗
```

---

# 9. 预备动作是单次生命周期

本轮对“暂时失效后是否恢复”作了进一步收紧。

最终原则：

> **只要已锁定预备动作赖以成立的观察、目标、工具或执行条件中途失去，旧预备动作的监听循环就结束，不会自动恢复。**

状态：

```text
locked_waiting
→ triggered
→ resolving
→ completed
```

或：

```text
locked_waiting
→ invalidated
→ closed
```

不存在：

```text
closed → locked_waiting
```

如需继续：

```text
下一轮声明阶段
→ 玩家重新创建 PreparedActionDeclaration
```

---

# 10. 中途失效后立即关闭

例如：

```text
锁定的观察方式失效
武器被击落
目标离开锁定区域
指定入口坍塌
角色失去行动能力
执行所需的唯一对象不再存在
```

处理：

```text
等待中
→ 条件或执行基础失效
→ 立即关闭
→ 停止匹配后续事件
→ 本轮行动不返还
```

即使之后：

```text
烟雾散去
武器被捡回
目标重新进入
设备重新通电
```

旧预备动作也不会恢复。

手机：

```text
预备动作已结束

结束原因：
你已无法继续通过锁定方式观察该区域。

该预备动作不会自动恢复。
如需再次准备，请在下一轮重新声明。
```

---

# 11. 锁定后不能主动取消

一旦玩家确认并锁定：

```text
预备动作已锁定
→ 占用本轮主动行动
→ 等待触发
```

玩家不能根据后续局势主动选择：

```text
放弃射击
取消预备
换成观察
保留到更好的时机
```

否则预备动作会变成“先保留时序优势，看到局势后再决定是否执行”的免费期权。

锁定后的预备动作只能通过以下方式结束：

```text
首次有效触发并执行
触发时无法执行
成立基础中途失效
本轮结束仍未触发
```

手机不提供“取消预备”按钮。

---

# 12. 预备动作只允许一个主要动作

合法：

```text
人影越过推车时，用左轮向它射击。
```

其中：

```text
举枪
瞄准
扣动扳机
```

可以属于同一主要动作的自然过程。

不合法：

```text
射击后退到门后
射击后把钥匙交给安娜
先开门再攻击
攻击目标 A 后压制目标 B
```

系统提示：

```text
这项预备声明包含多个独立行动：

1. 向人影射击
2. 退到门后

预备动作只能包含一个主要行动。
```

预备动作不复用普通组合行动的双步骤能力。

---

# 13. 允许完成主要动作所需的附带位移

允许：

```text
从门框后探身射击
转身拉下身后的开关
伸手接住物品
原地调整姿势
侧身让出射击角度
```

前提：

```text
位移只是完成主要动作的自然组成部分
且规则包不将其视为独立移动
```

不允许获得独立战术收益：

```text
移动到另一区域
改变距离等级
进入或离开近战范围
移动到新掩体
绕到目标侧面
越过门槛
射击后撤退
攻击后追击
```

判断标准不是“走了几步”，而是：

> 位移是否独立改变了区域、距离、掩体、位置关系或战术状态。

若产生这些权威状态变化，就不是附带位移。

---

# 14. 锁定时不预留武器和资源

锁定预备动作时只记录计划：

```text
武器引用
预计弹药
预计 MP
预计物品次数
```

不进行：

```text
资源扣除
资源冻结
武器锁定
弹药预留
使用次数预占
```

触发时才：

```text
重新校验武器与资源
→ 到达实际消耗节点时扣除
→ 原子提交规则和状态
```

这样允许场景中的真实变化正常发生，例如：

```text
武器被击落
武器被夺走
武器损坏
弹药因其他规则消耗
```

但一旦这些变化破坏了预备动作成立条件，旧预备动作按单次生命周期立即关闭，不会因资源恢复而重新激活。

---

# 15. 锁定当下必须已经具备最低执行条件

虽然资源不冻结，但锁定时动作必须当前可执行。

校验：

```text
角色当前能行动
目标或选择器有效
武器、物品当前可用
最低必要资源当前充足
感知依据已建立
规则允许预备该动作
```

例如左轮弹药为 0 时，不能锁定“目标出现后开枪”。

不能依赖未来可能发生的：

```text
队友递交弹药
另一角色替你装填
角色可能捡到武器
资源可能恢复
```

因为这些尚未成为事实。

---

# 16. 工具准备是否属于主要动作，由规则包裁定

前端和 AI-KP不能仅按动词数量或叙事合理性自行合并。

例如：

| 声明 | 规则包认定 | 处理 |
|---|---|---|
| 从枪套拔出左轮并射击 | 单一攻击允许拔枪 | 允许 |
| 解除保险并射击 | 属于射击必要过程 | 允许 |
| 举起手电照射 | 单一使用动作 | 允许 |
| 从背包取出燃烧瓶并投掷 | 规则认定为同一动作 | 允许 |
| 给空枪装填后射击 | 两个独立动作 | 拒绝 |
| 跑到武器旁、拾取后射击 | 多个独立动作 | 拒绝 |

规则包版本必须随房间策略锁定，战斗中不能临时改变。

---

# 17. 必要准备检定属于预备动作内部阶段

如果规则允许“拔枪并射击”，但要求快速拔枪检定：

```text
触发成立
→ 进行快速拔枪检定
→ 提交准备结果
→ 按规则判断是否继续射击
```

仍然是一项预备动作，而不是：

```text
一次预备拔枪
+
额外一次射击
```

准备失败后不询问换动作。

手机可显示：

```text
预备动作已触发

✓ 触发条件
● 快速拔枪：正在结算
○ 射击：等待准备结果
```

准备失败后的结果由规则包定义：

```text
射击无法完成
或
带惩罚继续射击
或
其他明确规则结果
```

AI-KP不能修改规则结论，只负责叙事。

---

# 18. 资源按实际消耗节点结算

不能统一规定：

```text
预备一触发就扣全部资源
```

也不能统一规定：

```text
最终成功才扣资源
```

资源必须按规则阶段的实际节点结算：

```text
准备成本
启动成本
执行成本
结果成本
```

例如：

```text
快速拔枪失败，尚未扣动扳机
→ 不扣弹药

已经开枪但未命中
→ 扣弹药

燃烧瓶已经点燃但投掷失败
→ 道具已进入新状态，按规则处理

已经支付能力启动成本
→ 后续失败不自动退款
```

每个资源节点应有：

```text
resourceRef
amount
consumeWhen
refundPolicy
failureBehavior
```

---

# 19. 每个阶段开始前重新校验资源

预备动作可以存在多个规则阶段：

```text
准备阶段
→ 启动阶段
→ 主动作阶段
→ 结果阶段
```

每个阶段开始前重新检查该阶段需要的资源。

例如：

```text
准备阶段消耗 1 MP
→ 提交 MP -1

其他规则效果又扣除 1 MP

主效果需要 2 MP
→ 当前只剩 1 MP
→ 主效果无法执行
```

已发生的准备成本：

```text
不返还
不补偿
不回滚
```

除非规则包明确规定退款。

---

# 20. 资源不足时不自动采用弱化版本

若规则支持：

```text
完整效果：3 MP
弱化效果：1 MP
```

玩家锁定完整效果后，触发时不足 3 MP：

```text
完整效果无法执行
→ 不自动降级
→ 不询问临时改选
→ 不改变作用范围、时长或目标数量
```

弱化版本属于另一项玩家选择，不能由系统代选。

---

# 21. 玩家自由决定的资源投入量必须提前锁定

例如：

```text
投入 1—5 MP，越多越强
使用多发弹药进行压制
消耗任意 Luck 提升效果
```

预备声明必须写明具体数值：

```text
触发时消耗 3 MP
触发时使用 3 发弹药
```

不允许：

```text
视情况投入
最多投入 5 MP
有多少用多少
按危险程度决定
使用剩余全部资源
```

触发后：

```text
资源足够 → 按锁定量执行
资源不足 → 动作无法按原声明执行
```

不自动降低，也不临时询问。

---

# 22. 自动计算型资源消耗可以锁定公式与上限

本轮最后确定：

> **如果资源消耗量不是玩家临时选择，而是由规则根据触发时实际合法对象数量或客观状态自动计算，则可以在声明时锁定规则公式和最大上限。**

例如规则规定：

```text
每影响 1 个合法目标消耗 1 MP
```

玩家可以声明：

```text
如果邪教徒进入房间，
我就对进入区域的所有合法目标施法。

每个合法目标消耗 1 MP，
最多影响 3 个目标，
最大消耗 3 MP。
```

内部锁定：

```text
costFormula = 1 MP × actualLegalTargetCount
targetCap = 3
resourceCap = 3 MP
```

触发时：

```text
规则系统计算实际合法目标数量
→ 套用已锁定公式
→ 不超过锁定目标上限和资源上限
→ 校验资源
→ 执行
```

若实际有 2 个合法目标：

```text
消耗 2 MP
影响 2 个目标
```

若实际有 5 个合法目标：

```text
最多选入前 3 个符合锁定确定性顺序的目标
消耗 3 MP
```

目标选择必须仍然来自预先锁定的确定性选择规则，不能由 AI-KP挑选最危险目标。

---

# 23. 公式消耗与自由投入的区别

## 自由投入

玩家可以决定投入多少：

```text
投入 1—5 MP，投入越多越强
```

必须锁定具体数值：

```text
投入 3 MP
```

## 自动计算

规则根据客观数量确定：

```text
每个实际合法目标消耗 1 MP
```

可以锁定：

```text
公式 + 目标上限 + 资源上限
```

关键判断：

> 触发时的实际消耗是否存在玩家自由裁量。

若存在玩家自由裁量，则不能用公式逃避提前锁定具体值。

---

# 24. 自动计算型消耗的边界

允许：

```text
每个合法目标消耗 1 MP，最多 3 个目标
每米有效屏障消耗固定资源，最多建立 5 米
每个已锁定区域节点消耗固定次数，最多 2 个节点
```

不允许：

```text
根据当时危险程度决定投入
选择最值得影响的若干目标
系统判断投入多少最划算
资源够多少就使用多少
优先保留足够资源用于之后
```

这些仍然属于策略判断。

---

# 25. 公式消耗触发时资源不足

例如锁定：

```text
每个目标 1 MP
最多 3 个目标
```

触发时有 3 个合法目标，但角色只有 2 MP。

系统不能自动问玩家，也不能自动借用其他资源。

需要由规则包明确处理方式，例如：

```text
规则要求必须覆盖全部已解析目标
→ 资源不足，动作无法执行

规则允许按确定顺序处理可支付数量
→ 按锁定顺序处理前 2 个目标，消耗 2 MP

规则规定效果自动缩小
→ 按规则处理
```

前端和 AI-KP不能自行决定采用哪一种。

因此内部规则必须包含：

```text
insufficientResourcePolicy
```

---

# 26. UI 仍保持自然语言

玩家不需要填写公式编辑器。

确认摘要示例：

```text
确认预备动作

当公开敌对单位进入房间时，
你会对进入区域的合法目标施放束缚。

资源消耗
每个合法目标消耗 1 MP。

作用上限
最多影响 3 个目标，
本次最大消耗 3 MP。

目标顺序
按声明中已确定的进入顺序处理。

如果本轮未触发，
动作不会执行，本轮主动行动仍然消耗。

[确认预备]
[修改描述]
```

后台保存公式，但玩家看到的是清晰自然语言。

规则计算：

# 28. 本轮明确否决的方案

```text
玩家端展示条件树或 AND/OR 编辑器
对所有模糊点持续追问
一次解析连续问多个问题
追问失败后由 AI-KP补全
只改确认摘要文字、不重新解析后台结构
行动类型改变但后台类型不变
预备未触发时执行备用主动行动
预备动作暂时失效后自动恢复
锁定后允许主动取消
一份预备动作包含多个主要动作
附带独立移动获得战术收益
锁定时冻结武器或预留资源
锁定时资源不足但赌未来补充
由 AI-KP自行判断准备步骤是否免费
准备检定失败后重新让玩家选动作
触发时一次性扣除全部预计资源
最终成功后才统一扣资源
后续阶段资源不足时返还准备成本
资源不足时自动采用弱化效果
可变投入触发时再决定
用“最多投入”让系统替玩家选择实际量
自动计算资源时由 AI-KP选择最优目标数量
```

# 29. 本轮最终决策表

| 主题 | 最终决定 |
|---|---|
| 玩家输入 | 只使用自然语言 |
| 内部结构 | 后台解析，不暴露条件编辑器 |
| 歧义追问 | 只追问影响核心语义的一项 |
| 追问次数 | 每份候选最多一次 |
| 重新提交 | 重新获得一次追问机会 |
| 确认摘要 | 允许直接编辑，但必须重新解析 |
| 行动类型 | 普通与预备可自动互转 |
| 备用动作 | 未触发时禁止另一项主动行动 |
| 生命周期 | 一次性，结束后不恢复 |
| 锁定后取消 | 不允许 |
| 动作复杂度 | 一个主要动作 |
| 附带位移 | 仅规则认定的必要组成 |
| 资源预留 | 不预留、不冻结 |
| 锁定资格 | 当前状态下必须可执行 |
| 工具准备 | 由规则包判断是否属于同一动作 |
| 准备检定 | 预备动作内部规则阶段 |
| 资源扣除 | 在实际消耗节点执行 |
| 阶段校验 | 每阶段开始前重新校验资源 |
| 已付成本 | 不自动返还 |
| 弱化版本 | 不自动降级 |
| 自由投入 | 提前锁定具体数值 |
| 规则计算投入 | 锁定公式、目标上限和资源上限 |
| 资源不足策略 | 必须来自规则包 |

# 30. 本轮最终产品表达

> **玩家只需要用自然语言说明“什么情况发生时，我准备做什么”。系统最多针对一个关键歧义进行追问，并用可编辑的自然语言摘要让玩家确认。确认后，预备动作成为一项不可取消、只在本轮有效的单次行动计划。工具、准备检定和资源成本全部按规则包分阶段结算；玩家自由决定的投入必须提前锁定，规则客观计算的投入则可以锁定公式与上限。AI-KP负责把这些确定性规则结果组织成连贯叙事，而不能替玩家恢复失效动作、选择备用行动、改变资源投入或优化目标。**
