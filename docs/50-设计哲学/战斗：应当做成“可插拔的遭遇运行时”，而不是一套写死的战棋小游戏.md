# 

从你们现有架构看，战斗的零件其实已经存在：

- Rule 层已经有 `combat attack / dodge / defend / assist / flee / wait` 和追逐 Handler；
    
- Host 端已经有遭遇确认、拒绝、下一轮、结束、临时 NPC 等入口；
    
- Transaction 已经定义了行动幂等、回合结算、State 先落库再投影、Host 演出事务；
    
- State 也已经意识到遭遇开始、轮次推进、参与者变化和结束必须有版本、事件和 Checkpoint 语义。
    

真正缺少的不是“攻击按钮”，而是一套统一的：

# **Encounter Runtime / 遭遇运行时协议**

它应该同时承接：

```text
战斗
追逐
伏击
围攻
逃脱
仪式中断
护送
守点
非致命制服
```

但具体规则由 Ruleset Adapter 决定。

一句产品定义：

> **玩家仍然用自然语言表达战术意图，AI 帮助结构化目标、方法和备选方案；规则包决定行动是否合法、如何排序和如何结算；State 原子地写入伤害、状态、位置和物品消耗；Projection 再把不同视角的结果安全地展示出来。**

---

# 一、战斗不能默认等于“D&D 式先攻 + 网格 + 每回合六秒”

这是第一条要写死的边界。

不同 TRPG 的战斗结构差异很大：

- 有的严格先攻排序；
    
- 有的全员先声明，再统一结算；
    
- 有的使用行动方和反应方对抗；
    
- 有的以场景、距离带、区域为核心；
    
- 有的战斗非常致命，重点是逃跑和谈判；
    
- 有的有复杂动作经济、反应、装备槽和法术资源；
    
- 有的根本不需要精确位置。
    

所以平台核心不能写死：

```text
每人一回合
每回合一个动作一个移动
固定 AC
固定六格移动
HP=0 就死亡
```

应当由规则包提供：

```text
EncounterFlowPolicy
InitiativePolicy
ActionEconomyPolicy
ReactionPolicy
DamagePolicy
ConditionPolicy
DeathPolicy
MovementPolicy
EndConditionPolicy
```

平台只负责：

```text
参与者
顺序
行动事务
等待决策
状态版本
投影
恢复
审计
```

# 二、建议新增一个独立模块

# **26-Combat / Encounter 战斗与遭遇系统**

它不是第二套 Rule，也不是第二套 State。

它的定位是：

> **管理一场遭遇从提出、初始化、行动、反应、轮次、结束到复盘的运行态生命周期。**

模块边界：

|能力|归属|
|---|---|
|攻击、闪避、伤害数学|Rule|
|玩家自然语言理解|AI-Keeper|
|行动顺序和事务幂等|Transaction|
|HP、状态、位置、弹药写入|State|
|谁能看到什么|Projection / Safety|
|战斗日志和回放|Journal|
|地图和位置|Scene / Map|
|角色技能和资源|Character|
|武器、弹药、装备|Item / Inventory|
|遭遇生命周期|Combat / Encounter|

---

# 三、战斗至少需要十层数据对象

## L0：`EncounterTemplate`

来自不可变 `ModuleVersion`，描述“可能发生的一场遭遇”。

```text
敌人候选
遭遇目标
环境
区域
触发条件
增援条件
NPC 战术倾向
撤退条件
可选结局
战利品和线索绑定
```

它不是已经发生的战斗。

---

## L1：`EncounterProposal`

AI、模组 Trigger、玩家敌对行动或 Host 提出：

> 当前条件可能进入战斗。

```json
{
  "proposalId": "enc_prop_102",
  "type": "combat",
  "reason": "玩家向守卫开枪",
  "sourceRefs": [
    "action:act_481",
    "trigger:guard_hostile_response"
  ],
  "participantCandidates": [
    "char:a",
    "npc:guard_01"
  ],
  "riskLevel": "high",
  "approvalMode": "host_required"
}
```

这不是遭遇已经开始。

---

## L2：`EncounterInstance`

房间中真正存在的遭遇运行态。

```json
{
  "encounterId": "enc_782",
  "roomId": "room_xxx",
  "templateRef": "encounter:guards",
  "rulesetId": "coc7e",
  "type": "combat",
  "status": "active",
  "flowPolicy": "ordered_activation",
  "objectiveRefs": [
    "objective:escape_hospital"
  ],
  "round": 2,
  "encounterVersion": 8,
  "stateVersion": 91
}
```

---

## L3：`EncounterParticipant`

```text
角色或 NPC
所属阵营
当前参战状态
先攻值
当前位置
当前姿态
已用资源
本轮是否行动
当前反应能力
```

参与者必须引用稳定 ID：

```text
characterId
npcInstanceId
temporaryNpcId
```

临时 NPC 不能自动变成长期 NPC 档案。

---

## L4：`EncounterRound`

```text
roundId
roundIndex
status
startedAtSequence
resolvedAtSequence
initiativeSnapshot
```

状态：

```text
planning
collecting
resolving
aftermath
resolved
blocked
```

---

## L5：`Activation`

表示轮到谁进行一次激活。

```text
activationId
participantId
initiativeSlot
status
availableActions
movementBudget
reactionBudget
```

---

## L6：`CombatIntent`

玩家确认后的战斗行动合同。

```text
攻击谁
用什么方法
使用什么武器
是否移动
是否消耗资源
是否瞄准
是否非致命
目标优先级
行动失败时的备选方案
```

---

## L7：`DecisionWindow`

用于处理：

```text
闪避还是反击
是否使用反应
是否花 Luck
是否使用护甲能力
选择哪个目标
是否接受代价成功
是否中断当前动作
```

这是网团战斗中极其重要的对象。

---

## L8：`CombatResolution`

包含：

```text
规则计划
权威骰子
对抗结果
伤害计算
状态效果
物品消耗
位置变化
条件变化
允许叙述的事实
```

---

## L9：`EncounterStatePatch`

由 State 应用的权威变化：

```text
HP
SAN
状态
位置
弹药
装备
物品耐久
遭遇参与状态
Clock
场景状态
```

---

## L10：`CombatReceipt`

玩家和 Host 可查看的裁决回执。

```text
你声明了什么
系统采用了什么规则
掷出了什么
对方做了什么反应
最终造成什么变化
为什么
来源在哪里
是否可复核
```

# 四、遭遇生命周期必须独立于房间状态

建议：

```text
proposed
    ↓
awaiting_confirmation
    ↓
initializing
    ↓
active
    ↓
paused
    ↓
resolving
    ↓
completed

任意未落地阶段
    → rejected / cancelled

异常阶段
    → blocked
```

`room.status=active` 只表示房间正在跑团。

不等于：

```text
当前一定在战斗
```

所以不能把战斗状态塞进：

```text
rooms.status
```

一间 active 房间可以处于：

```text
自由探索
对话
调查
战斗
追逐
演出暂停
```

# 五、战斗开始也要先 Plan，再 Apply

和前面开局设计一样，遭遇不能由 AI 一句话直接生成。

正确流程：

```text
玩家敌对行动 / 模组 Trigger / NPC 行动
        ↓
EncounterProposal
        ↓
参与者、目标、环境、规则校验
        ↓
Host / RoomPolicy Gate
        ↓
EncounterBootstrapPlan
        ↓
State 原子写入
        ↓
Encounter Started Event
```

## `EncounterBootstrapPlan`

至少包含：

```text
参与者
阵营
目标
规则包
流转模式
先攻策略
初始位置
意外状态
初始条件
当前装备
NPC 战术档案
可用退出路线
结束条件
```

Host 看到无剧透预览：

```text
遭遇类型：武装冲突
玩家参与者：3
敌对单位：2 个已公开目标
规则系统：CoC 7e
战斗形式：顺序激活
地图：区域模式
可开始：是
```

不能显示：

```text
第二波隐藏怪物
Boss 的真实身份
未揭示能力
秘密撤退通道
```

# 六、什么时候必须 Host 确认

## 可以自动进入

只有同时满足：

```text
玩家明确执行敌对行动
规则和目标清楚
参与者明确
无隐藏身份剧透
RoomPolicy 预授权
没有重大不可逆剧情变化
```

例如：

> 玩家明确向已公开敌人开枪。

## 必须 Host 确认

```text
AI 判断“对话可能变成战斗”
隐藏 NPC 即将出现
战斗会造成重大剧情分支
可能导致角色死亡
会创建持久 NPC 或新阵营
会触发核心结局
参与者或阵营不确定
旧模组抽取置信度不足
```

Host 不在线时：

```text
重大遭遇停在 HostReviewPacket
```

玩家仍可：

```text
讨论
准备行动
整理装备
尝试撤离
进行不触发重大状态的操作
```

# 七、战斗必须支持多种回合模式

建议由 `EncounterFlowPolicy` 决定。

## 1. 顺序激活 `ordered_activation`

```text
按先攻顺序
→ 当前参与者行动
→ 可能打开反应窗口
→ 结算
→ 下一个参与者
```

适合强调严格轮次的规则系统。

---

## 2. 全员声明、顺序结算 `declare_then_resolve`

```text
所有玩家提交行动计划
→ NPC 提交计划
→ 锁定声明
→ 按先攻或规则顺序逐一结算
```

适合网团，减少玩家长时间等待。

但需要：

```text
主行动
备用行动
目标失效时的 fallback
```

例如：

```text
主行动：攻击守卫 A
备用：如果 A 已倒下，协助安娜
```

---

## 3. 同步阶段制 `phase_based`

```text
声明阶段
移动阶段
远程阶段
近战阶段
结算阶段
```

由规则包定义。

---

## 4. 自由对抗 `freeform_contested`

没有固定全局先攻，每次行动触发对抗和反应窗口。

适合一些叙事型系统。

---

## 5. 追逐 `chase`

使用相同 Encounter Runtime，但有独立：

```text
距离
速度
障碍
位置序列
逃脱条件
```

不要把追逐硬塞成“攻击回合”。

---

# 八、建议 P0 先做“顺序激活”，P1 再做并行声明

你们现有 `room_turns` 是“全员提交后统一结算”的结构，而严格战斗经常需要：

```text
当前参与者
反应窗口
即时状态变化
下一个参与者
```

因此不要直接把 `room_turns` 当成完整战斗轮次。

建议层级：

```text
Session
└── Scene
    └── Encounter
        └── EncounterRound
            └── Activation
                └── Action
                    └── DecisionWindow / Reaction
```

`room_turns` 可以作为宏观叙事回合。

进入战斗后：

```text
room_turn.mode = encounter
room_turn.encounterRoundId = ...
```

但详细先攻和激活仍由 Encounter 管理。

# 九、玩家自然语言要编译成战斗意图合同

玩家说：

> “我躲到门后，等怪物扑向安娜的时候开枪打它的腿。”

这里包含：

```text
移动：门后
姿态：掩护
条件：怪物扑向安娜
反应动作：开枪
目标部位：腿
武器：当前装备枪械
```

不能简单编译成：

```text
attack monster
```

建议结构：

```json
{
  "actionType": "prepared_attack",
  "actorId": "char_a",
  "movement": {
    "targetZone": "zone:door_cover"
  },
  "triggerCondition": {
    "type": "target_attacks_character",
    "targetCharacterId": "char_anna"
  },
  "attack": {
    "weaponItemId": "item:revolver_01",
    "targetParticipantId": "npc:creature_01",
    "calledShot": "leg"
  },
  "fallback": {
    "type": "take_cover"
  }
}
```

玩家确认界面：

> **我理解为：**  
> 你先移动到门后取得掩护。  
> 如果怪物攻击安娜，你将使用左轮向其腿部射击。
> 
> **预计消耗：**1 发弹药。  
> **触发前：**你不会主动开枪。  
> **若条件未发生：**本轮保持掩护。

# 十、战斗行动类型不要写死成几个按钮

平台可以提供快捷按钮，但权威行为来自规则包。

通用动作语义可以包括：

```text
attack
defend
dodge
counterattack
assist
move
sprint
take_cover
aim
use_item
interact
grapple
disarm
escape
prepare
delay
protect
stabilize
surrender
wait
```

规则包决定：

```text
当前系统有没有这个动作
要消耗什么
是否需要检定
是否可作为反应
是否会触发机会行为
```

前端按钮只是 `CombatIntent` 的快速生成器。

---

# 十一、反应和决策窗口是战斗系统的核心

如果没有 `DecisionWindow`，AI 会替玩家做太多决定。

例如玩家被攻击时，系统不能自动替玩家选择：

```text
闪避
反击
格挡
使用护盾
消耗 Luck
```

建议对象：

```json
{
  "windowId": "dw_512",
  "sourceActionId": "act_enemy_attack",
  "decisionType": "defense_response",
  "eligibleParticipantIds": [
    "char_a"
  ],
  "options": [
    "dodge",
    "fight_back",
    "use_item:item_shield",
    "accept_hit"
  ],
  "defaultOption": "dodge",
  "expiresAt": "...",
  "status": "open"
}
```

玩家端显示：

> 怪物正在攻击你。请选择反应：
> 
> **闪避**：使用闪避 40  
> **反击**：使用斗殴 55，风险更高  
> **使用护符**：消耗 1 次  
> **不反应**

超时策略由 RoomPolicy 决定：

```text
暂停等待
默认防御
Host 代选
规则包默认
```

AI 不能自行选择消耗玩家资源。

---

# 十二、NPC 决策必须遵守“有限认知”，不能全知作弊

NPC 战斗 AI 应读取：

# `NpcCombatKnowledgeView`

只包含该 NPC 合理知道的：

```text
当前能看见谁
已观察到的武器
已知受伤状态
听到的声音
同伴发出的信息
自己的目标
自己的恐惧和士气
```

不能读取：

```text
玩家精确私密 HP
玩家未使用的隐藏能力
玩家私人行动计划
地图隐藏区域
其他 NPC 不知道的真相
```

特别是全员同时声明时：

> **NPC 计划必须在看不到玩家未公开行动声明的情况下生成。**

可以记录：

```text
npcPlanKnowledgeStateVersion
npcPlanEventSequence
```

防止 NPC AI 每次都“完美反制”玩家。

---

# 十三、NPC 需要结构化战术档案

# `NpcTacticsProfile`

```json
{
  "npcRef": "npc:guard_01",
  "combatGoal": "阻止调查员进入档案室",
  "riskTolerance": "medium",
  "morale": "fragile",
  "retreatThreshold": {
    "hpPercentBelow": 30
  },
  "preferredActions": [
    "warn",
    "take_cover",
    "attack_nearest"
  ],
  "forbiddenActions": [
    "execute_incapacitated_target",
    "leave_post_without_trigger"
  ],
  "targetPolicy": "nearest_active_threat",
  "surrenderAllowed": true
}
```

AI 可以在这套边界中选择动作。

不能让普通守卫突然：

```text
牺牲自己召唤远古神
精准知道最脆弱的玩家
无理由处决倒地角色
```

# 十四、AI 不可用时，NPC 仍然必须能行动

需要确定性 fallback：

```text
1. 检查必须处理的危险
2. 检查撤退/投降条件
3. 检查可用防御
4. 选择合法目标
5. 使用最高优先级合法动作
6. 无合法动作则 wait / defend
```

AI 只提升：

```text
战术多样性
角色表现
目标解释
叙事质量
```

不能成为战斗能否继续的单点故障。

---

# 十五、空间模型建议 P0 使用“区域 + 距离带”

不建议 P0 直接做精确网格、动态光照和复杂视线。

建议：

```text
Zone
ZoneConnection
RangeBand
Cover
Hazard
Engagement
```

例如：

```text
入口大厅
护士站
走廊
档案室门口
档案室内部
```

关系：

```text
入口大厅 ↔ 护士站
护士站 ↔ 走廊
走廊 ↔ 档案室门口
```

参与者位置：

```text
char_a：护士站
char_b：走廊
guard_01：档案室门口
```

区域可以有：

```text
cover: partial
lighting: dim
hazard: broken_glass
capacity
lineOfSightRefs
```

规则包再把它映射成：

```text
engaged
near
medium
far
out_of_range
```

这样：

- 手机端更易用；
    
- 调查型游戏不需要战棋精度；
    
- 后续仍可挂接网格地图；
    
- AI 更容易理解空间关系；
    
- 不会把所有系统强制战棋化。
    

---

# 十六、位置变化必须经过战斗规则

玩家说：

> “我绕过守卫冲进档案室。”

系统需要验证：

```text
区域是否相邻
是否被敌人阻挡
是否需要脱离接战
是否有障碍
是否超过移动预算
是否触发反应
```

不能简单调用普通地图移动。

战斗移动链路：

```text
CombatIntent
→ Encounter Movement Validator
→ Reaction Windows
→ RuleExecutor
→ State
→ Map / Encounter position patch
```

---

# 十七、战斗目标不能默认是“杀光敌人”

每场遭遇应有显式目标：

```text
击退
逃脱
拖延三轮
保护 NPC
夺取物品
封闭出口
中断仪式
抓捕
非致命制服
守住区域
护送
让对方投降
```

`EncounterObjective`：

```json
{
  "objectiveId": "obj_escape",
  "type": "escape",
  "sideRef": "party",
  "successConditions": [
    "all_active_party_members_in:zone_exit"
  ],
  "failureConditions": [
    "all_party_members_incapacitated"
  ],
  "visibility": "party"
}
```

显式目标能避免 AI 把所有冲突都升级成死亡战。

---

# 十八、战斗结束也必须由规则条件判断

结束条件可能是：

```text
目标完成
一方全部失去战斗能力
一方撤退
一方投降
规定轮数结束
仪式完成或被中断
双方脱离接触
Host 受控结束
```

AI 可以提出：

```text
当前遭遇可能已经结束
```

但高影响情况下仍需 Rule/Host 验证。

结束后不能简单删除遭遇。

应进入：

```text
aftermath
```

处理：

```text
倒地角色
持续流血
武器弹药
掉落物品
俘虏
逃跑 NPC
尸体和痕迹
地图状态
场景 Clock
获得线索
战斗噪音后果
```

全部处理完成后才：

```text
completed
```

# 十九、HP 为 0 不能在平台核心中写死为死亡

```text

impaired
incapacitated
unconscious
dying
dead
escaped
surrendered
captured
```

```text

是否需要死亡检定
是否能稳定伤者
是否允许负 HP
```

平台核心只存结果，不自行解释。

# 二十七、战斗演出和战斗事实要分开

事实：

```text
攻击成功
造成 4 点伤害
弹药减少 1
目标获得流血
```

演出：

```text
枪声在走廊中炸响，怪物踉跄撞上墙壁。
```

演出失败、断线或 BGM 播放失败，不能影响事实。

正确链路：

```text
RuleResult
→ State Commit
→ CombatResolution
→ Host RevealTransaction
→ Player StatePatch
→ Public Narrative
```

Transaction 文档已要求 State 成功后才能发版本化 patch 和 action completed，战斗必须完全沿用这条时序。

# 二十九、Retry 要区分三种语义

## 1. `replay_only`

只重新播放演出。

```text
不重掷
不改状态
不扣资源
```

## 2. `recompute_from_existing_roll`

规则参数错误时，用原骰子重新计算。

```text
不重新掷骰
通过补偿事务修状态
```

## 3. `restore_checkpoint`

真正恢复到此前状态，形成新历史分支。

```text
必须 confirm + reason
```

不能把所有“再试一次”都做成重新结算。

# 三十六、最关键的工程验收

```text
1. EncounterProposal 不等于遭遇已经开始。
2. AI 不能绕过 Host/Policy Gate 启动重大遭遇。
3. 同一 encounter start request 不会重复创建参与者。
4. 同一 actionId 不会重复攻击或重复扣弹药。
5. 只有当前合法参与者可以行动。
6. pending_approval / left 角色不能进入战斗。
7. 反应窗口不能由 AI替玩家自动消耗资源。
8. NPC AI 看不到未公开玩家行动计划。
9. Attack、damage、ammo、condition 在同一事务中提交。
10. State 失败时不发成功演出。
11. Projection 失败时不重复应用伤害。
12. 战斗位置变化经过 Encounter/Rule 校验。
13. 临时 NPC 不污染 Module NPC 模板。
14. 隐藏敌人不进入 PlayerCombatView。
15. 玩家看不到敌人隐藏 HP 和未揭示能力。
16. AI 叙事不能改变 RuleResult。
17. CombatReceipt 能追溯 actionId、encounterId、roundId、transactionId、stateVersion 和 eventSequence。
18. 重连后恢复当前轮次、激活者和 DecisionWindow。
19. replay_only 不重掷、不扣资源。
20. Encounter 结束后持续状态和物品变化仍存在。
21. Checkpoint 能恢复遭遇、参与者、位置和条件。
22. AI 不可用时确定性 NPC fallback 仍能继续战斗。
```

# 一个完整示例

玩家输入：

> “我躲到门后，用左轮朝扑向安娜的怪物开枪。如果它没有攻击安娜，我就不开枪。”

## 1. AI 结构化

```text
移动到门后
取得掩护
准备射击
触发条件：怪物攻击安娜
目标：怪物
武器：左轮
失败备选：保持掩护
```

## 2. 玩家确认

系统显示：

```text
预计消耗：条件触发后消耗 1 发弹药
条件未触发：不会开枪
```

## 3. State 写入准备动作

```text
位置移动
prepared_action condition
reaction reserved
```

## 4. 怪物行动

NPC AI 根据自己的认知和 TacticsProfile 提议攻击安娜。

## 5. 打开准备动作窗口

系统确认准备动作触发。

## 6. RuleExecutor

```text
读取权威手枪技能
读取武器弹药
读取距离和掩体
服务器掷骰
计算命中和伤害
```

## 7. State 原子提交

```text
弹药 -1
怪物 HP 变化
怪物状态变化
 prepared_action 清除
 encounterVersion +1
 stateVersion +1
```

## 8. 投影

玩家看到：

> 你从门后开枪，命中了怪物。弹仓剩余 2 发。

安娜看到公共枪击叙事。

Host 审核视图看到完整骰子、伤害、敌人状态和来源。

AI 不能额外写：

> 怪物其实是院长变成的。

除非这个事实已经通过 RevealGate 正式公开。

# 最终定义

> **AI-Keeper 的战斗不是独立于主链路的战棋小游戏，而是一套规则可插拔、状态可追踪、反应可交互、结果可解释的 Encounter Runtime：玩家用自然语言声明战术意图，AI 只负责结构化和 NPC 合法决策，规则包负责先攻、行动、反应、伤害和死亡语义，State 原子写入角色、物品、位置和遭遇状态，Projection 再按 Host、Player 和公开视角安全呈现。战斗可以主动推进，但不能替玩家选择、不能让 NPC 全知作弊，也不能绕过规则、事务和状态。**
