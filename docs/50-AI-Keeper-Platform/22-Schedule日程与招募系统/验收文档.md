# Schedule 日程与招募系统验收文档

## 文档定位

本文档用于在收到工程师的 `回执-YYYY-MM-DD.md`、代码改动说明、测试结果之后，判断 `22-Schedule日程与招募系统` 本轮工作是否真正完成。

它只负责验收，不替代：

- `功能列表.md`
- `PRD.md`
- `DeepSeek计划.md`

默认分两层结论：

- `本轮工程验收通过`：表示 Schedule 本轮 P0 主链路已经闭环；
- `生产可运营完成`：表示除了本轮范围外，私域招募、日程投票、提醒任务和通知依赖也已基本收口。

除非证据非常完整，否则默认只给 `本轮工程验收通过`，不直接给 `生产可运营完成`。

## 验收输入

验收前至少应拿到以下材料：

- 本模块四份基线文档：`功能列表.md`、`PRD.md`、`DeepSeek计划.md`、`验收文档.md`
- 工程师回执：`回执-YYYY-MM-DD.md`
- 本轮改动文件清单
- 实际测试命令与结果
- 如涉及前端大厅页，附 `npm run build` 结果

## 结论等级

| 结论 | 含义 |
| --- | --- |
| `本轮工程验收通过` | 房间入桌、ready、开局检查、进行中加入审批和公开字段白名单与文档对齐 |
| `本轮工程验收有缺口` | 主链路大体可用，但缺关键测试、关键证据或关键边界未闭环 |
| `不通过` | 出现待审批越权进入运行态、token/剧透泄露、公开 DTO 越界、测试未过等硬问题 |
| `生产可运营完成` | 仅在私域招募、日程投票、提醒任务和通知依赖也收口后才能给出 |

## 一票否决项

出现任一情况，本轮不得判通过：

- `join-info` 或 `GET /api/rooms/{room_id}` 仍返回 `owner_token`、`player_token`、`scenario raw_text`、truth、ending、隐藏线索或隐藏 NPC
- `active` 房间加入仍可直接成为 `joined`
- `pending_approval` 仍计入 ready 或普通 start 检查
- `pending_approval` 仍会因为房间 active 自动进入主舞台
- `pending_approval` 仍可提交运行态 intent
- `pending_approval` 仍可访问 player archive
- `pending_approval` 仍可收到 player-only event
- HostLobby 仍没有 approve / reject 入口
- `force_start` 新前端仍继续依赖 legacy `{ force_start: true }`，且回执未说明
- approve / reject 或 `force_start` 审计缺失关键 actor / target / status 证据
- 工程回执未说明 reject 后 token 如何处理
- 关键测试命令未提供，或测试未通过

## 必备回执材料

工程师回执里至少应说明：

- 本轮覆盖了哪些 `Schedule Batch`
- 实际修改了哪些文件
- 实际运行了哪些测试，结果是什么
- `RoomJoinInfoDTO`、`RoomPublicInfoDTO`、`LobbySnapshotDTO` 最终落在哪些接口
- `draft -> direct` 是否作为当前产品选择保留

- reject 后 `player_token` 是否立即失效；若不失效，剩余可访问接口和页面是什么
- approve / reject 审计最终落在哪个事件或记录层
- 审批审计是否完全不进入 `public export`
- `force_start` 新前端是否已传 `confirm + reason`
- `Schedule-4` / `Schedule-5` 是否明确未进入本轮工程
- 本轮 remaining limitations 是什么

## 生产可运营加签条件

以下条件未关闭前，不应给 `生产可运营完成`：

- reject 后 token 生命周期仍未明确
- `pending_approval` 的 archive / team-message / player-only event 边界仍缺专项自动化测试
- approve / reject 审计仍未完整落库或未与 export 边界隔离
- `force_start` 前端仍未彻底切到 `confirm + reason`
- `Schedule-4`、`Schedule-5`、`Schedule-6` 仍停留在文档阶段
