# Schedule 日程与招募系统功能列表 V2.1

## 当前阶段说明

- 本文档当前阶段为：`P0 主链路 + 房间入桌、ready、开局检查与进行中加入审批风险识别版`。
- 第一轮目标不是做公开招募广场，而是把当前已经落在 Room / User / Player Join / Host Lobby 上的会前调度链路写成稳定工程口径。
- 本轮重点锁定：房间码加入、`join-info`、角色绑定、`ready_toggle`、普通 `start`、`force_start`、`active -> pending_approval`、Host approve/reject 前端闭环、公开字段白名单。
- 本轮不实现公开招募列表、完整报名表、候补系统、日历视图、自动提醒、社区匹配、信誉体系。
- 文档里的“未来能力”用于约束后续方向，不代表当前仓库已经实现。

## 模块定位

Schedule 负责跑团开始前和跑团进行中的组队协调：招募、报名、候补、开团时间、出勤确认、提醒和临时加入审批。它回答的是“谁来、什么时候来、能不能进桌”，不是“行动如何裁决”。

当前仓库没有独立的 Schedule 或 Recruit 子系统。已经落地的能力主要挂在 Room、User、Player Join、Host Lobby 上：房间码加入、角色绑定、ready、开局检查、进行中加入变为 `pending_approval`、Host 后端审批。V2.1 必须把这些真实锚点和未来平台能力分开，避免 DeepSeek 把长期招募广场误当成本轮核心链路任务。

## `join_mode` 当前状态矩阵

当前代码的 `join-info` 口径是：

| `rooms.status` | `join_mode` | 当前规则 |
| --- | --- | --- |
| `draft` | `direct` | 当前代码允许加入；如后续要改成 `closed`，必须同步所有接口和前端 |
| `lobby` | `direct` | 可直接绑定角色入房 |
| `active` | `host_approval` | 加入后角色状态为 `pending_approval` |
| `paused` | `closed` | 当前代码按“非 draft/lobby/active”统一关闭 |
| `completed` | `closed` | 不应生成有效运行态加入 |
| `archived` | `closed` | 不应生成有效运行态加入 |

补充规则：

- `join-info` 可以公开返回 `join_mode`，但 `join-info` 本身不产生权限。
- 真正入房仍必须登录并提交 `join-with-character`。
- 如果未来要把 `paused` 改成 `host_approval`，必须在 Room、Player Join、Lobby UI、测试和文档中一起改。

## `pending_approval` 权限边界

`pending_approval` 是当前 active 房间里的“待审批运行态前置状态”，不是完整报名系统，也不是普通成员。

目标边界必须写硬：

- 不计入普通 `start` 的 ready 检查。
- 不进入 active 主舞台。
- 不可提交运行态 intent。
- 不可移动地图。
- 不可查看 player archive。
- 不可接收 player-only 事件。
- P0 默认不进入 active `party` 队伍消息流；如需保留 waiting page 上的安全提示，工程回执必须明确范围。
- 可看到“等待 Host 审批”的安全页面。
- reject 后不得继续进入 active 主链路；token 是否立即失效或只保留失败页读取能力，工程回执必须说明。

当前代码风险：

- `submit_intent` 只按房间 `active` 判断，未按 `characters.status` 额外挡住 `pending_approval`。
- `PlayerLobby` 当前在 `room_status === active` 时会自动跳到 `/player/{roomId}`，未区分 pending。
- approve / reject 当前只有状态修改和大厅广播，尚无单独审批审计事件。

## P0 MVP 功能

P0 只承接当前主链路已经需要的会前调度，不新增独立 Schedule 表。目标是让“玩家进桌、准备、开局、进行中补人审批”稳定，不做公开招募广场。

| 功能 | 当前状态 | 进入 MVP | 依赖模块 | 用户价值 | 验收口径 | 当前风险 |
| --- | --- | --- | --- | --- | --- | --- |
| 房间码加入入口 | 已有 | 是 | Room、User、Character | 私密团可直接拉人进桌 | 玩家输入有效房间码后可进入角色选择与加入流程 | 仅支持私域加入 |
| 入房公开信息 | 已有 | 是 | Room、Safety | 玩家加入前知道房间状态和剧本公开标题 | `join-info` 返回 `room_status`、`scenario_title`、`join_mode`，不返回 owner token、raw_text、隐藏真相 | DTO 白名单尚未显式成文化 |
| 登录后加入 | 已有 | 是 | User、Character | 角色和账号可恢复 | 未登录玩家加入前跳登录，登录后可提交角色并保存 account 归属 | 仍需锁死未登录不可绑定角色 |
| 角色绑定入房 | 已有 | 是 | Character | 玩家带角色进入房间 | `join-with-character` 支持 preset、template、builder、upload、copy 且来源互斥 | 暂无报名申请态 |
| 加入限速 | 已有 | 是 | Safety | 防止刷接口和撞房间码 | 同 IP 频繁 join 被限制，不能绕过审批 | 仅基础内存限流 |
| 大厅玩家列表 | 已有 | 是 | Room、Projection | Host 和玩家知道谁已进桌 | `s2c_room_lobby_snapshot` 包含玩家名、调查员名、状态、ready | pending / joined 当前前端未显式分区展示 |
| ready toggle | 已有 | 是 | Player Client、Rule/Engine | 开局前确认玩家可开始 | 玩家提交 `ready_toggle` 后 `characters.is_ready` 翻转并可被大厅看到 | 只表示当前开局，不表示现实排期 |

| Host 审批前端入口 | 未实现 | 是 | Host Client | 让后端审批能力可被实际使用 | HostLobby 能看到 `pending_approval` 玩家，并提供批准/拒绝操作 | 当前真实产品缺口 |
| pending 审批态玩家页 | 未实现 | 是 | Player Client、Projection | 待审批玩家不会误进主舞台 | pending 玩家只看到等待审批页，不自动进入 `/player/{roomId}` | 当前会因房间 active 自动跳转 |
| pending 运行态隔离 | 未实现 | 是 | Player、Projection、Journal、Safety | 待审批玩家不能绕过审批进入游戏 | pending 玩家不能提交 intent / 看 archive / 收 player-only event | 当前后端未完全锁死 |

## 功能边界

- Schedule 不参与 AI 裁决，不调用 AI-Keeper 决定玩家能否成功行动。
- Schedule 不写世界状态，不创建线索、NPC、地图状态或事务。
- Schedule 不替代 Room 生命周期；Room 仍是开房、大厅、active、归档的权威。
- Schedule 不替代 User 权限；报名、白名单、审批都必须绑定账号和房间身份。
- Schedule 不替代 Character；角色绑定属于 Character，Schedule 不解析角色数值。
- Schedule 不替代 Channel；通知和会前聊天可以引用 Channel，但不在 Schedule 内重写聊天系统。
- Schedule 不替代 Community；公开招募广场是 Community 能力，Schedule 只定义招募数据和排期流程。
- Schedule 不替代 Admin/Ops；提醒、后台任务、Webhook、邮件、短信都依赖 Ops。
- Schedule 的公开信息只能使用剧本公开标题、公开简介、人数、时间、规则系统、内容警示，不能暴露 `raw_text`、truth、隐藏线索、隐藏 NPC、结局。

## MVP 验收主链路

1. Host 登录并创建带剧本的房间。
2. 玩家登录，输入房间码，读取 `RoomJoinInfoDTO`。
3. 玩家选择或创建角色并加入房间。
4. 玩家在大厅 ready，Host 与 Player 都收到 `s2c_room_lobby_snapshot`。
5. Host 普通开局时，未 ready 的有效成员会阻止开局并返回名单。
6. Host 显式 `force_start` 时可以绕过 ready 检查；新前端必须传 `confirm + reason`。
7. 游戏 active 后，新玩家加入应为 `pending_approval`。
8. Host 能在前端看到待审批玩家并批准或拒绝。
9. pending 玩家只看到等待审批页，不能进入 active 主舞台，不能提交运行态 intent。
10. pending 玩家默认不进入 active `party` 队伍消息流。
11. 被批准玩家进入房间成员列表；被拒绝玩家不进入 active 主链路。
12. 整个流程不暴露 owner token、player token、模组真相和隐藏线索。
