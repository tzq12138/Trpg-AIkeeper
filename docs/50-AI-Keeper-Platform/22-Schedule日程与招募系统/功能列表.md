# Schedule 日程与招募系统功能列表 V2.0

## 模块定位

Schedule 负责跑团开始前和跑团进行中的组队协调：招募、报名、候补、开团时间、出勤确认、提醒和临时加入审批。它回答的是“谁来、什么时候来、能不能进桌”，不是“行动如何裁决”。

当前仓库没有独立的 Schedule 或 Recruit 子系统。已经落地的能力主要挂在 Room、User、Player Join、Host Lobby 上：房间码加入、角色绑定、ready、开局检查、进行中加入变为 `pending_approval`、Host 后端审批。V2.0 文档必须把这些真实锚点和未来平台能力分开，避免 DeepSeek 把长期招募广场误当成本轮核心链路任务。

本模块需要和以下文档保持一致：

- `docs/50-AI-Keeper-Platform/01-Room团房间系统/`
- `docs/50-AI-Keeper-Platform/02-User用户与权限系统/`
- `docs/50-AI-Keeper-Platform/05-Character角色卡系统/`
- `docs/50-AI-Keeper-Platform/21-Safety跑团安全边界系统/`
- `docs/50-AI-Keeper-Platform/23-Community社区生态系统/`
- `docs/50-AI-Keeper-Platform/24-Plugin-Admin-Ops开放API与后台运维/`

| --- | --- | --- |

| `src/client/src/pages/AdminDashboard.tsx` | 管理房间详情、显示创建和开始时间、玩家状态 | 可用于后台排查；不是招募运营后台 |

| `tests/server/test_room_security.py` | 创建权限、active join 变 `pending_approval`、角色恢复安全 | 覆盖加入审批和身份恢复安全 |
| `tests/server/test_character_join_import.py` | 加入房间、角色来源互斥、大厅快照事件 | 覆盖入房与大厅同步 |

## 核心对象

| 对象 | 含义 | 当前载体 | Schedule 口径 |
| --- | --- | --- | --- |
| `RoomJoinInfo` | 玩家输入房间码后看到的公开入房信息 | `GET /api/player/rooms/{room_id}/join-info` | 当前可用；必须保持无剧透 |
| `JoinMode` | 当前房间是否可直接加入 | `direct`、`host_approval`、`closed` | 已有初版；未来扩展为密码、白名单、招募申请 |
| `LobbySnapshot` | 大厅玩家、ready、房间状态快照 | `s2c_room_lobby_snapshot` | 当前会前同步核心 |
| `ReadyState` | 玩家是否准备开局 | `characters.is_ready` | 当前只表达“可开局”，不表达“某天有空” |
| `CharacterStatus` | 玩家角色在房间中的状态 | `joined`、`pending_approval`、`left` 等 | 可作为入房审批状态；不是完整招募申请状态 |
| `ForceStart` | 房主跳过 ready 或空房检查开局 | `POST /api/rooms/{room_id}/start` 的 `force_start` | 保留为显式急救能力，默认 start 仍应严格 |
| `RecruitPost` | 公开或半公开招募帖 | 未实现 | 未来独立对象，引用 Room 和 scenario 公开摘要 |
| `Application` | 玩家报名申请 | 未实现 | 未来先申请再入房，不应提前发正式 `player_token` |
| `WaitlistEntry` | 候补玩家 | 未实现 | 满员或 Host 暂不接纳时使用 |
| `SchedulePoll` | 开团时间投票 | 未实现 | 未来独立于 ready，不写世界状态 |
| `AvailabilityVote` | 某玩家某时间段是否可参加 | 未实现 | 未来绑定 account，可选绑定 application 或 character |
| `SessionSlot` | 已确认的一次跑团时间 | 未实现 | 未来用于提醒、缺席、回放归档 |
| `AttendanceRecord` | 出勤、请假、迟到、缺席记录 | 未实现 | 未来用于长团管理和社区信誉，但不影响 AI 裁决 |
| `ReminderJob` | 邮件、站内、Webhook 或浏览器提醒 | 未实现 | 未来依赖 Admin/Ops 后台任务 |

## P0 MVP 功能

P0 只承接当前主链路已经需要的会前调度，不新增独立 Schedule 表。目标是让“玩家进桌、准备、开局、进行中补人审批”稳定，不做公开招募广场。

| 功能 | 当前状态 | 进入 MVP | 依赖模块 | 用户价值 | 验收口径 |
| --- | --- | --- | --- | --- | --- |
| 房间码加入入口 | 已有 | 是 | Room、User、Character | 私密团可直接拉人进桌 | 玩家输入有效房间码后可进入角色选择与加入流程 |
| 入房公开信息 | 已有 | 是 | Room、Safety | 玩家加入前知道房间状态和剧本公开标题 | `join-info` 返回 `room_status`、`scenario_title`、`join_mode`，不返回 owner token、raw_text、隐藏真相 |
| 登录后加入 | 已有 | 是 | User、Character | 角色和账号可恢复 | 未登录玩家加入前跳登录，登录后可提交角色并保存 account 归属 |
| 角色绑定入房 | 已有 | 是 | Character | 玩家带角色进入房间 | `join-with-character` 支持 preset、template、builder、upload 且来源互斥 |
| 加入限速 | 已有 | 是 | Safety | 防止刷接口和撞房间码 | 同 IP 频繁 join 被限制，不能绕过审批 |
| 大厅玩家列表 | 已有 | 是 | Room、Projection | Host 和玩家知道谁已进桌 | `s2c_room_lobby_snapshot` 包含玩家名、调查员名、状态、ready |
| ready toggle | 已有 | 是 | Player Client、Rule/Engine | 开局前确认玩家可开始 | 玩家提交 `ready_toggle` 后 `characters.is_ready` 翻转并可被大厅看到 |
| Host 开局检查 | 已有 | 是 | Room、Host Client | 防止空房或未准备误开局 | 普通 start 要求有剧本、至少一名玩家、所有玩家 ready |
| `force_start` 急救 | 已有 | 是 | Room、Host Client | 允许线下特殊情况继续 | 只有 owner/admin 可显式 `force_start: true`，普通 UI 不默认绕过 |
| active 入房转审批 | 已有 | 是 | Room、Host | 跑团中临时加入不直接进入主链路 | active 房间 join 返回 `pending_approval` |
| Host 审批后端 | 已有 | 是 | Host、Room | 房主决定进行中加入者是否进桌 | owner token 调 `approve` 后状态变 `joined`，调 `reject` 后变 `left` |
| Host 审批前端入口 | 未实现 | 是 | Host Client | 让后端审批能力可被实际使用 | HostLobby 能看到 `pending_approval` 玩家，并提供批准/拒绝操作 |
| 房主房间列表 | 已有 | 是 | User、Room | Host 能找回自己开的团 | `/api/rooms/mine` 返回自己的房间和创建、开始时间 |
| 账号角色恢复 | 已有 | 是 | User、Character | 玩家换设备后继续回房间 | 账号只能恢复自己角色的 session，不能恢复他人角色 |
| 基础时间戳 | 已有 | 是 | Room、Journal | 用于后续归档和日程扩展 | `rooms.created_at`、`started_at` 可在后台或房间列表查看 |

## P1 应补功能

P1 是“私域招募和排期”，服务于房主邀请熟人或小范围招募，不做平台社区广场。

| 功能 | 当前状态 | 进入 MVP | 依赖模块 | 用户价值 | 验收口径 |
| --- | --- | --- | --- | --- | --- |
| 房间容量 | 未实现 | 否 | Room | Host 控制最多几名玩家 | 达到容量后新申请进入候补或被拒绝，不能继续直接入房 |
| 房间密码或邀请码 | 未实现 | 否 | User、Safety | 私密团防撞房间码 | 无密码或邀请码不能申请加入受保护房间 |
| 白名单入房 | 未实现 | 否 | User | 固定团只允许指定账号 | 非白名单账号无法直接加入，只能提交申请或被拒绝 |
| 申请表单 | 未实现 | 否 | User、Character | Host 先看玩家意向再放行 | 申请包含昵称、简介、可用时间、是否自带角色，不生成正式玩家状态 |
| 申请审批 | 后端审批可复用思想 | 否 | Host Client、Room | 报名与入房分离 | Host 批准申请后才创建或绑定角色入房 |
| 候补列表 | 未实现 | 否 | Room | 满员后保留替补 | 候补不进入大厅 ready，不拿 player token |
| 招募帖草稿 | 未实现 | 否 | Room、Module | Host 可先编辑公开信息 | 草稿只 owner/admin 可见，可引用剧本公开标题 |
| 私域招募链接 | 未实现 | 否 | Room、Safety | Host 分享可控链接 | 链接只暴露公开信息，可撤销或过期 |
| 单次开团时间 | 未实现 | 否 | Room | 告诉玩家本次预计开局时间 | 房间能显示计划开团时间和时区 |
| 可用时间收集 | 未实现 | 否 | User | Host 快速找共同时间 | 玩家提交可用时段，Host 看到聚合结果 |
| 请假/迟到状态 | 未实现 | 否 | Journal、User | 长团协调现实时间 | 玩家能标记本次无法参加，不影响角色状态 |
| 会前备注 | 未实现 | 否 | Safety、Channel | 收集雷点、偏好、设备问题 | 备注有可见范围，不进公开 replay |

## 功能边界

- Schedule 不参与 AI 裁决，不调用 AI-Keeper 决定玩家能否成功行动。
- Schedule 不写世界状态，不创建线索、NPC、地图状态或事务。
- Schedule 不替代 Room 生命周期；Room 仍是开房、大厅、active、归档的权威。
- Schedule 不替代 User 权限；报名、白名单、审批都必须绑定账号和房间身份。
- Schedule 不替代 Channel；通知和会前聊天可以引用 Channel，但不在 Schedule 内重写聊天系统。
- Schedule 不替代 Community；公开招募广场是 Community 能力，Schedule 只定义招募数据和排期流程。
- Schedule 公开信息只能使用剧本公开标题、公开简介、人数、时间、规则系统、内容警示，不能暴露 raw_text、truth、隐藏线索、隐藏 NPC、结局。

## 现状风险

| 风险 | 影响 | V2.0 处理口径 |
| --- | --- | --- |
| 没有独立数据模型 | 容易把招募字段硬塞到 `rooms` | P0 不新增 Schedule 表；P1 再设计 `recruit_posts`、`applications`、`schedule_polls` |
| Host 审批前端缺口 | 进行中加入虽有后端但 Host 难以操作 | P0 应补 HostLobby 的 `pending_approval` 展示和 approve/reject 按钮 |
| `pending_approval` 和报名混用 | 未来招募申请可能提前获得玩家 token | 未来报名申请应独立于角色运行态，批准后再转入房间 |
| `join-info` 是公开接口 | 公开页可能泄露不该展示的模板或玩家信息 | Safety 需要审核字段，只允许公开入房所需信息 |
| ready 被误当日程 | 玩家 ready 只表示当前可开局，不表示未来时间可用 | 日程投票必须是独立对象，不复用 `is_ready` |
| 无人数容量 | 房间可能无限加入或进入审批堆积 | P1 增加容量、候补、关闭申请 |
| 无时间和时区 | 长团无法安排现实时间 | P1/P2 增加 session slot 和 timezone |
| 无提醒任务 | 玩家错过开团时间 | P2 依赖 Admin/Ops 的后台任务和通知通道 |
| 招募公开页可能剧透 | 公开描述如果引用模组真相会破坏体验 | 招募字段必须走 Safety 口径和 Admin 审核 |
| 历史中文文案乱码 | 影响玩家理解加入失败、审批、开局错误 | 相关 Batch 需要修正文案，但不要扩大源码重构 |

## MVP 验收主链路

1. Host 登录并创建带剧本的房间。
2. 玩家登录，输入房间码，读取 `join-info`。
3. 玩家选择或创建角色并加入房间。
4. 玩家在大厅 ready，Host 与 Player 都收到 `s2c_room_lobby_snapshot`。
5. Host 普通开局时，未 ready 玩家会阻止开局并返回名单。
6. Host 显式 `force_start` 时可以绕过 ready 检查。
7. 游戏 active 后，新玩家加入应为 `pending_approval`。
8. Host 能在前端看到待审批玩家并批准或拒绝。
9. 被批准玩家进入房间成员列表，被拒绝玩家不进入 active 主链路。
10. 整个流程不暴露 owner token、player token、模组真相和隐藏线索。
