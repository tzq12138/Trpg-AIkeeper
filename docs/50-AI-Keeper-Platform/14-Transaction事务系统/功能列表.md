# Transaction 事务系统功能列表 V2.0

## 模块定位

Transaction 负责把一次玩家意图变成可追踪、可重试、可回放的结算单元。它覆盖三层事务：行动事务、回合事务、Host 演出事务。

Transaction 不等同于数据库事务，也不承载规则判定本身。规则由 Rule/AI-Keeper 产出裁决，世界真相由 State 写入，分层可见性由 Projection/Safety 控制，Transaction 负责把这些步骤按正确顺序串起来，并保证失败、重复提交、断线重连时不会产生双重结算或提前剧透。

## 当前代码真实锚点

| 代码位置 | 当前职责 | 备注 |
| --- | --- | --- |
| `src/server/player/router_player.py` | `/api/player/intent` 入口，active 房间走回合收集，非 active 走即时结算 | active 路径先写 action，再查 duplicate，存在孤儿 queued action 风险 |
| `src/server/engine/engine.py` | `Engine.submit_intent` 入队、幂等、版本冲突、ready_toggle | 普通 action 入队时会推进 `rooms.state_version`，语义需要收口 |
| `src/server/turn_manager.py` | `room_turns` 创建、行动绑定、all submitted、skip、mark resolving/resolved | 缺少并发锁和 settle 幂等屏障 |
| `src/server/engine/resolution_pipeline.py` | action resolving/resolved/rejected、规则执行、投影、状态变更调用 | 当前先投影再 StateService 落状态，时序需与 State/Projection 统一 |
| `src/server/engine/projection.py` | 写 `events` 并通过 WS 投递 | 每次 emit 独立 commit，不是整条事务的唯一提交点 |
| `src/server/host/host_store.py` | Host 演出队列、urgent 抢占、delayed events、host state | 没有独立 transaction 表，active transaction 恢复能力有限 |
| `src/server/host/router_host.py` | Host WS、pause/reset/retry-turn、`host_step_complete` 释放 delayed events | ACK 没有形成可审计的完成事件 |
| `src/server/player/router_reconnect.py` | pending actions、player_sequences、action status 查询 | 重连侧能查 pending，但事件过滤和版本屏障仍需增强 |
| `src/server/db_adapter.py` | `actions`、`room_turns`、`events`、`host_states` 表 | 当前没有独立 `transactions` 表 |

## 核心数据对象

| 对象 | 所属模块 | 当前字段 | Transaction 口径 |
| --- | --- | --- | --- |
| `PlayerIntent` | Player Client / Engine | `action_id`、`intent_type`、`declared_intent`、`base_state_version`、`params` | 玩家提交的唯一意图请求，`action_id` 是幂等键 |
| `actions` | Transaction | `action_id`、`room_id`、`character_id`、`intent_type`、`status`、`turn_id`、`result` | 行动事务账本，必须能从提交追到裁决和投影 |
| `room_turns` | Timeline / Transaction | `turn_id`、`turn_index`、`status`、`summary` | 回合事务账本，控制 collecting 到 resolving 到 resolved |
| `ResolutionResult` | Rule / AI-Keeper | mechanic、success、metadata、mutations、reveal_steps、narrative | 裁决输出，不直接等于已落库事实 |
| `RevealTransaction` | Host Client / Projection | `transactionId`、priority、steps、summaryText、audioAction | Host 演出事务，仅包含 Host 可见内容 |
| `events` | Journal / Projection | sequence、event_type、audience、payload | 事务外显记录，供重连、日志、回放使用 |
| `host_states` | Host Client | HostStore 序列化状态 | Host 舞台恢复辅助，不是权威世界状态 |

## P0 MVP 功能

| 功能 | 当前状态 | 进入 MVP | 依赖 | 用户价值 | 验收口径 |
| --- | --- | --- | --- | --- | --- |
| 玩家 action 幂等 | 已有 `actions.action_id` 主键和 `Engine.submit_intent` 查询 | 是 | User、Player Client | 刷新、重试、弱网不会重复提交同一行动 | 同一 `action_id` 重复提交只保留一条 action |
| 状态版本冲突入口 | `base_state_version` 已在 Engine 检查 | 是 | State、Player Client | 玩家基于旧状态行动时能被拦截 | 非 0 旧版本返回 conflict/current version |
| action 入队回执 | 已有 `s2c_action_queued` 和 202 响应 | 是 | Projection、Journal | 玩家知道行动已进入系统 | 成功提交返回 `action_id`，事件日志可查 |
| active 回合绑定 | 已有 `TurnManager.submit_action` 更新 `actions.turn_id` | 是 | Timeline | 行动属于当前回合，便于批量结算 | active 房间非 ready action 必须带 `turn_id` |
| 单玩家单回合一次行动 | 已有 duplicate 检查 | 是 | Timeline、User | 防止一名玩家刷多次行动 | 重复提交返回 409，且不得留下新 queued action |
| 回合自动结算 | `all_submitted` 后触发 `_settle_turn_background` | 是 | Rule、AI-Keeper | 所有人行动后自动推进剧情 | 当前 turn 标记 resolving/resolved，并创建下一 turn |
| action 状态机 | 已有 queued/resolving/resolved/rejected，模型含 batched/timeout | 是 | Engine、Journal | 前端和重连能展示行动状态 | 每个 action 最终进入 resolved 或 rejected |
| 裁决失败处理 | `_reject` 写 rejected 并发 `s2c_action_completed` | 是 | Rule、Projection | 失败不应半落库或半投影 | Rule 异常时只有 rejected 回执，无公共剧情投影 |
| 裁决结果持久化 | `ResolutionPipeline` 写 `actions.result` | 是 | Rule、Journal | 日志和回放能解释行动结果 | result 包含 mechanic、metadata、mutations、narrative |
| State 写入编排 | Pipeline 调 `StateService.apply_change` | 是 | State | 裁决后的权威变更进入世界状态 | 有 mutation 时通过 StateService 写 runtime state |
| Host reveal transaction | 已有 `s2c_reveal_transaction` | 是 | Projection、Host Client | Host 看到 roll/status/narrative 演出步骤 | Host 事件包含 `transactionId`、priority、steps |
| Player 完成回执 | 已有 `s2c_action_completed` | 是 | Projection、Player Client | 玩家解除等待并看到结果 | resolved/rejected 都发给对应角色 |
| 事务日志沉淀 | `events` 记录投影，`actions` 记录行动 | 是 | Journal | 复盘能追溯“谁做了什么，系统如何裁决” | action、event、turn 能互相定位 |
| Host 急救入口 | 有 pause/reset/retry-turn、turn retry/skip | 是 | Host Client、Timeline | 跑团现场卡住时可恢复节奏 | owner/admin 才能执行，所有操作可审计 |

## P1 强化功能

| 功能 | 当前状态 | 进入 MVP | 依赖 | 验收口径 |
| --- | --- | --- | --- | --- |
| action 入队原子化 | 当前 active 路径先写 action 后判 duplicate | 是 | Engine、TurnManager | duplicate 场景不写新 action、不发 queued、不 bump state version |
| queue 版本与世界版本分离 | 当前普通 action 入队推进 `rooms.state_version` | 是 | State | 只有真实世界状态变化推进 state_version |
| 回合结算锁 | 当前 `_settle_turn_background` 可被多入口触发 | 是 | Timeline | 同一 turn 同一时间只能有一个 resolving worker |
| resolve 幂等屏障 | 当前 resolved/rejected 会直接返回，但 resolving 中断恢复不足 | 是 | Journal | 重启或重试不会重复落同一 mutation |
| 整条事务提交顺序 | 当前 action resolved commit、Projection emit commit、StateService commit 分散 | 是 | State、Projection | 权威状态先落库，再发版本化 patch 和完成事件 |
| Host 播放 ACK | 仅有 `host_step_complete` 释放 delayed events | 是 | Host Client | Host 完成关键 step 后记录可审计 ACK |
| 私密结果延迟屏障 | `Engine.complete_action` 和 HostStore 有 delayed 机制，但主 pipeline 未统一使用 | 是 | Projection、Safety | 玩家私密 patch 不早于 Host 公共演出安全点 |
| 事务 ID 统一 | Host `transactionId` 为随机 UUID，未绑定 action/turn | 是 | Journal | Host transaction 可追到 action_id、turn_id、state_version |
| 事件注册统一 | 代码 emit `s2c_turn_resolved`，注册表和前端类型未登记 | 是 | Channel、Timeline | 新事件进入 registry、类型和测试 |
| action 查询隔离 | `/api/player/actions/{action_id}` 已按 character 过滤 | 是 | User | 玩家不能查他人 action，404 隐藏资源存在性 |
| timeout/cancel | 模型有 timeout，工程链路未闭合 | 否 | Host Client | 超时行动能被标记并安全解锁 UI |
| checkpoint 时机 | Turn resolved 后自动 checkpoint，失败场景需细化 | 是 | Journal、State | 只有成功完成的一轮生成可恢复 checkpoint |

## P2 平台增强

| 功能 | 是否进入 MVP | 依赖 | 说明 |
| --- | --- | --- | --- |
| 独立 `transactions` 表 | 否 | Journal、Projection | 若 Host 演出恢复需求增大，再保存 transaction 状态、step 进度和 ACK |
| 批量行动编排器 | 否 | Timeline、Rule | 多玩家同步行动、协作检定、冲突行动排序 |
| Host 审批事务 | 否 | AI-Keeper、Host Client | AI 建议先给 Host 审阅，确认后再落状态或投影 |
| 事务可视化面板 | 否 | Admin/Ops | 查看 pending/resolving/failed 事务，支持人工恢复 |
| 失败补偿动作 | 否 | State、Journal | 部分成功后失败时生成补偿事件，而不是静默回滚 |
| 事务指标 | 否 | Admin/Ops | 统计平均裁决耗时、失败率、重试率、超时率 |

## P3 长期能力

- 多房间事务调度和优先级限流。
- 多 Host 舞台同步播放。
- 观众延迟流和直播安全延迟。
- 可剪辑的事务回放轨道。
- 插件化事务步骤，例如 VTT 动画、音效、字幕、投票。

## 不属于 Transaction 的内容

| 内容 | 归属模块 | 原因 |
| --- | --- | --- |
| 技能成功失败计算 | Rule | Transaction 只编排，不决定规则结果 |
| AI 叙事和裁决建议 | AI-Keeper | Transaction 消费已校验输出 |
| HP/SAN/线索/地图真相写入 | State | Transaction 不能绕过 StateService |
| 受众过滤和防剧透 | Projection、Safety | Transaction 不决定玩家能看什么 |
| 事件展示和搜索 | Channel、Journal | Transaction 只保证事件可追溯 |
| 房间生命周期 | Room | 开房、开局、归档不归 Transaction |
| 游戏内日历和历史顺序表达 | Timeline | Transaction 只保证结算顺序 |

## 现状风险清单

| 风险 | 代码锚点 | 优先级 | 处理方向 |
| --- | --- | --- | --- |
| active 提交先写 action 再判 duplicate | `router_player.py` | P0 | 调整为先查当前 turn duplicate，或同一数据库事务内写 action 与 turn_id |
| duplicate 后可能已有 `s2c_action_queued` 和 state_version bump | `engine.py`、`turn_manager.py` | P0 | queued event 和版本推进必须晚于 duplicate 通过 |
| action 入队推进世界 `state_version` | `Engine.submit_intent` | P0 | 区分 action queue version 与世界 state version |
| Pipeline 先投影再 StateService 落状态 | `resolution_pipeline.py` | P0 | 权威状态落库成功后再发 patch/completed |
| ProjectionDispatcher 每个事件独立 commit | `projection.py` | P1 | 明确哪些事件属于同一事务后的投影，不依赖多事件原子性 |
| 回合 settle 缺少锁 | `_settle_turn_background`、`TurnManager` | P0 | turn status 从 collecting 到 resolving 需要条件更新 |
| retry turn 对已 resolved turn 的语义不清 | `router_rooms.py` | P1 | 区分重播、重算、恢复，不默认重复规则结算 |
| `s2c_turn_resolved` 未入事件注册表 | `router_player.py`、`events_registry.py` | P1 | 统一 registry、前端类型和测试 |
| HostStore 队列未完整持久化 | `host_store.py` | P1 | 保存 active/queued transaction 或明确只做内存舞台状态 |
| Host ACK 不可审计 | `router_host.py` | P1 | ACK 记录 event 或 transaction state |
| delayed private events 主链路未统一 | `engine.py`、`host_store.py`、`resolution_pipeline.py` | P0 | 私密 patch/completed 由 transaction barrier 控制 |
| 代码和文档存在历史乱码 | 多处现状文件 | P1 | 修改相关文件时同步修正触达文案，不做无关大清洗 |

## MVP 验收主链路

1. Host 开始房间后创建第 1 个 collecting turn。
2. Player 提交带 `action_id` 和 `base_state_version` 的 intent。
3. 系统先校验 token、房间、当前 turn、duplicate，再写入 action。
4. 同一玩家重复提交同一回合行动返回 409，数据库无多余 queued action。
5. 所有 active 玩家提交后，turn 进入 resolving。
6. Pipeline 顺序 resolve queued actions，失败 action 进入 rejected 且不产生公共投影。
7. 成功 action 的权威状态先由 StateService 写入，再投影 Host/Player/Party 事件。
8. Host 收到 reveal transaction，Player 不早于安全点收到私密 patch 和 completed。
9. turn 标记 resolved，生成下一 collecting turn。
10. 重连后 Player 可看到自己的 pending/resolved action、正确 stateVersion 和未丢失事件。
