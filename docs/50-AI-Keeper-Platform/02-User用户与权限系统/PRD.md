# User 用户与权限系统 PRD 初版

## 目标

建立平台用户、房间成员、角色绑定和权限审计的统一模型，保证玩家、房主、旁观者、AI 和 Engine 的读写边界清晰。

## 范围

包含账号身份、房间身份、角色绑定、权限校验、私密信息可见性和操作审计。不包含复杂社交关系、好友系统、评价体系和商业订阅权限。

## 角色

| 角色 | 权限 |
|---|---|
| 用户 | 拥有平台账号和多个房间身份。 |
| 房主 | 管理房间、Session 和有限急救。 |
| 玩家 | 操作绑定角色，查看授权投影。 |
| 旁观者 | 查看公共内容。 |
| 管理员 | 处理平台运维和安全事件。 |

## 用户故事

| 编号 | 用户故事 | 优先级 |
|---|---|---:|
| USER-1 | 作为玩家，我只能操作自己的角色。 | P0 |
| USER-2 | 作为房主，我能管理房间但不会看到完整剧本真相。 | P0 |
| USER-3 | 作为系统，我能拒绝伪造 token 或越权请求。 | P0 |
| USER-4 | 作为管理员，我能审计高风险操作。 | P1 |

## 数据边界

平台身份与房间身份分离。用户账号保存平台级资料，房间成员保存 role、room token、character binding、joinedAt、status。私密线索、个人目标和暗线归属到角色或玩家，不因房主身份自动公开。

## 接口 / 事件方向

- REST：登录或开发态身份签发、房间成员查询、角色绑定、踢出成员、授权管理。
- Event：`member_role_changed`、`character_bound`、`member_removed`、`permission_denied`。
- Audit：记录房主急救、踢出、授权、恢复快照等高风险操作。

## 验收标准

- 玩家不能用自己的 token 操作其他角色。
- 旁观者不能提交行动。
- 房主不能直接读取 KP-only 真相接口。
- 权限失败有明确错误，并写必要审计日志。
