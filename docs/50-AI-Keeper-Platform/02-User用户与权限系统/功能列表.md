# User 用户与权限系统功能列表

## 模块定位

User 模块负责 AI-Keeper 的身份、凭证、角色绑定和鉴权边界。第一轮目标不是做完整社区用户中心，而是保护核心跑团链路里的“谁可以请求、请求者属于谁、请求后最多能碰到哪一层资源”。

核心链路是：

`平台账号 -> 房间房主身份 -> 玩家角色身份 -> 接口鉴权 -> 资源隔离 -> 可见范围`

User 只回答“谁能请求”。请求后“能看到什么”仍由 Room、Projection、Safety、Clue、AI-Keeper 等模块继续裁剪。

当前阶段说明：

- 本文件已可作为工程执行入口，但当前阶段仍是“P0 主链路 + 生产风险识别版”。
- 文档里写清了账号、owner、player 三层身份边界，也识别出了 token 生命周期、WS 鉴权、bootstrap admin、RAG 裁剪等生产缺口。
- 这些缺口目前是“已识别未关闭”，不能把文档完善误解成正式环境已经安全。

## 凭证与边界对照

| 凭证/标识 | 归属模块 | 当前用途 | 不等于什么 | 当前现状 |
|---|---|---|---|---|
| `account_token` | User | 平台登录、Admin 后台、Host 开房、RAG 入口 | 不等于玩家角色 token | 已实现，自带 `iat/exp`，但无撤销/封禁/版本策略 |
| `owner_token` | Room / User 边界 | 管理单个房间、Host REST/WS 兼容路径 | 不等于平台账号 token | 已实现，数据库明文存储，创建时返回 |
| `player_token` | Character / User 边界 | 绑定单个角色、提交 intent、查询私人资源、Player WS | 不等于账号登录态 | 已实现，数据库明文存储，加入或恢复时返回 |
| `room_id` | Room | 当前公开查询和加入入口 | 不是权限凭证 | 当前直接对外使用 |
| `room_code` | Room | 未来短码入房入口 | 不是 owner/player token | 当前未实现 |
| `invite_token` | Room | 未来邀请链接或一次性入房凭证 | 不能替代玩家 token | 当前未实现 |
| `ws_ticket` | User / WS 边界 | 未来短期 WebSocket 鉴权票据 | 不是长期身份凭证 | 当前未实现 |

## 优先级口径

| 优先级 | 含义 |
|---|---|
| P0 | 保护主链路必需，直接影响注册登录、开房、入房、角色隔离、越权拦截 |
| P1 | 安全硬化和真实运营需要，很多项不阻塞本地开发，但不能带着缺口进入正式环境 |
| P2 | 长期平台化能力，如多设备会话、邀请体系、细粒度 RBAC |
| P3 | 社区和商业化用户能力 |

## P0 主链路功能

| 功能 | 是否进入 P0 | 当前代码现状 | 依赖模块 | 用户价值 | 验收口径 | 现状风险/备注 |
|---|---|---|---|---|---|---|
| 用户注册 | 是 | 已有 `POST /api/auth/register`，第一个账号自动成为 `admin`，后续默认为 `player` | Admin/Ops | 平台可产生稳定账号身份 | 注册返回 `account_id`、`username`、`display_name`、`role`、`token` | 首账号自动 admin 适合开发，不适合裸生产 |
| 用户登录 | 是 | 已有 `POST /api/auth/login`，密码使用 PBKDF2-HMAC-SHA256 | Admin/Ops | 用户可恢复平台账号身份 | 正确密码返回 account token，错误返回 401 | `JWT_SECRET` 允许默认值，生产基线不足 |
| account token 基础校验 | 是 | 自带 `iat/exp`；每次请求重新查 `accounts` 表获取当前 `role` | Room、Admin/Ops | 角色调整后权限能及时反映 | 降权后旧 token 再请求时按数据库新角色生效 | 仍无主动撤销、封禁、强制下线能力 |
| 当前账号查询 | 是 | 已有 `GET /api/auth/me` | 前端身份栏、Admin | 前端可确认当前账号角色 | token 有效返回账号摘要，无效返回 401 | DTO 仍需继续分层化 |
| 平台角色模型 | 是 | 当前只支持 `admin/host/player` | Room、Admin/Ops | 区分谁能开房、谁能进后台、谁只能入房 | player 不能开房，host/admin 可以 | 角色判断散落多个 router，缺统一 capability 层 |
| Admin 后台鉴权 | 是 | `_require_admin` 保护 `/api/admin/*` | Admin/Ops、Safety | 后台操作不被普通用户误用 | 未登录 401，非 admin 403 | 高风险后台操作缺结构化审计 |
| Admin 调整账号角色 | 是 | `PATCH /api/admin/accounts/{account_id}` 可改 `role/display_name` | Admin/Ops | 平台可把玩家提升为 host | 角色只允许 `admin/host/player` | 需补防误操作与审计 |
| Host 开房权限 | 是 | `POST /api/rooms` 要求 account role 为 `host/admin` | Room、Module | 只有授权用户能开房 | player 创建返回 403 | `host` 是平台角色，不自动等于任意房间 owner |
| owner account 鉴权 | 是 | `owner_account_id` 绑定平台账号；owner 或 admin 可管理房间 | Room、Host Client | 房主换设备后仍能管理自己的房间 | 非 owner 的 host 账号不能管理他人房间 | 需要和 01-Room 文档一起反复强调 |
| owner token 兼容链路 | 是 | 创建房间返回 `owner_token`，Host REST/WS 可用 | Room、Host Client | 兼容当前 Host 舞台和旧链路 | 正确 token 可进 Host 管理链路 | 明文存储且前端常驻，泄露风险高 |
| player token 绑定角色 | 是 | `characters.player_token` 绑定单个 `character_id` | Character、Player Client | 玩家只能操作自己的角色 | Player 接口通过 token 反查角色 | 当前仍是明文存储 |
| Player intent 鉴权 | 是 | `/api/player/intent` 只接受 `X-Room-Token` | Engine、Transaction | 玩家行动进入受控核心链路 | account token 不能直接提交玩家 intent | 前端传入 `characterId` 不能成为信任来源 |
| Player 私人资源隔离 | 是 | clues、objectives、actions、archive 都通过 player token 回查角色/房间 | Clue、Timeline、Archive | 玩家看不到他人的私密资源 | 他人 action 返回 404，私密线索和个人目标隔离 | 部分接口仍有 403/404 口径不完全统一 |
| 账号绑定角色 | 是 | 入房时登录用户会把 `account_id` 写入 `characters` | Room、Character | 登录玩家可找回自己的角色 | 加入后 `account_id` 正确写入 | 游客恢复能力仍弱 |
| 玩家身份恢复 | 是 | `restore-session` 校验 `characters.account_id` 后直接返回已有 `player_token` | Player Client、Reconnect | 登录玩家换端后能找回角色会话 | 只能恢复自己名下角色 | 当前返回的是原 token，不是新 token 或短期恢复凭证 |
| 复制角色授权 | 是 | 复制角色要求同账号或持有源 `player_token` | Character | 防止盗用他人角色数据 | 他人账号角色不可随意复制 | 规则细节仍归 Character 模块 |
| Host WS 鉴权 | 是 | 当前通过 `/ws?role=host&room=...&ownerToken=...`，并尝试 owner/admin 账号鉴权 | Host Client、Projection | 公共舞台只给合法房主连接 | 错误 token 或非 owner 连接被拒绝 | query token 在浏览器/代理/日志层面风险高 |
| Player WS 鉴权 | 是 | 当前通过 `/ws?role=player&room=...&token=...` | Player Client、Projection | 玩家只接收自己所在房间事件 | token 与 room 不匹配时拒绝连接 | query token 同样存在高敏凭证暴露面 |
| RAG 房间级鉴权入口 | 是 | `rag_router` 先判断 admin / owner / 房间成员 | AI-Keeper、WorldBook | 非成员不能滥用房间知识检索 | player 不能写 index，非成员不能 search | 当前只有成员级鉴权，未做结果 visibility/discovered 裁剪 |
| 公开 DTO 脱敏 | 是 | 当前 Room 公开接口不返回 `owner_token`、`owner_account_id`、`player_token` | Room、Safety | 公开接口不泄露敏感凭证 | `GET /api/rooms/{room_id}` 不含敏感字段 | DTO 分层还不够系统化，WS payload 也要一起检查 |
| 前端多身份 slot | 是 | `identity.ts` 在 `localStorage` 中维护 `account/owner/player` token | DevEx、Host Client、Player Client | 单机调试可同时模拟多身份 | 切换 slot 时兼容 legacy token | 明确只适用于开发调试，不是生产会话设计 |

## P0 生产安全基线（当前缺口）

这些项不一定阻塞本地开发主链路，但不能带着当前缺口进入正式环境。

它们现在都属于“未关闭缺口”，不是“已有能力只差接线”。

| 基线 | 当前代码现状 | 建议方向 | 风险说明 |
|---|---|---|---|
| 首账号 admin bootstrap | 当前第一个注册账号自动成为 admin | 仅开发环境允许；生产要求初始化命令或 `BOOTSTRAP_ADMIN_CODE` | 裸部署时可能被外部用户抢注 admin |
| `JWT_SECRET` 生产 fail-fast | 当前允许默认值 `aikeeper-change-me-in-production` | 生产环境若为空或默认值则拒绝启动 | 默认密钥会导致伪造 account token 风险 |
| WS 短期票据 | 当前 Host/Player WS 都使用 query token | 正式环境切到短期一次性 `ws_ticket` | URL query 会进入浏览器历史、代理日志和监控链路 |
| owner/player token 生命周期 | 当前明文存储、无 rotate/revoke、恢复返回原 token | 至少规划 hash、rotate、revoke 和失效策略 | 泄露后是长期高危凭证 |
| account token 撤销与封禁 | 当前有 `exp`，无 `token_version`、`disabled_at`、会话表 | 增加版本、封禁和主动失效能力 | 改密码、封号、强制下线都缺统一落点 |
| Player-facing RAG 结果裁剪 | 当前只做成员级鉴权，`rag.search` 直接返回检索结果 | 玩家结果必须再过 `visibility/audience/discovered_state` | 可能把 `scenario_truth` 或未发现线索直接返给玩家 |

| 游客恢复与设备绑定 | 是 | 当前主要靠登录账号恢复；游客几乎只能靠旧 token | Player Client | 降低游客丢失身份风险 | 可选一次性恢复码或设备绑定 | 需要与 token 生命周期一起设计 |

## 核心边界

- `account_token`、`owner_token`、`player_token` 三者绝不能混用。
- `host` 是平台角色，不是任意房间 owner；只有 `owner_account_id` 匹配后才拥有该房间 owner 权限。
- `player_token` 绑定的是“某个角色”，不是“某个账号”。
- 前端传入的 `characterId` 不能作为安全身份，只能作为查询目标或展示辅助。
- `room_code`、`invite_token`、`ws_ticket` 都不应被当成长期角色控制凭证。
- User 模块只负责“谁能请求”；玩家读到什么内容，仍由 Projection / Safety / AI-Keeper / Clue 等模块裁剪。
- Host 不是全知 KP，User 不授予 Host 读取完整 `scenario_truth` 的权限。

## 数据模型演进方向

当前事实：

- `accounts`：已有 `account_id`、`username`、`password_hash`、`display_name`、`role`、`last_seen_at`、`created_at`
- `rooms`：已有 `owner_token`、`owner_account_id`
- `characters`：已有 `player_token`、`account_id`、`status`
- account token 为 HMAC 签名 token，带 `iat/exp`，每次请求重新从数据库取当前角色
- 当前没有 `token_version`、`disabled_at`、`owner_token_hash`、`player_token_hash`、`account_sessions`

后续建议：

- `accounts` 增加 `token_version`、`disabled_at`、`updated_at`
- 为 account token 补会话撤销或版本失效策略
- `rooms` 增加 `owner_token_hash`、`owner_token_rotated_at`、`owner_token_revoked_at`
- `characters` 增加 `player_token_hash`、`player_token_version`、`joined_at`、`left_at`
- 新增 `auth_audit_events` 或同级审计表，记录 actor、target、result、reason、ip/user_agent 摘要

## 第一轮落地判断

第一轮 User 只追求把身份边界打稳：

`账号登录 -> 平台角色判断 -> Host 开房 / 管房 -> 玩家 token 绑定角色 -> 玩家只能操作自己 -> Host/Player/Admin/RAG/WS 越权被拒绝`

多设备会话、正式邀请体系、细粒度 RBAC、完整游客恢复、社区账号资料都不混入本轮主链路；但 `JWT_SECRET`、首账号 admin、WS query token、owner/player token 生命周期这些生产安全基线，必须在文档里明确标为高风险缺口。
