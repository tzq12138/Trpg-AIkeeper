# User 用户与权限系统功能列表

## 模块定位

User 模块负责 AI-Keeper 的身份、令牌、角色、绑定关系和鉴权边界。它不是完整社交用户中心，也不是平台商业会员系统；第一轮目标是保护核心跑团链路里的读写权限：

`平台账号 -> 房间房主身份 -> 玩家角色身份 -> 接口鉴权 -> 可见范围`

当前仓库已经存在三层身份：

| 身份层 | 凭证 | 当前用途 | 代码锚点 |
|---|---|---|---|
| 平台账号 | `Authorization: Bearer <account_token>` 或 `X-Account-Token` | 登录、注册、admin/host/player 平台角色、创建房间、Admin 后台、RAG 权限 | `src/server/router_auth.py`、`src/server/router_admin.py`、`src/server/rag_router.py` |
| 房主身份 | `X-Owner-Token` 或 owner account | 房间管理、Host WS、开局、暂停、checkpoint、回放、地图监督 | `src/server/router_rooms.py`、`src/server/host/router_host.py`、`src/server/router_archive.py` |
| 玩家角色身份 | `X-Room-Token` 或 WS `token` | 操作绑定角色、提交 intent、查个人状态、私密线索、断线恢复 | `src/server/player/router_player.py`、`src/server/main.py`、`src/server/player/router_reconnect.py` |

前端当前通过多身份 slot 存储 `account_token`、`owner_token`、`player_token`，主要服务本地开发和单机多身份测试，不能等同正式多端会话管理。

## 优先级口径

| 优先级 | 含义 |
|---|---|
| P0 | 保护主链路必需：登录、角色、token、房主/玩家/admin 鉴权、越权拦截 |
| P1 | 真实跑团运营需要：审计、封禁、助理房主、token 轮换、权限诊断 |
| P2 | 平台长期能力：多端会话、账号资料、组织关系、邀请体系 |
| P3 | 社区和商业化：好友、声誉、会员、创作者权限 |

## P0 MVP 功能

| 功能 | 是否进入 MVP | 当前代码状态 | 依赖模块 | 用户价值 | 验收口径 | 现状风险 |
|---|---|---|---|---|---|---|
| 用户注册 | 是 | 已有 `POST /api/auth/register`，首个账号自动为 admin，其后默认为 player | Admin/Ops | 平台能产生稳定账号身份 | 注册返回 `account_id`、`username`、`display_name`、`role`、`token` | 错误文案有乱码；首账号 admin 策略需部署时明确 |
| 用户登录 | 是 | 已有 `POST /api/auth/login`，密码使用 PBKDF2-HMAC-SHA256 | Admin/Ops | 用户可恢复平台账号身份 | 正确密码返回 account token，错误密码返回 401 | `JWT_SECRET` 有默认值，生产必须改为强随机密钥 |
| 当前账号查询 | 是 | 已有 `GET /api/auth/me` | 前端身份栏、Admin | 前端可确认当前账号角色 | token 有效返回账号摘要，无效返回 401 | token 撤销能力未实现 |
| 平台角色 | 是 | 当前角色为 `admin/host/player` | Room、Admin/Ops | 控制谁能开房、管理后台、普通入房 | player 不能创建房间或导入剧本；host/admin 可以创建房间 | 角色权限散落在各 router，缺统一权限 helper |
| Admin 后台鉴权 | 是 | `_require_admin` 保护 `/api/admin/*` | Admin/Ops、Safety | 管理员可维护房间、账号、角色、素材、AI 配置 | 非登录返回 401，非 admin 返回 403 | 后台高风险操作审计不完整 |
| 管理员提升角色 | 是 | `PATCH /api/admin/accounts/{account_id}` 可改 `role/display_name` | Admin/Ops | 管理员可把玩家提升为 host | role 只允许 `admin/host/player` | 需要防误操作与审计 |
| Host 创建房间权限 | 是 | `POST /api/rooms` 要求 account role 为 host/admin | Room、Module | 只有授权用户能开房 | player 创建返回 403；host/admin 创建成功 | Host 权限是平台级，房间 owner 是房间级，两者需区分 |
| 房主 owner token | 是 | 创建房间返回 `owner_token`，Host REST/WS 可用 `X-Owner-Token` | Room、Host Client | 兼容无完整账号流的房间管理 | 正确 owner token 可进 Host WS，错误 token 关闭连接 | 高敏令牌存前端 localStorage，泄露风险高 |
| owner account 鉴权 | 是 | 房间保存 `owner_account_id`，owner account 或 admin 可管理房间 | Room、Host Client | 房主换设备登录后仍能管理自己的房间 | owner account 可 start、查 turn、配置房间；其他 host 不行 | 部分前端仍优先依赖 owner token |
| Player token 绑定角色 | 是 | `characters.player_token` 绑定一个 `character_id` | Character、Player Client | 玩家只能操作自己的角色 | 提交 intent、查线索、查 action 都由 token 反查角色 | 旧 `join` 接口可创建未命名角色，需标清兼容路径 |
| Player token 提交 intent | 是 | `/api/player/intent` 只接受 `X-Room-Token` | Engine、Transaction | 玩家行动进入受控核心链路 | 缺 token 返回 401，无效 token 返回 403 | 不能信任前端传入 characterId |
| Player WS 鉴权 | 是 | `/ws?role=player&token=...` 校验 token 和 room | Projection、Player Client | 玩家只收到本房间事件 | token 与 room 不匹配时关闭连接 | catch-up 事件的 audience 过滤需由 Projection/重连策略继续加强 |
| Host WS 鉴权 | 是 | `/ws?role=host&ownerToken=...` 校验 owner token，后端也尝试 account auth | Host Client、Projection | 公共舞台只给房主连接 | 无 token 或错误 token 被拒绝 | account token 未作为 WS query 明确传入，代码里存在未使用变量痕迹 |
| 玩家账号绑定角色 | 是 | `join-with-character` 可把 `account_id` 写入 characters | Character、Room | 登录玩家可恢复角色 session | 登录玩家加入后 `account_id` 正确；只能恢复自己角色 | 游客角色恢复能力有限 |
| 恢复玩家 session | 是 | `POST /api/player/characters/{character_id}/restore-session` 校验 account_id | Player Client、Reconnect | 登录玩家换端可取回 player token | 账号不匹配返回 403 | 返回 player token 属高敏操作，需要前端谨慎保存 |
| 复制角色权限 | 是 | 复制角色时校验同 account 或源 player token | Character | 防止复制他人角色卡 | 他人账号角色不可复制；游客需持源 token | 复制策略归 Character 模块，User 只管授权 |
| 私密线索权限 | 是 | `/api/player/clues` 用 token 反查角色，只列本人线索和已分享线索 | Clue、Projection | 防止私密线索外泄 | 玩家看不到他人未分享线索 | 线索公开摘要策略归 Clue/Safety |
| 个人目标权限 | 是 | `/api/player/objectives` 返回团队目标和本人 personal 目标 | Timeline、Clue | 防止个人目标外泄 | A 玩家看不到 B 玩家 personal objective | 个人目标写入来源需在剧情模块约束 |
| action 查询隔离 | 是 | `/api/player/actions/{action_id}` 按 token 绑定 character 过滤 | Transaction、Reconnect | 玩家只能查自己的 pending/resolved action | 其他玩家查同 action 返回 404 | 404 用于隐藏资源存在性，文档需明确 |
| RAG 读写权限 | 是 | `_require_auth_for_room`：admin 全局，owner 可写，房内玩家可读 | AI-Keeper、WorldBook、Safety | 知识检索不被非成员滥用 | player 不能 index；非房间成员不能 search | RAG 内容裁剪还需 Safety/AI-Keeper 协同 |
| 公开 DTO 脱敏 | 是 | `GET /api/rooms/{room_id}` 不返回 owner token、owner account | Room、Safety | 房间公开查询不泄露管理凭证 | 测试确认无 `owner_token`、`owner_account_id` | 其它导出/admin 接口也需持续脱敏审查 |
| 多身份 slot | 是 | 前端 `identity.ts` 支持多个本地身份 slot | DevEx、Host Client、Player Client | 单机调试可同时模拟 Host 和 Player | 切换 slot 时同步 legacy token | 这是开发态便利，不是正式会话系统 |

| 账号会话撤销 | 否 | 未实现 | Admin/Ops | 管理员可踢出被盗账号 session | 被撤销 JWT 不再可用 | 当前 JWT 无服务端 session 表 |

| 用户资料 | 否 | 账号有 display_name，无头像/偏好 | Asset、Community | 玩家可被识别 | 大厅显示稳定昵称和头像 | 不应把账号资料扩展成社交系统 |

## 核心边界

- 前端传来的 `characterId` 不能作为安全身份，只能作为展示或请求目标；后端必须用 token 反查身份。
- 平台角色 `host` 只表示可以创建和拥有房间，不等于传统全知 KP。
- `owner_token` 是房间管理高敏凭证，不能出现在公开 DTO、公共事件或日志全文中。
- `player_token` 是角色操作高敏凭证，只能返回给对应玩家或经过账号校验的恢复接口。
- Admin 是平台运维身份，不应被玩家链路或 Host 舞台误用。
- User 模块管“谁可以请求”，Projection/Safety/Clue 模块管“请求后能看到什么”。
- AI 不拥有用户身份，也不能绕过 User 权限直接检索或写入房间数据。

## 第一轮落地判断

第一轮 User 模块只追求稳定身份边界：

`账号登录 -> 平台角色判断 -> 房主开房/管理 -> 玩家 token 绑定角色 -> 玩家只能操作自己 -> Host/Player/Admin/RAG/WS 越权被拒绝`

多端会话、一次性邀请、黑名单、助理房主、正式审计、社区账号资料等能力放入后续批次。DeepSeek 执行时优先修当前乱码、散落鉴权、测试缺口和 token 泄露风险，不扩展外围社区能力。
