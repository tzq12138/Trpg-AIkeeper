# Clue 线索与道具系统验收文档

## 文档定位

本文件用于在收到工程师的 `回执-YYYY-MM-DD.md`、代码改动说明、测试结果后，判断 `08-Clue` 本轮工作是否真正完成。

它只负责验收，不替代 `功能列表.md`、`PRD.md`、`DeepSeek计划.md`。

默认分两层结论：

- `本轮工程验收通过`：表示 Clue 本轮承诺的 P0 主链路、证据链边界和状态一致性已完成。
- `生产安全完成`：表示除本轮范围外，Clue 的长期高风险缺口也已关闭。

除非证据非常完整，否则默认只评 `本轮工程验收通过`，不直接给 `生产安全完成`。

## 验收输入

验收前至少应拿到以下材料：

- 本模块三份基线文档：`功能列表.md`、`PRD.md`、`DeepSeek计划.md`
- 工程师回执：`回执-YYYY-MM-DD.md`
- 本轮改动文件列表，至少说明改了哪些 clues、inventory、objectives、state、AI、archive、export、测试文件
- 测试命令与结果
- 如涉及玩家页、线索页、Archive 页或导出页面，附 `npm run build` 结果和手动验证结果

## 结论等级

| 结论 | 含义 |
|---|---|
| `本轮工程验收通过` | 私密线索、公共分享、Inventory/Luck、Archive、AI/RAG 过滤、Export 口径和关键测试都已对上 |
| `本轮工程验收有缺口` | 主链路基本可用，但仍缺关键证据、关键测试或关键安全边界 |
| `不通过` | 出现 clue 原文泄露、public export 泄露、AI 可直接读未发现 clue/truth、Luck/Inventory 半成功、测试未过或回执与实际不符 |
| `生产安全完成` | 只有在 Host debug 审计、share scope 扩展、长期 clue/version 演进、跨模块口径完全闭环后才可给出 |

## 一票否决项

出现任一情况，本轮不能判通过：

- 玩家 B 可以直接读到玩家 A 未分享的 `clues.text`
- `clues.is_private=false` 被某个接口、Archive、Export 或 AI 路径解释成“原文全队公开”
- 默认分享仍会把 `clues.text` 原样公开，或自动摘要原文导致泄露
- `share_full_text=true` 被实现成绕过 SpoilerGuard 的开关
- `_tool_engine_save_clue` 仍直接 `INSERT clues`
- 追溯道具仍只改 `characters.xlsx_data.luck`，不更新运行态
- Inventory、Luck、Action、Journal、state patch 之间出现半成功
- public export 仍直接导出 `clues.text`
- player-facing AI / RAG 能直接看到未发现 WorldBook clue template 或完整 `truth`
- 测试命令未提供，或关键测试明显未通过

## 必备回执材料

工程师回执里至少应明确：

- 本轮对应的 Batch 范围，例如 `Clue-1 ~ Clue-4`
- 实际修改文件
- 实际测试命令
- 实际测试结果
- 明确完成项
- 明确未完成但保留为后续 Batch 的项
- 如果修了 share scope，说明最终采用的是“补 `room_id`”还是“`JOIN clues` 过滤 room_id”
- 如果保留了 `xlsx_data` 同步，说明它与 `character_runtime_state` 的主从关系

如果回执把文档里明确属于后续项的缺口写成“已完成”，验收时应直接降级处理。

## 本轮工程验收清单

### 1. 私密线索与公共分享边界

- 玩家 A 获取私密 clue 后，玩家 B 看不到该 `clues.text`
- 玩家 A 分享后，玩家 B 只能看到 `public_version`
- `clues.is_private=false` 不会被任何 player-facing 路径当成“原文已公开”
- Host 默认普通运营视角不会混入 `clues.text` 原文
- 若存在 Host/Admin debug 路径查看原文，需有权限边界和审计说明

### 2. `public_version` 安全分享

- 分享必须产生 `public_version`
- 未传 `public_version` 时，使用固定安全默认文案，而不是自动摘要原文
- 默认安全文案不会泄露 clue 隐藏事实
- `share_full_text=true` 需要后端显式确认字段
- `share_full_text=true` 仍经过 SpoilerGuard 或等价检查
- 分享事件只包含 `publicVersion`，不包含原始 `text`

### 3. `clue_shares` room scope 与 share 语义

- `clue_shares` 的 room scope 已有明确实现
- 若未补 `room_id`，则所有 room-scope 查询均通过 `JOIN clues` 用 `clues.room_id` 过滤
- 同一 room 的 share 可正常读取
- 不同 room 之间不会串 share、串 unlock、串 Archive 数据
- 文档里的“本轮 share 默认 scope=party”在实现里有清晰对应

### 4. 统一 Clue 写入路径

- `_tool_engine_save_clue` 不再直接插库
- 线索发现通过统一受控入口落库
- 该入口已负责房间绑定、角色绑定、来源记录、事件记录
- StateService share 与 player share API 复用同一套 share builder / validation
- 缺失 `public_version` 的 StateService 路径不会再触发 DB 约束问题

### 5. Journal / Archive 证据链

- clue 发现会写 `s2c_clue_discovered` 或等价私密事件
- clue 分享会写 `s2c_clue_shared`
- `party` 事件 payload 不包含 `clues.text`
- Archive 能按 `clue_id` 聚合发现和分享
- 队友 Archive 只能看到 `publicVersion`
- public export 只能导出公共版本和公开事件摘要

### 6. Inventory / Luck / Action 一致性

- 追溯道具成功后，背包增加、Luck 变化、Action 结果、state patch、Journal 事件保持一致
- `auto_pass` 成功路径已验证
- `roll_required` 成功路径已验证
- `forbidden / roll failed` 不写 inventory
- Luck 当前值优先来自 `character_runtime_state`
- 如保留 `xlsx_data` 同步，它不是唯一权威来源

### 7. AI / RAG 证据过滤

- player-facing AI 只读取 owned private clue、shared public clue、公开事件
- shared clue 在 AI 上下文中表现为 `public_version`
- 未发现 WorldBook clue template 不进入玩家 prompt
- `truth` 不因 share、Archive、Export 直接进入玩家可读上下文
- 如有 context preview，能说明 clue 的过滤原因

### 8. `/sync`、`/clues`、Objective、Export 口径统一

- `/sync` 与 `/clues` 对同一条 clue 的可见字段一致
- owned clue 返回原始 `text`
- shared clue 返回 `public_version`
- `team` objective 对同房间玩家可见
- `personal` objective 不泄露给其他玩家
- public export 不再导出 `clues.text`

### 9. 端到端主链路

至少应手动或自动证明以下链路：

1. 玩家 A 通过行动获得私密 clue
2. 玩家 B 看不到该 clue
3. 玩家 A 分享公共版本
4. 玩家 B 只看到 `public_version`
5. 玩家 A 发起追溯道具主张
6. 成功时 Inventory 与 Luck 一致更新
7. Archive 能查到 clue 发现、分享、道具获得
8. public export 只包含公共摘要
9. AI 上下文只含允许证据
10. 任一步失败时，不产生半成功数据

## 生产安全加签条件

以下条件未关闭前，不应给 `生产安全完成`：

- Host/Admin debug 读取 `clues.text` 仍未形成稳定审计边界
- share scope 仍固定为粗粒度 `party`，尚未支持更细粒度目标范围
- `clue_shares` 的 room scope 实现虽可用，但未完全沉淀为稳定 schema/查询规范
- AI/RAG clue 索引与 visibility 虽已收口，但长期 version/重建策略未成型
- Inventory / Objective 与 Projection / Journal / Export 的全链路复盘仍未完全闭环
- public/private/debug export 体系仍未完整分层
