# Character 角色卡系统验收文档

## 文档定位

本文用于在收到工程师的 `回执-YYYY-MM-DD.md` 后，判断 `05-Character` 本轮工作是否真正完成。
Character 的验收核心不是“能导入一张卡”，而是“玩家在房间内拥有一个可归属、可恢复、可被规则读取、且不会把私密角色数据乱泄露的角色实体”。

默认分两层结论：

- `本轮工程验收通过`：表示 Character 的 P0 主链路、运行态权威源和权限脱敏边界已达到本轮文档要求。
- `生产安全完成`：表示长期会话恢复、RAG 裁剪、隐私边界、状态收敛和异常降级等高风险项也已经闭环。

## 验收输入

- 本模块三份基线文档
- 工程师回执：`回执-YYYY-MM-DD.md`
- 修改文件列表
- 测试命令与结果
- 如改了玩家入房页、角色页、Host HUD 或相关 UI，附 `npm run build` 结果

## 结论等级

| 结论 | 含义 |
|---|---|
| `本轮工程验收通过` | 入房建卡、角色归属、运行态合并、DTO 脱敏、技能检定权威源和恢复链路已对齐本轮口径 |
| `本轮工程验收有缺口` | 主链路基本可用，但缺关键测试、关键脱敏证据、或仍存在明显兼容/权限风险 |
| `不通过` | 出现越权恢复、私密字段泄露、运行态与静态卡双轨漂移、或前端值覆盖服务端权威值 |
| `生产安全完成` | 仅在 token 恢复风险、RAG 索引裁剪、状态收敛、异常降级和长期隐私边界也全部闭环后给出 |

## 一票否决项

- `GET /api/player/character`、`GET /api/player/sync`、Host HUD 仍然读取不同来源，导致 HP/SAN/MP/Luck 不一致
- 前端提交的 `skill_value`、`roll` 或其他角色值被采纳为正式权威值
- Lobby snapshot、公开 DTO、普通日志或公共事件中泄露 `player_token`、完整 `xlsx_data`、私密背景、恐惧、秘密、私人目标
- `restore-session` 可以恢复非本人账号角色，或可凭他人 `character_id` 拿到有效玩家身份
- `pending_approval` 角色在未批准前已能进入正式行动、投影或结算链路
- 新写入仍继续使用 `active` 扩大角色成员状态口径，而不是收敛到 `joined/pending_approval/left`
- Character/RAG 链路把完整 `xlsx_data` 原样喂入 player-facing AI 检索

## 本轮工程验收清单

### 1. 入房与角色归属

- `join-with-character` 仍是入房主链路
- 预设卡、模板、XLSX、前端建卡器、复制已有角色等来源互斥明确
- 同房间预设卡重复占用会返回稳定错误
- 复制已有角色时做账号所有权或原 `player_token` 所有权校验
- `join-with-character` 如返回完整角色 DTO，也只返回给当前加入者，不进入 lobby snapshot 或公共广播

### 2. 静态卡与运行态分层

- `characters.xlsx_data` 明确作为静态角色卡快照
- `character_runtime_state` 明确作为战局运行态权威源
- `GET /api/player/character` 会合并运行态，而不是只读静态卡
- `GET /api/player/sync` 会合并运行态，而不是只回旧快照
- Host HUD 与玩家角色页最终看到同一组当前 HP/SAN/MP/Luck
- StateService 改值后，刷新玩家页和 Host HUD 都能看到同样结果

### 3. 运行态初始化与降级

- 入房后会初始化 `character_runtime_state`，或在首次读取时安全懒初始化
- 运行态初始化失败不会直接把主链路打死
- 初始化失败有结构化 warning/error 记录
- 懒初始化也失败时，会返回明确 degraded 状态或等价提示
- 不允许 Host HUD 长期读运行态、玩家页长期读静态卡而无任何风险提示

### 4. Lobby / Host / Self DTO 脱敏

- Lobby snapshot 不包含 `player_token`
- Lobby snapshot 不包含完整 `xlsx_data`
- Lobby snapshot 不包含私密背景、恐惧、秘密、私人笔记、私人目标
- 玩家本人 `SelfCharacterDTO` 能看到自己的完整必要字段
- Host DTO 只包含公开摘要、公共战局状态与被授权字段
- 普通日志、公开事件、公共投影不泄露私密角色字段

### 5. 技能检定权威源

- 正式技能检定链路读取服务端角色数据，而不是信任前端传值
- 前端提交 `skill_value=999` 也不会覆盖服务端真实技能值
- `/api/player/skill-check` 如仍保留，只能是 debug/兼容/降级入口
- `/api/player/skill-check` 不得静默替代正式 intent/action lifecycle
- Character 与 `04-Rule` 的技能检定口径保持一致

### 6. 账号恢复与身份安全

- 登录账号只能看到自己的角色列表
- `restore-session` 只能恢复当前账号拥有的角色
- 非本人账号不能凭 `character_id` 恢复玩家身份
- 如果仍直返原 `player_token`，回执中必须明确标记兼容风险
- 后续安全方向是否采用短期恢复票据、rotate 或设备绑定，回执需说明当前实现位置

### 7. 角色状态收敛与审批

- 角色成员状态新写入只允许 `joined/pending_approval/left`
- `active` 仅作历史兼容读取，不再继续写入
- 活动房间新加入角色进入 `pending_approval`
- Host approve 后转为 `joined`
- Host reject 后转为 `left`
- 未批准角色不能参与正式行动、结算、公共投影或房间开始条件计算

### 8. RAG 与 AI 上下文边界

- Character 相关索引前先构建裁剪后的 `AICharacterContextDTO`
- 索引或检索链路带有 `visibility / audience / discovered_state` 或等价元数据
- player-facing 检索不会读到其他玩家私密背景、恐惧、秘密、私人目标
- 不允许把完整 `xlsx_data` 原样写进面向玩家的 RAG 索引

### 9. 端到端主链路

至少应手动或自动证明以下链路：

1. Host 创建房间
2. 玩家通过预设卡或 XLSX 入房
3. 玩家查看自己的角色页
4. 玩家 ready
5. Host 开局
6. 玩家发起技能检定
7. Engine/Rule/State 完成裁决并更新运行态
8. 玩家角色页与 Host HUD 同步看到一致运行态
9. 日志可查到角色加入、ready、行动与状态变更

## 生产安全加签条件

以下条件未关闭前，不应给 `生产安全完成`：

- `restore-session` 仍依赖长期有效 `player_token` 直接恢复
- RAG 索引或检索仍未统一复用字段可见性裁剪
- Host、Player、Archive、Projection 对 Character DTO 的字段边界仍不一致
- 运行态初始化失败仍可能静默降级成双轨读值
- HP/SAN/MP/Luck 的默认可见性策略仍未和 Room / Rule / Projection 的房规口径最终对齐
- `character_profiles` 虽已存在，但长期成长、跨房归档和权限继承仍未形成稳定产品闭环
