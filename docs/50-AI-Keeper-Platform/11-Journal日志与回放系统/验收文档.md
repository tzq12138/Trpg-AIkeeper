# Journal 日志与回放系统验收文档

## 文档定位

本文档用于在收到工程师的 `回执-YYYY-MM-DD.md`、代码改动说明、测试结果后，判断 `11-Journal` 本轮工作是否真正完成。

它只负责验收，不替代：

- `功能列表.md`
- `PRD.md`
- `DeepSeek计划.md`

默认分两层结论：

- `本轮工程验收通过`：表示 Journal 本轮承诺的 P0 主链路、可见性边界、导出安全、checkpoint 恢复语义和来源引用链已经闭环。
- `生产安全完成`：表示除本轮范围外，Journal 的长期高风险缺口也已基本关闭。

除非证据非常完整，否则默认只给 `本轮工程验收通过`，不直接给 `生产安全完成`。

## 验收输入

验收前至少应拿到以下材料：

- 本模块四份基线文档：`功能列表.md`、`PRD.md`、`DeepSeek计划.md`、`验收文档.md`
- 工程师回执：`回执-YYYY-MM-DD.md`
- 本轮改动文件清单，至少说明改了哪些 event log、archive、export、campaign、checkpoint、registry、前端和测试文件
- 实际测试命令与测试结果
- 如涉及 Host / Player 日志页面，附 `npm run build` 结果和手动链路验证结果

## 结论等级

| 结论 | 含义 |
| --- | --- |
| `本轮工程验收通过` | Journal 本轮 P0 / P1 目标已经实现，关键权限边界、导出边界、checkpoint 语义和测试结果对齐 |
| `本轮工程验收有缺口` | 主链路基本可用，但仍缺关键证据、关键测试或关键边界闭环 |
| `不通过` | 出现权限泄露、导出泄露、restore 语义不成立、事件注册缺口严重、测试未过或回执与实际不符 |
| `生产安全完成` | 只有在长期遗留项也基本关闭、公共与运维边界稳定、回放与导出长期策略都明确后才可给出 |

## 一票否决项

出现任一情况，本轮不能判通过：

- Player 可以访问 Host timeline 或读取 Host-only event
- public events 仍以 `audience != 'player'` 作为主要过滤口径
- Player archive 能读到其他玩家 private event
- 私密事件缺少 `characterId` / `recipientCharacterId` 时仍会下发给 Player
- public export 泄露 `owner_token`、`player_token`、`account_id`、email、原始 `xlsx_data`
- public export 泄露未公开 clue 原文、`raw_text`、truth 字段、`original_file_path`
- public export 或 full export 泄露 raw AI prompt / raw AI response / API key / 明文 secret
- `/campaign` 仍无 public / full 权限分层
- restore 不要求 `confirm=true + reason`
- restore 后没有新的 `s2c_checkpoint_restored` 审计 marker
- restore 原始审计 payload 直接出现在 Player 视角
- `s2c_checkpoint_created`、`s2c_checkpoint_restored`、`s2c_turn_resolved` 仍未对齐 registry / model / TS
- `ai_call_logs`、`spoiler_audits` 进入 Player Journal 或 public export
- 关键测试命令未提供，或明显未通过

## 必备回执材料

工程师回执里至少应明确：

- 本轮对应的 Batch 范围，例如 `Journal-1 ~ Journal-5`
- 实际修改文件
- 实际测试命令
- 实际测试结果
- 明确完成项
- 明确未完成但保留为后续 Batch / P1 / known limitation 的项
- `clue_shares` 是否已补入 checkpoint snapshot
- `encounter_participants` 是否已补入 checkpoint snapshot
- 如未补齐，上述两项是否已在回执中明确列为遗留限制
- public summary 传给 AI 之前是否已经过滤到玩家可见事件
- full summary 是否仍排除 raw prompt / token / secret

如果回执把文档里明确属于后续项的缺口写成“已完成”，验收时应直接降级处理。

## 本轮工程验收清单

### 1. Host timeline 权限

- `GET /api/rooms/{room_id}/events`
- `GET /api/rooms/{room_id}/timeline`
- `GET /api/rooms/{room_id}/timeline/{sequence}`

必须满足：

- 只有 Owner / Admin 可读
- Player 请求返回 401 / 403
- Host timeline 能按 `room_id + sequence` 稳定查看房间事件

### 2. public events 与 `system_safe` 白名单

- public events 不再依赖 `audience != 'player'`
- public events 只返回 public / `party` / `system_safe` 中允许公开的事件
- `system` 事件默认不 public，必须显式进入白名单

最小白名单示例建议至少验证：

- `s2c_turn_resolved` 的安全摘要
- `s2c_game_time_updated` 的 `safeReason`
- 如产品允许，`s2c_checkpoint_created` 的安全摘要

默认不可作为 `system_safe` 的示例：

- `s2c_checkpoint_restored` 原始审计 payload
- `admin override`
- `spoiler audit`
- `internal error`
- `debug`
- raw restore reason

### 3. Player archive 私密边界

- Player archive 看不到 Host-only event
- Player archive 看不到其他玩家 private event
- 私密事件缺少 `characterId` / `recipientCharacterId` 时默认不下发
- `payload.characterId` 与 `payload.character_id` 口径若并存，均已正确处理

### 4. 统一可见性 helper

以下入口必须复用同一套服务端可见性 helper：

- public events
- Player archive
- replay
- public export
- public campaign summary

验收时至少应看到：

- 统一 helper 的代码入口
- 至少一组跨接口对齐测试
- archive / public events / export 对同一事件集合给出一致的安全结果

### 5. `room_id + sequence` 查询边界

以下能力必须按 `room_id + sequence` 运作：

- timeline 查询
- replay
- reconnect / catch-up
- export 事件读取
- public / player 视角历史读取

不应存在只凭全局 `sequence` 跨房间读事件的路径。

### 6. public / full export 边界

#### public export 必须不包含

- `owner_token`
- `player_token`
- `account_id`
- email
- 原始 `xlsx_data`
- 未公开 clue 原文
- `raw_text`
- truth 字段
- `original_file_path`
- host-only payload
- admin/debug payload
- raw AI prompt
- raw AI response

#### full export 必须满足

- 仅 Owner / Admin 可取
- 不是数据库原样导出
- 仍脱敏 raw token、API key、明文 secret、账号敏感字段
- 不包含 raw AI prompt / raw AI response

如未来需要 raw AI / Ops 审计导出，应另设 `admin_audit export scope`，不能复用 `full export`。

### 7. campaign summary 权限与 AI 输入源

- `/campaign` 存在 public / full 权限分层
- public summary 只基于玩家可见事件生成
- full summary 仍排除 raw prompt / token / secret
- AI 不能为 summary 补写未发生事实

验收时必须关注的不只是输出结果，还包括：

- 传给 AI 的输入事件集合是否先过滤
- Player 是否能通过 summary 拿到本不该知道的 clue / truth / debug 信息

### 8. checkpoint / restore 语义

restore 必须满足：

- 请求必须带 `confirm=true`
- 请求必须带 `reason`
- restore 后写新的 `s2c_checkpoint_restored`
- restore marker 至少包含 `checkpointId`、`actorAccountId`、`reason`、`restoreMode`、`createdAt`
- Host timeline 能看到恢复断点
- 原始 restore 审计 payload 不直接下发给 Player

如需要通知 Player，必须另发 party-safe 摘要，而不是复用原始 restore payload。

### 9. checkpoint snapshot 补表与遗留项

重点检查：

- checkpoint snapshot 是否已覆盖 `clue_shares`
- checkpoint snapshot 是否已覆盖 `encounter_participants`

若本轮未补齐：

- 回执必须明确列为 known limitation
- 必须说明 restore 后会影响哪些关系恢复
- 不得在回执中把该项描述成“已完整支持”

### 10. 事件注册、模型与 TS 类型

以下事件至少应完成三处对齐：

- `s2c_checkpoint_created`
- `s2c_checkpoint_restored`
- `s2c_turn_resolved`

三处包括：

- `events_registry.py`
- 服务端 model / DTO / schema
- `src/client/src/shared/types.ts`

### 11. DTO 边界

验收时应核对：

- `JournalEventDTO` 最低字段稳定
- `HostJournalEventDTO` 如带 `debugMeta`，只能包含业务排错摘要
- `debugMeta` 不得包含 raw prompt、API key、token、账号敏感字段
- 更深层 raw debug 进入 `AI/Ops Audit`
- `PlayerArchiveEventDTO` 仅输出 `safeText` / `safePayload`
- `PublicExportEventDTO` 仅输出 `publicText` / `publicPayload`

### 12. source reference chain

至少应验证以下引用链：

- action 事件带 `actionId` / `characterId` / `intentType` / `turnId`
- state patch 带 `transactionId` / `stateVersion`
- clue 事件带 `clueId` / `sourceEventSequence` / `sharedBy` / `sharedTo`
- map 事件带 `mapId` / `sceneId` / `transactionId` 或等价引用
- checkpoint 事件带 `checkpointId` / `sourceSequence` / `reason`
- campaign archive 带 `sourceSequences[]`

Journal 必须能回答“这件事为什么发生”，而不只是“存了一段文案”。

### 13. AI / Ops 审计边界

以下内容必须保持 `admin_only` / `never_export`：

- `ai_call_logs`
- raw prompt
- raw response
- provider trace
- token 用量明细
- `spoiler_audits`
- 内部 debug / error 审计

验收时应确认：

- 不进入 Player Journal
- 不进入 public export
- 不进入 public campaign summary

### 14. 前端日志面板与文案

如本轮涉及前端，需确认：

- Host / Player 日志筛选项与后端能力一致
- public / full export UI 区分明确
- restore 确认文案明确要求“会覆盖当前房间状态，且必须填写原因”
- 中文文案无乱码

### 15. 端到端主链路

至少应手动或自动证明以下链路：

1. Host 创建房间。
2. Player 加入、绑定角色、ready。
3. Player 提交行动。
4. 系统完成 AI / 规则裁决。
5. Host timeline 可看到行动、检定、状态 patch、地图变化、回合完成。
6. Player archive 只能看到公开事件和自己的私密结果。
7. Host 创建 checkpoint。
8. Host restore checkpoint，timeline 出现 restore 断点。
9. public export 不包含任何不应公开的字段。
10. full export 仅 Owner / Admin 可取，且仍无 raw secret。

## 生产安全加签条件

以下条件未关闭前，不应给 `生产安全完成`：

- `system_safe` 白名单仍依赖人工维护，尚未沉淀为稳定 registry 策略
- checkpoint snapshot 对间接关系表的覆盖仍存在已知缺口
- restore 后 replay / archive 的长期解释策略仍未完全稳定
- full export 与未来 admin audit export 的长期分层仍未最终定型
- public summary / full summary 的 AI 输入过滤虽已闭环，但长期回归覆盖仍不足
- 前端日志体验、批量回放、长团导出策略仍未成型
