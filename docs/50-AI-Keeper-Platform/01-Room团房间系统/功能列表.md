# Room 团房间系统功能列表

## 模块定位

Room 是 AI-Keeper 的跑团生命周期与成员协作边界。它负责把房主、玩家、角色、剧本、大厅、开局、回合入口和基础权限绑定在同一个房间上下文里。

Room 不负责 AI 裁决、规则结算、世界真相写入、线索剧透控制和投影分层。相关能力由 AI-Keeper、Rule、State、Transaction、Projection、Clue、Journal 等模块承担，Room 只保存它们运行所需的房间归属和生命周期状态。

当前代码锚点：

| 方向 | 当前文件 |
|---|---|
| 房间 REST API | `src/server/router_rooms.py` |
| 玩家入房与 ready | `src/server/player/router_player.py` |
| 房主大厅与 Host 鉴权 | `src/server/host/router_host.py` |
| 回合入口 | `src/server/turn_manager.py` |
| 状态版本基础字段 | `src/server/engine/engine.py`、`src/server/db_adapter.py` |
| 前端开房与大厅 | `src/client/src/pages/HostCreate.tsx`、`HostLobby.tsx` |
| 前端玩家入房与大厅 | `src/client/src/pages/PlayerJoinPage.tsx`、`PlayerLobby.tsx` |
| 现有测试 | `tests/server/test_rooms.py`、`test_room_security.py`、`test_host_room_lifecycle.py`、`test_character_join_import.py`、`test_player_intent.py`、`test_ws_auth.py` |

## 优先级口径

| 优先级 | 含义 |
|---|---|
| P0 | MVP 主链路必需，影响创建房间、玩家加入、ready、开局和进入回合 |
| P1 | 真实网团体验需要，但不阻塞第一条主链路 |
| P2 | 长期组织、运营、迁移或多人管理能力 |
| P3 | 平台化增强能力，等核心链路稳定后再做 |

## P0 MVP 功能

| 功能 | 是否进入 MVP | 当前代码状态 | 依赖模块 | 用户价值 | 验收口径 | 现状风险 |
|---|---|---|---|---|---|---|
| 房主创建房间 | 是 | 已有 `POST /api/rooms`，要求 host/admin 登录并选择 `scenario_id` | User、Module | 房主能从剧本创建一场跑团 | host/admin 创建成功返回 `room_id`、`owner_token`、`status=lobby` | 错误文案存在乱码，需要统一 UTF-8 文案 |
| 管理员代建房间 | 是 | admin 可通过 `owner_account_id` 指定房主 | User、Admin/Ops | 管理员可协助组织房间 | admin 创建房间后 owner 归属正确 | 需确保玩家角色不能创建房间 |
| 查询公开房间信息 | 是 | 已有 `GET /api/rooms/{room_id}`，不返回 `owner_token` 和 `owner_account_id` | User、Safety | 玩家可确认房间与剧本，Host 可刷新大厅 | 返回房间状态、剧本标题、玩家数和玩家 ready 摘要 | 公开信息必须持续脱敏，不能泄露房主令牌 |
| 选择或切换剧本 | 是 | 已有 `GET /scenario-options` 与 `PATCH /scenario`，仅 owner/admin 可用 | Module、Safety | 房主可在开局前调整剧本 | lobby/draft/paused 可切换，active/completed/archived 拒绝 | paused 能否切换剧本需后续产品口径收紧 |
| 玩家加入房间 | 是 | 已有 `POST /api/player/rooms/{room_id}/join-with-character` | User、Character | 玩家用房间码进入指定跑团 | 正确房间码、玩家昵称、唯一角色来源可换取 `player_token` | 当前没有一次性邀请码或签名校验，只是房间码加入 |
| 玩家绑定角色 | 是 | 支持预设、上传 xlsx、角色构筑器、剧本模板、复制角色 | Character、WorldBook | 入房时完成调查员身份绑定 | 加入后写入 `characters`，返回 `character_id`、`player_token`、角色摘要 | 角色能力细节归 Character 模块，Room 只校验来源数量 |
| 入房速率限制 | 是 | `_check_rate_limit` 默认同 IP 每分钟 5 次 | Safety | 降低房间码撞库和刷入房请求 | 超过限制返回 429 | 当前为进程内内存限制，多实例部署时需要集中式限制 |
| 大厅 ready | 是 | `ready_toggle` 通过 `/api/player/intent` 进入 Engine 后切换 `is_ready` | Player Client、Engine | 玩家自行确认准备完成 | 玩家 token 有效时可切换 ready，Host/Player 大厅可见 | 当前 ready 不强制检查角色适配报告，适配由 Character 模块负责 |
| 大厅状态同步 | 是 | 加入和 ready 后广播 `s2c_room_lobby_snapshot`，前端有 WS 与轮询兜底 | Projection、Host Client、Player Client | Host 和玩家看到同一大厅进度 | 新玩家加入、ready 变化、开局均推送 snapshot | active join 审批后是否广播需要补验 |
| 开始游戏 | 是 | 已有 `POST /api/rooms/{room_id}/start`，owner token、owner account 或 admin 可用 | Rule、Transaction、Timeline | 房主从大厅进入正式跑团 | 有剧本、至少一名玩家、所有玩家 ready 时变为 `active` | 接口里 `scenario_title` 变量存在潜在未定义风险，需要工程复核 |
| 强制开局 | 是 | `force_start: true` 可跳过未 ready 或空房检查 | Safety、Journal | 房主在演示、补救、测试场景中可急救开局 | 默认 start 不跳过检查，显式 force 才可绕过 | 必须记录为房主急救行为，不能变成普通开局路径 |
| 首回合创建 | 是 | start 后通过 `TurnManager._create_turn` 创建第一回合 | Transaction、Rule | 开局后玩家行动能进入回合收集 | 返回 `turn_id`、`turn_index`，房间为 active | 回合细节归 Transaction/Rule，不在 Room 内继续扩展 |
| 开局初始化副作用 | 是 | start 时尝试初始化地图状态、创建自动 checkpoint、广播 active snapshot | Scene/Map、Journal、Projection | 开局后 Host/Player/地图/日志同步进入正式状态 | map confirmed 时初始化；checkpoint 创建失败不阻塞开局 | 失败目前以 warning 处理，DeepSeek 需确认是否足够可观测 |
| 进行中加入审批 | 是 | active 房间加入会创建 `pending_approval`，Host 有 approve/reject 接口 | Host Client、Character、Safety | 跑团中途补人不直接进入场内 | active join 不直接成为正式成员，需房主审批 | approve/reject 当前缺少明显大厅广播和前端闭环 |
| 房主有限急救 | 是 | Host 有 pause/reset/retry-turn，Room 有 turn retry/skip-character | Transaction、State、Journal | 直播或跑团中出现异常时可恢复节奏 | 急救动作必须经过 owner/admin 鉴权 | 不能让房主绕过 Engine 直接改世界真相 |
| 房间权限边界 | 是 | owner token、account owner、admin 三类鉴权并存 | User、Safety | 支持本地令牌兼容和正式账号体系 | 玩家不能创建/开始/管理房间，公开 DTO 脱敏 | owner token 是高敏凭证，前端存储与泄露风险需持续控制 |
| 基础断线恢复入口 | 是 | 玩家可通过 account 恢复角色 session，也有 player sync | User、Player Client | 手机刷新或换端后可找回身份 | 登录账号下的角色可恢复 `player_token` | 游客模式恢复能力有限，长期需设备绑定或一次性恢复码 |

## P1 真实网团体验功能

| 功能 | 是否进入 MVP | 当前代码状态 | 依赖模块 | 用户价值 | 验收口径 | 现状风险 |
|---|---|---|---|---|---|---|
| 房间公告 | 否 | 未独立实现，当前可用 team-message 近似沟通 | Channel、Journal | 房主固定展示规则、时间、注意事项 | 公告可编辑、置顶、进入日志 | 不应和普通聊天混为同一权威信息 |
| 房间密码 | 否 | 未实现 | User、Safety | 私密团减少误入 | 无密码或密码错误不能加入 | 与房间码、邀请签名的优先级需统一 |
| 白名单入房 | 否 | 未实现 | User、Schedule | 控制只有受邀账号可加入 | 非白名单账号无法入房 | 游客模式与白名单存在产品冲突 |
| 旁观者模式 | 否 | 未实现 | Projection、Host Client、Safety | 支持观众看公共舞台 | 旁观者只看公共投影，不能提交行动 | 必须避免剧透和私密事件泄露 |
| 房间 Session 归档 | 否 | 已有 archive/replay/checkpoint 相关能力，但 Room 文档尚未统一口径 | Journal、Timeline | 长团按场次复盘 | 每次 session 有开始、结束、摘要、事件索引 | 当前 Room 没有显式 session 表达，需要 Journal/Timeline 协同 |
| 房间模板 | 否 | 未实现 | Module、Rule、Character | 快速创建不同规则或玩法默认配置 | 选择模板后生成默认设置 | 模板不应覆盖剧本导入产生的关键资产 |
| 房间复制 | 否 | 未实现 | State、Asset、Module | 复用配置和剧本开新团 | 复制后新房间不共享玩家私密数据 | 必须严格排除旧团状态和私密线索 |
| 房间备份 | 否 | 未实现 | Journal、Admin/Ops | 降低长团数据丢失风险 | 可生成可恢复备份包 | 备份包必须有权限与脱敏策略 |

## 核心边界

- Room 是生命周期和成员边界，不是世界真相边界。世界真相由 State/Engine 管理。
- 玩家不能直接写房间状态，只能提交受控 intent 或通过受控入房接口改变成员状态。
- Host 可以创建、开始、暂停、急救房间，但不能借 Room 能力读取完整 KP 真相。
- AI 不直接创建房间、不直接开始房间、不直接写 Room 表；AI 只能通过核心链路给建议或产出待校验结果。
- 公开房间信息必须脱敏，`owner_token`、账号归属、玩家 token、私密线索、模组真相不得出现在公共 DTO。
- 所有影响跑团主链路的状态变化都应有事件或日志可追踪，不能只保存在前端本地状态。

## 第一轮落地判断

第一轮 Room 模块只追求一条稳定主链路：

`Host 登录 -> 创建房间 -> 玩家加入并绑定角色 -> 玩家 ready -> Host 开局 -> 房间 active -> 创建首回合 -> Host/Player 收到状态变化`

房间密码、白名单、旁观者、候补、复制、导入导出、社区招募、付费能力全部放在后续批次。DeepSeek 执行时不得把这些长期平台能力混入 P0 修复。
