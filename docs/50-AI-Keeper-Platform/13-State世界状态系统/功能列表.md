# State 世界状态系统功能列表 V2.0

## 模块定位

State 是 AI-Keeper 跑团世界的权威状态写入层，负责管理房间状态版本、角色运行时状态、场景状态、地图状态、线索/背包/遭遇等可变状态的持久化和可追溯变更。它承接 Rule/Engine 的权威结果，不接受 AI、Host、Player 直接把建议写成事实。

本模块的第一原则是：规则和 AI 可以产生变更请求，只有受控 State 写入路径能落库；Projection 只能投影已确认状态；Journal 记录状态变更证据链；Player 重连时必须通过 state version 屏障避免旧 patch 覆盖新状态。

## 当前代码真实锚点

| 能力 | 当前文件 | 现状判断 |
| --- | --- | --- |

| 状态变更模型 | `src/server/models.py` | 已有 `StateChangeSet`、`CharacterMutationItem`、`SceneChange`、`MapChangeItem` 等。 |
| 房间版本 | `rooms.state_version` | Engine 和 StateService 都会推进版本，语义仍需收口。 |
| 角色运行时状态 | `character_runtime_state` | 已从 `characters.xlsx_data` 初始化，HP/SAN/MP/Luck 可独立变更。 |
| 长期角色档案 | `character_profiles` | 初始化时可从账号角色创建 profile，后续长期成长未完整产品化。 |

| 遭遇状态 | `encounters`、`encounter_participants` | 有独立 persistence；`StateService` 明确拒绝 `encounter_changes`。 |
| 玩家同步 | `src/server/player/router_reconnect.py`、`/api/player/sync` | 已返回 `stateVersion`，但 patch 版本字段和 runtime 快照仍需增强。 |

| Checkpoint | `src/server/events/event_log.py` | 可快照/恢复部分状态表，但间接关系和 runtime 表覆盖仍需复核。 |

## 核心数据对象

| 对象 | 归属 | 用途 | 边界 |
| --- | --- | --- | --- |
| `rooms.state_version` | State | 房间级全局状态版本，用于意图提交、patch、重连屏障。 | 只有真实状态变更才应推进。 |
| `character_runtime_state` | State | 每房间角色 HP/SAN/MP/Luck/status/temp modifiers。 | 运行时真相，不再回写 `xlsx_data`。 |
| `character_profiles` | Character/State | 跨房间长期角色资料和成长。 | 不作为当前房间即时 HP/SAN 真相。 |
| `room_scene_state` | State/Scene | 当前场景、已访问场景、触发器、公开事实、场景变量。 | 不存隐藏真相全文。 |
| `room_map_state` | Scene/Map/State | 地图探索、隐藏节点、地图局部版本。 | 需和房间版本、投影事件保持一致。 |
| `character_map_positions` | Scene/Map/State | 角色在地图节点的位置。 | Host 强制移动也必须写事件和版本。 |
| `clues`、`clue_shares` | Clue/State | 线索获得、私密/公开、分享记录。 | 线索真相与可见文本由 Clue/Safety 管。 |
| `inventory` | Character/State | 道具获得、移除、数量、来源。 | 私密道具不能提前公开投影。 |
| `encounters`、`encounter_participants` | NPC/Scene/State | 战斗/追逐的运行状态。 | 当前仍由 encounter persistence 管，需逐步纳入统一版本。 |
| `events` | Journal | 记录 `s2c_state_patch`、`s2c_scene_sync` 等变更证据。 | Journal 记录事实，不替代 State 写入。 |

## P0 MVP 功能

| 功能 | 当前状态 | 进入 MVP | 依赖模块 | 验收口径 |
| --- | --- | --- | --- | --- |
| 单一权威状态源 | 已有 `StateService`，但直写路径仍多 | 是 | Engine、Rule | HP/SAN/MP/Luck、背包、线索、地图等变更最终走统一服务或明确封装。 |
| 角色运行时初始化 | 已有 `initialize_character_state` | 是 | Character | 玩家入房/上传角色后创建 runtime state，重复调用不重复插入。 |
| 角色运行时 mutation | 已支持 HP/SAN/MP/Luck/max/status/temp | 是 | Rule、AI-Keeper | 数值 clamp 到合法范围，runtime version 递增，`xlsx_data` 不被改写。 |
| 房间 `state_version` | 已有并会递增 | 是 | Player Client、Projection | 每次真实状态变更递增一次，patch 和 snapshot 携带版本。 |
| 意图提交版本冲突 | Engine 已检查 `base_state_version` | 是 | Player Client | 旧版本意图返回 conflict 和 current_version。 |
| State patch 事件 | 已写 `s2c_state_patch` | 是 | Projection、Journal | patch 包含 actionId、baseStateVersion、stateVersion、patches 和可见性范围。 |
| 持久化先于投影 | 当前需修正 | 是 | Transaction、Projection | 状态先落库并获得版本，再投影 Host/Player patch。 |
| Player runtime 读模型 | 部分接口仍读 `xlsx_data` | 是 | Player Client | `/api/player/sync`、角色面板、行动回执读取 runtime state。 |
| Host HUD runtime 读模型 | 已优先读 runtime | 是 | Host Client | Host HUD 显示最新 HP/SAN/status，不依赖旧快照。 |
| 场景状态 | 已有 `room_scene_state` | 是 | Scene/Timeline | 切场景写 scene state、事件和版本。 |
| 重连版本屏障 | 文档已有方向，接口只返回版本 | 是 | Player Client、Projection | snapshot 到达后丢弃旧 patch，按版本应用剩余 patch。 |
| Checkpoint 恢复一致性 | 部分已有 | 是 | Journal | 恢复后 runtime、scene、map、inventory、clue、turn 等状态一致。 |

## P1 强化功能

| 功能 | 当前状态 | 进入 MVP | 依赖模块 | 验收口径 |
| --- | --- | --- | --- | --- |
| 空变更不推进版本 | 当前空 `StateChangeSet` 也会 bump | 是 | Projection | 无实际 applied 内容时不递增 `state_version`，或显式标记为 heartbeat。 |
| map/clue/inventory pass-through 收口 | 当前混合直接写和 pass-through | 是 | Map、Clue、Character | 所有写入统一返回 applied、events、stateVersion。 |
| 线索分享 State 写入修正 | `StateService` 插 `clue_shares` 缺 public_version | 是 | Clue | 线索分享写入满足表约束，并写来源事件。 |
| 地图版本统一 | 地图有独立 state_version | 是 | Scene/Map、Projection | 地图变更同步推进房间版本或明确双版本字段。 |
| 遭遇状态接入策略 | 当前 `encounter_changes` raise | 是 | NPC/Faction、Rule | 明确继续独立 persistence，或纳入 StateChangeSet 并补版本/事件。 |
| 直接写库路径盘点 | 已知多处 | 是 | Room、Admin、Host、Player | retroactive item、admin character、host map、encounter、ready 等路径有封装或豁免说明。 |
| State patch 去重 | Pipeline 可能发 patch，StateService 也写 patch | 是 | Projection、Journal | 一次状态变更只产生一条权威 patch 或明确分层事件。 |
| 读模型一致性 | Host/Player/Admin 读取源不同 | 是 | User、Client | 所有当前状态 UI 均读取 runtime/read model，不读取旧 `xlsx_data` 作为权威。 |
| Patch schema 版本 | 暂无 | 是 | Player Client | patch 有 schemaVersion，客户端能拒绝未知格式。 |
| 权限边界 | 部分接口直接改状态 | 是 | User、Safety | Player 只能提交意图，Host/Admin 操作有审计，AI 不能直接写 State。 |

## 不属于 State 的内容

| 内容 | 归属模块 | State 的接口边界 |
| --- | --- | --- |
| 检定成功失败 | Rule | State 接收已结算结果，不掷骰。 |
| AI 是否可信 | AI-Keeper、Safety | State 只接受 Engine 校验后的 change set。 |
| 谁能看到 patch | Projection、Safety | State 提供版本和变更，Projection 分层投影。 |
| 事件审计和导出 | Journal | State 写事件引用，但不负责战报。 |
| 地图显示布局 | Scene/Map、Client | State 只保存探索/位置等事实。 |
| 房间生命周期 | Room | State 可写 room status，但不决定开房/开局流程。 |

## MVP 验收主链路

1. 玩家加入房间后生成 `character_runtime_state`，`xlsx_data` 保持原始角色卡。
2. 玩家提交带 `base_state_version` 的行动，版本冲突时被拒绝并返回当前版本。
3. Rule/Engine 产生 HP/SAN/状态标签变化，StateService 先持久化并递增版本。
4. `s2c_state_patch` 带 `baseStateVersion`、`stateVersion`、`actionId` 和 patches。
5. Player 和 Host UI 都读取 runtime state，显示一致。
6. 玩家断线后重连，snapshot 与 patch 按版本屏障应用，不重复扣血或回滚。
7. Checkpoint 恢复后，角色 runtime、场景、地图、背包、线索和日志可对应。
8. AI、Player、Host 不能绕过 Engine/State 直接把建议写成权威状态。
