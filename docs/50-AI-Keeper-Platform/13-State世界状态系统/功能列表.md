# State 世界状态系统功能列表 V2.1

## 当前阶段

本轮文档对应的是：

- `P0 主链路 + 权威状态写入与版本屏障风险识别版`
- 不是 State 模块的最终生产安全完成版
- 重点先锁定 `权威写入`、`state_version 语义`、`重连版本屏障`、`checkpoint/restore 一致性`

当前已经识别但尚未完全收口的真实风险包括：

- `src/server/engine/state_service.py` 进入 `apply_change()` 就先 bump `rooms.state_version`
- `StateChangeSet()` 为空时，当前测试仍允许 bump 版本
- `src/server/engine/resolution_pipeline.py` 仍存在先投影、后状态落库的时序
- `src/server/engine/engine.py` 在 action 入队时也会 bump `rooms.state_version`
- `src/server/player/router_reconnect.py` 需要 snapshot 时会返回整房间事件，未做玩家可见性裁剪
- `src/server/events/event_log.py` 的 checkpoint 还未完整覆盖 `character_runtime_state`、`room_scene_state`、房间 `state_version`
- 地图、后台角色修改、retroactive item 仍有多条直写路径

## 模块定位

State 是 AI-Keeper 的权威世界状态写入层，负责：

- 接收 Rule / Engine 已确认的状态变化
- 管理房间级 `state_version`
- 持久化角色 runtime、场景、地图、线索、背包等可变事实
- 为 Projection、Reconnect、Journal、Checkpoint 提供统一版本基线

State 不负责：

- 判定检定成功失败
- 决定 AI 建议是否可信
- 决定玩家能看到哪些内容
- 把 Host 舞台播放状态当成世界真相

## 状态数据分层

| 层级 | 数据对象 | 说明 | 边界 |
| --- | --- | --- | --- |
| L0 | `rooms.state_version` | 房间级权威状态版本 | 只随世界真相变化推进 |
| L1 | `character_runtime_state` | 房间内角色实时状态 | 权威 HP/SAN/MP/Luck/status 来源 |
| L2 | `room_scene_state` | 场景推进状态 | 不存隐藏真相全文 |
| L3 | `room_map_state` + `character_map_positions` | 地图探索与位置事实 | 需与房间版本或事件序列可对齐 |
| L4 | `clues` + `clue_shares` + `inventory` | 线索与物品事实 | 可见性由 Clue / Safety / Projection 控制 |
| L5 | `AppliedStateChange` / `s2c_state_patch` | 状态变化结果与对外补丁 | 只能来自已持久化状态 |
| L6 | Player / Host read model | 玩家端和 Host 端读模型 | 不能反向写真相 |
| L7 | `CheckpointState` | checkpoint 快照与恢复基线 | 需要覆盖主链路关键表 |
| L8 | Journal / Audit 引用 | 事件序列、来源链、恢复审计 | Journal 记录证据，不替代 State 写入 |

## `rooms.state_version` 语义

第一轮必须把 `rooms.state_version` 固定为：

- 用于权威世界状态屏障的房间级版本号
- 只在以下变化发生时推进：
  - 角色 runtime 数值 / 状态标签变化
  - 场景状态变化
  - 线索归属 / 分享事实变化
  - 背包物品增删或数量变化
  - 地图探索、显隐、角色位置变化
  - 明确纳入 State 的房间内真相状态变化

第一轮明确不应推动它的内容：

- action 入队
- `ready_toggle`
- typing / chat / 纯 UI 操作
- 纯日志、纯投影、纯舞台播放事件
- heartbeat / no-op

| 角色 runtime 初始化 | 已有 `initialize_character_state()` | 是 | Character | 入房时初始化，重复调用幂等 | 当前 lazy init 会在写链路内独立 commit |

| 版本冲突屏障 | `submit_intent()` 已校验 `base_state_version` | 是 | Room、Player Client | 旧版本意图返回 conflict 和 `current_version` | 当前版本含义不纯 |
| `s2c_state_patch` 契约 | 已有事件类型 | 是 | Projection、Journal | 至少带 `schemaVersion`、`baseStateVersion`、`stateVersion`、`actionId`、`patches` | 当前 payload 缺关键字段 |
| 持久化先于投影 | 当前裁决链路顺序反了 | 是 | Transaction、Projection | 先写 State，后发 Host/Player patch | 断线重连会吃到未落库 patch |
| 重连版本屏障 | 当前只有注释和 `stateVersion` | 是 | Player Client | snapshot 返回 `snapshotStateVersion`，旧 patch 丢弃，缺口触发 full sync | 当前需要 snapshot 时会返回全量事件 |
| checkpoint / restore 最小一致性 | 当前 restore 语义已要求 `confirm + reason` | 是 | Journal、Archive | restore 形成新历史分支，写 `s2c_checkpoint_restored`，Player 只拿安全 snapshot | 快照尚未覆盖 runtime / scene / room state_version |

## 不属于 State 的内容

| 内容 | 归属模块 | State 的接口边界 |
| --- | --- | --- |
| 检定成功失败 | Rule | State 只接收已确认结果 |
| AI 建议是否可信 | AI-Keeper、Safety | State 只接收 Engine 校验后的 change set |
| patch 可见性裁剪 | Projection、Safety | State 提供变化与版本，不决定玩家能看到多少 |
| 导出、战报、证据汇总 | Journal | State 负责写入事实，Journal 负责叙事与归档 |
| 房间开局 / ready / lobby | Room | 这些流程不应滥用房间世界状态版本 |

## MVP 验收主链路

1. 玩家入房后创建 `character_runtime_state`，`characters.xlsx_data` 保持角色卡基线。
2. 玩家提交带 `base_state_version` 的行动，旧版本被拒绝并返回 `current_version`。
3. Rule / Engine 产出状态变化后，State 先持久化真实变化，再推进 `rooms.state_version`。
4. `s2c_state_patch` 至少带 `schemaVersion`、`baseStateVersion`、`stateVersion`、`actionId`、`patches`。
5. Player 与 Host 当前状态都读取 runtime / read model，而不是旧 `xlsx_data`。
6. 断线重连时，snapshot 先落地到客户端，再按版本丢弃旧 patch、补应用新 patch。
7. checkpoint restore 后，runtime、scene、map、inventory、clue、turn、journal 引用能够重新对齐。
8. Player / Host / AI 都不能绕过 Engine / State 直接把建议写成权威状态。
