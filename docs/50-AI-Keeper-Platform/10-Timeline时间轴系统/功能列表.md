# Timeline 时间轴系统功能列表 V2.0

## 模块定位

Timeline 模块负责定义跑团进程中的顺序与时间索引：回合顺序、行动归属、事件 sequence、断线补发游标、Host 审计时间线、Player 可见历史、检查点位置，以及未来的游戏内时间。

Timeline 不保存完整日志内容，日志内容归 Journal；Timeline 不裁决行动成功失败，裁决归 Rule、AI-Keeper、Transaction；Timeline 不直接写世界真相，状态归 StateService。它的价值是让“发生了什么、按什么顺序发生、谁能看到、能否回放”有统一口径。

## 当前代码真实链路

| 链路 | 当前代码锚点 | 现状判断 |
| --- | --- | --- |
| 房间开局创建首回合 | `src/server/router_rooms.py` 的 `start_room` 调 `TurnManager._create_turn` | 已有首回合创建，同时开局会创建 auto checkpoint |
| 回合管理 | `src/server/turn_manager.py` | 已有 collecting、resolving、resolved、blocked 状态和 `turn_index` |
| 玩家提交行动 | `src/server/player/router_player.py` 的 `submit_intent` | active 房间中提交 intent 后绑定当前 turn，并在全员提交后触发结算 |
| 回合自动结算 | `_settle_turn_background` | 顺序 resolve queued actions、生成本轮叙事、标记 resolved、创建下一回合 |
| 事件顺序 | `src/server/engine/projection.py` 和 `src/server/events/event_log.py` | 事件写入 `events.sequence`，作为全局递增房间事件游标 |
| Host 时间线 | `src/server/router_archive.py` 的 `GET /api/rooms/{room_id}/timeline` | Host/owner/admin 可查全量事件，可按 event_type 和 keyword 过滤 |
| 单事件回放 | `GET /api/rooms/{room_id}/timeline/{sequence}` | Host 可按 sequence 获取单个事件 |
| Player 历史 | `src/server/player/router_player_archive.py` 的 `/api/player/archive` | 有类型筛选、keyword、分页，但可见性过滤仍需加固 |
| 断线补发 | `src/server/player/router_reconnect.py`、`src/server/host/ws_manager.py`、`src/server/main.py` | 有 `player_sequences` 和 lastSequence 概念，但补发过滤不够严格 |
| 检查点 | `EventLog.create_checkpoint`、`restore_checkpoint` | 可创建、列出、恢复 snapshot；事件 sequence 在恢复时会重新生成 |
| 前端 Host 日志 | `src/client/src/components/HostLogsPanel.tsx` | 有 Host 事件列表、筛选、checkpoint、导出入口，文案存在乱码 |
| 前端 Player 日志 | `PlayerActionPage.tsx` 内 `PlayerLogsPanel` | 有玩家 archive 查询和本地消息 fallback，分类与后端枚举不完全对齐 |

## 四条时间轴

| 时间轴 | 当前字段 | 归属 | 说明 |
| --- | --- | --- | --- |
| 写入时间 | `events.issued_at`、`actions.created_at`、`completed_at`、`rooms.started_at` | Journal / DB | 真实服务器时间，用于审计和排序辅助 |
| 事件顺序 | `events.sequence`、`EngineEvent.roomSequence` | Projection / Journal | WS、回放、断线补发的主顺序 |
| 回合顺序 | `room_turns.turn_index`、`actions.turn_id` | Timeline / Transaction | 行动收集和批量结算的顺序 |
| 游戏内时间 | 尚未专门建模 | State | 故事里的日期、时刻、倒计时、阵营时钟，未来由 StateService 版本化 |

## 数据对象

| 对象 | 类型 | 说明 |
| --- | --- | --- |
| `room_turns` | 回合状态 | `turn_id`、`room_id`、`turn_index`、status、started_at、resolved_at、summary |
| `actions` | 玩家行动 | 通过 `turn_id` 归属回合，通过 created/completed 记录真实时间 |
| `events` | 投影事件 | 通过 BIGSERIAL `sequence` 记录顺序，payload 保存事件内容 |
| `player_sequences` | 玩家补发游标 | 保存玩家已确认或服务端认为已交付的最后 sequence |
| `checkpoints` | 状态检查点 | 保存 room snapshot，用于回滚和恢复 |
| `campaign_archives` | 团期归档 | 保存结局摘要、highlights、角色弧光 |
| `rooms.started_at` | 房间真实开始时间 | 用于团期 duration 计算 |
| 未来 `gameTime` | 游戏内时间字段 | 可先放入 StateService 管理的房间或场景状态中 |

## P0 MVP 必须稳定

| 功能 | 当前状态 | 进入 MVP | 依赖模块 | 验收口径 |
| --- | --- | --- | --- | --- |
| 房间 active 后有当前回合 | 已在 start_room 创建首回合 | 是 | Room | 开局后存在 exactly one collecting turn |
| 行动绑定当前回合 | active 房间已有 `TurnManager.submit_action` | 是 | Player、Transaction | 玩家行动必须有 `turn_id`，不能留下无回合 queued action |
| 单玩家单回合一次行动 | 已有 duplicate 检查，但顺序存在风险 | 是 | User、Transaction | duplicate 返回 409 时不得写入新 action 或孤儿 action |
| 全员提交触发结算 | 已有 `all_submitted` 自动结算 | 是 | Rule、AI-Keeper | 所有参与者提交或被 Host skip 后，回合进入 resolving 并完成结算 |
| 回合结算幂等 | 当前缺少强锁和状态保护 | 是 | Transaction | 同一 turn 不会被并发 settle 两次，不会创建多个下一回合 |
| 事件 sequence 单调递增 | 已有 `events.sequence` | 是 | Journal、Projection | 同房间事件按 sequence 可稳定分页、补发、回放 |
| Player 时间线可见性过滤 | 已有 archive，但过滤口径偏散 | 是 | Projection、Safety | 玩家只能看到 party/system 安全事件和自己的 player 事件 |
| 断线补发安全过滤 | 当前 reconnect 可能返回全量事件 | 是 | Projection、Player Client | reconnect 不能补发 host-only 或其他玩家 private 事件 |
| Host 时间线鉴权 | 已有 owner/admin 鉴权 | 是 | User、Host Client | 非房主、非 admin 不能读 `/timeline` 和单事件 |
| 检查点顺序可追踪 | 已有 checkpoint 事件 | 是 | Journal、State | checkpoint 创建/恢复有事件记录，恢复后能解释 sequence 变化 |

## P1 第一轮加固

| 功能 | 当前状态 | 进入近期版本 | 依赖模块 | 验收口径 |
| --- | --- | --- | --- | --- |
| `s2c_turn_resolved` 事件注册 | 后端会 emit，但 registry/model 未见定义 | 是 | Projection、Frontend | 事件注册表、Pydantic Literal、前端类型统一包含该事件 |
| 回合参与者集合统一 | 当前取 `joined/ready/active` | 是 | Room、User | pending_approval、left、removed 不参与 all_submitted；ready 状态口径一致 |
| Host skip 审计 | 已有 skip action，但文案乱码且审计不完整 | 是 | Host、Journal | skip 记录操作者、目标角色、turn_id、原因 |
| retry turn 限制 | 已有 retry 接口 | 是 | Host、Transaction | 只能重试 blocked/resolved 中允许的 turn，并避免重复结算副作用 |
| Timeline DTO 固化 | 当前各接口返回字段不完全一致 | 是 | Journal、Frontend | Host timeline、Player archive、Replay 采用稳定字段名 |
| 游戏内时间初版 | 尚未建模 | 是 | State、Scene / Map | 支持手动设置和推进 `gameTime`，不做复杂历法 |
| 事件分类来自 registry | 当前前后端有硬编码 | 是 | Journal、Projection | 筛选项使用 registry/domain，不遗漏新事件 |
| 前端中文文案修复 | HostLogsPanel、PlayerLogsPanel 有乱码 | 是 | Host Client、Player Client | 时间线、检查点、日志筛选文案可读 |

## 不属于本模块

| 不做内容 | 交给哪个模块 | 原因 |
| --- | --- | --- |
| 事件 payload 的完整保存与导出 | Journal | Timeline 只定义顺序和索引口径 |
| 行动成功失败裁决 | Rule、Transaction、AI-Keeper | Timeline 不判断规则结果 |
| 世界真相写入 | State | 游戏内时间也是状态字段，不由 Timeline 直接写 |
| 玩家聊天信息流 | Channel | Team message 会进入事件流，但频道体验归 Channel |
| 团期结局摘要生成 | Journal、AI-Keeper | Timeline 提供顺序，摘要由归档系统生成 |
| UI 视觉布局 | Host Client、Player Client | Timeline 定义数据和行为口径 |

## 当前最高风险

| 风险 | 影响 | 建议优先级 |
| --- | --- | --- |
| active 提交路径先写 action 再判 duplicate | duplicate 后可能留下无 `turn_id` queued action | P0 |
| 回合结算缺少强幂等保护 | 并发触发可能重复 resolve 或创建多个下一回合 | P0 |
| Player reconnect 可能返回全量 events | host-only 或其他玩家私密事件可能泄露 | P0 |
| `EventLog.get_public_events` 使用 `audience != 'player'` | host-only 事件可能被当成 public | P0 |
| `s2c_turn_resolved` 未进入事件注册表和类型定义 | 事件分发、前端类型、日志筛选口径不一致 | P1 |
| `GET /turns/current` 会确保并创建 turn | Host 在非 active 房间查询可能产生多余回合 | P1 |
| 检查点恢复跳过 events.sequence 原值 | 恢复后的事件顺序需要明确为新历史或另建 restore marker | P1 |
| 源码和前端时间线文案存在乱码 | 运维和用户理解成本高 | P1 |
| 游戏内时间未建模 | 真实写入时间和故事时间容易混用 | P1 |

## MVP 验收主链路

1. Host 创建房间，玩家加入并 ready。
2. Host 开局，系统创建第 1 回合。
3. 玩家提交行动，action 绑定当前 `turn_id`。
4. 同一玩家重复提交被拒绝，数据库没有无回合 queued action。
5. 所有参与玩家提交或被 Host skip 后，回合进入 resolving。
6. Engine 顺序结算 queued actions。
7. 回合标记 resolved，系统创建下一 collecting turn。
8. Host 时间线能按 sequence 查到 queued、completed、turn resolved、public observation。
9. Player archive 只能看到公开事件和自己的私密事件。
10. Player 断线重连只补发自己有权看到的事件，并返回正确 last_sequence。
