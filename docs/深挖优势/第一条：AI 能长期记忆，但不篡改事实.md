

这条真正的差异化，不应该被定义为：

> “AI 能记住很长的聊天记录。”

而应该被定义为：

> **AI 维护一份有来源、有权限、有时间状态、可以纠错的战役记忆；它知道什么是事实、什么是证词、什么是猜测、谁知道这件事，以及这件事现在是否仍然成立。**

我建议把这个能力命名为：

# **可信战役记忆**

英文可以叫：

```text
Campaign Memory Ledger
Evidence-backed Campaign Memory
Trusted Campaign Memory
```

一句产品话术可以是：

> **AI 不是记住更多，而是记住得有依据、有边界、可纠正。**

---

# 一、玩家真正需要的不是“AI 什么都记得”

在多人 TRPG 中，“AI 什么都记得”反而可能是危险的。

它可能记得：

- Host-only 的模组真相；
    
- 其他玩家的私密线索；
    
- 已经过期的状态；
    
- NPC 说过的谎言；
    
- 玩家随口提出的猜测；
    
- 被后续剧情推翻的结论；
    
- Checkpoint 恢复前另一条历史分支；
    
- AI 自己曾经生成错的一句话。
    

因此，真正高质量的长期记忆应该回答五个问题：

```text
1. 发生了什么？
2. 谁知道这件事？
3. 我们凭什么认为它是真的？
4. 这件事现在还成立吗？
5. 它是事实、观察、证词，还是猜测？
```

这五个问题就是你们和普通“长上下文 AI”之间最核心的差异。

---

# 二、从玩家角度，这项能力应该给我什么承诺

作为玩家，我需要平台保证：

|玩家关心的问题|平台承诺|
|---|---|
|三个月后回来还记得吗|记得关键事件、线索、NPC、承诺和未完成目标|
|AI 会不会把猜测当事实|不会，事实、证词、推测明确分层|
|AI 为什么这么说|每条关键结论可以追溯来源|
|我的私密线索会泄露吗|不会，不同玩家拥有不同记忆视图|
|NPC 说的话一定是真的吗|不一定，系统记录“NPC 说过”，不自动认为内容真实|
|状态变化后旧信息怎么办|保留历史，但明确当前有效状态|
|AI 记错了怎么办|可以纠错，但不能静默覆盖历史|
|Host 改设定后怎么办|生成正式修订或 Retcon 记录|
|我角色知道这件事吗|系统可以明确回答“知道 / 不知道 / 只知道部分”|
|我忘了上次剧情怎么办|自动生成有证据的“继续战役”摘要|

---

# 三、记忆必须分层，不能只建一个“大记忆库”

建议至少区分六种记忆对象。

|记忆类型|示例|谁能创建|AI 是否能把它当事实|
|---|---|---|---|
|**世界事实**|门已打开、NPC 已死亡、当前 HP 为 8|State、Engine、Host 受控操作|可以，但必须在当前视角可见|
|**历史事件**|玩家在 23:10 打开了地下室门|Transaction、Journal、Timeline|可以作为历史证据|
|**观察结果**|玩家看见教授手在发抖|Engine、Projection、Journal|只能说“观察到”，不能直接推断原因|
|**证词与传闻**|护士说教授从未去过地下室|NPC 对话、玩家发言|只能说“护士声称”，不能认为内容真实|
|**玩家推测**|玩家怀疑教授是邪教成员|玩家笔记、证据板|不能当作世界事实|
|**AI 摘要**|“队伍目前怀疑教授与地下室有关”|AI 派生生成|只是摘要，不能成为新的权威来源|

这里最重要的一条是：

> **“某人说了什么”可以是事实，但“他说的内容”不一定是真相。**

例如：

```text
事实：
护士在事件 #512 中说：
“教授从来不去地下室。”

不一定是事实：
教授从来不去地下室。
```

AI 必须理解这两者的区别。

---

# 四、建议建立“事实账本 + 认知账本 + 推测账本”

为了让产品概念更清晰，可以把整个系统理解为三本账。

## 1. 事实账本

记录世界当前真正发生和成立的事情：

```text
当前房间状态
角色当前 HP / SAN / Luck
NPC 生死和位置
地图节点状态
门是否打开
线索是否生成
物品归属
当前场景
当前游戏时间
```

来源主要是：

```text
13-State
14-Transaction
09-Map
08-Clue
10-Timeline
11-Journal
```

AI 不能直接写事实账本。

---

## 2. 认知账本

记录“谁知道什么”。

同一件世界事实，对不同人可能是不同状态：

```text
Host：知道完整真相
玩家 A：亲眼见过
玩家 B：听 A 分享过公开版本
玩家 C：完全不知道
Party：只知道公共摘要
Public：不能知道
```

认知账本至少需要记录：

```text
knowledgeId
subject
knownBy
knowledgeScope
sourceEventSequence
sharedBy
sharedAt
publicVersion
privateVersion
```

这实际上是你们现有这些模块的组合：

```text
08-Clue
15-Projection
21-Safety
11-Journal
```

但目前还缺一个统一的“谁知道什么”的产品视图。

---

## 3. 推测账本

记录玩家自己的判断，但绝不升级成世界事实。

例如：

```text
事实：
教授进入过地下室。

证词：
护士说教授从不去地下室。

玩家 A 的推测：
护士在撒谎。

玩家 B 的推测：
有人伪装成教授。

AI 建议：
当前存在身份冒用或证词矛盾的可能。
```

推测账本可以用于：

- 私人笔记；
    
- 队伍证据板；
    
- 未解决问题；
    
- AI 整理不同假说；
    
- 标记已证实、已证伪、仍未知。
    

但 AI 不能说：

> “护士确实在撒谎。”

除非已经存在正式证据。

---

# 五、每一条记忆都应该带来源

这是可信记忆和普通 AI 摘要最本质的区别。

建议定义一个统一的记忆声明对象：

```json
{
  "claimId": "claim_xxx",
  "roomId": "room_xxx",
  "subject": {
    "type": "npc",
    "id": "npc_professor"
  },
  "predicate": "entered_location",
  "value": {
    "locationId": "basement"
  },
  "epistemicStatus": "confirmed",
  "visibility": {
    "scope": "party",
    "characterId": null
  },
  "validFromSequence": 481,
  "validToSequence": null,
  "sourceRefs": [
    {
      "type": "event",
      "sequence": 481
    },
    {
      "type": "map",
      "mapVersion": 12
    }
  ],
  "createdBy": "engine",
  "supersedes": null,
  "createdAt": "..."
}
```

其中最重要的字段是：

```text
epistemicStatus
visibility
validFromSequence
validToSequence
sourceRefs
createdBy
supersedes
```

# 六、记忆状态不能只有 true / false

建议给记忆声明固定一套“认知状态”。

|状态|含义|
|---|---|
|`confirmed`|已由权威状态或正式事件确认|
|`observed`|某角色观察到，但未必知道完整原因|
|`reported`|某人声称或转述|
|`inferred`|根据证据推导出的可能结论|
|`hypothesis`|玩家或 AI 提出的假说|
|`disputed`|存在互相冲突的信息|
|`disproven`|已被后续证据否定|
|`superseded`|曾经成立，但已被新状态替代|
|`unknown`|当前没有足够证据|

AI 回答时必须把状态表现出来。

不应该说：

> 教授从不进入地下室。

应该说：

> **护士声称**教授从不进入地下室，但队伍后来在事件 #481 中确认教授曾进入地下室，因此该证词目前存在矛盾。

---

# 七、AI 不能直接创建“已确认事实”

这是工程上最重要的一条硬边界。

建议写成以下权限矩阵：

|内容|AI 可生成|AI 可直接写入权威记忆|
|---|--:|--:|
|剧情摘要|可以|不可以|
|线索整理|可以|不可以|
|NPC 关系推测|可以|不可以|
|玩家行动意图摘要|可以|不可以|
|机制建议|可以|不可以|
|世界状态变化|只能建议|不可以|
|新线索真相|只能建议|不可以|
|玩家推测|可以记录为 hypothesis|不可以升级为 confirmed|
|矛盾提醒|可以|不可以自行裁决哪个是真相|

权威事实只能来自：

```text
StateService
RuleExecutor
Transaction
ClueService
MapStateService
正式 Host 操作
Checkpoint / Restore
经过校验的 Engine 事件
```

AI 只能产生：

```text
candidate claim
summary
inference
hypothesis
contradiction warning
```

---

# 八、纠错不能静默覆盖，必须形成修订链

普通 AI 记忆系统最危险的行为是：

```text
原来记成 A
后来直接覆盖成 B
最终没人知道为什么变了
```

你们应该使用追加式修订：

```text
旧声明仍保留
新声明 supersedes 旧声明
旧声明标记 validToSequence
新声明标记 validFromSequence
形成 correction / retcon 事件
```

建议区分三种纠错。

## 1. 展示纠错

例如人名错别字、乱码、翻译问题。

```text
不改变世界事实
只修正显示文本
保留内部实体 ID
```

## 2. 事实修订

例如 Host 发现某 NPC 的位置被错误写入。

```text
创建 correction event
记录 actor
记录 reason
记录 before / after
更新当前状态
保留旧历史
```

## 3. 剧情 Retcon

例如 Host 正式修改已经发生的设定。

```text
必须显式确认
必须有 reason
写 retcon event
说明哪些事实被替代
说明哪些线索、NPC、地图、摘要需要重新计算
```

AI 不能偷偷帮 Host 把历史改干净。

---

# 九、Checkpoint 恢复也不能让 AI“忘记历史”

你们在 Timeline、Journal、State 中已经定义：

```text
Restore 不是删除旧历史
而是从 Checkpoint 开出新的历史分支
```

可信记忆必须继承这个规则。

例如：

```text
原历史：
事件 100 -> 150 -> 200

恢复到 Checkpoint 120 后：
事件 100 -> 120
               \
                -> checkpoint_restored -> 201 -> 202
```

AI 回答当前事实时，只使用当前分支。

但 Host 查审计时，仍可以看到旧分支发生过什么。

玩家端则只能看到当前视角允许的安全内容。

# 十、检索不能只是向量相似度搜索

只做普通 RAG 会出现四个问题：

```text
检索到已过期状态
检索到 Host-only 真相
检索到其他玩家私密信息
检索到玩家推测并当成事实
```

正确流程应该是：

```text
玩家提出问题
    ↓
识别 viewer / character / room / current branch
    ↓
权限过滤
    ↓
当前状态过滤
    ↓
历史时间过滤
    ↓
事实等级过滤
    ↓
检索相关证据
    ↓
生成带来源和不确定性标签的回答
```

向量检索只能负责：

```text
找相关内容
```

不能负责：

```text
判断内容是否真实
判断玩家是否有权知道
判断内容是否已经过期
判断它是事实还是猜测
```

# 十一、玩家端应该出现哪些核心功能

## 1. “继续战役”首页

玩家每次回来首先看到：

```text
上次游戏时间
当前地点
当前游戏内时间
队伍当前目标
我的角色目标
最近获得的线索
重要 NPC 变化
未解决问题
我的 pending action
下一步建议回顾
```

示例：

> **上次停在：圣玛丽医院地下档案室**  
> 游戏时间：1926 年 11 月 14 日 23:40
> 
> 队伍目标：查明失踪病人的共同点。  
> 你的角色已知：烧焦处方上的签名与院长办公室相同。  
> 尚未确认：地下脚步声是否来自教授。  
> 未解决问题：护士为何否认教授进入过地下室？

注意最后一句是“尚未确认”，不是“真相”。

---

## 2. “问战役”功能

玩家可以问：

```text
我们第一次见到教授是什么时候？
我的角色知道地下室密码吗？
护士说过哪些互相矛盾的话？
目前有哪些确认事实？
我们有哪些仍未证实的猜测？
这把钥匙是谁发现的？
为什么 AI 认为教授可疑？
```

回答必须带来源：

> 队伍第一次见到教授是在事件 #182，对应第二次 Session 的医院接待室场景。  
> 你的角色当时在场，因此该信息属于你的已知记忆。

---

## 3. 事实标签

所有关键内容都应该有标签：

```text
已确认
亲眼观察
听闻
玩家推测
AI 推导
存在争议
已证伪
已过期
Host-only
本人私密
队伍公开
```

这会显著提升玩家对 AI 的信任。

---

## 4. “为什么 AI 记得？”

每个 AI 回答旁边可以展开：

```text
来源：
事件 #481
线索 clue_017
地图版本 12
玩家 A 于事件 #497 分享
当前状态版本 43
```

这比单纯显示“AI 记忆”有价值很多。

---

## 5. “我的角色知道吗？”

这是非常适合 TRPG 的独特功能。

玩家点击某个 NPC、地点、物品或线索，可以看到：

```text
世界中是否存在这件事：未知
你的角色是否知道：知道
队伍是否知道：部分知道
你是如何知道的：事件 #481 中亲眼观察
是否已经分享：已于事件 #497 分享
```

这项功能会成为你们非常有辨识度的能力。

---

## 6. Session 结束后的“记忆差异”

每局结束自动生成：

```text
本局确认的新事实
本局获得的新线索
本局被推翻的猜测
NPC 状态变化
地图变化
角色状态变化
新产生的未解决问题
哪些私密信息已分享
```

这不是普通总结，而是“记忆账本变化”。

# 十二、一个完整场景示例

假设剧情中发生以下事情：

```text
1. 玩家 A 私下看见教授进入地下室。
2. 玩家 A 猜测教授是邪教成员。
3. 护士公开声称教授从不进入地下室。
4. 玩家 A 把“教授进入地下室”分享给队伍。
5. Host-only 真相是教授进去救人，并不是邪教成员。
```

系统应该记录：

|内容|类型|可见范围|
|---|---|---|
|A 看见教授进入地下室|observed|A 私密|
|A 怀疑教授是邪教成员|hypothesis|A 私密|
|护士说教授从不进入地下室|reported|Party|
|A 分享教授进入地下室|confirmed observation|Party|
|教授实际进去救人|host-only truth|Host|

此时玩家 B 问：

> “我们目前知道教授和地下室有什么关系？”

正确回答应该是：

> **已确认：**玩家 A 曾看见教授进入地下室，该信息后来已向队伍分享。来源：事件 #481、#497。
> 
> **证词：**护士声称教授从不进入地下室。来源：事件 #512。
> 
> **矛盾：**护士的说法与玩家 A 的观察冲突。
> 
> **尚未知：**教授进入地下室的目的目前没有公开证据。

不能回答：

> 教授进入地下室是为了救人。

因为这是 Host-only 真相。

也不能回答：

> 教授是邪教成员。

因为这只是玩家 A 的推测。

# 十四、是否需要新增一个独立 Memory 模块

我认为值得新增，但它不能成为第二个 State。

可以定义为：

# **Memory / Knowledge 可信记忆与认知系统**

它应该是：

```text
只读派生层
证据索引层
认知投影层
AI 检索入口
```

它不应该：

```text
直接写世界状态
替代 Journal
替代 Clue
替代 Projection
让 AI 创建世界事实
```

推荐结构：

```text
State / Timeline / Journal / Clue / Map
                ↓
         Memory Compiler
                ↓
       Memory Claim Index
                ↓
     Viewer-aware Memory View
                ↓
        AI Query / Resume UI
```

AI 生成的摘要可以随时重建。

真正不可替代的是：

```text
权威事件
状态版本
来源引用
认知归属
修订历史
```

# 十五、实施优先级

## P0：形成核心差异化

|功能|原因|
|---|---|
|Memory Claim 数据结构|所有可信记忆的基础|
|事实 / 观察 / 证词 / 推测分类|防止 AI 把推测当事实|
|每条事实带 sourceRefs|支持解释与复核|
|玩家 / Party / Host 认知视图|防止跨视角泄密|
|当前事实与历史事实分离|防止旧状态覆盖新状态|
|“继续战役”卡片|玩家最直接感知价值|
|“问战役”带来源回答|差异化核心体验|
|Host 纠错 / Retcon 流程|防止错误永久污染记忆|
|AI 禁止直接写 confirmed fact|产品信任底线|

## P1：形成强壁垒

|功能|价值|
|---|---|
|矛盾检测|自动发现证词和事实冲突|
|未解决问题追踪|长团推进神器|
|NPC 关系和承诺时间线|提升人物连续性|
|私人笔记与假说|保留玩家推理权|
|队伍证据板|支持共同调查|
|Session Memory Diff|显示本局新增和推翻内容|
|“我的角色知道吗”|独特且强 TRPG 属性|
|分享前后知识差异|显示谁知道、何时分享|

## P2：形成高级体验

```text
角色失忆、精神异常等特殊认知规则

不可靠叙事

跨战役世界设定记忆
Host 自定义记忆保留策略
长期 NPC 关系趋势
```

# 十六、工程验收不能只测“AI 能回答”

至少要验证：

```text
1. AI 不能把玩家 hypothesis 当 confirmed fact。
2. 玩家 A 私密线索不能出现在玩家 B 回答里。
3. Host-only truth 不能进入 Player memory。
4. NPC 证词必须保留 reported 状态。
5. 已过期状态不会作为当前状态回答。
6. 每条 confirmed claim 必须有 sourceRefs。
7. AI 不能直接创建 confirmed claim。
8. 修订必须保留旧记录和 supersedes 关系。
9. Checkpoint restore 后使用当前分支事实。
10. “不知道”是合法回答。
11. 摘要删除后可以从底层证据重新生成。
12. 同一个问题在 Host、Player A、Player B 视角下答案不同。
```

最关键的安全测试是：

```text
同一个问题
同一个房间
不同 viewer
得到不同但各自正确的答案
```

# 十七、衡量这项差异化是否成功

不要只统计“记忆库有多少条”。

建议看这些指标：

|指标|目标方向|
|---|---|
|无来源事实回答率|越接近 0 越好|
|跨玩家私密信息泄露|必须为 0|
|Host-only 真相泄露|必须为 0|
|AI 直接写 confirmed fact|必须为 0|
|关键事实 sourceRef 覆盖率|接近 100%|
|错误记忆纠正后仍复发率|越低越好|
|玩家回归后理解当前局面的时间|越短越好|
|Host 每局手工整理时间|显著下降|
|“不知道 / 证据不足”正确回答率|应允许且准确|
|玩家对 AI 记忆可信度评分|持续提升|

一个非常实际的体验目标可以是：

> **玩家间隔一个月回来后，在 60 秒内能够知道：自己在哪里、队伍在做什么、掌握了什么、还缺什么、下一步可以做什么。**

# 十八、真正的竞争壁垒在哪里

这项能力的壁垒不是模型本身。

模型可以更换，Provider 可以更换，Prompt 也可以被模仿。

真正难复制的是长期积累的：

```text
事件证据链
状态版本
认知归属
线索分享关系
时间有效性
修订历史
玩家推测和事实边界
```

也就是说，你们最终积累的不是一堆聊天记录，而是一张：

# **可追溯的战役认知图谱**

普通 AI 可以“总结这场团”。

你们的平台应该能够回答：

```text
这件事是否真的发生过？
谁亲眼看见？
谁只是听说？
谁现在知道？
哪个证据支持？
什么时候开始成立？
后来是否被推翻？
当前分支还有效吗？
```

这才是难以替代的差异化。

# 这一条最终可以收敛成一句产品定义

> **AI-Keeper 维护的不是聊天记忆，而是一份可追溯的战役认知账本：每条记忆都有来源、权限、时间和可信状态；AI 可以整理和解释，但不能把猜测升级为事实，也不能静默改写历史。**

下一条可以继续挖：

> **AI 能理解自然语言，但结算透明。**
