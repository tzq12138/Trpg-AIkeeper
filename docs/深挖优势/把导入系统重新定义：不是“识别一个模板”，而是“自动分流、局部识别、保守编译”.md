
你指出的是关键问题：

> **不能把作者提供规范素材包或 `module.yaml` 当成前提。**

现实里的旧模组通常是：

```text
一本双栏 PDF
+ 若干扫描图片
+ 一个 NPC Excel
+ 单独的地图文件
+ 手写勘误
+ 不规则命名的 Handout
+ 不同版本的补充资料
```

甚至只有一个扫描 PDF。

所以，作者 Manifest 应当只是“有则优先使用”的增强能力；平台真正的主路径必须是：

# **零 Manifest 自动导入**

```text
用户把拥有的全部资料拖进来
→ 系统自动识别文件形态
→ 自动判断每份资料的角色
→ 自动归纳当前文档自己的排版模板
→ 按页、章节、表格和图片分别走不同处理器
→ 跨文件对齐人物、地点、线索、规则和素材
→ 高置信度内容自动编译
→ 低置信度内容保守隔离
→ 用户几乎不需要阅读剧本内容
```

这里最重要的不是“AI 抽取准确率达到 100%”，而是：

> **不确定时宁可少自动化，也不猜错、不泄密、不要求用户读完整剧本。**

# 一、“模板”其实有四种，不能用一个分类器解决

之前把它统称为“模板识别”还不够清楚。系统实际上要分别判断四个问题。

|层级|要判断什么|示例|决定什么|
|---|---|---|---|
|**格式模板**|文件技术形态|数字 PDF、扫描 PDF、DOCX、XLSX、图片包|使用哪个解析器|
|**排版模板**|页面怎样组织信息|双栏、地点编号页、NPC 卡片、彩色主持框|阅读顺序和区域切分|
|**资料角色**|这份资料是做什么的|核心剧本、地图册、勘误、规则补充、Handout|权威性、可见性和覆盖关系|
|**剧情结构模板**|模组怎样运行|调查型、地点探索型、线性场景型、沙盒型|抽取哪些运行时对象|

这四层必须独立判断。

例如同一个文件：

```text
格式：PDF
排版：双栏 + 彩色朗读框 + NPC 数值块
资料角色：核心剧本
剧情结构：前半调查、后半地点探索
```

所以系统不能得出：

```text
这是 PDF → 用 PDF 模板
```

而应该得出：

```text
第 1—30 页：背景与调查资料
第 31—65 页：地点编号探索
第 66—72 页：NPC 附录
第 73—78 页：玩家 Handout
```

**分流粒度必须下沉到页、章节、区域和表格，不能只给整本书贴一个标签。**

视觉丰富文档中的文字、页面图像和布局都会影响分类与理解，不能只提取纯文本；LayoutLMv3 一类文档模型正是把文字与图像布局联合建模。Docling 也采用布局分析和表格结构识别，将多种文档转换成统一、结构丰富的表示。([arXiv](https://arxiv.org/abs/2204.08387 "[2204.08387] LayoutLMv3: Pre-training for Document AI with Unified Text and Image Masking"))

# 二、最终导入管线应该长这样

```text
用户上传一个或多个文件
        ↓
1. Package Inventory
   文件清单、安全扫描、格式探测、哈希、重复检测
        ↓
2. Format Router
   PDF / Scan / DOCX / XLSX / Image / JSON 分流
        ↓
3. Document Profiler
   页面布局、章节结构、语言、规则系统、文本密度
        ↓
4. Template Router
   已知模板匹配
   → 文档本地模板归纳
   → 通用解析 fallback
        ↓
5. Source Role Classifier
   核心剧本 / 勘误 / NPC 表 / 地图 / Handout / 规则补充
        ↓
6. Section Router
   每页、每章节、每表格、每图片分别选择语义抽取器
        ↓
7. Semantic Candidate Extraction
   Scene / NPC / Clue / Rule / Trigger / AssetBinding
        ↓
8. Cross-Source Resolver
   跨 PDF、Excel、地图、图片、勘误进行对齐
        ↓
9. Risk × Confidence Gate
   自动接受 / 参考资料 / 隔离 / 阻断
        ↓
10. Machine Verification
    独立验证、Schema 校验、引用校验、剧透检测
        ↓
11. Minimal Blind Review
    仅在必要时提出不剧透的少量问题
        ↓
12. Compile Immutable ModuleVersion
        ↓
13. 生成运行时专用视图
```

# 三、第一步不是让 AI 看内容，而是做技术画像

每个文件先生成一个 `SourceTechnicalProfile`。

```json
{
  "sourceId": "src_001",
  "detectedFormat": "pdf",
  "pdfType": "hybrid",
  "pageCount": 128,
  "textLayerCoverage": 0.72,
  "imagePageRatio": 0.28,
  "ocrRequiredPages": [3, 44, 45, 96],
  "columnPatterns": ["single", "double"],
  "tableCountEstimate": 18,
  "embeddedImageCount": 43,
  "bookmarkDepth": 3,
  "languages": ["zh-CN", "en"],
  "possibleRulesets": [
    {
      "id": "coc7e",
      "confidence": 0.91
    }
  ]
}
```

这里的 `hybrid` 很重要。

一本 PDF 可能同时包含：

```text
数字正文页
扫描地图页
图片 Handout 页
复杂表格页
纯插画页
```

不能整本 PDF 统一走 OCR，也不能整本统一走文本抽取。

必须逐页路由：

```text
Page 1：封面处理器
Page 2：目录处理器
Page 3：扫描 OCR
Page 4—20：双栏正文
Page 21：NPC 数值块
Page 22：地图与 Key
```

# 四、不同格式必须走不同的处理方案

|文件形态|自动判断信号|主要处理方案|核心产物|
|---|---|---|---|
|数字 PDF|有文本层、书签、字体、可提取坐标|布局分析、阅读顺序、标题层级、表格和框体识别|Section、Paragraph、Table、Callout|
|扫描 PDF|页面基本是图片、文本层很少|页面增强、OCR、区域分割、置信度记录|OCRBlock、ImageRegion|
|混合 PDF|部分页有文本、部分为扫描|逐页选择数字解析或 OCR|混合 Source IR|
|DOCX / ODT|标题样式、段落样式、表格、批注|直接读取文档结构和样式|Heading、Paragraph、Table、Comment|
|XLSX / CSV|Sheet、表头、合并单元格、数据类型|Sheet 分类、表结构推断、行对象抽取|NPCRow、RuleRow、TimelineRow|
|PPTX|幻灯片、文本框、图片、备注|按 Slide 和 Notes 分离|SceneCard、Handout、SpeakerNote|
|HTML / EPUB / Markdown|DOM、章节、锚点、语义标签|树形解析|SectionTree、Link|
|PNG / JPG|尺寸、文字区域、视觉内容|分类为地图、Handout、人物图、示意图|AssetCandidate、MapRegion|
|JSON / YAML|Schema、字段名、引用|结构验证、字段映射|StructuredCandidate|
|ZIP / 混合包|文件树、目录名、内部 Manifest|解包安全检查、文件关系分析|SourcePackageGraph|
|音频 / 视频|时长、声道、字幕、说话人|默认 `reference_only`，非模组 Canon|TranscriptReference|
|未知文件|无可用解析器|保存为 `opaque_asset`|文件元数据 + 人工说明|

关键原则：

> **解析失败不等于文件丢弃，也不等于让 AI猜内容。**

系统无法理解时：

```text
存为 opaque_asset
默认 host_only
不进入自动 Trigger
不进入 Player RAG
允许以后手动绑定
```

# 五、如何判断“这是哪一种模板”

## 1. 建立内部 Template Registry

模板库不是让作者提供，而是平台自己维护。

```json
{
  "templateProfileId": "tpl_coc_classic_two_column_v3",
  "scope": {
    "format": "pdf",
    "ruleset": "coc",
    "editionRange": ["6e", "7e"]
  },
  "signatures": {
    "pageSizes": ["A4"],
    "columnCount": [2],
    "headingPatterns": [],
    "headerFooterPatterns": [],
    "fontFamilies": [],
    "statBlockLabels": [
      "STR",
      "CON",
      "SIZ",
      "DEX",
      "INT",
      "POW"
    ],
    "crossReferencePatterns": [
      "见第{n}页",
      "Handout {n}"
    ]
  },
  "pageClasses": [
    "chapter_start",
    "body",
    "npc_stat_block",
    "location_key",
    "handout",
    "random_table"
  ],
  "extractorPlanVersion": "3.2.0"
}
```

模板匹配同时看五类信号：

```text
文件元数据
页面视觉布局
重复排版结构
规则术语与数值标签
跨文件命名和引用方式
```

不是仅凭：

```text
文件名
出版社名
封面标题
```

## 2. 推荐的匹配评分

下面只是建议初始权重，后续必须用测试语料校准：

```text
30% 页面布局指纹
25% 规则术语和字段序列
20% 文档元数据
15% 重复页面结构
10% 跨文件关联信号
```

路由策略：

|匹配结果|处理|
|---|---|
|高置信度|使用专用模板处理器|
|中等置信度|专用处理器和通用处理器双跑，自动比较|
|低置信度|不硬套模板，进入本地模板归纳|
|无法判断|通用解析 + 保守编译|

不能出现：

> “看起来像某出版社旧版，所以直接套模板。”

# 六、旧模组的关键：让系统现场归纳“本书自己的模板”

这叫：

# **Document-Local Template Induction**

即使平台从没见过这本书、出版社已经不存在、作者也不会提供 Manifest，系统仍可从文档内部重复结构中归纳模板。

## 流程

### 1. 抽样页面

从这些位置取样：

```text
开头
目录附近
每个章节首尾
中间随机页
图片密集页
表格密集页
附录
最后若干页
```

### 2. 计算页面指纹

包括：

```text
栏数
标题位置
字体大小层级
框体位置
背景颜色
表格比例
图片比例
页眉页脚
编号模式
常见字段顺序
```

### 3. 聚类页面类型

系统可能归纳出：

```text
Cluster A：普通双栏正文
Cluster B：NPC 页面
Cluster C：编号地点说明
Cluster D：玩家朗读框
Cluster E：Handout
Cluster F：地图 Key
```

### 4. 给聚类赋予语义标签

通过文字、布局和规则系统共同判断。

例如某一类区域反复出现：

```text
STR
CON
SIZ
DEX
APP
INT
POW
EDU
HP
SAN
```

系统可以高置信度判断：

```text
npc_stat_block
```

### 5. 对整本文档应用本地模板

不需要模板库提前收录这本书。

### 6. 用机器验证器抽查

验证：

```text
相同 Cluster 是否真的字段结构一致
标题层级是否连贯
数值块是否符合规则 Schema
页码与交叉引用是否能解析
```

因此模板识别的优先级应是：

```text
作者 Manifest（可选）
        ↓
平台已知 TemplateProfile
        ↓
本书现场归纳的 LocalTemplate
        ↓
通用解析器
        ↓
opaque / reference-only
```

而不是：

```text
没有 Manifest → 导入失败
```

# 七、不要判断整本模组是哪一种类型，要判断每个章节是哪一种结构

很多模组是混合型：

```text
第一幕：线性场景
第二幕：调查沙盒
第三幕：地点探索
附录：NPC 和规则
```

所以“剧情结构分类”也应该是局部的。

|章节结构|主要抽取对象|特别关注|
|---|---|---|
|调查 / 推理|Clue、Testimony、Timeline、KnowledgeGate|证词不能当事实|
|地点探索 / 地城|Location、AreaKey、Adjacency、Encounter|地图编号和空间关系|
|线性场景|Scene、Transition、ReadAloud、Trigger|场景顺序与分支|
|沙盒|Faction、Clock、Location、RandomTable|非线性关系和状态时钟|
|Hexcrawl|Hex、TravelRule、EncounterTable、Region|地理坐标和旅行规则|
|战役集 / 章节集|SubModule、SharedEntity、ChapterBoundary|章节隔离和共享人物|
|规则补充|RuleSpec、Override、Table|不生成剧情事件|
|NPC 包|NpcTemplate、Faction、StatBlock|人物别名和规则版本|
|地图 / Handout 包|Asset、MapRegion、RevealBinding|默认隐藏|
|Actual Play|ExampleEvent、HostNote|`example_only`，不进 Canon|

同一文件内部可以同时走多个抽取器。

# 八、系统如何把剧本和辅助资料串起来

不能依靠“文本相似度最高就认为是同一对象”。

需要建立：

# **Module Source Graph**

```text
SourceDocument
    ↓ contains
SourceFragment
    ↓ expresses
SemanticCandidate
    ↓ refers_to / defines / illustrates / overrides
CanonicalEntity
    ↓ compiles_to
RuntimeTemplate
```

关系类型至少包括：

```text
defines
describes
illustrates
statblock_for
handout_for
map_for
map_key_for
rule_for
errata_for
overrides
translation_of
actual_play_of
derived_from
```

GraphRAG 的索引管线会从非结构化文本中抽取实体、关系和 claims；你们可以借鉴这种多产物索引，但 TRPG 还必须额外加入可见性、条件、权威等级、规则覆盖和运行时状态。([GitHub上微软](https://microsoft.github.io/graphrag/index/overview/ "Overview - GraphRAG"))

# 九、跨资料关联必须按可靠性分级

## 一级：显式引用

可自动确认：

```text
Manifest
assetId
NPC_ID
表格主键
内部超链接
文件书签
“见 Handout 3”
“见区域 B17”
```

## 二级：确定性结构引用

通常可以自动确认：

```text
PDF 写“参见附录 NPC-07”
XLSX 有 NPC_ID=NPC-07
图片名 NPC-07_portrait.png
```

## 三级：布局关联

例如：

```text
图片位于“烧焦处方”标题正下方
NPC 数值块位于该 NPC 章节内
地图 Key 表位于地图后一页
```

## 四级：语义候选

例如：

```text
陈教授
陈致远
医院顾问
戴银框眼镜的人
```

只能建立：

```text
possible_same_entity
```

## 五级：人工或机器强验证

验证后才能升级成：

```text
confirmed_same_entity
```

每条链接都要记录：

```json
{
  "linkId": "link_xxx",
  "fromRef": "asset:portrait_07",
  "toRef": "npc:professor_chen",
  "linkType": "illustrates",
  "linkMethod": "explicit_id",
  "linkConfidence": 0.99,
  "reviewStatus": "confirmed",
  "sourceRefs": []
}
```

# 十、不要把跨文件信息覆盖到一个实体字段里

错误做法：

```text
PDF 说年龄 54
Excel 说年龄 56
勘误说年龄 55

最终 NPC.age = 55
其余信息全部丢失
```

正确做法是保留三条 Claim：

```text
Claim A：54，来源 PDF
Claim B：56，来源 Excel
Claim C：55，来源勘误
```

然后由权威解析器选择：

```text
effectiveValue = 55
reason = canonical_override
```

W3C PROV-O 提供了 `wasDerivedFrom`、`wasRevisionOf`、`hadPrimarySource` 等来源和修订关系；不一定要直接采用 RDF，但这类来源链、修订链和生成活动非常适合模组编译。([W3C](https://www.w3.org/TR/prov-o/ "PROV-O: The PROV Ontology"))

# 十一、辅助资料覆盖规则必须按领域分别处理

不能使用一个简单的：

```text
后上传文件覆盖先上传文件
```

## 剧情事实

```text
Host 正式 Retcon
> 官方 Errata
> 当前核心剧本
> 官方补充
> 参考资料
> AI 推断
```

## 规则

```text
房间 House Rule
> 模组 Rule Override
> 指定 Ruleset Edition
> 通用默认规则
> AI 建议
```

## 本地化文本

```text
Host 手工修订
> 官方译文
> 社区译文
> 机器翻译
> 原文 fallback
```

## 素材

```text
Room 运行态指定素材
> Module AssetBinding
> 默认素材
> AI 推荐
```

覆盖关系必须显式：

```text
overrides
supersedes
appliesTo
effectiveFromVersion
```

# 十二、如何让人尽可能少参与、少被剧透

这里不能靠“把所有内容都展示给 Host 检查”。

我建议提供三种导入模式。

## 1. 安全自动模式——默认

用户不看剧本内容。

系统：

```text
高置信度 + 低风险：自动接受
高置信度 + 高风险：双重机器验证后接受
低置信度 + 低风险：降级为 reference-only
低置信度 + 高风险：隔离或禁用
关键路径无法确认：标记 highRisk / blocked
```

用户只看到无剧透报告：

```text
解析页数：128 / 128
已识别场景：24
已识别 NPC：38
已识别线索模板：61
已验证 Trigger：79
禁用的不确定 Trigger：4
未绑定素材：3
高风险可见性问题：0
自动化等级：标准
```

不显示：

```text
凶手姓名
结局
隐藏线索名称
最终地点
NPC 真实身份
```

## 2. 盲审模式

只问不剧透的问题。

例如：

```text
检测到规则系统可能为 CoC 7e，是否确认？
A 文件可能是核心剧本，B 文件可能是勘误，是否接受？
低置信度实体是否默认保持分开？
不确定 Trigger 是否默认禁用？
未确定可见性的素材是否默认 host_only？
```

这些问题不会要求用户阅读全文。

## 3. 完整策展模式

只给愿意阅读剧本的管理员、编辑者或第三方策展员使用。

可看：

```text
原文片段
实体合并
Trigger
规则覆盖
隐藏内容
地图绑定
```

普通 Host 或玩家不需要进入这个模式。

# 十三、风险和置信度要共同决定是否自动接受

|风险|置信度|自动处理|
|---|---|---|
|低风险|高|自动接受|
|低风险|中|自动接受并记审计|
|低风险|低|`reference_only`|
|高风险|高|独立抽取器 + 独立验证器 + Schema 校验后接受|
|高风险|中|隔离，不激活|
|高风险|低|阻断或禁用|

## 高风险对象

```text
truth
ending
隐藏身份
可见性
Trigger condition/effect
Rule override
实体合并
Handout 揭示条件
勘误覆盖
地图秘密拓扑
玩家可见内容
```

## 低风险对象

```text
文档标题
页码
章节层级
图片尺寸
文件语言
普通元数据
明确表头
显式 ID
```

# 十四、不确定时必须有安全默认值

这会让用户几乎不用介入。

|不确定事项|安全默认|
|---|---|
|两个人物是否同一人|保持分开|
|一段是事实还是例子|`reference_only`|
|一条规则是否覆盖基础规则|不激活覆盖|
|Trigger 是否正确|禁用自动执行|
|素材是否能给玩家看|`host_only`|
|Handout 何时揭示|`hidden_until_reveal`|
|地图区域是否相连|不自动建立边|
|OCR 是否准确|保留原图，标记低置信度|
|文件用途未知|`opaque_asset`|
|是否属于主线关键内容|不作重要性排序|
|Actual Play 是否是模组设定|`example_only`|

这一原则很重要：

> **少自动化是可恢复的；错误自动化和剧透往往不可恢复。**

---

# 十五、机器验证不能只是让同一个模型“再想一遍”

建议至少拆成四个独立角色。

## 抽取器

负责：

```text
从来源中提出候选对象
```

## 验证器

只看：

```text
来源片段 + 候选结构
```

回答：

```text
来源是否真的支持这个候选？
是否遗漏了条件词？
是否把例子当事实？
```

## 一致性检查器

检查：

```text
ID 是否存在
关系是否闭合
数值是否符合规则 Schema
随机表范围是否完整
Trigger 是否引用合法对象
```

## Safety 检查器

检查：

```text
可见性
Host-only
玩家剧透
隐藏素材
Player RAG 风险
```

只有四者通过，才可进入 `confirmed`。

同时必须允许：

```text
unknown
unsupported
ambiguous
```

成为合法结果。

不能逼模型在所有内容上给一个确定答案。

# 十六、建议设置“用户问题预算”

为了做到真正少打扰，给每次导入设置：

```text
默认最多询问 3 个非剧透问题
```

优先级：

1. **规则系统和版本**无法判断时；
    
2. **核心文件**和补充文件无法判断时；
    
3. 用户选择**安全优先还是自动化优先**。
    

其他问题不再打扰用户，直接采用安全默认。

例如：

```text
1/3：系统判断该模组使用 CoC 7e，是否正确？
2/3：core.pdf 似乎是核心剧本，errata.pdf 似乎是勘误，是否接受？
3/3：不确定的自动触发器默认禁用，是否接受？
```

用户数据是否用于改进模板，应有明确隐私和授权策略；默认可以只保存匿名的排版指纹和已确认模板规则，不保存用户上传的完整受版权保护内容。

# 二十二、建议工程批次

## Import-0：基准语料和模板分类

建立代表性旧模组测试集，不改运行时。

## Import-1：Format Router

实现数字 PDF、扫描 PDF、DOCX、XLSX、图片和混合包分流。

## Import-2：Template Registry 与 Local Template Induction

支持已知模板和单本文档现场归纳。

## Import-3：Source Role 与 Section Router

判断核心剧本、勘误、地图、Handout 等，并按局部章节路由。

## Import-4：Semantic Candidate Extractors

分别处理 NPC、Scene、Clue、Rule、Trigger、地图和素材。

## Import-5：Cross-Source Resolver

建立稳定 ID、跨文件引用、勘误覆盖和实体候选关系。

## Import-6：Risk Gate 与无剧透导入

实现安全默认、机器双检、盲审问题预算和无剧透报告。

## Import-7：ModuleVersion 编译与运行时视图

输出不可变版本和 Narrative / Rule / Investigation / Asset 等任务视图。

## Import-8：全量回归

测试旧模组、扫描模组、混合资料包、规则冲突、实体误合并和剧透隔离。

# 二十三、最关键的验收标准

```text
1. 没有 Manifest 的旧模组仍能进入自动导入。
2. 一本混合 PDF 能逐页选择解析路线。
3. 系统不会把整本书强制归为一种剧情模板。
4. 系统能从单本文档重复布局中归纳 LocalTemplate。
5. “若成功搜查则发现钥匙”不会被编译成已经发现钥匙。
6. Actual Play 不会变成新房间 Canon。
7. Errata 能覆盖旧信息，同时保留来源链。
8. 低置信度人物不会自动合并。
9. 不确定 Trigger 默认禁用。
10. 不确定素材默认 host_only。
11. 用户不阅读剧本内容也能完成安全导入。
12. 导入最多只询问少量非剧透问题。
13. 高风险内容必须经过独立验证。
14. 所有关键语义对象都有 SourceRef。
15. Player 运行时永远不读取未触发线索和隐藏真相。
16. active room 固定在不可变 ModuleVersion。
17. 导入报告不通过名称或错误描述泄露剧情。
18. 无法解析的文件变成 opaque_asset，而不是 AI 虚构内容。
```

# 最后收敛

这套方案最关键的调整是：

> **我们不要求作者整理素材，也不要求用户阅读剧本来帮 AI 校对。**

平台自己承担：

```text
格式识别
排版归纳
资料角色识别
局部语义路由
跨文件对齐
机器验证
风险隔离
版本编译
```

用户只在极少数情况下回答不剧透的问题。

最终产品定义可以改成：

> **AI-Keeper 的模组导入不是依赖作者模板的表单导入，而是一套面向遗留资料的自动编译系统：它能逐文件、逐页、逐章节识别格式和用途，自动归纳未知排版模板，连接剧本、规则、地图、角色、手out和勘误；高置信度内容自动生效，不确定内容保守隔离，让用户无需阅读剧本也能完成尽可能安全的导入。**
