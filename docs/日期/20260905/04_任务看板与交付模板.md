## 1. 状态规则

| 状态 | 含义 |
|---|---|
| 可开始 | 前置允许开始，尚无本批完成证据 |
| 待前置 | 前置任务尚未交付；可先阅读/准备测试 |
| 执行中 | 已指定执行者，正在复现、修改或验证 |
| 自动化通过 | 指定自动测试已过，尚缺任务要求的浏览器/故障证据 |
| 已验收 | 文件、接口、测试、人工/浏览器证据全部达到该任务出口 |
| 受阻 | 写清具体原因、已尝试动作和需要的信息/外部条件 |

更新“已验收”时必须附证据，不能只写“已修复”“测试正常”。发布状态与任务状态分开：若有全量收集错误、未披露失败、真实证据缺失，RC 仍不通过。

## 5. 每个任务完成时填写的交付记录

复制下表作为新条目，记录真实值；本表是填写模板，不是已完成事实。放在本文件末尾或同目录新建 `交付记录-任务ID-日期.md`，只含脱敏摘要。

| 字段 | 填写要求 |
|---|---|
| 任务 ID / 执行者 / 日期 | 对应上方编号和实际承担者 |
| 起点 / 终点 | 起始HEAD、结束commit；未提交部分单列，不能省略dirty状态 |
| 解决的问题 | 用具体触发→原行为→新行为描述，避免“优化了系统” |
| 修改文件 | 精确文件；复用旧改动还是新增改动；未触及范围 |
| 接口/DDL变化 | 路径、请求/响应、事件、状态语义、迁移与旧数据兼容 |
| 红例证据 | 修复前复现命令、实际错误与退出码 |
| 定向测试 | 命令、退出码、通过/失败/跳过数、日志位置 |
| 全量测试/构建 | 独立记录；未跑/中止/收集失败不得填通过 |
| 浏览器与Provider | 实际人数、是否有Stage、Provider/模型、房间版本、动作Trace |
| 故障/恢复 | 注入点、原骰/事务/投影计数、重试后结果 |

如果某行不适用，写“不适用：原因”；不要留下不解释的空白。包含原始 token、密钥、私密线索或 prompt 的日志只留本地，交付表提供脱敏摘要。

## 6. 范围与旧测试处置记录

新增/变更测试契约时，每组都记录以下事实，避免不知不觉扩大工作量：

| 内容 | 需要回答的问题 |
|---|---|
| 原测试/接口 | 哪个文件、哪个用例、实际调用方是谁？ |
| 冻结要求 | 对应哪条AIO；没有对应则说明实验/后置归属 |
| 处理方式 | 补齐现行实现、迁移到等价接口验证，或单列实验分支 |
| 保留的行为 | 原有权限、幂等、隐私、投影断言由哪个测试继续证明？ |
| 回归口径 | 哪个完整命令仍会运行该范围，是否还有失败？ |

不接受”因为它红了所以删掉””新接口看起来更统一所以全替换””把实验测试跳过后全量通过”。

**B1 处置记录：**
1. `tests/server/test_action_resolution_scheduler.py::test_non_turn_action_uses_room_batcher_instead_of_immediate_worker` —— 原测试/接口：断言调度必须经 `RoomActionBatcher`（batcher 仅存在于测试与引擎模块，生产零调用点）。冻结要求：自动、幂等结算；不要求特定 batcher（01 B1”只有确有生产需要才接”）。处理方式：迁移为”同一后台 worker 等价断言 + 无 pipeline/pg_db 时 no-op”，不接 batcher；理由：batcher 无生产生命周期宿主、原子 queued→resolving 领取已是防重机制、2s 合并窗口延迟自由行动且”普通自由行动不得等待”。保留的行为：后台 worker 路径仍被调用、同步无环不炸。回归口径：`tests/server/test_action_resolution_scheduler.py` 全文件绿。
2. `test_background_resolution_runtime.py` 新增泄漏断言初版按意图文字黑名单 → 误报合法公开行动目标播报（”Player 1 把行动目标定在「…」”为公开叙事摘要）。处理方式：改为结构化字段检查（`”mutations”`/`”declared_intent”` 键不进 party），保留等价隐私覆盖并注释理由。
