## 实现内容

- `src/server/engine/resolution_journal.py`：新增 `release_interrupted_resolution(tx, action_id)`——暂停事务内创建（或释放）run 行，`resolution_id` 跨恢复保持。
- `src/server/engine/room_pause.py`：
  - `_write_pause_statements` 在**同一事务**记录/释放被暂停 action 的账本行；
  - `settle_owner_pause_at_boundary` 对 `paused_system`/`recovering` 直接返回 False——系统暂停绝不通过 Owner 暂停边界机制被转成 `paused_by_owner`（恢复期间结算完成曾把房间翻成 `paused_by_owner` 导致 finalize 失败，修复后红转绿）。
- `src/server/engine/resolution_pipeline.py`：
  - 新增 `resume_action(action_id)`：仅接受 `resolving` action + 已存在账本行 + 空 stage cursor（pre-commit 窗口）；`claim_resolution` 重领（gen+1、同 `resolution_id`）；`transition_action(resolving→queued)` 留痕后走 `_resolve_action_core`；finally 释放 claim。拒绝路径：`action_not_resolving` / `resolution_run_missing` / `resume_stage_unsupported` / `claim_busy`。
  - `_is_recovery_resume(action_id)` 实例级旁路三处门禁：房间 pause 门禁、`integrity_status != healthy` 拒绝、`_pause_before_rule_execution` 重排队——恢复运行本身不被"房间处于恢复中"挡回。
- `src/server/engine/system_recovery.py`：
  - `execute_system_recovery` → 阶段 1：校验（dry-run、房间 `paused_system`、版本一致、checkpoint 完整性）→ 写 `recovering`+`executing`+返回 `actions_to_resume`（resolving + 账本释放态）；`executed` 重复调用返回已知状态；`executing`/`failed` 分别 409。
  - 新增 `finalize_system_recovery(ok=True/False)`：ok 且无遗留 resolving → `running`/`healthy`/legacy `active`/proposal `executed`/completed 事件；失败 → 保持或回退 `paused_system` + 可追踪 reason + proposal `failed`，绝不假称完成。
- `src/server/router_archive.py`：execute 路由编排阶段 1 → 用统一后台装配 `_create_background_pipeline` 逐个 `resume_action` → 阶段 2 finalize；resume 未完成 → 409（带 action/status），异常 → 502，proposal 标 failed。
