# 结论

你现在**不是缺功能，也不是缺架构**。你缺的是一个能够证明产品成立的核心目标：

> **2–4 名玩家在没有人类 KP、没有人工裁决、没有后台改数据的情况下，能够从开房一直跑到有效结局，并且过程公平、连贯、不剧透、不卡死。**

当前文档已经覆盖房间、玩家、Host、AI、剧本、规则、战斗、事件、管理、治理、安全、持久化等大量模块。项目的核心假设也已经明确：AI 是 KP，人类房主只负责开房、邀请、暂停、重试；玩家移动端和 Host 公共大屏分别承担交互与展示。

所以，下一阶段不要继续横向增加系统功能。应该转入：

> **从“系统功能建设”切换到“AI-KP 能力验证和完整跑团体验打磨”。**

# 一、当前最需要解决的矛盾：它还不是真正的纯 AI-Keeper

你的架构原则本身是正确的：

* Engine 是唯一权威写入口；
* AI 只给建议，不直接改状态；
* Player 不越权；
* Host 不承载规则判定。

这里的“纯 AI”不应该理解成“让大模型直接修改 HP、SAN 和线索”。**确定性规则引擎和状态服务必须保留。**

真正的纯 AI 是：

> **游戏过程中不需要人类 KP 介入理解意图、裁定规则、处理争议或推动剧情。**

但当前链路还有明显的人类依赖：

* Director 低置信度或意图模糊时，会进入 `player_clarification_required`，随后路由到 `host_exception`。
* Host 可以处理动作异常、接受或修改玩家审查请求，甚至通过补偿变更影响状态。
* `HostAutonomy` 虽然已经有 `host_required`、`conservative`、`delegated` 三种策略，但 `host_required` 仍然是一个正式运行路径。

这意味着现在的产品更接近：

> **AI 主持 + 人类 Host 兜底**

而不是：

> **AI 完整主持 + 人类只做设备与安全控制**

## 应当建立纯 AI 模式的闭环策略

建议增加明确的 `AiOnlyResolutionPolicy`，在 `session_mode="ai_only"` 时彻底禁止普通游戏流程进入 `awaiting_host_exception`。

| 情况              | 纯 AI 模式处理方式                   |
| --------------- | ----------------------------- |
| 低风险的轻微歧义        | 采用最可逆、最保守的解释，并在叙事中说明解释        |
| 不同解释会产生明显不同结果   | 向玩家提出一个选择题式澄清                 |
| 涉及伤害、资源消耗、不可逆状态 | 要求玩家明确确认                      |
| 规则缺失            | 使用规则版本内的保守默认值，或者判定为无需检定       |
| AI Provider 失败  | Provider 降级 → 本地规则路径 → 安全回退叙事 |
| 玩家质疑结果          | 自动执行意图重解释、规则重算和补偿事务           |
| 系统不可恢复错误        | 暂停房间并提示系统故障，不能让 AI 编造结果       |
| 人类 Host 离线      | 不影响游戏正常运行                     |

Host 可以继续保留，但应重新定义为：

* 房间运营者；
* 公共舞台控制器；
* 紧急暂停和系统恢复入口；
* 调试与审计人员。

**不能再是正常游戏链路中的裁判。**

# 二、你最需要打磨的不是“AI 功能”，而是“KP 行为内核”

当前系统已经有 Director、Narrator、MechanicCompiler、规则引擎、SpoilerGuard、RAG 和状态服务，但这些主要解决的是：

* AI 能不能理解输入；
* 能不能生成结构化输出；
* 能不能安全更新状态；
* 能不能避免明显剧透。

它们还不等于“会带团”。

一个合格 AI-KP 还必须稳定回答以下问题：

1. 玩家这个行为是否需要检定？
2. 需要什么技能、什么难度？
3. 玩家失败后，场景是否还能继续？
4. 什么时候应该给线索，什么时候应该保留信息？
5. 玩家卡住时，如何推动而不直接告诉答案？
6. NPC 此时为什么这样做，而不是为了配合剧情强行行动？
7. 什么时候应该简短回答，什么时候应该展开描述？
8. 多名玩家都在行动时，谁先得到反馈？
9. 玩家提出剧本外方案时，AI 可以创造到什么程度？
10. 如何确保“失败有代价，但不会导致无意义死局”？

文档只说明 `soul.md`、`rules.md` 和 `contract.md` 已经存在，但没有提供这些文件的具体内容，因此目前无法判断 KP 行为规则是否已经达到可运行质量。

下一轮最值得专项审查的，正是这三个文件。

## KP 行为内核至少要形成八组可测试规则

### 1. 意图解释规则

* 优先尊重玩家字面声明；
* 不替玩家增加未声明的动作；
* 不把玩家愿望当成已发生事实；
* 复合动作应拆分为连续步骤；
* 只在结果会明显不同的歧义上追问。

### 2. 检定触发规则

* 没有风险、时间压力或失败代价时，不要求检定；
* 信息获取不能因一次失败永久锁死；
* 玩家方案合理时，允许改变技能或难度；
* 隐藏检定必须有剧本或规则依据；
* 不能为了“增加游戏性”随意要求投骰。

### 3. 失败推进规则

失败不应该只是：

> “你失败了，什么也没发生。”

而应该在几类结果中选择：

* 成功但付出代价；
* 获得不完整信息；
* 引发新的危险；
* 消耗时间或资源；
* 改变 NPC 态度；
* 暴露玩家行动；
* 推进场景压力。

### 4. 线索调度规则

* 核心线索至少准备两到三种获取方式；
* 单次检定失败不能彻底摧毁主线；
* 提示应该分层，而不是直接揭底；
* AI 必须区分“玩家已经知道”“角色已经知道”“剧本真相”；
* 同一线索不能无意义重复描述。

### 5. NPC 自主规则

每个重要 NPC 至少需要：

* 当前目标；
* 知道什么；
* 隐瞒什么；
* 害怕什么；
* 能接受什么交换；
* 对各角色的态度；
* 压力下的行为；
* 可以临场创造的范围。

否则 NPC 很容易变成“等玩家点一下就吐信息的数据库”。

### 6. 节奏规则

AI 要能判断场景处于：

* 建立；
* 探索；
* 停滞；
* 升压；
* 危机；
* 收束。

停滞时应该引入压力、环境变化、NPC 行动或渐进提示，而不是继续问：

> “你们接下来要做什么？”

### 7. 多人聚光灯规则

* 记录每位玩家最近一次有效行动；
* 避免连续多轮只回应同一人；
* 区分公共行动、私密行动和同时行动；
* 必要时主动询问尚未行动的玩家；
* 不把玩家之间的讨论误认为角色动作。

### 8. 叙事表达规则

* 先给结果，再给氛围；
* 一次叙事只承载有限的新信息；
* 避免重复玩家原话；
* 避免替玩家描述心理活动；
* 每次输出都应明确当前局势或可行动空间；
* 战斗描述和调查描述使用不同节奏。

这些规则需要进入结构化契约和测试，而不能只写成宽泛的“像一个优秀 KP 一样主持”。

# 三、剧本结构现在还不够支撑高质量即兴主持

现有 `ScenarioKnowledgeGraph` 已经包含：

* 场景；
* NPC；
* 线索；
* 真相；
* 结局；
* 分支。

同时已有质量检查、审查工作台和三套黄金模块。 

这些解决了“剧本内容有什么”，但 AI-KP 还需要知道：

> **内容应该在什么情况下、以什么方式、以什么代价进入游戏。**

建议把运行时剧本模型继续补到下面这个程度：

```yaml
scene:
  purpose: 本场景在主线中的作用
  entry_conditions: 进入条件
  exit_conditions: 离开条件
  available_actions: 常见可执行行为
  core_clues: 核心线索
  optional_clues: 可选线索
  fallback_clues: 失败后的替代线索
  pressure_clock: 场景压力进度
  escalation_events: 停滞时可触发事件
  improv_boundaries: AI 可以自由创造的范围

npc:
  goals: 当前目标
  knowledge: 已知事实
  secrets: 隐藏事实
  attitude: 对角色的态度
  leverage: 可交易信息或资源
  lie_policy: 何时撒谎、如何撒谎
  reaction_rules: 面对威胁、贿赂、说服时的行为
  exit_conditions: 何时离场或改变立场

clue:
  importance: core / supporting / flavor
  reveal_conditions: 揭示条件
  alternative_sources: 替代来源
  failure_outcome: 获取失败后的结果
  dependencies: 前置知识
  public_version: 可公开描述
  secret_fact_refs: 内部真相引用

ending:
  progress_requirements: 需要完成的进度
  required_facts: 必要事实
  optional_modifiers: 改变结局质量的条件
  trigger_policy: 自动触发或玩家主动触发
```

这会直接提升 AI 的：

* 即兴能力；
* 线索调度；
* 防卡团能力；
* NPC 连贯性；
* 结局判定；
* 剧本外行动承接能力。

# 四、必须建立“整场跑团评测”，不能再只看单元测试

当前项目已有大量后端测试、前端测试和三套黄金模块。文档记录了 124+ 个测试文件，以及 Golden Module 完整套件。

但在这三份文档中，我没有看到以下产品级证据：

* 真人完整跑完多少场；
* 完团率是多少；
* 平均需要多少次人工干预；
* 多少动作被错误理解；
* 多少次出现卡团；
* 是否出现提前剧透；
* 玩家是否认为裁决公平；
* 玩家是否觉得自己有选择权；
* AI 是否会重复描述和遗忘信息；
* 一场团的成本和响应延迟。

这就是现在最重要的方向缺口。

## 建议新增 `AI-Keeper Session Benchmark`

它不是普通接口测试，而是整场游戏仿真。

### 模拟玩家类型

至少覆盖：

* 正常调查型玩家；
* 谨慎型玩家；
* 暴力推进型玩家；
* 完全偏离预设路线的玩家；
* 规则律师型玩家；
* 沉默玩家；
* 高频插话玩家；
* 喜欢追溯声明物品的玩家；
* 尝试操纵 AI 或套取剧透的玩家；
* 玩家之间发生意见冲突的团队。

### 每场记录完整链路

```text
原始玩家输入
→ Director 解读
→ 意图契约
→ 机制计划
→ 骰点与规则回执
→ 状态变更
→ RevealLedger 结果
→ Narrator 输出
→ SpoilerGuard 结果
→ 最终玩家可见事件
```

### 第一阶段验收指标

| 指标              |   建议初始目标 |
| --------------- | -------: |
| 人类 Host 裁决次数    |        0 |
| 权威状态非法写入        |        0 |
| 严重剧透            |        0 |
| 不可恢复卡死          |        0 |
| 检定回执验证失败        |        0 |
| 脚本跑团到达有效结局      |    ≥ 80% |
| 动作澄清比例          |    ≤ 15% |
| 普通文本动作 P95 响应时间 |   ≤ 15 秒 |
| 玩家对清晰度、主动权、氛围评分 | 平均 ≥ 4/5 |

这些数值不是最终产品标准，而是第一轮能用来发现问题的门槛。

# 五、现在最值得做的单一里程碑

当前主线已经明确为 **CoC 7e 调查短团**。

不要同时验证三套剧本。建议直接选：

> **`02-short-team-glass-rain`，2–4 人短团，作为 AI-Only Golden Run v1。**

完成标准如下：

1. 玩家不需要创建人类 Host 角色；
2. 创建房间后可直接进入 AI 主持模式；
3. 2–4 名玩家可以完成角色选择；
4. AI 自动开场和建立场景；
5. 调查、对话、技能检定、冲突、线索分享都能跑通；
6. 所有歧义由玩家澄清或 AI 保守处理；
7. 不进入 `awaiting_host_exception`；
8. 不需要后台人工改 HP、SAN、物品或线索；

13. 可以完整回放每一次 AI 决策和状态变更。

**这个里程碑通过以前，不再扩展其他规则系统和平台功能。**

# 六、UI/UX 应该打磨什么

你现在的 UI 不应该继续以“有多少页面”为目标，而要以“玩家是否知道现在发生了什么、该做什么”为目标。

## 玩家端最重要的五个体验

### 1. 无 Host 开团

创建房间后直接选择：

* 单人 AI 团；
* 多人 AI 团；
* 是否启用公共舞台。

公共舞台是显示设备，不是人类裁判。

### 2. 降低动作确认摩擦

当前已有动作草稿分析、确认、取消和复合动作延续机制。正常动作如果每次都确认，会明显破坏跑团节奏。

建议：

* 普通、低风险动作直接提交；
* 只对歧义动作、复合动作和不可逆动作要求确认；
* 明确展示 AI 的解释，例如：

> 你准备通过观察窗框寻找近期撬动痕迹，将进行侦查检定。

### 3. 结果必须可理解

每次动作结果建议固定显示四层：

1. AI 理解了什么；
2. 是否进行了检定；
3. 检定结果与状态变化；
4. 场景叙事。

不要让玩家只能看到一段文学叙事，却不知道自己为什么失去 SAN 或为什么失败。

### 4. 公共信息和私人信息明确分开

* 公共叙事；
* 私人发现；
* 角色内心或秘密；
* OOC 消息；
* 系统提示。

必须在视觉和声音上有明显区别。

### 5. 玩家永远知道当前局势

页面需要持续显示：

* 当前地点；
* 当前目标；
* 已公开线索；
* 当前危险或压力；
* 正在等待谁；
* 自己是否有待确认动作；
* 当前行动是否已经结算。
