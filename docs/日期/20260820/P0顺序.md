# 这个优先级可以定，但执行顺序需要微调

六项方向没有问题。不过它们不是六个可以依次勾掉的独立任务，而是三组存在强依赖的工作：

1. **先定义产品边界**：P0-1、P0-2
2. **再补齐 AI-KP 能力和剧本表达能力**：P0-3、P0-4
3. **最后通过可观测的完整跑团验证**：P0-6A、P0-5、P0-6B

尤其需要调整的是：

> **决策 Trace 不能放在完整跑团之后。**

没有 Trace 就开始跑 `02-short-team-glass-rain`，最后只能得到“这一场感觉不好”“这里好像判错了”，却无法确认问题究竟出在 Director、规则编译、规则执行、状态变更、线索授权、Narrator，还是 SpoilerGuard。

# P0-1：定义纯 AI 模式

这是当前真正的第一优先级。

你的产品假设已经明确：**AI 是 KP，人类房主只负责开房、邀请、暂停、重试**；核心架构也声明 Host 不承担规则判定。 

但当前实现仍存在几条与该定位冲突的路径：

* Director 低置信度或存在歧义时，会进入 `player_clarification_required → host_exception`；
* Host 可以处理异常动作；
* Host 可以接受、修改、拒绝动作审查；
* Host 可以执行状态补偿和难度重算。 

因此，P0-1 不是简单增加一个 `session_mode="ai_only"` 开关，而是需要定义：

## 1.1 纯 AI 模式不变量

在 `ai_only` 模式中必须始终成立：

```text
AI 不直接写状态
Engine 仍是唯一权威写入口
Host 不参与普通动作裁决
Host 不参与规则解释
Host 不处理玩家申诉
Host 离线不影响游戏运行
不可恢复系统故障不得由 AI 编造结果
```

“取消 Host 正常裁决依赖”不等于取消确定性引擎。现有的 Engine、StateService、RollReceipt、RevealLedger、SpoilerGuard 都应继续保留。

## 1.2 纯 AI 路由矩阵

| 情况             | 处理方式                  |
| -------------- | --------------------- |
| 低风险轻微歧义        | 采用最保守、最可逆解释           |
| 多种解释会导致不同结果    | 向玩家提出结构化澄清            |
| 涉及不可逆后果        | 玩家明确确认                |
| 涉及其他玩家利益       | 进入玩家同意流程              |
| 缺少规则依据         | 使用规则源中的默认保守策略         |
| AI Provider 超时 | 切换 Provider 或本地确定性回退  |
| 叙事生成失败         | 使用经过验证的本地叙事           |
| 玩家质疑动作理解       | 自动重新解释原始意图            |
| 玩家质疑规则结果       | 使用原始 RollReceipt 自动重算 |
| 状态写入失败         | 事务回滚并进入系统暂停           |
| 上下文损坏或状态无法恢复   | 暂停房间，显示系统故障，不继续编剧情    |

## 1.3 状态机调整

当前动作状态机允许进入：

```text
awaiting_host_exception
```

纯 AI 模式应改为：

```text
resolving
├─ awaiting_player_clarification
├─ awaiting_player_confirmation
├─ awaiting_player_consent
├─ retrying_provider
├─ system_paused
├─ completed
├─ rejected
└─ timeout
```

在 `ai_only` 模式下，任何普通游戏动作都不得进入 `awaiting_host_exception`。

## P0-1 完成标准

* `ai_only` 模式不存在必须由 Host 点击才能继续的普通路径；
* Host 关闭页面或断网后，游戏仍能继续；
* Host 只保留开房、暂停、重试、终止、公共舞台和系统诊断；
* 所有权威状态仍必须经过 Engine；
* 系统无法安全判断时，要求玩家澄清或暂停，不能让 AI 擅自编造裁决。

# P0-2：完成 `AI_ONLY_ACCEPTANCE_SPEC.md`

P0-2 不是普通产品说明文档，而是后续代码、Prompt、剧本和测试的统一验收基准。

建议固定为以下结构：

```text
1. 产品定位
2. 适用范围
3. 不做范围
4. 角色与权限边界
5. 纯 AI 模式不变量
6. 玩家动作完整生命周期
7. 自主决策矩阵
8. 歧义与澄清策略
9. 检定触发策略
10. 失败推进策略
11. 线索揭示策略
12. NPC 自主行为策略
13. 多玩家时序策略
14. Provider 降级策略
15. 系统异常策略
16. 玩家申诉与自动复核
17. 决策 Trace 要求
18. Golden Run 场景
19. 质量指标
20. 发布门槛
```

每一条要求都应有编号，例如：

```text
AIO-INV-001  AI 不得直接修改权威状态
AIO-HOST-001 ai_only 模式不得依赖 Host 完成普通动作结算
AIO-CLR-001  歧义会改变机制结果时必须向玩家澄清
AIO-RUL-001  无风险、无压力、无失败代价的动作不得强制检定
AIO-FAIL-001 核心线索不得因单次检定失败永久丢失
AIO-TRC-001  每次结算必须生成完整 Decision Trace
AIO-GRN-001  Golden Run 中 Host 裁决次数必须为 0
```

每条要求还需要映射到：

```text
代码模块
测试用例
运行指标
失败等级
发布阻断级别
```

## P0-2 完成标准

* 产品边界没有“Host 到底是不是裁判”的歧义；
* 每个异常分支都有明确责任主体；
* 每个验收条目可以转化为自动测试或人工跑团检查；
* 后续 Prompt、剧本结构和代码变更都必须引用验收条目编号。

# P0-3：深审 `soul.md`、`rules.md`、`contract.md`

目前上传的文档只说明三个文件存在及其职责，但没有包含三个文件的实际正文，因此现在还不能进行真正的内容级深审。

审查不能只看“人格是否像 KP”，而应分成三层。

## `soul.md`：主持价值观

重点检查：

* 是否尊重玩家主动权；
* 是否禁止替玩家决定心理和行为；
* 是否区分玩家知识与角色知识；
* 是否避免为了剧情强行让玩家失败；
* 是否有节奏意识和聚光灯公平；
* 是否允许玩家提出剧本外合理方案；
* 是否能够接受失败、撤退、放弃和非理想结局；
* 是否避免过度文学化、反复复述和空洞悬念。

## `rules.md`：操作性裁决政策

重点检查：

* 什么时候必须检定；
* 什么时候不应检定；
* 如何选择技能和难度；
* 如何处理奖励骰、惩罚骰、孤注一掷和幸运消耗；
* 如何处理核心线索失败；
* 如何处理复合动作；
* 如何处理同时行动；
* 如何处理玩家间冲突；
* 如何处理 NPC 的反应和主动行动；
* 如何处理规则缺失与剧本外方案；
* 如何进行失败推进；
* 如何决定是否需要玩家确认。

## `contract.md`：机器可验证输出

重点检查：

* 输出字段是否足以让 Engine 独立校验；
* AI 的事实引用是否全部使用 `fact_ref`；
* AI 是否明确区分建议与权威结果；
* 是否包含歧义项和澄清问题；
* 是否包含风险和不可逆后果；
* 是否包含检定理由，而非只给检定结论；
* 是否包含失败推进提案；
* 是否包含 NPC 状态变化建议；
* 是否禁止把自然语言状态变化绕过 Engine；
* Provider 重试后是否仍能保持契约一致。

## P0-3 完成标准

不是“Prompt 看起来写得不错”，而是：

* 每条 KP 行为规则都有正例和反例；
* 每个结构化字段都有 Schema 校验；
* 对相同输入重复运行时，核心机制决策基本稳定；
* Prompt 不再承担应由确定性 Engine 承担的职责；
* Prompt 不使用“根据情况灵活处理”这类无法验收的抽象描述。

# P0-4：强化剧本运行时

当前 `ScenarioKnowledgeGraph` 已经包含场景、NPC、线索、真相、结局和分支，这是一个较好的静态内容基础。

但纯 AI 主持需要的不只是“有哪些内容”，还需要“内容如何参与运行”。

建议只增加 Golden Run 真正需要的最小字段，不要马上构建过度通用的平台。

## 场景最小运行时字段

```yaml
scene:
  purpose:
  entry_conditions:
  exit_conditions:
  available_facts:
  core_clue_refs:
  optional_clue_refs:
  pressure_clock:
  escalation_events:
  improv_boundaries:
```

## NPC 最小运行时字段

```yaml
npc:
  current_goal:
  knowledge_refs:
  secret_refs:
  attitude_by_character:
  leverage:
  fear:
  reaction_policy:
  departure_conditions:
  improv_boundaries:
```

## 线索最小运行时字段

```yaml
clue:
  importance: core | supporting | flavor
  reveal_conditions:
  alternative_sources:
  failure_outcome:
  prerequisite_fact_refs:
  public_version:
  private_version:
```

## 失败推进字段

```yaml
failure_progression:
  cost_type:
  state_effect:
  pressure_effect:
  information_effect:
  npc_reaction:
  next_available_actions:
```

## P0-4 完成标准

* 每个核心线索至少有一个替代获取路径；
* 单次失败不能无意中锁死主线；
* 每个主要 NPC 有明确目标和反应策略；
* 场景停滞时有可验证的压力升级机制；
* AI 即兴内容受到 `improv_boundaries` 限制；
* 结局条件可以由 Engine 根据状态确定性判断。

# P0-6A：先建立决策 Trace

现有项目已经有 DecisionAudit、事件日志、动作状态历史、RollReceipt 和检查点，但它们尚不等同于“可诊断整次 AI-KP 决策的统一 Trace”。现有审计主要负责字段白名单和敏感信息清洗。

建议每次动作形成一个统一的 `resolution_trace_id`，记录：

```text
1. 玩家原始输入
2. 当前状态版本
3. Director 输入上下文摘要
4. Director 原始输出
5. Director 规范化结果
6. 歧义与置信度
7. AiOnlyResolutionPolicy 路由结果
8. MechanicCompiler 输出
9. RuleExecutor 权威结果
10. RollReceipt
11. StateService mutations
12. RevealLedger 提案及结果
13. Narrator 输入
14. Narrator 输出及 fact refs
15. SpoilerGuard 检查结果
16. 最终投影事件
17. Provider、重试和降级路径
18. 各阶段延迟
19. Token 使用量
20. 最终动作状态
```

## P0-6A 完成标准

出现以下问题时，能在一条 Trace 中定位原因：

* 为什么要求了这个检定；
* 为什么选择这个技能；
* 为什么是困难难度；
* 为什么扣了 SAN；
* 为什么没有获得某条线索；
* 为什么触发了澄清；
* 为什么生成了这段叙事；
* 为什么进入 Provider 回退；
* 为什么状态没有更新；
* 为什么玩家看到了或没看到某条信息。

# P0-5：跑通 `02-short-team-glass-rain`

现有黄金模块中，`02-short-team-glass-rain` 是 2–4 人调查短团，规模最适合验证多人纯 AI 主持主链路。

这一步的重点不是“脚本执行成功”，而是：

> 玩家是否能在没有人类 KP 的情况下完成一场有调查、选择、检定、失败、压力、线索和结局的团。

## Golden Run 必测路径

至少覆盖：

1. 正常调查核心路径；
2. 一次核心线索检定失败；
3. 玩家提出未预设方案；
4. 玩家误解场景事实；
5. 玩家声明不拥有的物品；
6. 多名玩家同时行动；
7. 玩家行动相互冲突；
8. NPC 被威胁、说服或欺骗；
9. 玩家长时间没有推进；
10. AI Provider 至少一次失败降级；
11. 玩家中途断线重连；
12. 至少一个非最佳结局；
13. 最终归档和回放。

## P0-5 完成标准

```text
Host 普通裁决次数 = 0
人工数据库修改次数 = 0
严重剧透次数 = 0
非法状态写入次数 = 0
无法恢复卡死次数 = 0
RollReceipt 验证失败次数 = 0
可以进入有效结局 = 是
完整决策 Trace 覆盖率 = 100%
```

# P0-6B：建立整场跑团仿真和质量门槛

项目当前已经有大量单元测试和 Golden Module 套件，但这些主要验证代码与模块链路，并不能完全证明“AI 会主持一场好团”。

需要增加模拟玩家：

* 正常调查型；
* 谨慎型；
* 暴力型；
* 偏航型；
* 规则质疑型；
* 沉默型；
* 高频行动型；
* 试图套取剧透型；
* 多玩家意见冲突型。

建议首轮质量门槛：

| 指标           |   初始门槛 |
| ------------ | -----: |
| Host 裁决次数    |      0 |
| 严重剧透         |      0 |
| 非法权威状态变更     |      0 |
| 不可恢复卡死       |      0 |
| 有效结局到达率      |  ≥ 80% |
| 不必要澄清率       |  ≤ 15% |
| 无意义检定率       |  ≤ 10% |
| 核心线索永久丢失率    |      0 |
| 重复叙事率        |  ≤ 10% |
| 普通动作 P95 总延迟 | ≤ 15 秒 |
| Trace 完整率    |   100% |

这些门槛后续可以根据实际跑团数据调整，但第一版必须先建立测量能力。

# 现在立即执行的工作
