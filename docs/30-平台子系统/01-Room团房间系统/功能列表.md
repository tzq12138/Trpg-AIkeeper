# Room 团房间系统功能列表

## 模块定位

Room 是 AI-Keeper 的房间生命周期与成员协作边界，负责把 `开房 -> 玩家加入 -> 大厅 ready -> 开局 -> 进入首回合` 这条主链路稳定串起来。

本模块只管理房间归属、成员关系、Lobby 同步、开局入口和基础权限，不负责 AI 裁决、规则结算、世界真相写入、私密线索发放、投影分层和长期日志全文。

基于当前代码，Room 现在同时承担了“房间入口”和“当前进行中的一场会话容器”两层职责。第一轮文档保留这一现状，但明确把 `Room / Session` 拆分定义为后续演进方向，不把未来表结构写成当前事实。

当前阶段说明：

- 本文件已可作为工程执行入口，但当前阶段仍是“P0 主链路 + 生产风险识别版”。
- 文档中标出的风险、演进方向和安全缺口，不等于这些问题已经在代码里闭环解决。
- 本轮目标是把 Room 主链路和风险边界讲清楚，不把“可开发”误写成“已生产安全完成”。

## 优先级口径

| 优先级 | 含义 |
|---|---|
| P0 | MVP 主链路必需，直接影响开房、入房、ready、开局、进入首回合 |
| P1 | 强化真实跑团体验与安全边界，建议尽快补齐，但不阻塞第一轮主链路 |
| P2 | 长团管理、迁移、归档、多场次能力 |
| P3 | 平台外围与组织化增强能力 |

## P0 MVP 功能

| 功能 | 是否进入 MVP | 当前代码现状 | 依赖模块 | 用户价值 | 验收口径 | 现状风险/备注 |
|---|---|---|---|---|---|---|
| 房主创建房间 | 是 | 已有 `POST /api/rooms`，要求 `host/admin` 登录并提供有效 `scenario_id` | User、Module | Host 可以从剧本创建一场团 | 返回 `room_id`、`owner_token`、`status=lobby`、`scenario_title` | `owner_token` 目前为明文兼容凭证，后续需收紧 |
| 管理员代建房间 | 是 | `admin` 可指定 `owner_account_id` 代建 | User、Admin/Ops | 便于运营或测试协助开房 | 代建后房间归属正确 | 必须持续阻止 player 角色创建房间 |
| 查询公开房间信息 | 是 | 已有 `GET /api/rooms/{room_id}`，返回脱敏大厅摘要 | Safety | 玩家入房前可确认房间和剧本 | 不返回 `owner_token`、`owner_account_id`、`player_token` | 当前公开入口直接使用 `room_id`，后续再拆 `room_code/invite` |
| 选择或切换剧本 | 是 | 已有 `GET /scenario-options` 与 `PATCH /scenario`，仅 owner/admin 可用 | Module、Safety | Host 可在开局前调整剧本 | `active/completed/archived` 不允许切剧本 | `paused` 是否允许切剧本需后续单独定口径 |
| 玩家加入房间 | 是 | 已有 `POST /api/player/rooms/{room_id}/join-with-character` | User、Character | 玩家可进入指定团房间 | 正确房间、昵称、唯一角色来源时返回 `player_token` | 当前玩家实际使用的是公开 `room_id`，不是独立短码 |
| 玩家绑定角色 | 是 | 支持 preset、xlsx、builder、template、copy 五种来源 | Character | 入房时完成玩家身份与角色绑定 | 只允许一种来源，写入 `characters`，返回 `character_id` | Room 只校验来源和占用，不承载角色细节规则 |
| 入房限速 | 是 | `_check_rate_limit` 按 IP 做内存级限制 | Safety | 降低撞库和刷入房请求 | 超限返回 429 | 多实例部署时需要集中式限流 |
| Lobby ready | 是 | `ready_toggle` 通过 `/api/player/intent` 改写 `is_ready` | Engine、Player Client | 玩家可明确准备完成 | 仅有效 `player_token` 可切换 ready | ready 本身不等于规则校验通过 |
| Lobby 状态同步 | 是 | 加入、ready、开局后会广播 `s2c_room_lobby_snapshot`，Host/Player 都已接入 | Projection、Host Client、Player Client | 大厅成员进度实时一致 | Host/Player 可收到同一份大厅快照 | 仍需持续检查 WS payload 脱敏，不只检查 REST DTO |
| 开始游戏 | 是 | 已有 `POST /api/rooms/{room_id}/start`，支持 owner token、owner account、admin | Rule、Transaction、Timeline | Host 能从大厅进入正式跑团 | 默认要求有剧本、至少一名玩家、且正式成员全部 ready | 这是 Room 到 Transaction 的边界入口，不承载裁决细节 |
| 强制开局 | 是 | `force_start: true` 可跳过空房/未 ready 检查 | Safety、Journal | 演示、补救、调试时可急救开局 | 仅 owner/admin 可显式使用 | 当前只做到风险识别，未完成风险闭环；后续实现应补 `reason + confirm + event/audit`，且不能把 force_start 变成默认路径 |
| 首回合创建 | 是 | 开局后通过 `TurnManager._create_turn` 创建首回合 | Transaction、Rule | 开局后能立刻进入行动提交链路 | 返回 `turn_id`、`turn_index`，房间状态变为 `active` | Room 只负责入口，不负责回合执行 |
| 开局副作用初始化 | 是 | 开局时尝试创建 checkpoint、初始化已确认地图，并广播 active 快照 | Scene/Map、Journal、Projection | Host/Player 在开局后进入一致状态 | 失败不应破坏主链路，但应有日志可查 | 当前更偏 warning 级别，后续需补观测性口径 |
| 进行中加入审批 | 是 | `active` 房间加入者写成 `pending_approval`；Host 有 approve/reject 接口 | Host Client、Safety | 迟到玩家不会直接进入场内 | 未审批前不进入正式成员列表 | 后端大厅广播已补上，但批准/拒绝后的“玩家结果通知、Projection 重算触发、Journal 成员变更记录、玩家重同步”仍未形成完整闭环 |
| 房主有限急救 | 是 | 当前急救接口分散在 Room 与 Host 路由：`start/skip-character/retry` 以及 `/api/host/{room_id}/pause/reset/retry-turn` | Transaction、State、Journal | 跑团中断时可补救 | 只允许 owner/admin | 文档必须区分“当前接口位置”和“未来统一整理方向” |
| 基础断线恢复入口 | 是 | 登录账号可恢复自己的角色会话；玩家端已有 sync/restore 入口 | User、Player Client | 刷新或换端后可找回身份 | 账号只能恢复自己名下角色 | 游客恢复能力仍弱，后续需补一次性恢复码或设备绑定方案 |
| 房间权限边界 | 是 | 当前并存 owner token、owner account、admin 三类鉴权 | User、Safety | 兼容开发期和正式账号体系 | player 不能创建/开局/审批房间；公开 DTO 持续脱敏 | `owner_token` 仍然过强，需被收敛到兼容路径，且不得继续扩大到更多新接口、分享链路或公开导出 |

## P1 真实跑团体验与安全强化

| 功能 | 是否进入 MVP | 当前代码现状 | 依赖模块 | 用户价值 | 验收口径 | 现状风险/备注 |
|---|---|---|---|---|---|---|
| Room / Session 概念拆分 | 否 | 当前 `room.status` 兼做团房间状态和当前一场进行状态 | Timeline、Journal、Schedule | 适配长期跑团、多场次管理 | 能明确区分房间生命周期与单场 Session 生命周期 | 若不拆，后续 Journal/Timeline/Schedule 会与 Room 纠缠 |
| `room_id / room_code / invite_token` 分离 | 否 | 当前公开查询和玩家加入都直接使用 `room_id` | User、Safety | 降低内部主键外露，提升分享体验 | 对外短码/邀请链接独立，对内主键保留 | 本轮只写演进方向，不假装代码已实现 |
| DTO 分层 | 否 | 当前已有公开 DTO 脱敏，但未系统定义 `Public/Host/Player/Admin` | Projection、Safety | 降低后续接口越写越乱和权限泄露风险 | 明确每类 DTO 可含字段边界 | WS payload 与 REST DTO 都要纳入同一套检查 |
| `owner_token` 硬化 | 否 | 当前明文存储、长期有效、兼容开发路径 | User、Safety、Admin/Ops | 降低泄露后直接控房风险 | 至少定义过期、撤销、哈希存储和高危操作复核方向 | 与现有大量测试和兼容链路相关，需渐进迁移 |
| 席位上限与加入策略 | 否 | 当前尚无 `max_players`、`join_policy`、`allow_late_join`、`allow_observer`、`requires_approval` 字段 | User、Character、Safety | 更符合真实开团配置 | 房主可配置人数上限、是否允许迟到加入、是否默认审批 | 建议数据字段尽早设计，UI 可后补 |
| 房间公告 | 否 | 未独立实现 | Channel、Journal | 固定显示房规、时间、注意事项 | 公告可编辑、置顶、进入日志 | 不应与普通聊天混成同一权威信息源 |
| 旁观者模式 | 否 | 未实现 | Projection、Safety、Host Client | 支持观众只看公共舞台 | Observer 只看公共投影，不得提交行动 | 容易引入剧透，需要在 Projection 完整落地后做 |

## 核心边界

- Room 只负责房间生命周期、成员关系和开局入口，不负责世界真相写入。
- 当前 `characters` 表同时承载角色与房间成员身份；后续若拆 `room_members`，应视为结构演进，不是当前事实。
- Session 是 Room 下面的未来子层，不应反过来把 Room 写成完整的长期日志系统。
- 玩家不能直接写房间状态，只能通过受控入房接口或 `intent` 改变成员状态。
- Host 可以管理房间，但不能借 Room 能力读取完整 KP 真相。
- AI 不直接创建房间、不直接开局、不直接写 Room 表。
- 公开 DTO、Host/Player WS payload 都必须做同等级别的敏感字段审查，不能只防 REST、不防广播。

## 数据模型演进方向

当前事实：

- `rooms`：已有 `room_id`、`scenario_id`、`owner_token`、`owner_account_id`、`status`、`spoiler_level`、`state_version`、`created_at`、`started_at`
- `characters`：当前同时承担角色实体和房间成员摘要，包含 `room_id`、`player_token`、`is_ready`、`account_id`、`status`
- 当前没有独立的 `room_code`、`room_invites`、`sessions`、`room_members`

后续建议：

- `rooms` 增加 `room_code`、`max_players`、`join_policy`、`allow_late_join`、`allow_observer`、`requires_approval`、`current_session_id`
- 视时机把成员关系从 `characters` 中拆出 `room_members`
- 新增 `room_invites` 管理邀请链接与失效策略
- 新增 `sessions` 管理每一场开团的开始、结束、摘要与回放引用

## 第一轮落地判断

第一轮 Room 只追求一条稳定主链路：

`Host 登录 -> 创建房间 -> 玩家加入并绑定角色 -> 玩家 ready -> Host 开局 -> 房间 active -> 创建首回合 -> Host/Player 收到大厅状态变化`

房间密码、白名单、旁观者、候补、房间复制、房间模板、长期 Session 管理、导入导出、社区招募都不混入本轮 P0 修复。
