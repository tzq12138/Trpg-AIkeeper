# Room 团房间系统验收文档

## 文档定位

本文件用于在收到工程师的 `回执-YYYY-MM-DD.md`、代码改动说明、测试结果后，判断 `01-Room` 本轮工作是否真正完成。

它只负责验收，不替代 `功能列表.md`、`PRD.md`、`DeepSeek计划.md`。

默认分两层结论：

- `本轮工程验收通过`：表示 Room 本轮承诺的 P0 主链路和安全底线已完成。
- `生产安全完成`：表示除本轮范围外，Room 的高风险缺口也已关闭。

除非证据非常完整，否则默认只评 `本轮工程验收通过`，不直接给 `生产安全完成`。

## 验收输入

验收前至少应拿到以下材料：

- 本模块三份基线文档：`功能列表.md`、`PRD.md`、`DeepSeek计划.md`
- 工程师回执：`回执-YYYY-MM-DD.md`
- 本轮改动文件列表，至少说明改了哪些后端、前端、测试文件
- 测试命令与结果
- 如涉及前端页面，附手动链路验证结果

## 结论等级

| 结论 | 含义 |
|---|---|
| `本轮工程验收通过` | P0 主链路、权限边界、关键测试与手动链路都已对上 |
| `本轮工程验收有缺口` | 主链路基本可用，但仍缺关键证据、关键测试或关键安全项 |
| `不通过` | P0 断链、越权、DTO/WS 泄露、测试未过或回执与实际不符 |
| `生产安全完成` | 只有在 owner token、active join 闭环、长期恢复和权限硬化等高风险项也关闭后才可给出 |

## 一票否决项

出现任一情况，本轮不能判通过：

- 玩家可以创建房间、开局、审批或直接改房间状态
- `GET /api/rooms/{room_id}` 或 Lobby/WS 广播泄露 `owner_token`、`owner_account_id`、`player_token`
- `Host 登录 -> 创建房间 -> 玩家加入 -> ready -> 开局 -> active -> 首回合创建` 主链路跑不通
- `active` 中途加入不经过 `pending_approval`
- 错误账号可恢复他人角色身份
- 测试命令未提供，或关键测试明显未通过

## 必备回执材料

工程师回执里至少应明确：

- 本轮对应的 Batch 范围
- 实际修改文件
- 实际测试命令
- 实际测试结果
- 明确完成项
- 明确未完成但保留为 P1/P2 的项

如果回执把 P1/P2 缺口写成“已完成”，验收时应直接降级处理。

## 本轮工程验收清单

### 1. 主链路

- Host 登录后可以创建房间
- 返回 `room_id`、`owner_token`、`status=lobby`、`scenario_id/scenario_title`
- 玩家可以加入房间并绑定角色
- 玩家可以切换 ready
- Host 正常开局后房间进入 `active`
- 开局后创建首回合，并能拿到 `turn_id/turn_index`

### 2. 权限与边界

- `POST /api/rooms` 仅 `host/admin` 可用
- 非房主、非管理员不能 `start/force_start/approve/reject`
- 玩家不能通过前端本地状态伪造 ready 或 active
- Room 不承载 AI 裁决、不直接写世界真相

### 3. 公开 DTO 与 WS 脱敏

- `GET /api/rooms/{room_id}` 不返回敏感 token
- Lobby 快照广播不返回敏感 token
- 回执里如果宣称修了 WS，同步要给出字段层面的脱敏说明

### 4. `force_start` 急救路径

至少要确认以下内容：

- 只有 owner/admin 可显式使用
- 普通 `start` 仍要求剧本、至少一名正式玩家、正式成员 ready
- 如果回执宣称已完成硬化，应提供 `reason + confirm + event/audit` 的证据
- 如果只做到兼容 `force_start: true`，必须在回执里明确仍属未关闭缺口

### 5. `active join` 审批链路

- `active` 房间新加入玩家状态为 `pending_approval`
- 非 owner/admin 不能 approve/reject
- reject 后不进入正式成员队列
- 若回执宣称“审批闭环已完成”，必须额外给出以下证据：
  - 玩家结果通知
  - Projection 重算触发
  - Journal 成员变更记录
  - 玩家重同步

只补大厅广播，不算“审批闭环已完成”。

### 6. 身份恢复

- 登录账号只能恢复自己名下角色
- 游客恢复若未做，不算本轮失败，但必须在回执里明确仍属后续项

### 7. 手动验收链路

回执至少应确认以下链路实际跑过：

1. Host 登录创建房间
2. 玩家加入并绑定角色
3. 玩家 ready
4. Host 开局
5. 房间进入 `active`
6. 首回合创建
7. Host/Player 都收到大厅状态变化

## 必跑测试

至少应包含：

```powershell
pytest tests/server/test_rooms.py tests/server/test_room_security.py tests/server/test_host_room_lifecycle.py tests/server/test_character_join_import.py tests/server/test_player_intent.py tests/server/test_ws_auth.py -q
```

如改了 Room 前端页面，还应包含：

```powershell
cd src/client
npm run build
```

## 生产安全加签条件

以下条件未关闭前，不应给 `生产安全完成`：

- `owner_token` 仍是长期兼容强凭证，未过期、未可撤销、未哈希化
- `approve/reject` 仍未形成完整四类后续动作闭环
- `room_id / room_code / invite_token` 仍未分层
- `max_players / join_policy / allow_late_join / requires_approval` 仍未建模
- 游客恢复、长期 Session 管理、归档导出仍未完成

## 回执最小模板

后续工程师回执至少应回答这几件事：

1. 本轮覆盖了哪些 FR / Batch
2. 改了哪些文件
3. 跑了哪些测试，结果是什么
4. 手动主链路是否跑通
5. 哪些 P1/P2 仍未做
6. 是否存在已知技术债或兼容路径
