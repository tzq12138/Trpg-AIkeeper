# State 世界状态系统验收文档

## 文档定位

本文档用于在收到工程师的 `回执-YYYY-MM-DD.md`、代码改动说明、测试结果后，判断 `13-State` 本轮工作是否真正完成。

它只负责验收，不替代：

- `功能列表.md`
- `PRD.md`
- `DeepSeek计划.md`

默认分两层结论：

- `本轮工程验收通过`：表示 State 本轮承诺的 P0 主链路、权威状态写入、房间版本屏障、重连版本屏障和 checkpoint/restore 语义已经闭环。
- `生产安全完成`：表示除本轮范围外，State 的长期高风险缺口也已基本关闭。

除非证据非常完整，否则默认只给 `本轮工程验收通过`，不直接给 `生产安全完成`。

## 验收输入

验收前至少应拿到以下材料：

- 本模块四份基线文档：`功能列表.md`、`PRD.md`、`DeepSeek计划.md`、`验收文档.md`
- 工程师回执：`回执-YYYY-MM-DD.md`
- 本轮改动文件清单，至少说明改了哪些 engine、state_service、player sync/reconnect、map、clue、admin、archive、event_log、tests 文件
- 实际测试命令与测试结果
- 如涉及前端 shared types 或状态同步入口，附 `npm run build` 结果和手动链路验证结果

## 结论等级

| 结论 | 含义 |
| --- | --- |
| `本轮工程验收通过` | State 本轮 P0 / P1 目标已实现，关键版本语义、事务时序、runtime 读模型、重连屏障和 restore 语义与文档对齐 |
| `本轮工程验收有缺口` | 主链路基本可用，但仍缺关键证据、关键测试或关键边界闭环 |
| `不通过` | 出现版本污染、先投影后落库、snapshot 泄露、checkpoint 覆盖缺失、直写路径未收口、测试未过或回执与实际不符 |
| `生产安全完成` | 只有在长期遗留项、Map 双版本策略、Encounter 长期策略和更广回归覆盖也基本稳定后才可给出 |

## 一票否决项

出现任一情况，本轮不能判通过：

- action 入队仍推进 `rooms.state_version`
- `ready_toggle`、chat、typing、纯 UI 事件仍推进 `rooms.state_version`
- 空 `StateChangeSet` 或 no-op 仍推进版本
- `ResolutionPipeline` 仍先投影后 State 落库
- `s2c_state_patch` 仍缺 `schemaVersion`、`baseStateVersion`、`stateVersion` 中的关键字段
- 同一状态变化仍被 Pipeline 和 StateService 双重发 patch
- 普通读取接口会静默创建 runtime 状态并独立 commit
- 当前 HP/SAN/MP/Luck 仍以 `characters.xlsx_data` 为权威
- `/api/player/reconnect` 需要 snapshot 时仍返回整房间原始事件
- Player reconnect / archive / sync 仍能看到 Host-only 或其他玩家 private 事件
- checkpoint 仍未覆盖 `rooms.state_version`、`character_runtime_state`、`room_scene_state`，却在回执中声称“完整恢复”
- restore 不要求 `confirm=true + reason`
- restore 后没有新的 `s2c_checkpoint_restored`
- restore 后把 Host full snapshot 或原始 restore 审计 payload 直接给 Player
- `encounter_changes` 仍会静默成功
- 关键测试命令未提供，或明显未通过

## 必备回执材料

工程师回执里至少应明确：

- 本轮对应的 Batch 范围，例如 `State-1 ~ State-6`
- 实际修改文件
- 实际测试命令
- 实际测试结果
- 明确完成项
- 明确未完成但保留为后续 Batch / P1 / known limitation 的项
- 哪些路径仍保留专项服务，没有并入 `StateService`
- `AppliedStateChange` 最终字段命名是否统一为 `eventRefs`
- Map 路径是否推进 `rooms.state_version`
- 如 Map 保留 local version，如何映射到 room version 或事件序列
- `CheckpointStateDTO.includes[]` 当前包含哪些表
- `CheckpointStateDTO.knownLimitations[]` 当前仍有哪些缺口
- Host / Admin 写入里哪些已经接入 `expectedStateVersion?`，哪些还没有

如果回执把文档里明确属于后续项的缺口写成“已完成”，验收时应直接降级处理。

## 本轮工程验收清单

### 1. `rooms.state_version` 语义

必须满足：

- action 入队不再 bump `rooms.state_version`
- `ready_toggle` 不再 bump `rooms.state_version`
- chat / typing / 纯 UI 事件不推进 world state version
- 真实状态变化只推进一次 `rooms.state_version`
- 空变更返回 `noOp=true` 时不推进版本

### 2. `StateService.apply_change()` 事务契约

至少验证：

- `apply_change()` 先读取当前版本，再校验，再应用真实变化
- `apply_change()` 只在 `appliedChanges > 0` 时 bump 版本
- `apply_change()` 返回：
  - `baseStateVersion`
  - `stateVersion`
  - `appliedChanges`
  - `eventRefs`
  - `noOp`
- `Projection` 只投影已持久化结果

### 3. 持久化先于投影

必须验证：

- `ResolutionPipeline` 顺序为先 `apply_change()`，后投影
- Player 不会先收到 patch，再发现数据库还没写进去
- 同一状态变化不会被 Pipeline 和 StateService 各发一条重复 patch

### 4. `s2c_state_patch` 契约

必须至少包含：

- `schemaVersion`
- `baseStateVersion`
- `stateVersion`
- `actionId`
- `patches`

如有事务或来源链，还应包含：

- `transactionId`
- `sourceRefs`

### 5. Player 意图冲突与 `StateConflictDTO`

必须验证：

- Player intent 旧 `base_state_version` 返回 conflict
- 响应中能拿到 `currentStateVersion`
- Host / Admin 如本轮暂未接入 `expectedStateVersion?`，回执必须说明具体豁免路径
- 对未接入乐观锁的 Host / Admin 路径，至少有审计和最新 `stateVersion` 回传

### 6. runtime 初始化与权威读模型

必须验证：

- 玩家入房后会初始化 `character_runtime_state`
- runtime 初始化幂等
- 普通 `GET /api/player/sync`、`GET /api/player/reconnect`、普通读取接口不会偷偷写库并独立 commit
- 当前 HP/SAN/MP/Luck/status 来自 `character_runtime_state`
- `characters.xlsx_data` 只作为角色卡基线

### 7. Admin 当前状态修改

必须验证：

- Admin 修改当前 HP/SAN/status 走 runtime 状态服务
- 不再把 `characters.xlsx_data` 当作当前状态写入口
- Admin 修改有审计

### 8. reconnect / snapshot 版本屏障

必须验证：

- `/api/player/sync` 返回 `StateSnapshotDTO`
- `/api/player/reconnect` snapshot 返回 `snapshotStateVersion`
- reconnect 的 recent / missed events 复用玩家可见性 helper
- reconnect 不返回 Host-only 事件
- reconnect 不返回其他玩家 private 事件
- 客户端能按 `baseStateVersion` / `snapshotStateVersion` 丢弃旧 patch、请求 full sync

### 9. `StateSnapshotDTO` 的线索边界

必须验证：

- `ownedClues[]` 只包含本人可见的安全 DTO
- `sharedClues[]` 只包含 `publicVersion` 或等价安全字段
- 不会把他人 `clues.text` 原文通过 snapshot 发给队友

### 10. 直写路径收口

重点核对这些路径：

- `src/server/engine/engine.py` action 入队
- `src/server/player/router_player.py` retroactive item
- `src/server/router_admin.py` `update_character()`
- `src/server/map_persistence.py` / `src/server/host/router_host.py`
- `src/server/player/router_clues.py`

每条路径都必须满足三选一：

1. 已收口到 `StateService`
2. 已收口到专项状态服务
3. 被明确声明为 Room / Lobby / UI 豁免路径

### 11. Map 双版本策略

这是本轮回执必须讲清楚的点。

至少要回答：

- 地图探索 / 显隐 / 位置变化是否推进 `rooms.state_version`
- 如果保留 map local version，字段名是什么
- map local version 与 room `stateVersion` 如何关联
- Player / Host 如何用该关联处理 patch 乱序

如果工程回执对这个问题说不清，本轮不能判“完全闭环”。

### 12. Encounter 策略

必须验证：

- `encounter_changes` 未支持时继续明确 raise
- 不存在“调用成功但什么都没保证”的静默路径
- 如果 Encounter 仍独立 persistence，回执必须说明：
  - 版本策略
  - 事件策略
  - restore 是否覆盖

### 13. checkpoint / restore 语义

必须验证：

- restore 要求 `confirm=true`
- restore 要求 `reason`
- restore 后写 `s2c_checkpoint_restored`
- restore 继续解释为“新历史分支”，不是“抹掉旧历史”
- Player 只收到安全 snapshot / 安全摘要，不收到 Host full snapshot

### 14. checkpoint 覆盖范围

至少检查以下内容是否已进入 `CheckpointStateDTO.includes[]`：

- `rooms.state_version`
- `character_runtime_state`
- `room_scene_state`
- `room_map_state`
- `character_map_positions`
- `inventory`
- `clues`
- `clue_shares`
- `room_turns`

如本轮未覆盖以下内容，必须在 `knownLimitations[]` 里显式说明：

- `encounters`
- `encounter_participants`
- 任何恢复后会造成证据链断裂的关系表

### 15. 端到端主链路

至少应手动或自动证明以下链路：

1. 玩家入房并初始化 runtime 状态。
2. 玩家提交带 `base_state_version` 的行动。
3. Rule / Engine 产出 HP/SAN 或状态标签变化。
4. State 先落库，再发带版本 patch。
5. Player 与 Host 看到一致的当前状态。
6. 玩家断线期间发生状态变化，重连后按版本正确应用。
7. Host 创建 checkpoint。
8. Host restore checkpoint。
9. restore 后 runtime、scene、map、inventory、clue 和日志引用重新对齐。

## 生产安全加签条件

以下条件未关闭前，不应给 `生产安全完成`：

- Map 双版本与 room version 的长期统一策略仍未完全稳定
- Host / Admin 写入的 `expectedStateVersion?` 乐观锁还未全面接入
- checkpoint 对间接关系表的覆盖仍存在已知缺口
- Encounter 是否并入统一状态写入仍未最终定型
- reconnect 与 snapshot 版本屏障虽可用，但跨更多事件族的长期回归仍不足
- runtime 初始化与历史角色卡基线迁移仍可能存在长期兼容问题
