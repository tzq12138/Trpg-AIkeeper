# Community 社区生态系统功能列表 V2.1

## 当前阶段说明

- 本文档当前阶段为：`P0 边界设计 + 公开发布安全、审核治理与数据模型风险识别版`。
- 当前仓库没有独立 Community 子系统，没有 `/api/community`、社区表、社区页面、评论、收藏、评分、举报和公开主页。
- 本轮重点不是实现社区，而是定义“什么内容能公开、谁能发、谁来审、怎么下架、怎么留痕”的统一边界。
- `Community-0` 到 `Community-3` 可作为文档、测试和前置设计批次；`Community-4` 之后的公开主页、模组发布、评论评分、举报后台、公开招募、公开战报，都必须在用户再次确认后再进入工程实现。
- 文档通过不等于可以直接把 `scenarios`、`events`、`public export` 或 `campaign archive` 打开成公开社区内容。

## 模块定位

Community 负责 AI-Keeper 的平台生态层：公开发现、内容发布、互动、举报审核和社区治理。它回答的是“哪些内容能被平台公开、谁可以发现它、谁可以互动、谁可以处理违规”，不回答“房间里发生了什么裁决”。

Community 不进入当前 AI 核心链路，不影响创建房间、玩家加入、ready、开局、AI 裁决、事务、状态和投影。它依赖 Module 提供可发布源对象，依赖 Safety 提供脱敏与可见性边界，依赖 Schedule 提供公开招募字段，依赖 Admin/Ops 提供审核、下架、恢复和审计能力。

## 发布对象状态机

以下公开对象应统一遵守发布状态机：

- `PublishedModule`
- `PublicBattleReport`
- `CommunityPost`
- `PublicRecruitPost`
- `PublicProfile`

统一状态机：

```text
draft -> reviewing -> published -> hidden -> published
reviewing -> rejected
published -> archived
rejected -> draft
```

补充规则：

- `Comment` 使用单独状态：`visible -> hidden -> removed`，作者删除可进入 `deleted`。
- `Report` 和 `ModerationCase` 使用独立状态机，不混用 `published` 语义。
- 任何下架、恢复、驳回、删除和申诉结果都必须进入 `CommunityAudit`。

## PublishedModule 公开边界

`PublishedModule` 永远不是源 `scenario` 的直接公开视图。

必须写硬的规则：

- 公开响应只能使用 `public_payload` 或 `module_version_public_payload`；
- `source_scenario_id` 只作为后台关联，不进入 Visitor DTO；
- `public_payload` 只允许包含公开标题、简介、规则系统、人数、时长、标签、内容警示、公开素材封面、非剧透质量摘要；
- 不得包含 `raw_text`、完整 `knowledge_graph`、truth、ending、隐藏 NPC、隐藏线索、原始 PDF 路径、本地路径、RAG chunk、AI prompt；
- 未授权素材不得进入 `PublishedModule` public payload。

## PublicBattleReport 发布边界

`PublicBattleReport` 必须满足“显式发布 + 脱敏来源 + 成员同意”三层约束：

- 必须由 source room owner 或授权成员显式创建分享；
- `public_payload` 必须来自 Safety 的 `public_export` 口径或等价安全构建流程，不得直接使用 raw events；
- 玩家角色名、高光片段、个人行动展示，默认需要成员同意或匿名化；
- `player-only`、`host-only`、hidden truth、private clue 永不进入公开战报；
- 如成员撤回同意，必须允许隐藏对应个人信息或下架报告。

进入工程前还要继续细化：

- 同意是按房间成员、按角色，还是按片段；
- 默认是匿名角色名，还是完全移除个人行动；
- 撤回同意后历史公开链接如何处理。

## PublicProfile 默认隐私

`PublicProfile` 默认应坚持最小公开：

- 不公开邮箱、手机号、登录凭证、account token；
- 不公开私密房间历史；
- 不公开角色详情；
- 不公开收藏，除非用户显式公开；
- 不公开出勤、举报、审核记录；
- 只展示 `displayName`、`bio`、`avatar` 和用户显式公开的作品、招募或战报。

补充说明：

- 真正进入 `Community-4` 工程前，必须补清 `profileId / slug` 策略；
- 必须明确 `slug` 是否可变、是否允许重复 `displayName`、保留词如何处理；
- 这些问题不阻塞当前文档通过，但会直接影响公开主页实现。

## 评论、评分、收藏反滥用规则

### Comment

- 仅登录用户可创建；
- 必须有基础限速；
- 作者可删除自己的评论；
- 内容作者可隐藏自己内容下的违规评论或发起处理请求；
- Admin/Ops 可执行 `hidden` / `removed`；
- 评论不写入房间事件流，不进入世界状态链路。

### Rating

- 同一账号对同一目标只能有一条评分；
- 重复评分应更新，不是新增刷分；
- 可在后续阶段增加“体验后评分”约束，但本轮只先写为后续选项；
- 评分变更必须有 `updated_at`。

### Favorite

- 默认私人；
- 不进入公开主页，除非用户显式公开；
- 取消收藏不影响目标对象本身。

## 举报、审核与授权素材

必须先写清的对象与字段方向：

- `ReportRequestDTO`：`targetType`、`targetId`、`reasonCode`、`detail?`、`reporterAccountId`、`createdAt`
- `ModerationCaseDTO`：`caseId`、`sourceReportId?`、`targetType`、`targetId`、`assignedAdminId?`、`status`、`decision`、`internalNote?`、`publicResultSummary?`、`createdAt`、`resolvedAt`
- `ModerationDecisionDTO`：`action`、`reason`、`notifyAuthor`、`notifyReporter`

素材授权最少字段：

- `assetId`
- `licenseType`
- `publicUseAllowed`
- `attribution?`
- `source?`
- `reviewerChecked?`

硬规则：

- 举报人身份不展示给被举报作者；
- 内部备注不进公开页；
- Admin 操作必须写入 `CommunityAudit`；
- 未授权素材不得进入公开 payload；
- 原始 PDF、本地路径、`storageKey` 不得出现在公开页面。

对 `PublishedModule` 还要继续确认作者授权边界：

- `author` 是否必须是 `source_scenario` owner；
- Admin 是否允许代管发布；
- 协作者模型是否存在；
- 导入者和作者是否等价。

## MVP 验收主链路
