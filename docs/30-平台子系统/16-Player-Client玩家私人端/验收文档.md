# Player Client 玩家私人端 验收文档

## 文档定位

本文档用于在收到工程师的 `回执-YYYY-MM-DD.md`、代码改动说明、测试结果后，判断 `16-Player-Client` 本轮工作是否真正完成。

它只负责验收，不替代：

- `功能列表.md`
- `PRD.md`
- `DeepSeek计划.md`

默认分两层结论：

- `本轮工程验收通过`：表示 Player Client 本轮 P0/P1 主链路已经闭环。
- `生产安全完成`：表示除本轮范围外，长期 token 策略、WS 握手、跨设备恢复、移动端回归等也基本稳定。

除非证据非常完整，否则默认只给 `本轮工程验收通过`，不直接给 `生产安全完成`。

## 验收输入

验收前至少应拿到以下材料：

- 本模块四份基线文档：`功能列表.md`、`PRD.md`、`DeepSeek计划.md`、`验收文档.md`
- 工程师回执：`回执-YYYY-MM-DD.md`
- 本轮改动文件清单
- 实际测试命令与测试结果
- 如涉及前端页面、共享类型或 WS 消费，附 `npm run build` 结果

## 结论等级

| 结论 | 含义 |
| --- | --- |
| `本轮工程验收通过` | 玩家端主链路、恢复链路、授权视图、错误恢复与文档对齐 |
| `本轮工程验收有缺口` | 主链路大体可用，但缺关键证据、关键测试或关键边界没有闭环 |
| `不通过` | 出现身份伪造、私密泄露、旧 patch 覆盖、匿名地图泄露、测试未过等硬问题 |
| `生产安全完成` | 仅在 token、WS、恢复与长期遗留项也收口后才能给出 |

## 一票否决项

出现任一情况，本轮不得判通过：

- 正式路径仍允许 `shared/api.ts:getPlayerToken()` 本地自造 `player_token`
- `join/restore-session` 返回的服务端 token 没有覆盖当前房间当前 slot
- `stateVersion` 屏障未落地，旧 patch 仍可能覆盖新状态
- 未来 patch 不能进入 buffer 并触发 `/api/player/sync`
- reconnect 返回未过滤的 Host-only 或他人 private 事件
- 玩家端仍能消费 Host-only 事件或他人 `player-only` patch
- `GET /api/map/{room_id}` 无 token 或错误 token 时仍返回隐藏节点、hidden NPC、未发现线索或私密位置
- 线索分享仍靠前端本地 `shared=true` 硬改，不重新拉取 `/api/player/clues`
- 401/403/404/409/429/500 没有明确恢复动作
- 关键测试命令未提供，或测试未通过

## 必备回执材料

工程师回执里至少应说明：

- 本轮覆盖了哪些 `Player Batch`
- 实际修改了哪些文件
- 实际运行了哪些测试，结果是什么
- 是否移除了 `getPlayerToken()` 的正式路径自造 token 逻辑
- 如保留 mock token，是否只允许显式 dev/mock mode
- 是否仍保留 `localStorage` token；如保留，是否写明是开发态遗留
- WS query token 是否做了日志脱敏
- 是否引入短期 WS ticket；如未引入，是否列为遗留项
- `PlayerApiErrorDTO.code` 最终枚举是什么
- `stateVersion` 最小测试覆盖了哪些场景
- archive 类型枚举是否已与服务端对齐
- 本轮 remaining limitations 是什么

如果回执把文档里明确标为“后续目标/遗留风险”的内容写成“已安全完成”，验收时应直接降级处理。

## 本轮工程验收清单

### 1. 入房、身份与 token

1. `npm run build` 是否通过。
2. 玩家触达页面中文是否无乱码。
3. `PlayerJoinPage` 是否登录后可回跳。
4. 四种角色来源是否互斥。
5. 入房成功是否保存服务端返回的 `player_token`。
6. `shared/api.ts` 是否移除正式路径中的本地自造 `player_token`。
7. 若保留 mock token，是否仅限显式 dev/mock mode。
8. `restore-session` 是否只允许恢复本人角色。
9. `restore-session` 是否只覆盖当前 `room/current slot`。
10. `IdentitySlot` 是否明确为开发态便利，而不是生产安全方案。
11. 若仍保留 `localStorage` token，回执是否明确说明遗留。
12. WS query token 是否至少做了日志脱敏。
13. 是否引入短期 WS ticket；若没有，是否列为遗留项。
14. `X-Room-Token` 是否随玩家 API 发送。
15. Authorization 是否只用于账号级接口。

### 2. Lobby、ready 与开局跳转

16. Lobby ready 失败是否回滚。
17. `team-message` 失败是否撤销本地乐观消息。
18. Host start 后是否自动跳行动页。
19. 轮询兜底是否不会重复跳转。
20. `s2c_room_lobby_snapshot` 是否刷新成员和 ready 状态。
21. `s2c_team_message` 是否只作为队内消息，不进入 AI 裁决。

### 3. 行动状态机、错误模型与 pending action

22. 行动提交是否生成 `action_id`。
23. 重复点击是否不会生成多条有效行动。
24. action UI 是否覆盖 `submitting / queued / batched / resolving / resolved / rejected / timeout`。
25. 409 duplicate 是否查询 action status。
26. 409 `state_version_conflict` 是否触发 sync。
27. 401 是否跳登录并保留 return path。
28. 403 是否清当前房间 session 并提示恢复角色。
29. 404 action 不存在时是否允许重新提交。
30. 429 是否显示限流与稍后重试。
31. 500 是否保留草稿并允许重试。
32. `PlayerApiErrorDTO.code` 是否至少包含：
    `not_authenticated`、`player_token_invalid`、`room_not_found`、`action_not_found`、`duplicate_action`、`state_version_conflict`、`rate_limited`、`server_error`
33. reconnect 是否恢复 `pending_actions`。
34. `queued` pending action 是否显示已排队。
35. `batched` pending action 是否显示本轮已入队。
36. `resolving` pending action 是否显示正在结算。
37. `resolved/completed` 是否会拉 action result 并解锁输入。
38. `rejected` 是否显示失败原因并允许新 action。
39. `timeout` 是否提示超时并允许新 action。
40. 本地 `submitting` 但 reconnect 找不到 action 时，是否先查 `/api/player/actions/{action_id}`。
41. action 404 后是否不本地伪造 `queued/completed`。

### 4. WS、reconnect 与 `stateVersion` 屏障

42. PlayerWS 是否暴露 `connecting/open/closed/reconnecting`。
43. WS 长断开或刷新后是否调用 reconnect。
44. `recent_events` 是否只使用服务端过滤结果。
45. `s2c_state_patch` 是否校验 `schemaVersion`。
46. 当前版本 patch 是否应用。
47. 旧 patch 是否丢弃。
48. 未来 patch 是否进入 buffer 并触发 `/api/player/sync`。
49. sync snapshot 后是否只应用仍有效的 buffered patch。
50. `lastSequence` 跳号是否不会被误当成权限错误。
51. 未知 `s2c_*` 是否默认忽略并 debug。
52. Player 端是否不消费 Host-only 事件。
53. Player A 是否收不到 Player B 的 private patch。
54. `stateVersion` 最小四类测试是否实际存在：
    旧 patch 丢弃、当前 patch 应用、未来 patch buffer+sync、sync 后只重放有效 patch。

### 5. 玩家资源视图

55. `currentHP/currentSAN/currentMP/currentLuck/status` 是否来自 runtime。
56. `skills/background/occupation` 是否来自角色卡基线。
57. Host HUD 与 Player 角色页当前 HP/SAN 是否一致。
58. 前端内部是否统一使用 `clueId`。
59. 适配层是否兼容 `clue_id/id`。
60. 线索分享是否使用服务端权威 `clue_id`。
61. 分享成功后是否重新拉 `/api/player/clues`。
62. Player archive 是否只含 `safeText/safePayload`。
63. archive 类型枚举是否与服务端一致，不再保留前端自造 `narrative` 偏差。
64. `GET /api/map/{room_id}` 无 token 时是否 401/403。
65. 地图响应是否不含隐藏节点、hidden NPC、未发现线索。
66. 地图移动是否走 intent。
67. 地图移动失败是否显示服务端原因。

### 6. 语音、移动端与增强输入

68. VoiceInput 失败时是否保留文本主路径。
69. 战术按钮是否只提交 intent，不本地判定成功。
70. 移动端底部 tab 是否不遮挡输入框。
71. 如项目当前无前端自动化测试，回执是否明确说明。

## 必跑测试

至少应包含：

```powershell
python -m pytest tests/server/test_character_join_import.py tests/server/test_player_intent.py tests/server/test_reconnect.py tests/server/test_clues.py tests/server/test_archive.py tests/server/test_ws_auth.py tests/server/test_host_room_lifecycle.py tests/server/test_player_runtime_state.py -q
```

如本轮补了 `stateVersion` 专项逻辑，建议额外提供更细粒度测试说明，至少覆盖：

- 旧 patch 丢弃
- 当前 patch 应用
- 未来 patch buffer + sync
- sync 后只重放有效 patch

前端至少应包含：

```powershell
cd src/client
npm run build
```

如项目当前已有前端测试，也应包含：

```powershell
cd src/client
npm run test
```

## 生产安全加签条件

以下条件未关闭前，不应给 `生产安全完成`：

- `player_token` 仍保存在 `localStorage`
- WS 仍主要依赖 query token，未切到短期握手票据或等价安全方案
- `IdentitySlot` 仍主要服务开发态，未与生产态会话策略解耦
- reconnect / sequence 仍缺少跨设备长期恢复策略
- 移动端、语音和弱网场景仍未做更大范围回归
