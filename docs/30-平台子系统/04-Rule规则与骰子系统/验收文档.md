# Rule 规则与骰子系统验收文档

## 文档定位

本文件用于在收到工程师的 `回执-YYYY-MM-DD.md` 后，判断 `04-Rule` 本轮工作是否真正完成。

Rule 的验收核心不是“骰子会转”，而是“服务端才是唯一数学裁决者，AI、前端、Host 都不能替代 Python RuleExecutor”。

默认分两层结论：

- `本轮工程验收通过`：表示 COC 7e 主链路、本轮规则口径和状态边界已完成。
- `生产安全完成`：表示私密骰、长期审计、随机数可追溯、多规则扩展等高风险项也已关闭。

## 验收输入

- 本模块三份基线文档
- 工程师回执：`回执-YYYY-MM-DD.md`
- 修改文件列表
- 测试命令与结果
- 如改了角色卡、玩家行动页或 Host 演出展示，附 `npm run build` 结果

## 结论等级

| 结论 | 含义 |
|---|---|
| `本轮工程验收通过` | 服务端权威掷骰、成功等级、bonusDice、State 边界和异常回执均已对上 |
| `本轮工程验收有缺口` | 主链路大体可用，但仍缺关键规则证据、关键边界值测试或关键安全项 |
| `不通过` | 前端/AI 能提交权威结果、成功等级漂移、状态写入越界或关键测试未过 |
| `生产安全完成` | 仅在私密骰、长期审计、visibility、触发器安全和随机数追溯等项也闭环后给出 |

## 一票否决项

- 前端提交的 `roll/result/successLevel` 被服务端采纳
- AI 返回的 `roll/result` 数值被服务端采纳为权威结果
- 成功等级枚举仍然双轨漂移
- `POST /api/player/skill-check` 悄悄替代正式 action lifecycle
- Rule Handler 直接写状态或直接写库
- Rule 异常后玩家端永久卡在 `resolving`

## 必备回执材料

回执至少应说明：

- 本轮覆盖了哪些 Rule 批次
- 改了哪些 skill_check / handler / executor / pipeline / archive / 前端展示文件
- 关键边界值测试结果
- 当前仍未关闭的私密骰、审计或多规则缺口

## 本轮工程验收清单

### 1. 正式主链路

- 权威规则检定仍以 `POST /api/player/intent` 为主入口
- `/api/player/skill-check` 仍只是 debug/兼容/降级入口
- `skill_check` intent 会进入正式 action lifecycle

### 2. 成功等级统一

必须确认：

- 全链路统一为 `critical/extreme/hard/regular/failure/fumble`
- `success_level`、`successLevel`、`level` 三者值等价
- 前端不再自己推导成功等级

### 3. COC 7e 边界值

回执至少应给出这些边界值测试证据：

- `roll=1`
- `roll=100`
- `roll=96`
- `skill=49`
- `skill=50`
- `hard` 门限
- `extreme` 门限

### 4. bonusDice 主链路

至少要确认：

- bonusDice 真正进入 RuleExecutor / Handler 主链路
- 负数惩罚骰也被正确处理
- bonusDice 有服务端范围限制
- 回执若声称已做可解释性，还需给出 raw dice components 保存证据

### 5. 权威来源边界

- `target/skillValue` 由服务端从角色卡或状态快照读取
- 前端传入的 skillValue 不覆盖权威值
- AI 只能给 mechanic 建议，不能给权威骰点

### 6. RollResult 与 visibility

至少要确认结果结构稳定包含：

- `rollId`
- `actionId`
- `characterId`
- `dice`
- `roll`
- `target`
- `difficulty`
- `successLevel/success_level`
- `bonusDice`
- `visibility`
- `source=server`

若回执声称支持私密骰，还应证明：

- 当前玩家只能看到自己的私密骰
- 其他玩家查不到私密骰结果

### 7. StateService 边界

- Rule Handler 只产出 mutation / ResolutionResult
- SAN / HP / Luck 变化由 StateService 应用
- Rule Handler 不直接写 SQL
- mutation 结构保持 RFC 6902 风格或等价标准 DTO

### 8. 异常与拒绝回执

至少要确认：

- Rule Handler 异常后 action 进入 `rejected`
- 玩家端收到 `s2c_action_completed` 或等价完成回执并被解锁
- 普通玩家只收到 `reasonCode/debugId` 级别信息
- 内部异常栈不会直接下发给普通玩家

### 9. 触发器 DSL 安全

- 触发器仍是 JSON 描述，不允许 Python/JS 脚本
- 未知 mechanic 不会被当成成功事实
- 质量检查若已做，应至少能发现未知 mechanic / 缺参数 / 非法 dice 表达式

## 必跑测试

至少应包含：

```powershell
pytest tests/server/test_skill_check.py tests/server/test_rules.py tests/server/test_rule_executor.py tests/server/test_mechanic_compiler.py tests/server/test_resolution_pipeline.py tests/server/test_player_intent.py tests/server/test_archive.py -q
```

如改了角色卡、玩家行动页或相关 UI：

```powershell
cd src/client
npm run build
```

## 生产安全加签条件

以下条件未关闭前，不应给 `生产安全完成`：

- 私密骰 visibility 仍未完整贯穿 Channel / Archive / Projection
- RollRecord 或等价随机数追溯仍不足
- 奖励/惩罚骰原始组成仍不可回放解释
- 多规则系统、房规和长期审计仍未设计完成
- 触发器 schema / quality 仍不稳定

后续工程师回执至少应回答：

1. 本轮覆盖了哪些 Rule 批次
2. 改了哪些 handler / executor / pipeline / 前端展示文件
3. 跑了哪些测试，结果是什么
4. 成功等级是否已完全统一

8. 还有哪些项只达到“工程执行通过”，尚未达到“生产安全完成”
