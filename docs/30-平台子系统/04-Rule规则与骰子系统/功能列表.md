# Rule 规则与骰子系统功能列表

## 模块定位

Rule 模块负责把玩家意图、剧本触发器和 AI-Keeper 的机制建议，转成服务端权威的规则事实：掷骰、成功等级、SAN/HP/Luck 变化、战斗/追逐结果、可播放的 reveal steps 和可落库的 state mutations。

Rule 不负责玩家身份、不负责状态最终落库、不负责公共舞台播放。它输出 `RuleResult/ResolutionResult`，由 Transaction、State、Projection、Journal 接续处理。

当前阶段说明：

- 本文件已可作为 Rule 模块工程执行入口，但当前阶段仍是“P0 主链路 + 规则口径风险识别版”。
- 文档已识别成功等级漂移、`/api/player/skill-check` fallback 混淆、bonusDice 主链路缺失、RollResult 字段不统一、SAN/HP mutation 与 StateService 边界、触发器 DSL 安全等风险。
- 这些风险不代表已经在代码中关闭；文档完成不等于生产安全完成。

## P0 功能

| 功能 | MVP | 当前代码 | 依赖 | 验收口径 | 现状风险 |
|---|---|---|---|---|---|
| 服务端权威掷骰 | 是 | 已有 `random.randint` 生成 D100 和 XdY | Engine、Journal | 前端不能提交权威 `roll/result` | 尚无统一 RollRecord，追溯依赖 action/event payload。 |
| COC 技能检定 | 是 | `roll_skill_check` 与 `CocSkillCheckHandler` 都能检定 | Character | 服务端从角色卡或状态快照读取权威技能值，返回 roll、target、success | 两条链路的成功等级口径不一致；前端传入的 `skillValue` 仍需明确为非权威。 |
| 难度门限 | 是 | regular/hard/extreme | Character | 60 技能对应 `60 / floor(60/2)=30 / floor(60/5)=12` | 规则文档还需要把 `floor` 和判定顺序写死，避免前后端各自理解。 |
| 大成功/大失败 | 是 | 独立函数覆盖 1/100；Handler 覆盖 1/100/低技能 96+ | Rule | 边界值有单测 | `critical_success` 与 `critical` 需要统一；`skill=49/50` 的大失败边界需明确默认口径。 |
| 奖励/惩罚骰 | 是 | `roll_skill_check` 支持 `bonus_dice` | Player Client | bonus 取更小十位，penalty 取更大十位 | 主 `CocSkillCheckHandler` 尚未接入 bonus_dice；默认允许范围和原始十位骰审计仍未写死。 |
| 玩家技能按钮 | 是 | `PlayerCharacter.tsx` 提交 `skill_check` intent | Player Client、Character | 点击技能不会在前端掷权威骰 | fallback `/skill-check` 只能视为兼容/降级路径，不应静默替代正式 action lifecycle。 |
| 机制编译 fallback | 是 | `MechanicCompiler._compile_python` | AI-Keeper | 搜索/聆听/图书馆/说服等文本可映射技能 | 技能词表较小，规则解释有限。 |
| 规则执行器 | 是 | `RuleExecutor.execute` | Engine | compiled mechanic 能路由到 handler | handler missing 只写 warning，不一定给玩家清晰反馈。 |
| 剧本触发器 | 是 | `evaluate_triggers` 支持 `$action/itemId` | Module、WorldBook | use_item 命中后可触发 sanity_check | 条件语法很窄，缺 schema 校验。 |
| SAN 检定 | 是 | `CocSanityCheckHandler` | State | 按成功/失败损失公式扣 SAN | `parse_dice` 仅支持 `XdY`，不支持 `1d6+1`。 |
| HP 伤害 | 是 | `CocCombatHandler` | State | 伤害后生成 `/character/hp` mutation | 普通 damage handler 和 encounter handler 不同口径。 |
| Luck 检定 | 是 | `CocLuckCheckHandler` | Character | d100 <= luck 判成功 | 没有 Luck 花费/扣减流程。 |
| Reveal steps | 是 | Handler 输出 `roll/status_delta/damage/move` | Transaction、Host Client | Host 可以播放骰子和状态变化 | step payload 字段尚未完全统一，`RollResult` 还缺 `rollId/visibility/source/bonusDice` 等标准字段。 |
| Action completed 投影 | 是 | `ResolutionPipeline._action_completed_payload` | Projection、Player Client | 玩家收到自己的 roll/target/success | payload 用 `level`，前端主要找 `success_level/successLevel`，有错配风险；私密骰还缺 visibility 约束。 |
| 状态 mutation 输出 | 是 | Handler 返回 RFC 6902 风格 mutation | State | Rule 不直接落库，StateService 应用 | mutation 结构要继续锁死，避免后续退回自由 dict。 |

## 关键边界

- AI-Keeper 可以建议 `rollRequests` 和 `triggeredMechanic`，不能生成权威骰点。
- 前端可以请求检定，不能提交权威 `roll/result/success_level`。
- 正式 `skill_check` 的 target/skillValue 必须由服务端从角色卡或状态快照读取，前端传值不得覆盖权威值。
- `POST /api/player/skill-check` 只是 debug/兼容/降级入口，不进入正式 action lifecycle，不写状态，不触发事务，不应成为默认主入口。
- Rule Handler 只输出规则事实和 mutation 建议；状态最终写入由 StateService 负责。
- Host 只播放 `s2c_reveal_transaction`，不能在播放层改写结果。
- Rule 产生的骰子结果进入 Channel/Archive 时，必须携带 `visibility` 和 `source=server`，查询仍走服务端过滤。
- 规则文档 RAG 只能用于解释和引用，不能覆盖 Python RuleExecutor 的数学结果。
