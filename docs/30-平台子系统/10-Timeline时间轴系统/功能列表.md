# Timeline 时间轴系统功能列表 V2.1

## 当前阶段说明

本模块当前处于 `P0 主链路 + 时间线顺序与可见性风险识别版`。

第一轮目标不是做完整长团年表或复杂日历，而是先把 `回合顺序 -> 行动归属 -> 事件 sequence -> 玩家可见历史 -> 断线补发 -> checkpoint 解释 -> gameTime 边界` 这条链路钉牢，避免顺序漂移、补发越权和回放口径不一致。

## 模块定位

Timeline 模块是 AI-Keeper 的 `顺序与可见性索引层`，负责定义：

- 当前房间处于第几回合
- 玩家行动归属哪个 turn
- 事件按什么 sequence 排序和补发
- Host 与 Player 各自能看到哪些历史
- checkpoint/restore 在时间线中怎么解释
- 游戏内时间如何接入而不与真实写入时间混用

Timeline 不负责：

- 保存完整日志正文
- 裁决行动成功失败
- 写世界真相或角色数值
- 替代 Journal、State、Rule、AI-Keeper

这些能力分别交给 `Journal`、`State`、`Rule`、`Transaction`、`AI-Keeper` 模块处理。

## Timeline 数据分层

| 层级 | 数据对象 | 归属模块 | 说明 | 禁止混用 |
| --- | --- | --- | --- | --- |
| L0 | `issued_at / created_at / completed_at` | DB / Journal | 真实服务器写入时间 | 不等于故事时间 |
| L1 | `events.sequence` | Timeline / Journal | 事件顺序主游标，用于分页、补发、回放 | 不等于回合号 |
| L2 | `room_turns.turn_index`、`actions.turn_id` | Timeline / Transaction | 回合批次和行动归属 | 不等于事件 sequence |
| L3 | `player_sequences.last_delivered_sequence` | Timeline / reconnect | 玩家补发游标 | 不等于权限过滤结果 |
| L4 | `HostTimelineView` | Host Client / Journal | Host 的完整房间事件投影 | 不能给 Player 复用 |
| L5 | `PlayerArchiveView` | Player Client / Projection | 玩家的过滤后历史 | 不能含 host-only 或他人私密事件 |
| L6 | `checkpoints` | Timeline / State / Journal | 状态恢复点和断点 | 不等于“回滚时间本身” |
| L7 | `gameTime` | StateService | 故事内时间、倒计时、时钟 | 不等于 `issued_at` |
| L8 | Journal 内容正文 | Journal | 事件 payload、归档内容、说明文字 | Timeline 只索引顺序，不替代正文存储 |

## Timeline DTO 分层

| DTO | 用途 | 允许字段 | 禁止字段 |
| --- | --- | --- | --- |
| `TimelineEntryDTO` | 时间线最小公共结构 | `sequence`、`eventType`、`audience`、`issuedAt`、`turnId`、`turnIndex`、`visibility`、`payload` | 未过滤的原始 payload |
| `HostTimelineEntryDTO` | Host 全量事件视图 | `TimelineEntryDTO` 全字段 + 审计字段 + 完整 payload | 仅内部调试字段可继续禁止 |
| `PlayerTimelineEntryDTO` | 玩家历史和重连事件 | `sequence`、`eventType`、`issuedAt`、`turnId`、`turnIndex`、`visibility`、安全 payload | host-only payload、他人 private payload、未白名单 system payload |
| `ReconnectEventDTO` | reconnect / catch-up 事件 | `PlayerTimelineEntryDTO` 的安全子集 + `lastSequence` 语义 | 不能绕过 archive 的过滤规则 |

## 可见性语义

原始事件 `audience` 保持：

- `host`
- `party`
- `player`
- `system`

Timeline 派生 `visibility` 建议统一为：

- `host`
- `party`
- `self`
- `system_safe`
- `private_filtered`

补充约束：

- `visibility` 是派生字段，不等于原始 `audience`
- Player archive、reconnect、WS catch-up 必须复用同一可见性 helper
- `system` 事件不能默认全部给 Player，必须走白名单

## sequence scope 与补发规则

- `events.sequence` 当前可以继续使用全局 BIGSERIAL。
- 但所有 timeline、archive、reconnect、replay 查询都必须以 `room_id + sequence` 为边界。
- 不能只凭 sequence 跨房间读取、补发或恢复事件。
- 同一房间内 sequence 单调递增即可满足分页和补发。

`player_sequences` 更新规则必须写死：

- 只能更新为“实际安全返回给该玩家的最大 sequence”
- 不能按房间全量 events 的最大 sequence 更新
- snapshot 分支也不能跳过过滤后直接把玩家游标推进到全量最大值

## 回合状态与并发锁语义

| 状态 | 含义 | 约束 |
| --- | --- | --- |
| `collecting` | 收集玩家行动 | 同一房间应最多存在一个 |
| `resolving` | 结算进行中 | 只有抢到状态转移的 worker 才能进入 |
| `resolved` | 本轮已完成 | 不应再次 settle |
| `blocked` | 本轮被暂停或需人工处理 | retry 必须带审计原因 |

补充约束：

- active 房间在 collecting 阶段应有一个 collecting turn。
- active 房间在 resolving 阶段，当前 turn 可以处于 `resolving`，不能为了满足“始终有 collecting turn”而提前开放下一回合提交。
- 下一 collecting turn 只应在当前 turn 真正 resolved 后创建。

回合结算必须以工程化策略保证幂等：

- `collecting -> resolving` 必须通过条件更新或事务锁完成
- 只有成功抢到状态的 worker 才能继续结算
- 创建下一 collecting turn 前必须检查是否已存在更新的 collecting turn

## 合法参与者集合

all_submitted 的参与者集合必须和 `01-Room`、`05-Character` 对齐：

- `joined` 参与
- `pending_approval` 不参与
- `left/removed` 不参与
- `ready` 只用于开局前，不应在 active 房间继续作为是否参与本回合的唯一口径
- `active` 仅用于 legacy read compatibility，不应继续作为新写入口径

## Host skip / retry 语义

- `skip-character` 是舞台急救能力，不是常规结算路径
- `retry-turn` 默认只允许对 `blocked` 或显式标记为 `retryable` 的 `resolved` turn 执行
- `collecting / resolving` turn 不允许 retry
- `skip` 与 `retry` 都应要求 `reason`
- `skip / retry` 必须记录操作者、目标角色、turn、原因、时间、影响 action 集合

duplicate 的“有效 action”集合也需要写清：

- 计入 duplicate 阻塞的状态应至少包括：`queued`、`batched`、`resolving`、`resolved`、`completed`、`blocked`
- `rejected / cancelled` 不计入 duplicate 阻塞
- 如代码中的最终状态枚举不同，工程回执必须明确实际采用的状态集合

## checkpoint restore 语义

本轮默认语义应明确为：

- restore 不重写旧历史的产品含义
- 当前代码会重插 snapshot 内 events，旧 `sequence` 不保留，这是“恢复后的新历史”
- restore 后必须写新的 `s2c_checkpoint_restored` marker
- `s2c_checkpoint_restored` 默认应作为 Host 可见审计事件处理；如需要通知 Player，应另发 party-safe 摘要，而不是直接复用原始 restore 审计 payload
- Host 回放和审计必须能看见这个断点
- Player replay/export 继续走安全过滤

## gameTime 写入边界

- `gameTime` 只能由 Host 显式接口或 Engine/StateService 事务结果写入
- AI 只能建议，不直接落库
- Player 只读安全展示字段
- 如果推进原因含剧透，应生成 `safeReason`，不能把 host-only reason 原文直接投给玩家

system 事件白名单也应收口到最小集合：

- 可对 Player 可见的示例：`s2c_turn_resolved`、`s2c_game_time_updated` 的 safe payload、`s2c_checkpoint_created` 的安全摘要（如果产品允许）
- 默认不对 Player 可见的示例：`s2c_checkpoint_restored` 原始审计、内部错误、debug 事件、restore reason、admin override

## P0 MVP 必须稳定

| 功能 | 当前状态 | 进入 MVP | 依赖模块 | 验收口径 |
| --- | --- | --- | --- | --- |
| active 房间存在当前 collecting turn | 已在开局创建 | 是 | Room | 开局后存在 exactly one collecting turn |
| 玩家行动绑定 turn | active 路径已绑定 | 是 | Player、Transaction | 玩家行动必须有 `turn_id`，不能留下孤儿 queued action |
| 单玩家单回合一次有效行动 | 已有 duplicate 检查 | 是 | User、Transaction | duplicate 返回 409 时不得新增 action/event/version |
| 回合结算幂等 | 当前缺少强锁 | 是 | Transaction | 同一 turn 只 resolve 一次，只创建一个下一回合 |
| Player archive 安全过滤 | 已有 archive，但规则分散 | 是 | Projection、Safety | 玩家只能看到 party、安全 system 和自己的 player 事件 |
| reconnect 安全补发 | 当前 snapshot 和普通分支都偏松 | 是 | Projection、Player Client | reconnect 不返回 host-only 或他人私密事件 |
| Host timeline 鉴权 | 已有 owner/admin 鉴权 | 是 | User、Host Client | 非房主、非 admin 不能读 `/timeline` |
| checkpoint 顺序可解释 | 已有 restore marker 入口 | 是 | Journal、State | 恢复后时间线断点有可追踪标记 |
| gameTime 与真实时间分离 | 尚未正式建模 | 是 | State | 不再用 `issued_at` 充当故事时间 |

## 不属于本模块

| 内容 | 交给哪个模块 | 原因 |
| --- | --- | --- |
| 事件 payload 正文存储与导出 | Journal | Timeline 只定义顺序和索引 |
| 行动成功失败裁决 | Rule、Transaction、AI-Keeper | Timeline 不裁决结果 |
| 世界真相和状态写入 | State | Timeline 只承接顺序与显示 |
| 玩家聊天产品体验 | Channel | Team message 会进入事件流，但频道体验归 Channel |
| 长团结局摘要生成 | Journal、AI-Keeper | Timeline 只给顺序和断点 |

## 当前最高风险

| 风险 | 影响 | 优先级 |
| --- | --- | --- |
| `submit_intent` 先 `engine.submit_intent` 再 `tm.submit_action` | duplicate 场景可能先写 action，再返回 409，留下孤儿 queued action | P0 |
| `ensure_current_turn` 在读路径自动创建 turn | 非 active 房间查询 current turn 可能产生多余回合 | P0 |
| `mark_resolving` 无条件更新，`_settle_turn_background` 直接创建下一 turn | 并发 settle 可能重复 resolve 和重复创建 collecting turn | P0 |
| reconnect snapshot 分支返回全量 events | host-only 或其他玩家 private event 可能直接泄露 | P0 |
| `manager.reconnect` 普通分支按 room 全量 sequence 拉 events | 未经过统一可见性 helper 的补发存在越权风险 | P0 |
| archive 和 `get_events_for_player` 把 `system` 基本整体放行 | system 事件可能带出不该给玩家的内部信息 | P0 |
| `payload.characterId` / `payload.character_id` 命名混用 | self event 过滤和补发可能口径不一致 | P1 |
| `s2c_turn_resolved` 未进入 registry / model / frontend type | 事件分发、日志筛选、前端解析口径不一致 | P1 |
| restore 重插 snapshot 内 events，旧 `sequence` 不保留 | 恢复后的历史语义不明确，回放解释困难 | P1 |
| gameTime 未正式建模 | `issued_at` 和故事时间容易混用 | P1 |

## MVP 验收主链路

1. Host 创建房间，玩家加入并 ready。
2. Host 开局，系统创建第 1 个 collecting turn。
3. 玩家提交行动，action 绑定当前 `turn_id`。
4. 同一玩家重复提交被拒绝，数据库没有新增孤儿 queued action。
5. 所有合法参与者提交或被 Host skip 后，回合进入 resolving。
6. 只有一个 worker 完成结算，并只创建一个下一 collecting turn。
7. Host timeline 能按 sequence 查到 queued、completed、turn resolved、checkpoint 事件。
8. Player archive 只能看到公开事件和自己的私密事件。
9. Player reconnect 只补发自己有权看到的事件，并返回正确 last_sequence。
10. gameTime 与真实写入时间分离，时间线断点可解释。
