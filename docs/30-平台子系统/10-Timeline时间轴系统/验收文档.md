# Timeline 时间轴系统验收文档

## 文档定位

本文件用于在收到工程师的 `回执-YYYY-MM-DD.md`、代码改动说明、测试结果后，判断 `10-Timeline` 本轮工作是否真正完成。

它只负责验收，不替代 `功能列表.md`、`PRD.md`、`DeepSeek计划.md`。

默认分两层结论：

- `本轮工程验收通过`：表示 Timeline 本轮承诺的 P0 主链路、顺序权威、可见性过滤、补发游标和恢复断点边界已完成。
- `生产安全完成`：表示除本轮范围外，Timeline 的长期高风险缺口也已关闭。

除非证据非常完整，否则默认只评 `本轮工程验收通过`，不直接给 `生产安全完成`。

## 验收输入

验收前至少应拿到以下材料：

- 本模块四份基线文档：`功能列表.md`、`PRD.md`、`DeepSeek计划.md`、`验收文档.md`
- 工程师回执：`回执-YYYY-MM-DD.md`
- 本轮改动文件列表，至少说明改了哪些 turn、timeline、archive、reconnect、event_log、state、前端、测试文件
- 测试命令与结果
- 如涉及 Host 日志页、Player 日志页，附 `npm run build` 结果和手动链路验证结果

## 结论等级

| 结论 | 含义 |
|---|---|
| `本轮工程验收通过` | 当前回合、duplicate 保护、turn 幂等、archive/reconnect 可见性、`player_sequences` 更新、checkpoint restore 断点、gameTime 初版边界和关键测试都已对上 |
| `本轮工程验收有缺口` | 主链路基本可用，但仍缺关键证据、关键测试或关键安全边界 |
| `不通过` | 出现孤儿 action、并发双结算、archive/reconnect 泄露、system 事件白名单失效、restore 断点不可解释、gameTime 越权写入、测试未过或回执与实际不符 |
| `生产安全完成` | 只有在 room-local/长期 sequence 策略、完整 replay 规范、restore 审计闭环、前端 timeline 体验和长期 gameTime 策略都稳定后才可给出 |

## 一票否决项

出现任一情况，本轮不能判通过：

- active 房间没有清晰当前 turn，或出现多个 collecting turn
- 玩家 duplicate 提交后仍写入新 action，或留下无 `turn_id` queued action
- 非 active 房间 `GET /turns/current` 仍隐式创建 turn
- 同一 turn 可被并发 settle 多次，或会创建多个下一 collecting turn
- Player archive / reconnect 仍能看到 host-only 事件
- Player archive / reconnect 仍能看到其他玩家 private 事件
- system 事件未按白名单过滤，导致内部/restore/debug 事件进入 Player 视图
- reconnect snapshot 分支仍返回 room 全量 events
- `player_sequences` 仍按房间全量最大 sequence 推进
- `s2c_turn_resolved` 仍未进入 registry / Pydantic / TS 联合类型
- restore 后没有 `s2c_checkpoint_restored` 审计 marker
- AI 仍可直接写 `gameTime`、`sequence` 或 `turn status`
- 测试命令未提供，或关键测试明显未通过

## 必备回执材料

工程师回执里至少应明确：

- 本轮对应的 Batch 范围，例如 `Timeline-1 ~ Timeline-5`
- 实际修改文件
- 实际测试命令
- 实际测试结果
- 明确完成项
- 明确未完成但保留为后续 Batch/P1 的项
- 如采用兼容方案，说明哪些仍是过渡实现

如果回执把文档里明确属于后续项的缺口写成“已完成”，验收时应直接降级处理。

## 本轮工程验收清单

### 1. 当前回合与 active 房间语义

- 开局后存在第 1 个 collecting turn
- active 房间在 collecting 阶段只有一个 collecting turn
- active 房间在 resolving 阶段当前 turn 可以为 `resolving`
- resolving 阶段不会为了“始终有 collecting turn”而提前开放下一轮提交
- 非 active 房间 `GET /turns/current` 不创建 turn

### 2. duplicate 与 action 生命周期

- 玩家提交 action 时必须绑定 `turn_id`
- duplicate 提交返回 `409`
- duplicate 不产生新 action
- duplicate 不产生无 `turn_id` queued action
- duplicate 不写多余 event
- duplicate 不 bump version
- 回执需说明 duplicate 阻塞的实际状态集合
- `rejected / cancelled` 默认不计入 duplicate 阻塞

### 3. all_submitted 合法参与者集合

- `joined` 参与 all_submitted
- `pending_approval` 不参与
- `left / removed` 不参与
- `ready` 不再作为 active 回合参与判定的唯一口径
- 如存在 legacy `active` 状态，回执需说明仅用于读兼容还是仍参与新写逻辑

### 4. turn 并发结算幂等

- `collecting -> resolving` 通过条件更新或等价事务锁完成
- 并发 settle 只有一个 worker 成功
- 同一 turn 只 resolved 一次
- 下一 collecting turn 只创建一个
- resolving 失败或重入不会撕裂 turn 状态

### 5. Host skip / retry 审计

- Host skip 需要 `reason`
- Host skip 记录 `actor / targetCharacterId / turnId / turnIndex / reason / createdAt`
- retry 需要 `reason`
- retry 默认只允许 `blocked` 或显式 `retryable` 的 `resolved` turn
- `collecting / resolving` turn 不允许 retry
- retry 审计至少有 `actor / fromStatus / affectedActionIds / reason`

### 6. archive / reconnect / WS catch-up 统一过滤

- archive 使用统一可见性 helper
- reconnect 使用统一可见性 helper
- WS catch-up 使用统一可见性 helper
- `payload.characterId` / `payload.character_id` 都能正确识别本人事件
- archive / reconnect 对同一批事件给出一致结果

### 7. Player 可见性与 system 白名单

- Player archive 看不到 host event
- Player archive 看不到其他玩家 private event
- reconnect 看不到 host event
- reconnect 看不到其他玩家 private event
- `system` 事件只有白名单可见
- 白名单最少应能说明：
  - `s2c_turn_resolved`
  - `s2c_game_time_updated` 的 safe payload
  - 若产品允许，`s2c_checkpoint_created` 的安全摘要
- 默认不可见的 system 示例应包括：
  - `s2c_checkpoint_restored` 原始审计
  - 内部错误
  - debug
  - restore reason
  - admin override

### 8. `player_sequences` 安全推进

- `player_sequences` 只按实际安全返回给该玩家的最大 sequence 更新
- 不按房间全量 events 最大 sequence 更新
- reconnect snapshot 分支也不应把玩家游标直接推进到全量最大值
- host-only / 非白名单 system 事件不会把玩家游标推过头

### 9. sequence 边界

- timeline 查询按 `room_id + sequence`
- reconnect 补发按 `room_id + sequence`
- replay 按 `room_id + sequence`
- 不存在只凭 sequence 跨房间读取事件的路径

### 10. 事件注册表、类型和 DTO

- `s2c_turn_resolved` 已进入 `events_registry.py`
- `s2c_turn_resolved` 已进入 Pydantic / `EngineEventType`
- `s2c_turn_resolved` 已进入前端 TS 联合类型
- Host timeline / Player archive / reconnect 返回字段和 `TimelineEntryDTO` 口径一致
- 前端类型收紧后 `npm run build` 通过

### 11. checkpoint / restore 断点语义

- restore 后写入 `s2c_checkpoint_restored`
- Host 能在 timeline 中看到恢复断点
- restore 后旧历史不被伪装成“同一条连续历史”
- 如当前实现仍重插 snapshot events，回执要明确 sequence 会重新生成
- `s2c_checkpoint_restored` 默认走 Host 审计可见
- 如果额外通知 Player，必须另发 party-safe 摘要，而不是复用原始 restore payload

### 12. gameTime 边界

- `gameTime` 与 `issued_at` 分离
- `gameTime` 只由 Host 或 Engine/StateService 受控路径写入
- AI 只能建议，不能直接写 `gameTime`
- Player 只看到安全展示字段
- 如有 reason，对 Player 应只投 `safeReason`

### 13. 端到端主链路

至少应手动或自动证明以下链路：

1. Host 创建房间，玩家加入并 ready
2. Host 开局，创建第 1 回合
3. 玩家提交 action，并成功绑定当前 `turn_id`
4. 玩家重复提交被拒绝，且无孤儿 action
5. 全员提交后自动结算
6. 同一 turn 没有双结算
7. Host timeline 能看到 turn/action/checkpoint 相关事件
8. Player archive 只能看到公开事件和自己的私密事件
9. 玩家断线 reconnect 只补发安全事件，并正确推进游标
10. Host 执行一次 checkpoint restore，timeline 出现恢复断点
11. Host 设置一次 gameTime，Player 只看到安全展示字段

## 生产安全加签条件

以下条件未关闭前，不应给 `生产安全完成`：

- resolving / next collecting 的长期调度策略仍未完全稳定
- `player_sequences` 与 reconnect snapshot 的长期一致性仍未经更大规模验证
- system 白名单仍处于手工维护期，未形成统一 registry 策略
- restore 重插事件与 replay 解释仍存在长期复杂度
- `s2c_checkpoint_restored` 的 Host/Player 双视图策略仍未完全定型
- gameTime 仅是初版，还未覆盖 countdown / absolute / relative 的完整模型
- 时间线前端筛选、回放和导出体验仍未完全成型
