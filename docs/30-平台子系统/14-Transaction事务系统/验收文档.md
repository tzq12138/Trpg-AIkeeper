# Transaction 事务系统验收文档

## 文档定位

本文档用于在收到工程师的 `回执-YYYY-MM-DD.md`、代码改动说明、测试结果后，判断 `14-Transaction` 本轮工作是否真正完成。

它只负责验收，不替代：

- `功能列表.md`
- `PRD.md`
- `DeepSeek计划.md`

默认分两层结论：

- `本轮工程验收通过`：表示 Transaction 本轮承诺的 P0 / P1 主链路已经闭环。
- `生产安全完成`：表示除本轮范围外，长链路恢复、事务补偿、持久化策略和更大范围回归也已基本稳定。

除非证据非常完整，否则默认只给 `本轮工程验收通过`，不直接给 `生产安全完成`。

## 验收输入

验收前至少应拿到以下材料：

- 本模块四份基线文档：`功能列表.md`、`PRD.md`、`DeepSeek计划.md`、`验收文档.md`
- 工程师回执：`回执-YYYY-MM-DD.md`
- 本轮改动文件清单，至少说明改了哪些 player/router、turn_manager、resolution_pipeline、projection、host_store、host_router、models、tests 文件
- 实际测试命令与测试结果
- 如涉及前端 `HostStage`、`shared/types.ts` 或 WS 协议，附 `npm run build` 结果与手动链路验证结果

## 结论等级

| 结论 | 含义 |
| --- | --- |
| `本轮工程验收通过` | Transaction 本轮 P0 / P1 目标已完成，duplicate、turn settle、State/Projection 时序、Host ACK、release gate、trace 与 retry 语义与文档对齐 |
| `本轮工程验收有缺口` | 主链路基本可用，但仍缺关键证据、关键测试或关键边界闭环 |
| `不通过` | 出现重复结算、重复投影、State 先后顺序错误、Host 私密泄露、恢复策略缺失、测试未过或回执与实际不符 |
| `生产安全完成` | 只有在补偿策略、长链路恢复、最小事务持久化和更广回归也稳定后才可给出 |

## 一票否决项

出现任一情况，本轮不能判通过：

- duplicate 保护仍只是普通“先查再写”，没有数据库级唯一约束或同事务锁
- 普通 action 入队仍推进 `rooms.state_version`
- 同一 turn 仍可能被多个 worker 重复 settle
- `ResolutionPipeline` 仍先对外投影，再去写 State
- State 失败时 action 仍以正常 `resolved` 语义返回
- `s2c_state_patch`、`s2c_action_completed`、`s2c_reveal_transaction` 缺关键 trace / version 字段
- Host reveal 仍携带 `player-only state patch`、`private_notice`、raw mutation、hidden truth
- `ReleaseGateDTO` 只存在于内存，却在回执中声称“Host 重连可恢复”
- `host_step_complete` 仍不校验 Host 身份、`transactionId` 或 `stepId`
- `projection_failed` 后仍通过重跑 Rule 或重写 State 来恢复
- `retry-turn` 默认会重放已落库 mutation
- reconnect 仍返回玩家不可见事件或其他玩家 private action
- 关键测试命令未提供，或实际未通过

## 必备回执材料

工程师回执里至少应明确：

- 本轮对应的 Batch 范围，例如 `Tx-1 ~ Tx-6`
- 实际修改文件
- 实际测试命令
- 实际测试结果
- duplicate 占位状态集最终如何实现
- `timeout` 是否继续占位
- `projection_failed` 的恢复策略
- `ReleaseGateDTO` 最终持久化在哪里
- `s2c_reveal_transaction` 的 Host-safe step 白名单
- 本轮是否新增最小 `transactions` 表
- 如未新增，`host_states` 新增了哪些恢复字段
- `GET /turns/current` 是否继续保留隐式创建 turn

如果回执把文档里明确属于后续项的缺口写成“已完成”，验收时应直接降级处理。

## 本轮工程验收清单

### 一、action 幂等与 duplicate

1. 同一 `action_id` 重复提交是否只保留一条 action。
2. 同一 `action_id` 重复提交是否不重复发 `s2c_action_queued`。
3. 同一 `action_id` 重复提交是否不重复发 Projection。
4. 同一 `action_id` 重复提交是否不重复应用 State mutation。
5. 同一角色同一 turn 第二个不同 action 是否返回 409。
6. duplicate 409 是否不写新 action。
7. duplicate 409 是否不写 queued event。
8. duplicate 409 是否不 bump `rooms.state_version`。
9. duplicate 是否有数据库唯一约束或同事务锁保护。
10. 有效 action 占位状态集是否在回执中说明。
11. `rejected/cancelled/system_skip` 是否被排除在 duplicate 阻断集外。
12. `timeout` 是否按本轮口径继续占位，且回执已说明。
13. `ready_toggle` 是否不进入 turn action。
14. 普通 action 入队是否不推进 `rooms.state_version`。
15. `base_state_version` 过旧时是否返回 409 + `currentVersion`。

### 二、turn settle 并发屏障

16. `mark_resolving()` 是否是条件更新。
17. `mark_resolving()` 失败的 worker 是否直接退出。
18. 未抢到 resolving 的 worker 是否不写事件。
19. 未抢到 resolving 的 worker 是否不创建 next turn。
20. 同一 turn 并发 settle 时是否只有一个 worker 继续。

### 三、单 action 事务顺序

21. `resolved` action 再 resolve 是否直接返回已有结果。
22. `rejected` action 再 resolve 是否直接返回已有结果。
23. 重复 resolve 是否不重复应用 State mutation。
24. 重复 resolve 是否不重复发 Projection。
25. 单 action 链路是否先 `mark resolving`。
26. 单 action 链路是否先 `compute resolution`。
27. `actions.result` 写入后是否仍不提前对外宣布 `completed`。
28. `StateService.apply_change()` 是否在 Projection 前执行。
29. State 成功后是否再发 `state patch`。
30. State 成功后是否再发 `action completed`。
31. State 失败时 action 是否不会正常 `resolved`。
32. `state_apply_failed` 是否有明确状态、回执或审计。
33. `projection_failed` 是否不会重放 State mutation。
34. `projection_failed` 是否只通过 replay Projection / redelivery event 恢复。

### 四、版本字段与 trace

35. `s2c_state_patch` 是否带 `actionId`。
36. `s2c_state_patch` 是否带 `baseStateVersion`。
37. `s2c_state_patch` 是否带 `stateVersion`。
38. `s2c_action_completed` 是否带 `actionId`。
39. `s2c_action_completed` 是否带 `stateVersion` 或等价 trace。
40. `s2c_reveal_transaction` 是否带 `transactionId`。
41. `s2c_reveal_transaction` 是否带 `actionId`。
42. `s2c_reveal_transaction` 是否带 `turnId`。
43. `s2c_reveal_transaction` 是否带 `stateVersion` 或等价版本引用。
44. 所有事务事件是否至少带 `actionId/turnId/transactionId` 之一。

### 五、Host reveal 与 release gate

45. Host reveal steps 是否只包含 Host-safe payload。
46. Host reveal 是否不包含 `player-only state patch`。
47. Host reveal 是否不包含 `private_notice`。
48. Host reveal 是否不包含未公开 clue 原文、raw mutation、hidden truth。
49. `ReleaseGateDTO` 是否由服务端生成。
50. Player 私密 patch 是否进入 release gate。
51. Player `private_notice` 是否进入 release gate。
52. Player `action_completed` 是否按 gate 释放。
53. `ReleaseGateDTO` 是否持久化到 `host_states`、最小 `transactions` 表或等价持久化链路。
54. delayed events / release gates 是否不会因 Host 重连丢失。

### 六、Host ACK 与恢复

55. `host_step_complete` 是否校验 Host 身份。
56. `host_step_complete` 是否校验 `transactionId`。
57. `host_step_complete` 是否校验 `stepId`。
58. Host ACK 是否只携带演出进度。
59. Host ACK 是否不携带规则结果。
60. Host ACK 是否不携带状态 mutation。
61. Host ACK 是否写事件或持久 transaction state。
62. Host 重连后是否不会重复播放已 ACK step。

### 七、retry-turn 与 system_skip

63. `retry-turn` 是否支持 `replay_only`。
64. `retry-turn` 是否支持 `recompute_unresolved`。
65. `retry-turn` 是否支持 `restore_from_checkpoint`。
66. retry resolved turn 是否不会默认重放 State mutation。
67. `skip-character` 是否生成 `system_skip`。
68. `system_skip` 是否带 `actor/target/reason` 审计。

### 八、事件注册、重连与 Journal

69. `s2c_turn_resolved` 是否进入 registry。
70. `s2c_turn_resolved` 是否进入后端模型。
71. `s2c_turn_resolved` 是否进入前端 TS 类型。
72. reconnect 是否只返回玩家可见事件。
73. reconnect 是否只返回自己的 pending actions。
74. Player 是否不能查询他人 action。
75. Journal 是否能按 `actionId` 查询事务链。
76. Journal 是否能按 `turnId` 查询事务链。
77. Journal 是否能按 `transactionId` 查询事务链。

### 九、持久化决策与接口遗留

78. 本轮是否新增最小 `transactions` 表。
79. 如未新增，`host_states` 是否补齐 `queue/active/currentStep/ack/delayedEvents`。
80. `GET /turns/current` 隐式建 turn 是否在回执中明确说明。
81. 如继续保留隐式建 turn，是否说明调用范围和后续迁移计划。

### 十、测试与构建

82. `pytest` 是否通过。
83. 如改动涉及 HostStage / shared types / WS 协议，`npm run build` 是否通过。

## 生产安全加签条件

以下条件未关闭前，不应给 `生产安全完成`：

- `host_states` 与最小 `transactions` 表的长期决策仍未完全稳定
- `projection_failed` 的补发与 replay 策略虽能用，但跨更多事件族的长期回归仍不足
- `ReleaseGateDTO` 的持久化和恢复覆盖仍局限于第一轮主链路
- `GET /turns/current` 的隐式建 turn 仍保留为历史兼容行为
- 事务补偿动作、长链路指标、可视化排障面板仍未进入工程闭环
