# Transaction 事务系统功能列表 V2.1

## 当前阶段

本轮文档对应的是：

- `P0 主链路 + 行动/回合/演出事务可靠性风险识别版`
- 不是 Transaction 模块的最终生产安全完成版
- 重点先锁定 `action 幂等`、`turn settle 并发屏障`、`State/Projection 时序`、`Host 演出释放屏障`、`重连恢复`

当前已经确认但尚未完全收口的真实风险包括：

- `src/server/player/router_player.py` 的 active 房间 duplicate 预检查已经前置，但仍是代码级“先查再写”，不是数据库级原子保护
- `src/server/turn_manager.py` 的 `mark_resolving()` 已经使用条件更新，但 `submit_action()` 仍缺唯一约束或同事务锁
- `src/server/engine/resolution_pipeline.py` 仍是先把 action 记为 `resolved`、先 `_project()`，再调用 `StateService.apply_change()`
- `src/server/engine/projection.py` 逐条事件独立 commit，不等于整条事务原子提交
- `src/server/host/host_store.py` 只持久化了 `delayed_events` 等舞台摘要，没有完整持久化 active transaction / queue / ack 进度
- `src/server/host/router_host.py` 的 `host_step_complete` 还没有形成可审计的 Host ACK 契约，也没有严格校验 `transactionId`
- `src/server/models.py` 的 `ActionReceipt`、`RevealTransaction` 仍偏薄，缺 `turnId/stateVersion/releaseGates`
- `retry-turn` 目前只有“重置 step”或“重跑 settle”两种散落实现，没有统一 `replay_only / recompute_unresolved / restore_from_checkpoint` 语义

## 模块定位

Transaction 是 AI-Keeper 主链路中的事务编排层，负责把一条玩家意图安全串成：

`Intent -> Transaction -> State -> Projection -> Journal`

它负责：

- 玩家 action 幂等与重复提交屏障
- active 回合内“一人一动作”的提交约束
- turn 从 `collecting -> resolving -> resolved` 的推进
- 单个 action 从 `queued -> resolving -> resolved/rejected` 的状态机
- State 写入前后的顺序控制
- Host reveal transaction 的演出队列
- Player 私密 patch / completed 的延迟释放
- 断线重连后的事务追溯与恢复入口

它不负责：

- 检定数学与规则裁决
- AI 是否可信
- 世界真相的权威写入
- 玩家可见性与防剧透裁剪
- Journal 导出与回放展示
- 房间生命周期和 lobby 逻辑

## 事务数据分层

| 层级 | 数据对象 | 说明 | 关键边界 |
| --- | --- | --- | --- |
| L0 | `PlayerIntent` | 玩家提交请求 | 不等于已入账 action |
| L1 | `ActionLedger` (`actions`) | 行动事务账本 | 不等于世界状态 |
| L2 | `TurnLedger` (`room_turns`) | 回合收集和结算顺序 | 不等于事件序列 |
| L3 | `ResolutionResult` | Rule / AI 的裁决输出 | 不等于已落库 State |
| L4 | `AppliedStateChange` | State 持久化后的权威变化 | Projection 只能消费它 |
| L5 | `ProjectionEnvelope` | Host / Player / Party 的投影载体 | 不修改裁决结果 |
| L6 | `RevealTransaction` | Host 演出事务 | 不得混入 player-only 私密内容 |
| L7 | `ReleaseGate` | 延迟释放的 player 事件 | 不能依赖前端本地状态决定释放 |
| L8 | `EventLog` (`events.sequence`) | 补发、审计、回放的序列记录 | 不替代权威状态写入 |
| L9 | `HostStageState` (`host_states`) | Host 舞台恢复状态 | 不是世界真相 |
| L10 | `TransactionTrace` | `actionId/turnId/transactionId/stateVersion/sequence` 追踪链 | 不允许断链 |

## 事务 DTO 初版

第一轮至少要固化以下 DTO 口径：

- `PlayerIntentDTO`
- `ActionTransactionDTO`
- `ActionReceiptDTO`
- `ActionResultDTO`
- `TurnTransactionDTO`
- `TurnSettlementDTO`
- `ResolutionTransactionDTO`
- `RevealTransactionDTO`
- `ReleaseGateDTO`
- `HostStepAckDTO`
- `TransactionTraceDTO`
- `RetryTurnRequestDTO`

最低要求：

- `ActionReceiptDTO` 不能只返回 `actionId/status`，还要能定位 `roomId/turnId/baseStateVersion`
- `RevealTransactionDTO` 不能只有 `transactionId/priority/steps`，还要能追溯 `actionId/turnId/stateVersion`
- `HostStepAckDTO` 只能确认演出进度，不能携带规则裁决或状态变更事实
- `ReleaseGateDTO` 必须是服务端控制对象，不允许前端自行推断释放时机

## Action 状态机

第一轮文档固定为：

```text
submitted
  -> queued
  -> batched
  -> resolving
  -> resolved

submitted
  -> rejected

queued / batched / resolving
  -> timeout
  -> cancelled

system_skip
  -> resolved
```

状态语义：

- `submitted`：请求进入服务端，但尚未写入稳定账本
- `queued`：已入账，等待回合或后台裁决
- `batched`：已绑定 turn，等待批量结算
- `resolving`：裁决中
- `resolved`：事务闭环完成，State / Projection / completion 已达成目标语义
- `rejected`：前置校验、规则、AI 输出校验或下游失败导致动作拒绝
- `timeout`：等待或结算超时，供 UI 解除阻塞
- `cancelled`：Host / Admin 明确取消
- `system_skip`：系统跳过动作，不能等同玩家主动提交

硬约束：

- 已经 `resolved/rejected` 的 action 再次进入 resolve，必须直接返回已有结果
- 不允许重复应用同一条 State mutation
- 不允许重复发出同一组 Projection 结果

## duplicate 占位状态集

第一轮默认口径固定为：

- `queued`
- `batched`
- `resolving`
- `resolved`
- `timeout`

这些状态都视为“已经占用本回合动作槽”，不能再提交第二个玩家 action。

以下状态不占用本回合动作槽：

- `rejected`
- `cancelled`
- `system_skip`

其中：

- `timeout` 默认按“本回合动作已进入事务但未安全闭环”处理，必须继续占位，直到 Host / Admin 通过 `cancelled`、`retry-turn` 或 `restore_from_checkpoint` 明确处置
- `cancelled` 代表 Host / Admin 明确撤销后释放动作槽
- `rejected` 代表动作未成功进入正式闭环，可允许重新提交
- `system_skip` 是系统补位动作，不阻断玩家下一回合正常提交

## 不属于 Transaction 的内容

| 内容 | 归属模块 | 原因 |
| --- | --- | --- |
| 检定成功失败算法 | Rule | Transaction 只编排，不决定数学结果 |
| AI 裁决建议 | AI-Keeper | Transaction 只消费校验后的输出 |
| 世界真相写入 | State | Transaction 不能绕过权威状态服务 |
| 受众过滤和防剧透 | Projection、Safety | Transaction 不决定谁能看到什么 |
| 房间开局 / ready / lobby 生命周期 | Room | 事务只承接开局后的行动链路 |
| 导出、回放、证据链展示 | Journal | Transaction 提供 trace，不负责展现层 |

## MVP 验收主链路

1. Player 提交带 `action_id` 和 `base_state_version` 的 intent。
2. 服务端先校验身份、房间、当前 turn 和 duplicate，再写入 action。
3. 同一角色同一 turn 第二个不同 action 返回 409，数据库不留下额外 queued action。
4. 所有 active 玩家完成提交后，turn 通过条件更新进入 `resolving`，只允许一个 worker 继续结算。
5. 单 action 裁决先完成规则 / AI 校验，再写 `actions.result` 与权威 State。
6. State 落库成功后，再生成 `s2c_state_patch`、`s2c_action_completed`、`s2c_reveal_transaction`。
7. Host 收到只包含 Host-safe steps 的 reveal transaction。
8. Player 私密 patch / completed 只有在 release gate 满足后才被下发。
9. turn 标记 `resolved`，再创建下一条 collecting turn。
10. Player / Host 重连后，事务不重复结算、不重复播放、私密结果不提前泄露。
