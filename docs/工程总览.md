# AI-Keeper 工程总览

本文档说明一个完整工程"是什么、为什么这么做、怎么组织、当前在哪"，面向需要从零理解整个项目的人。

---

## 1. 项目身份

**AI-Keeper** 是一个 AI 驱动的桌面角色扮演游戏（TRPG）自动主持系统。

核心产品假设只有一句话：**AI 是 KP（守秘人/游戏主持人），人类房主只负责开房、邀请、暂停和急救；玩家用手机参与，语音优先，Host 大屏展示公共舞台。**

当前聚焦规则系统为**克苏鲁的呼唤第七版（CoC 7e）**，技术栈为 Python FastAPI + React/TypeScript（Vite）+ PostgreSQL（pgvector）+ DeepSeek API。

## 2. 产品设计哲学

整个产品的设计根植于五条核心判断。它们不是功能清单，而是产品"为什么这么做"的理由。

### 2.1 第 1 条：AI 能长期记忆，但不篡改事实

不是"AI 记忆力好"，而是**可信战役记忆系统**——系统知道什么发生过、谁在场、谁不知道、信息是事实/证词/猜测中的哪一种、这件事现在是否仍然成立。核心数据结构是"记忆声明"（MemoryClaim），带认知状态（epistemic status）、可见性范围、来源引用和有效时间区间。

### 2.2 第 2 条：AI 能理解自然语言，但结算透明

玩家用自然语言说"我想撬锁"，系统将其编译为**可确认的意图合约**（Intent Contract）——目标、方法、约束、实体绑定——玩家确认后执行。结果以**裁决回执**（Resolution Receipt）返回，包含规则来源、骰子结果和状态变更。出错可以复核，但不能静默覆盖。

### 2.3 第 3 条：AI 能自动整理线索、人物和时间线，但不替玩家推理

AI 是档案员/索引员/审讯辅助，**不是侦探**。系统可以指出两条线索之间存在矛盾，但不能宣告谁在撒谎。调查工作台属于玩家，AI 只负责组织和呈现。

### 2.4 第 4 条：Host 不在线时仍能继续，但重要结果必须可复核

**受监督的自主运行 + 延迟复核**——房主离线时，玩家自主决策继续，确定性规则正常执行，但不可逆的信息泄露和重大世界变更停在复核门前。定义了 5 种房主存在状态和 4 级自主等级，裁决结果按维度切片（机制/状态/揭示/叙事/方向），每片独立门控。

### 2.5 第 5 条：玩家每次回来，都知道发生了什么、现在该做什么

不是一段 AI 摘要，而是**战役连续性系统**——从权威状态、事件日志、角色/物品差异、调查工作台、待决决策、队伍计划和承诺中结构化组装"连续性数据包"。区分 7 种回归场景（重连/短离/下次团/错过一次/长期回归/中途加入/检查点恢复），区分"玩家知道什么"和"角色知道什么"。

### 2.6 贯穿性设计原则

| 原则 | 含义 |
|------|------|
| **AI 不写状态** | AI 只输出建议，HP/SAN/物品/线索/场景进度必须 Engine 校验后写入 |
| **Player 不越权** | 所有写操作走 `POST /api/player/intent`，身份以服务端 token 为准 |
| **Host 不判定** | Host 只消费事件播放公共演出，不承载规则逻辑 |
| **房主不剧透** | 房主可开房/暂停/急救，但不能看到完整真相或未发现线索 |
| **PDF 本地优先** | 剧本原文本地存储，云端 AI 只接收处理所需片段 |

## 3. 系统架构

### 3.1 双层架构

```
Player Mobile (React) ──REST──▶ FastAPI ──▶ Engine（唯一权威写入口）
Host Big Screen (React) ◀──WebSocket──┘                │
                                                        ▼
                                              ResolutionPipeline
                                              ├── MechanicCompiler（DeepSeek API / 本地规则兜底）
                                              ├── RuleExecutor（COC 规则处理器）
                                              ├── StateService.apply_change()（结构化状态变更）
                                              ├── SpoilerGuard（输出侧反剧透安全网）
                                              └── ProjectionDispatcher（按 audience 拆分事件）
                                                        │
                                                        ▼
                                              PostgreSQL（pgvector）
                                                        │
                                              Redis（可选缓存层）
```

- 后端：FastAPI（端口 3001），14 个功能路由 + WebSocket 端点
- 前端：React/TypeScript + Vite（端口 5173），Bauhaus Neo-Brutalist 设计语言
- 数据库：PostgreSQL 16 + pgvector，连接池 2-10
- 独立服务：KP MCP Server（端口 9100），提供 prompt 契约与工具注册
- AI：DeepSeek API（`deepseek-v4-pro`），可通过 AiGateway 切换 provider

### 3.2 四阶段裁决管线

这是系统最核心的处理链路——从玩家说一句话到世界状态改变：

```
Player Intent（自然语言）
    │
    ▼
Phase 1: 资产验证（Python，零 token）
    —— 检查玩家是否有能力做这个动作、物品是否存在、场景是否允许
    │
    ▼
Phase 2: 机制编译（LLM，轻量模型，不生成叙事）
    —— 将自然语言编译为结构化 MechanicCompileResult（技能/目标/难度/条件）
    │
    ▼
Phase 3: 规则执行（Python 规则引擎，权威骰子 + 状态提交，零 AI）
    —— Strategy Pattern + Registry，COC 7e 规则处理器掷骰、计算成败、生成状态变更
    │
    ▼
Phase 4: 叙事渲染（LLM，注入级联状态后果）
    —— AI 生成叙事文本，但必须包含 Phase 3 产生的所有状态变更（防止"事实滞后"bug）
    │
    ▼
ProjectionDispatcher：按 audience 拆分 → host / player / party / system 事件
```

### 3.3 事件可见性模型

| audience | 可见范围 |
|----------|---------|
| `host` | Host 大屏（始终不可被玩家看到） |
| `party` | 全队可见（公共舞台） |
| `player` | 仅目标玩家可见 |
| `system` | 仅白名单系统事件对玩家可见 |

SpoilerGuard 在输出侧拦截——任何包含未发现线索、真相片段、NPC 隐藏信息的叙事文本都会被检测并重试。

### 3.4 PlayerIntent 生命周期

```
客户端 POST /api/player/intent
  → 前端幂等检查（action_id 已存在 → 直接返回）
  → Engine.submit_intent()：版本冲突检测（state_version）
  → INSERT actions(status='queued') → INSERT events(s2c_action_queued)
  → [Host 手动触发 OR 自动批次收集 OR GameLoop.process_turn()]
  → TurnManager.mark_resolving()（条件 UPDATE，幂等）
  → ResolutionPipeline.resolve_action()（四阶段管线）
  → 写 actions(status='resolved') + INSERT events + Redis 缓存 + 自动检查点
  → 推送 s2c_reveal_transaction(host) + s2c_state_patch(player) + s2c_action_completed(player)
```

状态机：`idle → submitting → queued → resolving → resolved`

- **已知未完成**：localStorage token 替换为安全存储、WebSocket 短效票据、前端 stateVersion 屏障、HostStore 持久化、完整 RAG 上下文过滤、生产备份/迁移基础设施

### 6.2 关键待解决风险

| 风险 | 说明 |
|------|------|
| **事实滞后** | LLM 叙事时不知道级联状态变更（角色已倒地但 AI 说"你站起身来"） |
| **剧透泄露** | 玩家私密状态补丁在 Host 公共舞台动画完成前到达玩家手机 |
| **幽灵补丁** | WebSocket 重连时补丁和 HTTP 快照竞态 |
| **音频避让失败** | 紧急音效未静音探索 BGM |

以上四项在 `20-核心架构/数据流bug+思考.md` 中有详细分析和修复方案。

当前处于第一轮核心链路阶段。6 阶段路线图定义在 `10-总览与路线/核心链路之后的阶段路线.md`：
