# 房间管理页面体验审计

日期：2026-07-18  
范围：当前工作区 `http://127.0.0.1:5174/admin` 的“房间”页  
方法：以管理员身份完成列表浏览、房间详情、创建表单展开与可见性检查；未创建、删除或修改任何真实数据。

## 结论

当前页面具备基本的查找、创建、详情、状态切换和删除入口，但更像“数据库记录清单”，尚不能支持管理员快速回答：哪几桌正在进行、谁负责、缺什么、是否能马上开团、应当如何安全清理历史房间。

最优先的可用性问题是：选择房间后，右侧“房间详情”在浏览器中呈现为近黑色空白区域；同一时刻可访问性树仍包含剧本、状态、创建时间、状态操作和三个入口。因此这不是数据不存在，而是详情区域的可见渲染或层叠问题。管理员无法据此完成管理决策。

## 浏览器观察

### 列表

- 页面默认一次展示大量房间卡；每张卡的最大信息是 8 位房间码，剧本名和状态被压缩在同一行。
- 卡片留下大量空白，但没有房主、玩家人数、最近活动、创建时间、下一场或异常状态等决策信息。
- 只有关键词搜索和“显示回收站”；没有按状态、剧本、房主、活跃度筛选，也没有默认区分“进行中”“等候开局”“历史”。
- 每行同时放置红色“删除”，重复出现且与常用查看操作竞争注意力；批量删除仅显示数量，缺少“全选当前筛选结果”“归档”“永久删除”的分层操作。
- 状态主要靠文字颜色表达；黄色 `active` 在浅色背景上辨识度较弱，也不应只用颜色区分状态。

### 详情

- 已选中房间 `1f5a1c4b` 时，可访问性树包含完整详情和链接，但视觉画面中的详情面板近黑且无可读内容。
- 即使渲染恢复，详情仍缺少管理员最关心的摘要：房主、玩家数/容量、最近活动、下一场、邀请链接/复制、AI 或连接异常、剧本发布门禁。
- 生命周期按钮“草稿、等待、进行、暂停、完成、归档”同级平铺；没有说明状态迁移后果，也没有将当前最合理的下一步作为主操作。

### 创建房间

- “新建房间”直接展开很大的内联区域，只有“选择剧本”“选择房主”和一个始终可点击的“确认创建”。
- 未选择剧本时仍可尝试提交，错误在提交后才出现；应在前置条件满足前禁用主操作并解释原因。
- 房主下拉列出普通玩家账户；前端与服务端都应只允许具备 Host/Admin 权限的账户作为房主，避免创建无人能管理的房间。
- 创建前看不到剧本是否已发布、质量门禁是否通过、规则系统、建议人数等开团关键信息；创建后也缺少明确的成功页来复制邀请、进入大厅或继续配置。

## 问题优先级

### P0：先恢复可管理性

1. 修复详情面板“DOM 有数据、视觉近黑空白”的渲染问题，并添加视觉回归测试。
2. 创建房间只允许 Host/Admin 作为房主；服务端必须再次校验，不能只依赖下拉框。
3. 未选已发布且可开团的剧本时禁用“确认创建”，并在按钮附近明确显示阻断原因。

### P1：让管理员一分钟内做出判断

1. 默认按“进行中、等候开局、已结束、归档”分组或筛选，并在标签上显示数量。
2. 将列表改为紧凑的房间工作台：剧本/房间名、状态、房主、玩家 `2/4`、最近活动、下一场、快捷操作。
3. 详情改为稳定的侧栏或主从布局：顶部显示状态和房间码，正文显示人员、剧本、会话、邀请和异常；将“进入大厅/舞台/玩家入口”作为明确动作。
4. 创建流程改为三步：选择已发布剧本（先看门禁）→ 选择合规房主 → 创建后复制邀请或进入房主大厅。

### P2：降低批量操作和长期维护风险

1. 搜索外增加剧本、房主、状态、最近活动的组合筛选和排序。
2. 进入“批量管理”模式后再显示复选框和危险操作；提供“全选当前结果、归档、移入回收站、永久删除”。
3. 永久删除显示影响数量与不可恢复说明；默认优先归档或回收站，不让红色删除成为日常主操作。
4. 状态使用文字、图标和对比足够的徽章共同表达，并为键盘操作和屏幕阅读器补齐标签与焦点顺序。

## 推荐目标流程

1. 管理员进入“进行中”视图，立即看到需要处理的房间、负责人和异常。
2. 选中一桌，在详情侧栏确认剧本、玩家、会话、邀请与运行健康度。
3. 新建时先选择通过发布门禁的剧本，再选择合规房主；创建成功后直接复制邀请或进入房主大厅。
4. 清理历史时切到批量管理，先归档或放入回收站；仅在明确二次确认后永久删除。
