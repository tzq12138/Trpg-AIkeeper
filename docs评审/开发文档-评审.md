# 《AI-Keeper 最终版本开发文档》评审报告

**评审对象**：`docs/开发文档/AI-Keeper最终版本开发文档.md`（373 行，版本 1.0，状态"待开发"），全文精读。

## 1. 概述

**整体质量评分：C**

文档结构清晰（目标→分层→边界→类型→接口→事件→流程→里程碑→MVP 边界→测试策略→注意事项→参考 PRD），"核心边界"五条（AI 不写状态、Player 不越权、Host 不判定、房主不剧透、PDF 本地优先）准确凝练。但它**名不副实**：自称"最终版本开发文档"，来源却只覆盖 PRD-00 到 PRD-28，明确遗漏 PRD-29/30 两份 Engine 裁决核心；内容约八成是 PRDs 的压缩复读，未声明自身与 PRDs 的权威关系，且漂移已经开始；作为"开发文档"缺少技术栈、数据模型、仓库结构、部署、非功能指标等一切动工要素，不能独立指导开发。

## 2. 主要问题

### P0-1 自称"最终版本"却遗漏 PRD-29/30，AI KP 核心流程与 PRD-29 管线矛盾

- **证据**：文档头部"来源：`模块设计/最终版本/PRDs` 中 PRD-00 到 PRD-28"；§12"参考 PRD"列表同样止于 PRD-28。PRD-29（四阶段意图裁决管线+后验物品主张，397 行，PRDs 全库最充实的一份）与 PRD-30（双层规则引擎）整份缺席：无四阶段管线、无 `retroactive_item_claim`、无 `rule_registry`/JSON5 触发器、无 `scenario_assets.json`。更严重的是 §7.5"AI KP 主持"流程与之矛盾：本文档写"AI 输出结构化结果：叙事、检定建议、状态建议、线索建议、下一目标 → Engine 校验 AI 建议并生成权威事件"——AI 同一步产出叙事+结算建议；PRD-29 §5.1 规定 LLM 阶段二"严禁生成叙事文本"、Python 阶段三绝对裁决后阶段四才包装叙事（规则先于叙事，`03-唯一权威矩阵`权威提交顺序同）。
- **影响**：Engine 开发者拿到两份结算哲学相反且都自称现行的文档；占全书技术深度一半的裁决管线在"开发文档"中不存在。
- **建议**：要么补写 PRD-29/30 对应章节（§2.1 Engine Core 展开四阶段、§4.2 增加 `MechanicCompileResult`/`ResolutionResult`/`ScenarioAssets`、§7.5 重写为管线拓扑），要么把文档降级改名为"PRD-00~28 开发导读"并声明 PRD-29/30 自证开发。

### P0-2 未仲裁反而复制了 PRDs 内部最大的矛盾（动作状态机）

- **证据**：§7.4"Engine 返回 202，Player 显示 queued"站在 PRD-25 一边；但 PRD-01 §7 与 PRD-09 §5.5 规定 202 后进入 `RESOLVING`。开发文档存在的意义应是终结此类分歧，它却只做了一方的传声筒，全文无一处标注"此处 PRD 间有冲突，以本文档为准"。
- **影响**：前端实现者依旧要在两份"现行"文档间猜。
- **建议**：在 §4 或新增"裁决记录"节显式登记与 PRDs 的全部差异及取舍。

### P1-3 与 PRDs 大面积重复、无权威声明，且漂移已开始

- **证据**：§5 REST 表≈PRD-00 §6+各工作流 PRD 接口表；§6 事件列表≈PRD-00 §5.9；§7 九大流程≈PRD-12~28 的功能需求缩写；§10 测试策略≈各 PRD 验收标准的分类汇编。全文无"本文档与 PRD 冲突时以谁为准"的声明。漂移实例：§4.1 `EngineEvent` 比 PRD-00 §5.1 多出 `transactionId`、`sourceActionId` 两字段，`visibility` 四值枚举（`public|private|party|hostOnly`）仅本文档出现；§6.1 Host 事件列表比 PRD-00 全集少了 `s2c_chat_stream`（该事件在 PRD-02 同样无人消费，三处口径互不相同）；§7.7 澄清窗口照抄 PRD-18 的"5 分钟/3 回合"，却漏掉 PRD-18 §5.8"可作为房间级配置项调整"。
- **影响**：重复即未来的矛盾源；已经开始的三处漂移证明这一点。
- **建议**：改为"差异文档"——只写 PRDs 没有的工程决策，协议/流程一律链接 PRD 单源；或反向宣布本文档为唯一工程入口并把 PRDs 降为需求背景。

### P1-4 不足以指导开发：缺技术栈、数据模型、部署、非功能指标

- **证据**：全文无编程语言与框架选型（PRD-29/30 明确"Python 规则引擎"，本文档只字未提 Python；前端 React/Zustand 仅能从被引用的 PRD 推断）；无数据库/存储选型（事件日志、快照、检查点落在什么存储无答案）；无仓库/模块结构；无部署拓扑与运行环境；无非功能指标（回合端到端时延、并发房间、AI 单场成本上限——`00-产品宪法`要求"指标先记录基线"，本文档连基线采集需求都未列）；§8 里程碑 M1–M6 无日期、无估期、无依赖关系、无人力假设。
- **影响**：新工程师读完仍无法搭起能跑的骨架；"开发文档"实际是一份"PRD 摘要+测试清单"。
- **建议**：补"技术选型与理由""数据模型与存储""仓库结构""部署与环境""非功能指标与基线采集"五节；里程碑补依赖与出口标准。

### P1-5 里程碑编号与 normative 规范的版本语义撞车

- **证据**：`00-产品规范/04-M0范围、里程碑与指标.md`定义 `M0`（可信文字主链内部验证）/`M1`（M0 稳定后扩展）/`M2` 的版本语义；本文档 §8 自定义 M1=协议底座、M2=PDF 导入……M6=稳定性与复盘，同名异义。且文档未引用任何规范文档，继承了 PRDs 与 ADR-002/003/004 的全部冲突（语音优先、PDF 起点、Stage 依赖，详见 PRDs 评审报告 P0-1）。
- **影响**：跨文档沟通时"M1"指代混乱；规范 Gate（G1–G6）与本文档里程碑无映射，验收无法对齐。
- **建议**：里程碑改名（如 Sprint/Phase 1–6），并给出与 G1–G6 Gate 的映射表。

### P2-6 其余问题

- §7 九大流程全部只写 happy path，异常流（导入失败、AI 连续失败、重连冲突）散落在 PRDs 中未做工程汇总。
- §11"开发注意事项"八条均为"不要 X"口号，无对应可执行的检查手段（如"不要把 AI 输出当作数据库写入命令"应落到 lint rule/代码评审 checklist/单测名称）。
- §10 测试策略只有分类没有数量/覆盖率目标与工具链（单测/契约/E2E 各用什么跑）。
- 无版本历史、无日期、无 owner、无 front matter（`00-产品规范` 已建立元数据标准，本文档未遵守），"最终版本"无从证伪与追溯。
- §6.2 Player 事件列表含 `s2c_campaign_ended`，但 PRD-07 的 Player 路由 FR 并未覆盖该事件——开发文档引出了 PRD 缺口却未标注（这一点倒可算无意中的贡献）。

## 4. 缺失项

1. PRD-29/30 全部内容（四阶段管线、后验物品主张、规则 Handler/JSON5 DSL、`scenario_assets.json`）。
2. 技术选型（语言、框架、存储、STT/LLM 供应商策略）。
3. 数据模型与存储设计（事件日志/快照/检查点/档案的表或文档结构）。
4. 仓库结构、模块划分、部署拓扑、环境配置。
5. 非功能指标与基线采集（时延、并发、AI 成本）。
6. 异常流工程汇总；测试工具链与覆盖率目标。
7. 与 PRDs 的权威关系声明、差异登记表。
8. 安全边界（X-card/安全暂停）——与 PRDs 同缺。
9. 文档治理元数据（日期、owner、版本历史）。

## 5. 亮点

- §3"核心边界"五条是全书对架构红线最精炼的表述，可直接引用。
- §9"MVP 边界/明确后置"清单果断（OCR、编辑器、回滚、blocking 字幕等八项后置），范围控制意识好。
- §10 测试策略按协议/API/导入/玩家/AI KP/Host/存档七域分类，覆盖了 PRDs 验收标准的主要面。
- §4.2 业务类型清单把散落各 PRD 的 15 个关键类型汇成一张表，有索引价值。

## 6. 结论与行动建议

这不是一份"最终版本开发文档"，而是"PRD-00~28 的忠实摘要"。它的最大价值（边界五条、MVP 边界、类型索引）完全可以并回 PRDs README；它的最大缺口（PRD-29/30、工程落地要素）恰是"开发文档"四字的本分。

**建议二选一**：
- **方案 A（推荐）**：降级为"开发者导读"，删除与 PRDs 重复的 §5/§6/§7/§10，保留边界、类型索引、里程碑，全文链接 PRD 单源，并补 PRD-29/30 导读。
- **方案 B**：升级为真正的工程文档：补技术选型、数据模型、仓库结构、部署、非功能指标，登记与 PRDs 的全部差异并声明"工程实现以本文档为准"。

无论哪条路，先解决 P0-1（补齐或显式排除 PRD-29/30）与 P0-2（仲裁动作状态机），否则文档越"最终"，误导越深。
