## 1. 概述

### 1.1 对照方法

- **方向一（设计→代码）**：以 24 个子系统《功能列表.md》自报的"当前代码锚点 / 当前代码现状"为基线，逐项与 README 目录树核对，并对关键否定性结论（"未实现"）做代码侧 grep 复核（如 X-card、community、schedule、gameTime、factions 表等），避免仅凭文档自述下结论。
- **方向二（代码→设计）**：将 README 目录树中全部后端模块文件、前端页面/组件名，逐个在 24 个子系统文档（全部 `.md`，约 120 个文件）中做全文检索，命中数为 0 者判定"代码有、设计无"。检索词与命中数在本文第 3 节逐项给出。
- **重要背景**：这批文档本身是"代码感知"的（每篇含真实文件锚点，回执日期 2026-07-06 ~ 07-08），整体质量高。但抽查发现**代码已明显超前于文档**（见 3.3 节"文档过期"清单），因此本评审以代码现状为准判定实现状态。

## 5. 结论与行动建议

### 5.1 总体结论

1. **设计→代码方向整体健康**：24 个子系统中 14 个主链路已实现，9 个部分实现，仅 23-Community 纯纸面（且为文档有意 gated）。文档质量高、代码锚点准确，"画了饼没下锅"的情况集中在各子系统的 P1/P2 层，属正常迭代节奏。
2. **代码→代码文档方向问题更严重**：至少 **11 个 P0 级模块/能力簇**（3.1 节）在 24 个子系统文档中零提及，其中 `v2_cutover/global_reset/room_migration`（数据销毁与迁移）、`game_loop/turn_timeout_worker`（自动回合推进）、`collaboration_contracts`（协作合约）、`solo_*`（单人团）、`rule_sets`（规则集注册）均为有成体系代码、无任何设计约束的能力，风险高于"漏实现"。
3. **文档时钟停在 2026-07-08，代码已向前跑**：至少 5 处文档自述缺口已被代码填上（3.3 节），其中 09-Scene-Map 与 21-Safety 对同一匿名地图问题口径互相矛盾，说明文档间也存在同步缺口。
4. **安全类缺口双向叠加**：文档侧 P0（统一可见性 helper、public export 过滤、CORS、pending_approval 隔离）经代码复核确认仍然开放（2.1/2.2/2.3/2.6），与无文档的高危能力（global_reset 数据销毁、host_autonomy 自主决策、Agent 写工具）叠加，构成当前最大风险面。
