## 2. 主要问题

### P0-1：KP_MCP_Design 的结算流程"叙事先于骰子"，违反本文件夹自己的 State-first 铁律

- **问题描述**：`KP_MCP_Design.md` 的后端调用流程把叙事推送放在掷骰和状态写入之前，与 PAO PRD、架构文档的核心承诺正面冲突。
- **证据**：
  - `KP_MCP_Design.md` §4.1 代码注释定义的新流程为：`kp_resolve_turn() → narrative → ProjectionDispatcher 直接推 → rollRequests → RuleExecutor 掷骰 → stateMutations → Engine 分级写入`；代码实现亦如此（先 `push_narrative`，再 `execute_roll`）。
  - 对照 `AIKP玩家行动编排与Host演出系统_PRD_V1.0.md` §4.4："权威状态必须先持久化，再对外投影。禁止先向 Player 或 Host 宣布成功，再回头尝试写 State"；§13.8"State 失败时 action 不得显示成功"。
  - 对照 `AI-Keeper核心链路架构.md` 四阶段裁决表：阶段三"规则执行"先于阶段四"叙事渲染"。
  - 更严重的实例：§2.1 `kp_resolve_turn` 输出示例中，`rollRequests` 还在请求"侦查"检定，同一份 `narrative.perCharacter.char_01` 已写出"你的医学知识告诉你，这些痕迹的量远超过一次普通的外科手术"——叙事在骰子执行前预设了检定成功的结果。
- **影响**：若按此实现，"骰子/数值由服务器权威结算、AI 不篡改数学结果"这一头号产品卖点（竞品分析 P0 层"可信一次行动"）在 MCP 链路直接崩塌；且叙事一旦先推送，后续骰出失败时无法收回。
- **改进建议**：KpResponse 拆为两段式——roll 前只产出 `rollRequests` + `stateMutations` 提案（Plan），RuleExecutor/Engine 执行后再回调 KP 生成叙事；或在文档显式定义"narrative 仅为候选、须经 Engine 校验且延迟到 State 成功后投递"的机制，并修改全部示例。

### P0-2：KP_MCP_Design 给 AI 开放 "direct 免校验写状态" 通道

- **问题描述**：KpResponse 的 `stateMutations[*].permission` 允许 `"direct"`（Level 2，后端直接写、不校验），且默认权限表把状态标签、场景切换列为 direct。
- **证据**：
  - `KP_MCP_Design.md` §3.2：`"direct" — Level 2 — 后端直接写，不校验`；§3.3 默认分配表将 `scene_transition`、`npc_reaction`、`add_status_tag`（"恐惧""重伤""昏迷"标签）列为直接写。
  - 对照 `AI-Keeper核心链路架构.md` 数据原则："AI 输出必须经过 schema、权限、真相、规则和状态边界校验"；角色边界表："AI KP 不可以直接落库、直接扣 HP/SAN"。
  - 对照 PAO PRD §16.4：状态标签是 StateService 的职责；§32 全局禁止事项："禁止 AI 直接写 HP、SAN、Luck、物品、地图、线索或真相"。
- **影响**：AI 一次幻觉即可不经任何校验给玩家挂上"昏迷"标签或切换场景——这正是 `数据流bug+思考.md` Bug 1（事实时差）想要防的事故，却被 MCP 设计合法化。
- **改进建议**：direct 权限收缩为纯展示类（narrative 文本、tacticalPrompts），且不落库；一切产生状态后果的 mutation 一律 validate + MutationValidator；`add_status_tag` 改列 validate 并校验标签枚举与来源。

### P0-3：soul.md 作为生产 system prompt 含有与架构冲突的指令，且存在双份权威源

- **问题描述**：`soul.md` 会被 `kp_mcp_server` 直接拼进 system prompt（`KP_MCP_Design.md` §5.3 `_load_system_prompt()` 读取 `prompts/soul.md`），但其中多条指令与系统架构冲突；且 docs 与 kp_mcp_server 各存一份，未声明谁是权威。
- **证据**：
  - `soul.md` §6："如果玩家希望你代骰，你可以直接代骰并说明结果"——与全部协议文档"AI 不得生成权威骰子"（PAO PRD §16.2、架构文档角色边界）直接矛盾。
  - `soul.md` §22 推荐模板要求自由文本输出（【场景】【你注意到】【你可以】…），与 KpResponse JSON schema（`narrative.public` / `narrative.perCharacter` / `rollRequests`）之间无任何衔接说明；模型同时收到"按模板自由输出"与"只输出 JSON"两套指令时的行为未论证。
  - `soul.md` §21 开局流程让 AI 交互式询问风格/时代/角色/骰子方式，与平台结构化开局（PRD-12 加入房间、PRD-21 开房、竞品分析 P0"首 15 分钟引导"的预设角色 + Session Zero）是两套互不承认的流程。
  - `工作区整理记录.md` 将 `soul.md` 迁入 `docs/20-核心链路/`，而 `KP_MCP_Design.md` §5.1 显示 `kp_mcp_server/prompts/soul.md` 也存在——双份无同步机制。
- **影响**：system prompt 是 AI 行为的最高指令，其中的架构冲突无法靠下游代码"兜底"消除；双份漂移后行为不可预测。
- **改进建议**：删除/改写代骰条款（改为"请求系统代骰，输出 rollRequest"）；在 soul.md 头部声明其权威源位置与同步方式；将开局流程段标注为"仅适用于无平台结构的开房场景"或删除。

### P0-4：PAO"PRD V1.0"与最终 PRD 体系是两套未对齐协议，且与同文件夹提案稿重复并存

- **问题描述**：`AIKP玩家行动编排与Host演出系统_PRD_V1.0.md` 自称"跨模块核心链路 PRD"，但其 DTO 体系未被权威 PRD 序列（docs/PRDs，PRD-00~30）采纳；同文件夹还并存一份内容大面积重复的提案稿，权威关系未声明。
- **证据**：
  - 对 `docs/PRDs/*.md` 与 `docs/00-产品规范/*.md` 全文检索，`IntentContract`、`IntentDraft`、`ResolutionBundle`、`PlayerActionEnvelope` 零命中——PAO 的核心对象在最终 PRD 体系中不存在。
  - `PRDs/PRD-01-Engine意图生命周期与状态写入边界.md` 冻结的上行契约是 `POST /api/player/intent` + `intentType`（actionId/intentType/declaredIntent/baseStateVersion/params）；PAO PRD §21.1 却提出 `POST /api/player/intent-drafts` + `inputMode`，并自述"是否拆成多个真实接口，可在工程阶段结合现有 `/api/player/intent` 兼容实现决定"——一份 PRD 对自己的接口是否生效都不确定。
  - `AIKP 接收玩家行动…完整协议.md` 是口语化提案稿（"这一块应该成为整个系统最核心的一条协议""你们现有文档已经明确""建议把这一整套协议命名为…"），与 PAO PRD 的 RevealTransaction 示例、确认策略、验收清单（22 条 vs 25 条）大面积重复，两份并存、均未标注取代关系。
- **影响**：实现者无法判断以 PRD-01 的 intentType 契约还是 PAO 的 inputMode 契约为准；PAO PRD 可能是一份未被收编的"影子 PRD"。
- **改进建议**：二选一——(a) 将 PAO 收编为正式 PRD 编号（如 PRD-31），修改 PRD-01 的冲突条款并废弃提案稿；(b) 将 PAO PRD 降级为"设计提案"并明确 PRD-01 为权威，删除重复 DTO。

### P1-6：上行契约漂移，且 PAO 遗漏 retroactive_item_claim

- **问题描述**：玩家上行存在 intentType 与 inputMode 两套并存契约；`数据流.md` 定义的 P0 机制在 PAO 全文中缺席。
- **证据**：
  - `数据流.md` 与 `数据流bug+思考.md` 的上行均为 `POST /api/player/intent`，字段含 `intentType`（如 `use_item`、`retroactive_item_claim`）；PAO PRD §11.1 的 `PlayerActionEnvelopeDTO` 用 `inputMode`（action/speech/party_chat/…），无 `intentType` 字段。

- **影响**：同一玩家动作（"我掏出口袋里的手套"）按不同文档会走不同契约与管线；后验主张在 PAO 的确认策略（高风险强制确认）下应如何处理（争议分支要求 Luck 暗骰）无规定。
- **改进建议**：统一上行信封（intentType 作为 inputMode=action 时的子类型或反之）；在 PAO PRD 补 retroactive_item_claim 的完整生命周期与验收测试。

### P1-8：《规则导入.md》存在可行性与规则正确性缺陷

- **问题描述**：示例实现细节违反本项目的审计/重算要求；CoC7 成功等级实现不完整；JSON 补丁写入无校验边界。
- **证据**：
  - (a) `CocSkillCheckHandler` 用 `random.randint(1, 100)` 掷骰，无 seed、无 rollId 持久化——PAO PRD PAO-FR-25 要求"规则重算默认复用原 rollId"，`数据流bug+思考.md` 的审计链也要求 roll 可追溯；当前实现无法支撑。
  - (b) 返回的 `level` 只有 `critical_success / success / failure / fumble`，没有困难成功、极难成功等级——但同文件夹 PAO 示例使用 `difficulty: "hard"`（困难目标 22），CoC7 对抗检定与战斗必须比较成功等级；`PRDs/PRD-30-双层规则引擎架构.md` 原样复制了同一段代码与缺陷（说明该错误已扩散进正式 PRD）。
  - (c) 剧本级 `apply_patch` 机制允许 JSON 配置直接写 `/skills/cthulhu_mythos` 等任意 RFC 6902 路径，全文未定义路径白名单或校验者——与 `KP_MCP_Design.md` §3.3 将 `skill_value_change` 列为"永不写 (block)"形成边界模糊（一个是创作者配置、一个是 AI 输出，但没有文档说明 apply_patch 的校验责任在哪层）。
  - (d) 文字错误："支持 DND 5e（扔 D20）或者 龙与地下城"——DND 5e 与龙与地下城是同一事物。
- **影响**：规则引擎是"可信"叙事的数学底座，(a)(b) 直接破坏可审计与 CoC7 正确性；(c) 留下创作者配置越权写状态的口子。
- **改进建议**：骰子服务注入可持久化 rollId 的 RNG 接口；level 枚举补 `hard_success / extreme_success` 并修 PRD-30；为 `apply_patch` 定义允许路径白名单与 MutationValidator 校验点。

### P1-9：《AI-Keeper核心链路架构.md》过于单薄且与 PRD 深度脱节

- **问题描述**：作为 docs/README 中"核心链路"入口（第 12 条），仅 64 行，其"四阶段裁决"未覆盖 PAO PRD 新增的意图编译、确认、入账、ReleaseGate 环节。
- **证据**：

  - docs/README 自己标注该文件"需与 M0 规范对照"——承认未对齐但仍作入口。
  - 四阶段管线（意图经四次顺序处理）与 `KP_MCP_Design.md` 的 `kp_resolve_turn` 单次 MCP 调用模型（编译+建议+叙事一次返回）在结构上也不兼容，无文档解释二者如何共存。
- **影响**：入口级架构图与实际协议脱节，新读者按入口理解会得到错误的链路模型。
- **改进建议**：重写为"协议分层视图"（接入/意图/事务/裁决/状态/投影/演出），显式标注与 PRD-01、PAO、PRD-29、KP_MCP 的对应关系。

### P2-10：RAG 文档的量化参数未论证、验收无量化门槛

- **问题描述**：rerank 权重、切块长度、混合比例均为经验值；22 条验收全是布尔项。
- **证据**：`剧本导入后的 RAG，应该怎么建、怎么写.md` §十五给出 `final_score = 0.35*semantic + 0.15*lexical + 0.20*entity_match + 0.15*authority + 0.10*recency + 0.05*source_quality`，无评测集或实验依据；§八"中文正文 300～800 字"、§十四"75% 向量 + 25% 关键词"同样无出处；§二十验收测试 22 条（如"检索准确性"）无阈值（如 citation 覆盖率 ≥ X%、host_only 泄露率 = 0 的测试集规模）。
- **影响**：RAG 质量无法回归，权重调整无客观依据。
- **改进建议**：建立小规模金标检索评测集（场景/NPC/规则各 N 条 query→期望 chunk），为验收补阈值。

### P2-11：并发与资源竞争路径覆盖不足

- **问题描述**：现有文档覆盖了幂等与断线重连，但多人同时行动的资源竞争未设计。
- **证据**：PAO PRD §12 状态机与 §22 错误模型均无"两名玩家同时声明拿取同一物品/攻击同一 NPC"的竞态处理；§20.4 Host 意外离线"A2 仅允许明确、低风险、可补偿事务"无超时数值（grace period 多长？）；`数据流bug+思考.md` 提到"防并发校验"仅一句带过；战斗轮 DecisionWindow 的超时与默认动作（PAO §9 decision_window）无定义。
- **影响**：多人并发正是竞品分析 P0"1–4 人完整闭环稳定性"要验收的场景，当前文档层无依据。
- **改进建议**：在 PAO PRD 补"资源竞争与回合冲突"一节（乐观锁/回合内串行化/先到先得回执），给出 grace period 与 DecisionWindow 超时的默认数值。

## 3. 一致性问题（与 PRDs、50-AI-Keeper-Platform、00-产品规范 对照）

1. **PAO 事件表与 PRD-00 事件全集不一致**：PAO PRD §21.2 新增 `s2c_intent_understanding`、`s2c_intent_clarification_required`、`s2c_intent_confirmation_required`、`s2c_action_resolving`、`s2c_private_notice`、`s2c_action_review_pending`、`s2c_host_stage_state` 等事件；`PRDs/PRD-00-全局协议与投影契约.md` 的事件枚举（其 §5 自称"冻结为单一产品事实源"）不含 intent_* 系列，且另有 PAO 未提的 `s2c_action_batched`、`s2c_clarification_prompt`/`s2c_clarification_result`（澄清事件两边命名不同）。PAO 自述"所有新增事件必须同步 registry…"但未声明与 PRD-00 的增补/替代关系。
2. **下行信封字段漂移**：`数据流bug+思考.md` 的信封含 `hostSequence` 但无 `playerSequence`；PRD-00 要求"Player 专属事件必须带 `playerSequence`"（§43-45）。
3. **KP_MCP_Design 与 12-AI-Keeper PRD 的关系未声明**：`50-AI-Keeper-Platform/12-AI-Keeper核心系统/PRD.md` 称"当前仓库已经具备 AiGateway、DeepSeek / MCP / local provider…"，与 KP_MCP_Design §8 一致；但 KP_MCP_Design §8.3 要将 `ai/ai_kp.py`、`agent/game_agent.py` "替换"、`agent/tools.py` "废弃"——这是重大架构决策，未在 `00-产品规范/06-决策记录 ADR.md` 中留下 ADR（评审中未见对应记录入口），Phase 3"移除 agent/ 目录"也无验收标准。
4. **规则 Handler 缺陷已扩散**：`规则导入.md` 的 CocSkillCheckHandler 被 `PRDs/PRD-30` 原样引用（含无 rollId、无困难/极难成功等级两处缺陷），说明 20-核心链路的草稿缺陷会直接污染正式 PRD——佐证了 P1-8 的严重性。
5. **可见性枚举**：RAG 文档 §二-6 指出 `ContentProjectionService`（player/host_only/keeper/internal）与 `RAGStore`（public/party/host_only/internal）枚举不一，并提议统一为 `public/party/character_private/host_only/admin_only/internal`；该提议与 `00-产品规范/03-领域对象与唯一权威矩阵.md` 中的 `party` 等受众口径、PRD-00 的 `audience: host|player|party|system`（明确"禁止 broadcast"）尚未对齐——RAG 文档的六值枚举是提案，未回写产品规范。
6. **现状盘点呼应**：竞品分析 P0"模型失败的可恢复体验"与 PAO PRD §24 降级链、`数据流bug+思考.md` 的容错自洽相互印证，方向一致——但 KP_MCP_Design 的 P0-1/P0-2 问题若存在，竞品分析"AI 不直接写权威状态"的"已验证"结论即不成立，现状盘点的证据需要重审。

## 4. 缺失项

- **战斗/追逐完整裁决链**：`KP_MCP_Design.md` 有 `kp_resolve_combat_round` 工具，但 encounter 内部状态机（先攻、多攻击、反击、重伤、追逐轮）在 PAO、四阶段、架构文档中均只有一个路由条目，无展开设计。
- **语音输入链路**：PAO §3 把"语音确认文本"列为输入源，但 STT 错误、语音与文本冲突、超时处理全文件夹零覆盖（20-Voice-Media 属平台层，核心链路至少应有接口约定）。
- **多人行动批处理**：PRD-25（自由行动收集与批次结算）在 20 文件夹内无任何呼应文档——回合内多玩家行动的归并、冲突、顺序规则缺席（见 P2-11）。
- **AI 成本与时延预算**：无任何文档给出每次行动的 token 预算、延迟 SLO（PAO §26.1 只有"快速返回"）或月度成本估算——对"AI  Provider 故障导致整桌停摆率接近 0"的指标，无容量设计支撑。
- **Safety 输入处理流程**：PAO §9 将 `safety`（X-card/fade）列为输入模式，但触发后的事务流（暂停谁、通知谁、如何恢复、是否落审计）无设计；soul.md §20 有面向玩家的机制说明，但无系统侧契约。
- **回滚/补偿的工程细节**：PAO 提出"补偿事务、不删除历史、Checkpoint 建新分支"（PAO-FR-26、§26.4），但补偿事务的 schema、权限、与原事务的关联字段、投影侧如何呈现"已补偿"均无定义。

## 5. 亮点

- **PAO PRD（V1.0）**：34 节结构完整——L0–L11 数据分层、四类状态机、错误模型（"系统故障不得包装成角色失败"）、降级链、12 条指标、25 条验收测试，是全部评审对象中最接近可施工 PRD 的文档。
- **RAG 文档**：现状诊断精确到代码级（`audience="ai"` 不过滤、NPC 结果被分类分支丢弃、`xlsx_data` 读旧 HP/SAN、缺 `rag_build_id`），并给出 RAG-0~RAG-7 批次与 22 条验收，"结构化事实走 SQL、模糊语义走向量"的三路线划分非常清晰。
- **《数据流bug+思考.md》的风险识别本身**：fact lag / spoiler leak / ghost patch / audio ducking 四个时序 bug 定位精准，修复方向（级联状态注入、版本屏障、补丁缓冲、音频 ducking）已被后续 PRD 采纳——内容价值高，差的是文档形态。
- **架构文档的"DeepSeek 实现红线"**：五条禁令简洁、可执行、可检查，是好的人机协作护栏。

## 6. 结论与行动建议

20-核心链路目前不是"一套"核心链路文档，而是**三代产物并存**：聊天草稿（数据流/bug 思考/soul/规则导入/完整协议）、收口 PRD（PAO V1.0、RAG）、以及带 P0 设计错误的服务设计（KP_MCP_Design）。主要风险不是写得不够，而是**权威关系未声明 + MCP 设计违反自身核心原则**。

按优先级建议：

1. 【P0】修复 `KP_MCP_Design.md`：结算流程改为"Plan → Rule/State → Narrative"两段式（P0-1）；direct 权限收缩为纯展示类（P0-2）。修复前不应按该文档施工 MCP 链路。
2. 【P0】修订 `soul.md`：删除"代骰"条款、声明权威源与同步方式、清理与结构化开局冲突的流程（P0-3）。
3. 【P0】解决 PAO 的权威身份：收编进 PRD 序列并对齐 PRD-01/PRD-00，或明确降级为提案并废弃重复的《完整协议》稿（P0-4）。
4. 【P1】统一上行契约（intentType vs inputMode）、在 PAO 补 retroactive_item_claim（P1-6）；统一 `executeAfterStep` 字段名（P1-7）。
5. 【P1】修规则引擎缺陷（rollId/RNG、困难与极难成功等级、apply_patch 白名单）并同步修 PRD-30（P1-8）；重写架构入口文档（P1-9）。
6. 【P1】对四份聊天稿做"转正"处理：去口语、补标题/日期/版本、删除无关类比，或移入 90-归档（P1-5、P1-7）。
7. 【P2】为 RAG 建金标评测集与量化门槛（P2-10）；补并发竞争、语音链路、Safety 事务流、补偿事务 schema 等缺失设计（P2-11 及缺失项）。
