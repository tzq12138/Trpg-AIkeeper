## 2. 主要问题

### P0-1：现役设计基线被打包进归档 zip，且与现役目录字节级重复

**问题描述**：`AI_Keeper_UI_Brainstorm_Rounds1-4_整理包.zip` 内文件日期为 **2026-07-21**（评审前一日）。其中 `AI_Keeper_UI_Complete_Consolidated_Spec.md` 开宗明义自称"**当前有效设计基线**……便于产品、UI、前端和后端直接阅读"，并规定冲突优先级。这是现行设计文档，不是历史档案。

**证据**：
- zip 内 `AI_Keeper_UI_Complete_Consolidated_Spec.md` 第 5-10 行："整理日期：2026-07-21""当前有效设计基线"。
- 实证：`diff` 对比 zip 内该文件与现役 `docs/设计前端/AI_Keeper_UI_Complete_Consolidated_Spec.md`，**字节级相同**；Round4 文件同样字节级相同。
- 同库 `方向性问题头脑风暴/README.md` 第 14 行规定"`原始材料/` 中的文件为逐字副本；不得在此目录修订产品定义"，第 20 行"档案中的'建议'不自动成为 M0 功能承诺"——zip 中的现役基线与该归档规则直接冲突。

**影响**：同一现役文档两处存放必然漂移；zip 格式使其无法被正常检索、链接和评审；"归档"标签会让读者误以为其已失效，或反过来让归档区读者误把 zip 当历史。归档的可信边界被破坏。

**建议**：将该 zip 从归档移出；Round1-3（现役目录没有）若为历史讨论记录，解压后以普通 md 放入归档并写明归档原因；Consolidated_Spec 与 Round4 只保留现役 `设计前端/` 一处。

### P1-1：归档纪律系统性缺失——无总 README，多数子目录无归档原因/日期/替代文档

**问题描述**：`90-归档/` 顶层**没有 README.md**。`host模块设计/`、`player模块设计/`、`compose/`、`superpowers/`、`设计前端备份-20260627/` 五个子目录均无任何归档说明。唯一像样的归档说明是 `方向性问题头脑风暴/README.md`（标杆），`历史计划/README.md` 与 `外部审查/README.md` 分别只有 3 行和 1 张单行表。

**证据**：
- `HOST_PROTOCOL_CONTRACT.md` 第 3 行自称"本文是 Host 端 + Player 端通信协议的**单一事实源**"——但它已被 `PRDs/PRD-00-全局协议与投影契约.md`（其第 5 行注明"来源：`HOST_PROTOCOL_CONTRACT.md` v2.0 修正版"）实质取代，文件内**无任何废弃/替代标注**。一个不知情的读者在归档里翻到它，会把它当现行契约。
- 对比：`方向性问题头脑风暴/README.md` 有 frontmatter（status/effective_date/last_validated）、使用规则 4 条、"档案与现行规则的关系"映射表——说明项目有能力做好，只是没推广。

**影响**：归档区对新成员是雷区：无法分辨哪些是死文档、哪些仍被引用。"单一事实源"类表述造成实质误导。

**建议**：补 `90-归档/README.md`（目录清单 + 每区归档原因/日期/替代文档）；为每个子目录补一行级 README 或在文件名/头部加归档横幅；`HOST_PROTOCOL_CONTRACT.md` 头部加"已废弃，由 PRD-00 取代"。

**问题描述**：`历史计划/` 25 份文件命名为 `plan.md`、`plan2.md`…`plan25.md`，文件名零语义。正文无日期、无作者、无完成/废弃状态标注。`历史计划/README.md` 仅说明"从根目录迁入"，无逐份索引。

**证据**：
- 抽查结果：`plan.md`=朋友项目功能迁移；`plan5.md`=AI 场景回合闭环；`plan15.md`=AI Gateway 收束；`plan20.md`=房主开房与多账号；`plan23.md`=等待室/Ready 同步；`plan25.md`=大厅实时与乱码修复。演进脉络清晰但只能靠逐份打开还原。

### P1-3：头脑风暴档案的 SHA-256 完整性清单已失效，校验机制名存实亡

**问题描述**：`方向性问题头脑风暴/README.md` 第 23-33 行给出 7 份原始材料的字节数与 SHA-256，第 45 行要求"验证档案时，应重新计算每个文件的 SHA-256，并与上表比对"。

**证据**：实测全部不匹配。例：M0 总计划声明 `1A656A621893…`、36,535 字节；实际 `sha256sum` 为 `08a903536c65…`、37,243 字节。7/7 全部不符（差异模式疑似归档/分发过程中的换行符转换，但无法证实）。

**影响**：这是该目录引以为傲的防篡改机制。按其自身规则执行验证，会得出"证据档案已被篡改"的错误结论；反之真正的篡改也无法被发现。机制比没有更糟——它提供虚假的安全感。

**建议**：以当前分发形态重算并更新清单；或改为记录生成时的哈希并注明"按 LF 换行计算"；在 CI 或归档流程中加自动校验步骤。

### P2-1：host/player 模块设计内部存在契约矛盾与示例代码错误（档案真实性瑕疵）

**问题描述**：模块设计整体专业度高，但存在以下硬伤，且其中一处已被 PRD-00 官方承认是"协议裂缝"：

## 5. 亮点

- **方向性问题头脑风暴归档是全库标杆**：frontmatter 状态机、使用规则、"档案与现行规则的关系"映射表、完整性清单的设计思路都正确；`ADR/裁决映射.md` 做到 200 问逐条闭环，覆盖检查声明"没有条目可被误写为已拒绝或已实现"。
- **头脑风暴总览与顶层审计质量极高**：矛盾分级（S0）、证据带行号、裁决建议可执行；且绝大多数建议已被现行 `00-产品规范` 与 ADR-001~008 吸收——归档与现役的血缘关系清晰可追溯。
- **host/player 模块设计专业度高**：统一信封、双序列号去重、指数退避+jitter、Watchdog 熔断、多级队列、确定性散列防位置跳变；每份开头有 v2.0 修订说明，新旧差异一目了然。
- **设计前端备份 INDEX.md** 有版本关系梳理、重复项自查、语义化重命名方案，且重命名方案已在现役目录真实落地。
- **外部审查** 22 个问题全部带文件行号和 P0/P1/P2 优先级，并诚实记录"第一轮误报已修复"清单，可执行性与自省性俱佳。

## 6. 结论与行动建议

**结论**：`90-归档` 的内容本身价值很高——它完整保存了产品从"三种方向并存"收敛到 M0 规范的决策史，头脑风暴→ADR 的血缘链路是文档治理的正面样板。但归档工程执行粗糙：一处原则性归档误判（现役 UI 基线打包进 zip）、同文三处副本、总 README 缺失、完整性校验失效、高价值审查与计划无核销闭环。当前状态的归档区对新成员是"雷区"而非"史料馆"。
