## 2. 主要问题

### P0-1：03 权威矩阵与 ADR-006 对"事件/投影/行动生命周期"的权威归属字面冲突

- **问题描述**：ADR-006 决定"只有 Engine 能验证前置条件、提交状态、写事件并生成投影"。但 03 的"唯一权威矩阵"把事件、投影、行动生命周期的权威分别判给了其他服务，Engine 反而只是"允许输入者"。
- **证据**：
  - `ADR/ADR-006-engine-only-authoritative-writes.md` 决定节："只有 Engine 能验证前置条件、提交状态、写事件并生成投影。"
  - `03-领域对象与唯一权威矩阵.md` 矩阵行："事件事实与审计 ｜ 唯一权威：Journal / Event Log ｜ 允许输入者：Engine、受控安全操作、补偿服务"——Engine 被降格为输入者；
  - 同矩阵："可见投影 ｜ 唯一权威：Projection 服务 ｜ 允许输入者：Engine 事件"；
  - 同矩阵："PlayerAction 生命周期 ｜ 唯一权威：Transaction 服务"。
- **影响**：全库最核心的一条不变量（"Engine 是唯一权威状态写入者"，见 README 快速不变量、ADR-006、04 验收表"权威"行）在自己的权威矩阵里找不到一致表述。Transaction 服务、Clue/Knowledge 服务、Journal、Projection 服务、Safety 服务与 Engine 的包含关系全文无任何定义。实现方按 ADR-006 会写一个巨型 Engine，按 03 会写六个对等微服务——两种架构都"有规范依据"。按 README 优先级规则（ADR > 其余 normative），03 应当败诉，但 03 恰恰是验收时核对"谁可以写什么"的操作手册（04 验收证据"权限与伪造身份测试"依赖它）。
- **改进建议**：在 03 开头增加一段"服务归属"定义，明确 Transaction/Clue/Journal/Projection/Safety 是 Engine 的内部子服务还是对等服务；若是对等服务，则 ADR-006 的"唯一写入者"措辞必须修正为"唯一权威状态提交者"，并逐行核对矩阵与 ADR 的措辞一致性。

### P0-2：01/ADR-005 宣布 Host 非法，02 却在规范状态机和 Session 0 中继续使用 host

- **问题描述**：01 明确"`Host` 不是规范概念：旧代码中的 Host 名称只能作为兼容别名"；ADR-005 决定"规范只使用 ScenarioPreparer、RoomOwner、TableSteward、Player、SharedStage、AIKeeper 和 Engine"。但同为 normative 的 02 仍两处使用 host。
- **证据**：
  - `02-核心用户旅程与生命周期.md` 行动状态节："`analyzing -> awaiting_confirmation -> queued -> batched -> resolving -> completed` 是正常路径。行动可在适用状态下进入 `canceled`、`rejected`、`timeout`、`awaiting_player_choice`、`awaiting_host_exception` 或 `sync_required`。"——`awaiting_host_exception` 是新造的规范状态名，不是"旧代码兼容别名"。
  - 同文件黄金路径第 3 步："开局前完成 Session 0：内容提示、边界确认、**AI/Host 方式说明**、隐私与设备说明。"
- **影响**：①规范内部直接违反自己的 ADR-005，"冲突时以 ADR 为准"的规则第一次实战就失效——因为违反者就是另一份 normative 文档，而非历史材料；②`awaiting_host_exception` 的处置角色在 01 权限表中无对应行：RoomOwner 只允许"建房、邀请、成员管理、开始/结束 Session"，TableSteward 允许"故障恢复、提出纠错请求"，05 提到"异常队列"但同样未指定属主。进入该状态的行动由谁、在什么时限内、以什么权限处理，全库无答案，验收时无法判定实现对错。
- **改进建议**：将状态改名为 `awaiting_steward_exception`（或 `awaiting_ops_exception`）并在 01 权限表中补充异常队列的处置角色与时限；Session 0 说明改为"AI 主持方式说明"；在 06 或 ADR-005 中增加一条"规范文档自身术语审计"要求。

### P1-1：ADR 模板自我违约——6/8 缺"可选方案"，全部缺"非目标"，零代价分析

- **问题描述**：`06-决策记录 ADR.md` 规定"每个 ADR 必须包含背景、可选方案、决定、影响、非目标和被替代口径"。实际只有 ADR-001、ADR-002 有"选项"节；ADR-003/004/005/006/007/008 均无"可选方案"；8 份全部没有"非目标"独立章节；全部以"后果"代替模板要求的"影响"；没有任何一份对落选方案做代价/成本分析。此外 ADR-001 背景自述曾存在"AI 独立 KP／房主复核剧情／AI 辅助真人 KP"三种叙述，但 frontmatter `supersedes: []` 为空，被替代口径未登记。
- **影响**：ADR 的核心价值是"为什么这么选、放弃了什么、代价是什么"。现状只记录了"决定了什么"，与产品宪法/规范正文信息重复，无法支撑未来的复审（例如 M1 评估 Human Keeper 时，找不到当年否决方案 2、3 的理由与代价）。且 06 自己定的模板自己先违反，治理权威受损。
- **改进建议**：为 6 份 ADR 补写"可选方案+代价"节（每个落选方案至少一行代价说明）；补"非目标"节；统一"影响/后果"用词；登记 ADR-001 的 supersedes。

### P1-2：里程碑全文零日期、指标无定义口径

- **问题描述**：`04-M0范围、里程碑与指标.md` 标题承诺"里程碑与指标"，但 G0–G6 七道 Gate 全部没有目标日期、负责人、预计顺序之外的信息；"首轮学习指标"列出 8 项指标（建房到开场耗时、行动端到端 P50/P95、澄清/确认/撤回/申诉率、重连成功率、安全暂停完成率、线索分享率、每场调用成本、人工故障恢复次数），但没有任何一项给出测量口径："行动端到端"的起点是玩家提交、确认完成还是叙事渲染完成？"恢复成功率"的分母是什么？"每场 AI 调用成本"含不含 embedding 与重试？宪法"指标先记录基线，不在缺少真实数据时伪造阈值"的诚信原则值得肯定，但**没有口径的基线同样无法测量**。
- **影响**：Gate 无法排期、无法问责；指标无法采集——不同工程师会按不同口径实现埋点，M0 验收时基线数据不可比。
- **改进建议**：为每项指标补"定义/起止点/分母/采集点/排除项"五要素；Gate 表增加目标日期或至少相对顺序与预估工期责任方。

### P1-3：05 性能目标与 04 发布门槛脱节，"用于验收"却无法判定阻断

- **问题描述**：`05-跨域安全与非功能基线.md` 规定"非 AI 接口 p95 不高于 500ms，WebSocket 事件 p95 不高于 1s，千事件房间重连目标不高于 3s"，并称"目标线在 M0 用于验收而非承诺……未达标必须在报告中披露环境和样本"。但 `04` 的"M0-Verified 发布门槛"列举的必须同时满足的条件中**不含任何性能项**。
- **影响**：性能未达标时，按 05 是验收问题，按 04 门槛却不阻断 M0-Verified——两份 normative 文档对同一验收行为给出不同结论，验收争议无裁决依据。
- **改进建议**：在 04 门槛中显式纳入或显式排除性能目标；若纳入，写明样本量与环境口径。

### P1-4：验收记录与优先级规则自相矛盾，且文件计数对不上

- **问题描述**：①README 规范优先级第 4 级写明"工程实现、测试和验收报告（实现证据，不改变产品定义）"，但 `验收记录-2026-07-15.md` 自带 `status: normative` 且物理上位于规范目录内，与"本目录 = normative 唯一入口"的目录语义混淆；②该记录声称"17 份 `00-产品规范` 文档均包含 status、version、owner……"，实测目录内含 frontmatter 的文件为 18 份（含验收记录自身），"17"与 18 的对应关系未说明。
- **影响**：治理元规则（什么是规范、什么是证据）在目录内就有反例；计数偏差削弱"静态验收通过"结论的可信度。
- **改进建议**：验收记录移至 `60-验收与测试报告/` 或将 status 改为 `evidence/report`；注明计数口径（是否含自身）。

### P1-5：隐私与合规停留在原则层，账号体系完全缺位

- **问题描述**：05 的数据最小化、AI 上下文裁剪写得较好，但全库没有：账号生命周期（注册/登录/找回/注销）、数据保留期限数值（仅"按保留策略删除"，策略本身不存在）、用户删除权流程、未成年人保护、第三方 LLM 的数据处理约定（prompt 会发往 Provider，05 只约束"日志不记录完整 prompt"，未约束 Provider 侧的数据使用/出境/DPA）、CoC 7e 规则与模组的版权使用边界（04 仅要求模组"原创、获授权或内部可合法使用"，无判定流程与责任人）。
- **影响**：对一个以"私密线索、安全反馈、私人笔记"为核心数据的产品，这些空白会直接导致上线合规风险；PRD-00 又明确"不包含：公网账号认证体系"，意味着账号问题在规范层和 PRD 层都被搁置，无人认领。
- **改进建议**：新增一份 07-数据与合规基线（或在 05 扩节），至少给出：账号模型决策（本地会话 vs 账号体系，建议立 ADR）、保留期限表、删除/导出流程、Provider 数据处理白名单。

### P2-1：可见性术语拼写漂移

`README.md` 快速不变量与 `01`、`02` 使用 "party-safe"；`03` 可见性层定义为 `stage_safe`，`04` 验收表写作 "stage-safe"。三种拼写并存（party-safe / stage_safe / stage-safe），且 party-safe 与 stage_safe 是否同义没有定义——从字面看，"队伍安全"与"舞台安全"甚至可能是两个不同受众。

### P2-2：版本治理"出生即巅峰"

全部 18 份文件 `version: 1.0`、`effective_date` 与 `last_validated` 同为 2026-07-15，无 changelog、无再验证周期、无"何时需要 bump version"的规则。评审日（2026-07-22）距生效仅一周，尚未过期，但治理机制上没有任何保证它不过期的东西。

### P2-3：边界情形未定义

宪法限定"2–4 名玩家"，但未说明：单人是否可玩、第 5 人/旁观者的处理（裁决映射第 197–200 问"死亡、替补与旁观"标为 later，意味着 M0 玩家死亡后无规范路径）；G6 只验证 2 人与 4 人两条路径，3 人路径无人提及。02 行动状态机中 `timeout` 的阈值、`awaiting_player_choice` 的超时去向均无定义。

## 3. 一致性问题（与 PRDs、50-AI-Keeper-Platform 抽查对照）

### C-1：Host 术语全面回流（最严重）

ADR-005 废止 Host 后，标称"最终版本 PRD v2.0、状态待开发"的 `PRDs/` 目录仍把 Host 作为一等协议概念：`PRDs/README.md` 定位行"Host 展示共同现实"；`PRD-00-全局协议与投影契约.md` 规定 `audience` 枚举为 `host | player | party | system`、"Host 专属事件必须带 `hostSequence`"；PRD-02 至 PRD-06 五份模块以 Host 命名；`50-AI-Keeper-Platform/README.md` 第 17 模块为"Host Client 公共舞台端"。这些不是 ADR-005 允许的"旧代码兼容别名"，而是 2026-07-15 规范生效后仍待开发的新设计文档。00-路线图同样使用"Host/Player 权限分离"。**04 的 Gate G0 退出证据"角色、权威、生命周期和范围均以本目录为唯一入口"在事实上不成立**——验收记录只证明了文档治理收敛，没有证明下游文档服从。

### C-2：语音定位正面冲突

ADR-003 决定"文字是唯一验收基线"；00-产品宪法非目标含"语音、视频、音效"。但 `PRDs/README.md` 首版核心假设写明"玩家输入**语音优先**，文字和战术按钮补充"，验收矩阵要求"手机行动体验：**语音优先**，行动有完整回执链"；`PRD-14-玩家行动面板与语音优先输入.md` 第 9 行"语音是主入口，文字和按钮是补充"；PRD-08 整份为"Player 对讲机与语音意图"；PRD-05 氛围引擎含 BGM/SFX（撞宪法"音效"非目标）。按 README 优先级 ADR 应胜出，但 PRDs 自述"最终版本"，执行者拿到的是两份互相否定的"最高指示"。

### C-3：PDF 导入的优先级冲突

ADR-002 决定"PDF 自动导入不作为验收前提……未通过发布门禁的版本不可成为 M0 黄金路径"；04 也将其列入"可保留但不阻塞 M0"。但 `PRDs/README.md` 实施建议第一批即"PRD-00、01、**22、23**、21，先让'PDF 到可开房'成立"——PDF 导入与一键开局被排进第一交付批，事实上成为黄金路径前置。

### C-4：三套并行里程碑词汇无映射

本目录用 M0/M1/M2/Later + Gate G0–G6；`50-AI-Keeper-Platform/README.md` 第 12 行"当前实现优先级仍以 `docs/30-DeepSeek任务包/` Batch-0 到 Batch-5 为准"；PRDs 用"第一批~第五批+后续批"。Batch、批次、Gate 之间没有任何对照表，"M0 什么时候算完"在三套话语里有三个答案。

### C-5：认证模型冲突

05 要求"每个请求都以独立角色凭证和房间边界授权；身份、角色、设备和投影端不可互相伪造"；01 权限原则"凭证和审计主体必须分离"。但 PRD-00 接口表对开房/开局两个敏感操作仅要求"房主本地会话"，且 PRD-00 范围"不包含：公网账号认证体系"。"本地会话"是否满足"独立角色凭证、不可伪造"无从判定，规范层也没有给出判定标准。

### C-6：03 四受众 vs PRD-00 四 audience 的映射缺失

03 定义 `internal / player_private / party / stage_safe`；PRD-00 定义 `host | player | party | system`。两者数目相同但语义不重合（system ≠ internal，host ≠ stage_safe 的命名漂移再次引入 Host），全库无映射表，投影实现极易对错号。

## 4. 缺失项

1. **商业模式完全空白**：无目标用户规模、定价、成本回收模型；唯一与钱相关的是"每场 AI 调用成本"指标。M0 定位为内部验证可以理解，但至少应有一节说明"M0 之后用什么商业假设决定去留"。
2. **指标口径手册**（见 P1-2）。
3. **账号与身份体系**（见 P1-5）。
4. **灾难恢复量化目标**：02/05 建立了追加式纠错与"永不覆盖历史"原则（设计正确），但没有 RPO/RTO、备份频率、单点故障清单；05 的"备份、导入和迁移先校验 schema、哈希……"只覆盖迁移场景。
5. **容量指标**：无任何并发房间数/玩家数/事件规模上限定义（仅"千事件房间"一个孤立样本点）。
6. **ADR 代价分析与落选方案记录**（见 P1-1）。
7. **规范的修订流程**：如何提案、谁批准、version 何时 bump、文档废止流程——README 只规定了"必须新建 ADR"的四种情形，其余变更管理缺失。
8. **第 2 份模组的准入路径**：M0 只绑定一份固定参考模组， ScenarioPreparer 如何准备、校验、发布第 2 份模组（质量报告字段、发布门禁 checklist）在规范层没有定义，ADR-002 只说了原则。
9. **玩家死亡/离席的 M0 口径**（见 P2-3）。

## 5. 亮点

- 唯一权威矩阵 + 四层可见性 + 追加式纠错不变量，是直击 AI 跑团核心风险（幻觉、剧透、越权写状态）的正确抽象，且贯穿所有文档。
- 裁决映射.md 对历史 200 项讨论给出 adopted/amended/archived/later 四态全覆盖，并自曝"早期第 80 问未形成裁决不计入序列"，溯源严谨度罕见。
- "指标先记录基线，不在缺少真实数据时伪造阈值"（00-产品宪法）体现了难得的指标诚信。
