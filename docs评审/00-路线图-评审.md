## 2. 主要问题

### P0-1：全文以 Host 为一等概念，与 ADR-005 正面冲突且未做任何标注

- **问题描述**：现行规范 ADR-005 决定"规范只使用 ScenarioPreparer、RoomOwner、TableSteward、Player、SharedStage、AIKeeper 和 Engine"，01 明确"`Host` 不是规范概念"。本文档却处处把 Host 当作与 Player 并列的一等角色。
- **证据**（`平台能力分层与MVP边界.md`）：
  - 核心判断节："把权威结果分别投影给 **Host 和 Player**"；
  - 能力分层表："**Host/Player 体验** ｜ Host 公共舞台、Player 手机端、等待室、回执"；
  - MVP 必做表："房主能创建房间，玩家能加入，**Host/Player 权限分离**"、"AI、**Host**、Player 都不能直接修改权威状态"、"一次裁决能同时生成 **Host 公共演出**、Player 私密反馈和事件日志"。
- **影响**：读者按此文档会重建"Host = 房主 = 大屏 = 主持端"的三合一错误模型——这正是 ADR-005 背景部分明确要消除的混淆（"单一 Host 概念会把房间管理、真相访问、大屏播放和剧情裁决错误地合并"）。"Host/Player 权限分离"在规范语义下根本无法翻译：是指 RoomOwner/Player 分离，还是 SharedStage/Player 分离？两者权限模型完全不同。
- **改进建议**：全局改写为规范角色（Host 公共舞台→SharedStage 公共舞台端；Host/Player 权限分离→RoomOwner 与 Player 凭证分离）；或在文首显式声明"本文档为历史文档，术语以 ADR-005 之前的口径书写"。

### P0-2：无状态声明，与 docs/README 的"历史/候选"标注脱节

- **问题描述**：`00-产品规范/` 全部 18 份文件均有 frontmatter（status/version/owner/effective_date/last_validated），验收记录还把"现行元数据"列为验收通过项。本文档是 docs 根目录 00 级别文件夹中唯一没有任何元数据的文件。`docs/README.md` 称其为"历史/候选路线"，但文件夹命名 `00-路线图` 在排序上先于 `00-产品规范` 之外的一切现行文档，文件名也不含任何"历史"字样。
- **影响**：按 `00-产品规范/README.md` 的优先级规则，`candidate` 文档排最末——但该规则只在读者已经知道本文档是 candidate 时才生效，文档自身对此只字未提。新人从文件夹结构出发，完全可能把它当作现行路线执行。
- **改进建议**：二选一——①补齐 frontmatter 并改写为与 M0/Gate 对齐的现行路线图；②文首添加显著废弃声明，或移入 `90-归档/`。

### P1-1：作为"路线图"没有任何路线——零日期、零里程碑、与 Gate 体系零映射

- **问题描述**：全文没有时间维度。唯一的阶段概念是"第一轮"和"核心主链路通过 **Batch 5** 验收后，再从该目录拆第二阶段及以后任务"。Batch 是 `30-DeepSeek任务包` 的执行批次词汇；现行规范 `04-M0范围、里程碑与指标.md` 使用 M0/M1/M2/Later + Gate G0–G6。两套体系之间没有对照表；"第一轮"是否已结束、当前处于哪个阶段，从本文档无从得知。
- **影响**：文档标题承诺"路线图"，实际只交付了一张静态能力分层表。无法回答路线图的三个基本问题：现在在哪、下一步是什么、什么时候到。
- **改进建议**：增加"M0（G0–G6）→ M1 → M2"阶段表，每阶段给出与 Batch 的映射、退出条件、目标日期；或降级为"能力分层备忘录"放弃路线图定位。

### P1-2：MVP 验收标准不可量化、与 05 已有量化基线不挂钩

- **问题描述**：MVP 必做表的验收标准均为二元描述："房主能创建房间，玩家能加入"、"断线重连：Player 刷新或断线后能恢复快照、pending action 和私密信息"——无时限、无成功率、无样本条件。而现行规范 05 已有量化口径（"千事件房间重连目标不高于 3s"、"非 AI 接口 p95 不高于 500ms"），本文档既未引用也未对齐。
- **影响**：同一件事在两个文档里有两套验收尺度，实现方可以选择对自己有利的一套。
- **改进建议**：验收标准改为引用 04 Gate 与 05 非功能基线，或标注本文档验收标准已被 04/05 取代。

### P1-3：投影模型只有 Host/Player 两层，遗漏 party 与 internal

- **问题描述**："把权威结果分别投影给 Host 和 Player"及 MVP 表"同时生成 Host 公共演出、Player 私密反馈和事件日志"，全文无第三层投影。现行规范 03 定义四层可见性（`internal / player_private / party / stage_safe`），且线索"主动分享后产生队伍可见摘要"的 party 层是 M0 验收项（04 验收表"信息"行）。
- **影响**：按此文档实施的投影架构会先天缺失 party 层与 internal 隔离，私密线索分享这一 M0 核心场景无法落地。
- **改进建议**：投影表述改为引用 03 的可见性层定义。

### P2-1："同时生成"与规范提交顺序表述冲突

MVP 表称"一次裁决能**同时**生成 Host 公共演出、Player 私密反馈和事件日志"。03 权威提交顺序是"Engine State commit → Event Log → Projection → AI narration from committed result"，且 README 快速不变量要求"权威规则结果先于叙事"。"同时生成"字面上允许叙事与状态并行产出，弱化了"先提交后投影"的核心不变量（可理解为描述投影 fan-out 而非时序，但措辞有歧义）。

### P2-2：把执行工具名写进产品路线

"不进入当前 **DeepSeek** 第一轮"、"统一沉淀到平台补全文档索引"——DeepSeek 是当下的工程执行代理，属于易变的组织事实，写进产品路线文档会导致文档随团队工具变化而过期（docs/README 第 44 行同样存在此问题："DeepSeek 负责后续实际实现，Codex 负责拆方向……"）。

### P2-3：无 owner、无风险、无依赖、无复盘机制

全篇无责任人、无风险登记、无外部依赖（如 LLM Provider、CoC 7e 规则授权），也无"什么情况下本路线图需要修订"的说明。

## 4. 缺失项

1. frontmatter（status/version/owner/日期）与自我状态声明——作为 00 级文档为全库唯一缺省。
2. 时间维度：任何日期、排期、阶段目标。
3. 与 M0/G0–G6 的映射，或显式的"本文档已被 04 取代"声明。
4. 量化验收标准（或与 04/05 的引用关系）。
5. M1/M2 的内容预览（能力分层表只到优先级，"第二阶段后再做"之后没有任何下文）。
6. 商业视角：生态商业层（社区、付费市场、插件）仅列为 P2/P3，无任何商业假设或验证条件。
7. 风险与依赖登记。
8. 修订责任人与修订触发条件。

## 5. 亮点

- 核心判断准确且有洞见："不应先做成 Roll20 或 Foundry 的完整替代品……AI-KP 平台的核心是有状态世界引擎"，一句话说清了产品护城河。
- "防越权、防剧透、防 AI 幻觉"三防概括与现行规范的不变量体系一脉相承，方向零偏差。
- 能力分层表 + 明确的"第一轮不做"清单（语音视频、社区、付费、动态光照、插件市场等十项），范围克制，且大部分判断后来被 ADR 验证为正确。
- "体验服从核心链路，不做过度视觉扩展"的优先级解释简洁可执行。

## 6. 结论与行动建议

这是一份"内容多半正确、身份完全不明的文档：战略判断经受住了时间检验（语音、PDF 的判断甚至优于更新的 PRDs），但作为路线图缺少时间、状态与量化验收，且术语停留在 ADR-005 之前。当前最大的风险不是内容错误，而是它以 00 级文件夹、无元数据的形态与现行规范并存，持续向读者输出已被废止的 Host 模型。

建议二选一，不要维持现状：

1. **升级路线（推荐）**：补齐 frontmatter；将"第一轮/Batch 5"改写为 M0（G0–G6）→ M1 → M2 的阶段路线并标注与 30-DeepSeek任务包批次的映射；Host 术语全部替换为规范角色；验收标准改为引用 04/05；补充 M1 候选清单（可从 04 的 Later 列表和本文档 P1/P2 层取材）。
2. **归档路线**：文首添加"本文档已被 `00-产品规范/` 取代，仅保留历史背景"声明并移至 `90-归档/`，同时在 docs/README 中移除其第 3 位推荐阅读位置。

无论选择哪条路线，都应先完成第 2 项的一半：给文件加上状态声明。这一步成本极低，且能立即消除"事实已失效、名义未退役"的漂移风险。
