**评审对象**：`docs/设计前端/`（47 个文件：2 份顶层规范 md、`stitch_host_player_frontend_interface/` 下 5 份模块技术方案 md + INDEX.md + bauhaus/DESIGN.md + 21 组 code.html/screen.png 界面稿）
**评审方式**：全部 md 精读；界面稿抽查 8 组（host：dashboard_v1、dashboard_v3_insanity、combat_v2 及 html 静态扫描全覆盖；player：skills_dynamic_v1、inventory_clue、map_cn、map_en、status_v1/v2 diff），并对 21 个 html 做了 bauhaus 规范合规与交互代码扫描。

### 整体质量评分：**C-**

规范文档（头脑风暴合并稿）本身思辨质量高、规则闭环严密，是全场最强资产；技术方案 5 份也达到了可评审的工程深度。但**两条设计线（7 月的头脑风暴规范 vs 6 月的 Stitch 界面稿+技术方案）互相矛盾且无任何对齐说明**，界面稿为纯静态演示、与工程方案零衔接，索引数据失实。作为"设计前端"交付物，目前无法指导开发。

## 2. 主要问题

### P0-1 两套互相矛盾的设计体系并存，无任何取舍说明

**问题描述**：Consolidated Spec（2026-07-21 整理）与 stitch 界面稿 + 5 份 v2.0 技术方案（INDEX 标注 2026-06-27 整理）在核心交互模型上直接冲突，全库没有任何文档说明哪条线是当前基线。

**证据**：

| 冲突点 | Consolidated Spec | 界面稿 / 技术方案 |
|---|---|---|
| 手机底部导航 | 固定 `[当前] [调查] [角色] [更多]`，且"地图不单独占底部入口"（Spec §1.3、附录1 §8） | 全部 player 稿为 `[SKILLS/GEAR/LOGS/MAP]`（如 `player_skills_dynamic_v1/screen.png`、`player_map_cn/screen.png`） |
| 技能交互 | "点击技能不会直接掷骰，而是将技能作为辅助标签带入行动输入"（Spec §1.6、附录1 §14.2） | `3_living_sheet_touch_to_roll.md` 的 `SkillButton` 点击即 `submitIntent('skill_check', ...)`；`player_skills_dynamic_v1` 技能卡即为可点检定按钮 |
| 战斗模型 | "全员声明 → 锁定 → AI-KP 统一排序整轮结算"，明确否决"逐人输入、逐人结算"（Spec §1.7、附录2 §1、§29） | `host_combat_v2/screen.png` 为"当前回合(CURRENT TURN)/行动顺序(下个回合)"的逐回合控制台 |

**影响**：开发拿到两套相反的需求，按任何一套做都必然推翻另一套；且技术方案已被 PRD-07~11 引用为来源（PRD-09 写明"来源： Player 模块 3"），意味着矛盾已固化进 PRD 层。

**建议**：由产品负责人裁决当前基线（建议以 7 月头脑风暴为准，因其明显更晚且更完整），在 INDEX.md 和 Consolidated Spec 头部互相引用并标注"界面稿中 XYZ 交互已作废"。

### P0-2 host 界面稿直接违反 Spec 的"大屏不是控制台"红线

**问题描述**：Spec 反复、明确地禁止公共大屏承担控制功能，但 host 界面稿就是一个全功能 KP 控制台。

**证据**：
- Spec §1.2："大屏不提供推进剧情、掷骰、修改 HP、添加单位等操作"；附录2 §3 禁止清单含"发起攻击/选择反应/手动掷骰/添加单位/调整 HP/推进结算"。
- `host_dashboard_v1/screen.png`：左侧栏有黄色大按钮"**掷骰 D100**"，中央有"**推进剧情**"按钮，顶部有"系统锁定"。
- `host_combat_v2/screen.png`：当前回合卡内含"行动/闪避/反击/物品/奖励骰/等待"六个操作按钮，左下角"**添加单位(ADD UNIT)**"，右侧"战术总览(QUICK ROLL) 1D100/1D10"，以及"演示伤害特效/演示击败特效"按钮。
- Spec §2.4："不显示 `8/12`、`54/70` 等精确值"；`host_dashboard_v1/screen.png` 调查员监控卡直接显示 `HP 12/15`、`SAN 38/85`、`4/10`、`72/80`、`2/14`、`45/75` 全部精确数值。

**影响**：若界面稿被当作设计基线，将实现出一个 Spec 明确否决的产品形态（KP 控制台），破坏"Party-safe 共享舞台"的核心定位与防剧透设计。

**建议**：明确"host_dashboard/host_combat 究竟是公共大屏还是 KP 私屏"——若是公共大屏，按 Spec 重画；若是 KP 工具屏，需在 Spec 中补"KP 私屏"这一终端（目前 Spec 只有公共大屏/玩家手机/桌务端三类，且桌务端"无剧透"，不含此类控制台）。

### P1-3 INDEX.md 数据失实、引用失效、自相矛盾

**证据**：
1. 第 7 行称"**47 张预览截图**"，实际目录中只有 21 张 screen.png（每页 1 张）。
2. 第 30 行与"回滚说明"称备份位于 `stitch_host_player_frontend_interface_backup_20260627/`（含全部 50 个原始文件），**该目录在当前文档库中不存在**——回滚指引失效。
3. 自相矛盾：第三节称 `2_push_to_talk_stt_gateway.md`、`5_tactical_chat_inline_buttons.md` 对应"战术聊天相关"设计稿，但第八节速查矩阵中通信/语音/聊天一行写的是"**（设计稿待补）**"——到底有无对应设计稿？
4. 第六节自认 4 项"待确认事项"（1 项截图重复 + 3 组近似重复未定最终版），即 2026-06-27 宣称"✅ 已完成"的去重实际未闭环。

**影响**：索引是 21 个界面稿的唯一导航，其失实会直接误导后续查阅与归档决策。

**建议**：修正截图计数；恢复或删除备份目录引用；统一"战术聊天设计稿是否存在"的表述；将 4 项待确认事项转为决议并标注最终版。

### P1-4 `player_map_en` 与 `player_map_2b_v1` 截图字节级重复，2B 病房稿无真实预览

**证据**：两文件 MD5 相同（`964b2db0379dd081b7fe0711e01abcba`，184,194 B），但 `code.html` 内容不同（2b_v1 为"病房 2B (WARD 2B)"区域）。INDEX 第 138、156 行仅标注"需确认是否为截图误放"，挂起未处理。

**影响**：`player_map_2b_v1` 实际视觉效果无法评审；若截图确为误放，说明截图生成流程无校验。

**建议**：重新生成 `player_map_2b_v1/screen.png` 并核对与其余 3 个地图稿的差异。

### P1-5 界面稿为纯静态演示，与工程实现零衔接，存在脱节风险

**证据**：
- 21 个 html 全部为 CDN Tailwind 静态页，数据全部硬编码；全库仅一处业务 JS：`player_skills_dynamic_v1/code.html:328-347` 用 `setTimeout` 把 SAN 从 45 硬编码改成 42 的"Simulate SAN drop"演示动画。
- 网络/状态代码扫描：8 个抽查文件中 `fetch/WebSocket/addEventListener` 命中数几乎为 0；`host_combat_v2` 的交互按钮是"演示伤害特效 (DEMO DAMAGE)""演示击败特效 (DEMO DEFEAT)"，`host_dashboard_v3_insanity` 顶部标"模拟：临时疯狂"——均为 demo 注入，非真实状态驱动。
- 5 份技术方案描述的 `actionState` 状态机、`s2c_state_patch` 驱动、序列号去重等，在界面稿中无任何对应物（无提交中/结算中/锁定/断线态的界面）。

**影响**：界面稿只能证明"视觉风格可行"，不能证明"交互模型可行"；前端按技术方案实现时将不得不自行脑补全部状态表现，设计-工程脱节风险高。

**建议**：至少为核心页（行动面板、技能检定、战斗声明）补"状态变体稿"（IDLE/SUBMITTING/RESOLVING/拒绝/超时），或在 INDEX 中明示"界面稿仅表达视觉风格，交互状态以技术方案为准"。

### P2-6 版本泛滥且多组无最终版标记

**证据**：21 页中存在 dashboard `v1 / v2_lite / v3_insanity`、skills `dynamic_v1/v2 / static_v1/v2`、status `basic / v1 / v2`、map `cn / en / 2b_v1 / 2b_v2`。INDEX 自认 `player_status_v1/v2`、`player_skills_dynamic_v1/v2`、`player_skills_static_v1/v2` 三组"高度相似/细微差异"未定最终版。diff 实证：`player_status_v1` 与 `v2` 差异仅在 keyframes 与按钮样式片段；`player_skills_dynamic_v1` 与 `v2` 差异仅为边框 4px→3px、动画位移幅度等像素级参数。命名上 `lite`、`insanity`、`2b`（病房号还是版本号？）、`basic` 混用，语义不清。

**建议**：每组标注"采用/归档"，将弃用版本移入 `archive/` 子目录；`player_map_2b_*` 改名为 `player_map_ward2b_*`。

### P2-7 cn/en 双版本无同步策略，且同屏中英混排

**证据**：
- `player_map_cn` 与 `player_map_en` 的 diff 显示两者仅为文案翻译关系（`<title>`、`调查员_0824/INVESTIGATOR_0824`、`生命: 12 / 理智: 45 / HP: 12 / SAN: 45`），靠手工复制维护，无同步机制——已出现不同步风险（`player_map_2b_v1` 与 `map_en` 截图完全相同，疑似复制时张冠李戴）。
- 双语覆盖不完整：skills/status 系列只有英文标题（`INVESTIGATOR_0824`、`CORE SKILLS`），仅 `player_skills_cn`、`player_map_cn` 两个中文孤岛。
- `host_dashboard_v1` 同屏中英混排：中文场景标题"场景 04：疗养院走廊"下方叙事正文却是英文 "The air in this wing is perceptibly colder..."。

**建议**：明确产品语言策略（单语还是双语）；若双语，建立翻译对照机制而非整页复制；界面稿叙事示例统一为产品目标语言。

### P2-8 bauhaus 规范大体被执行，但 host 端头部/命名不统一

**证据（合规面）**：21 页扫描显示圆角≈0、无软阴影（仅用 `shadow-[Npx_Npx_0px]` 偏移色块）、渐变仅用于地图网格线（`player_map_cn/code.html:92` 的 `linear-gradient` 画 2px 网格）——bauhaus 规范执行度良好。
**证据（不合规面）**：`host_dashboard_*` 头部为"阿卡的姆系统 / KEEPER_PRIME V.0.4.2_STABLE"，`host_combat_*`、`host_database`、`host_logs` 头部为"ARKHAM OS"，导航项分别为"会话/传说/资料库/日志"与"时间轴(TIMELINE)/参战者(COMBATANTS)/资料库(DATABASE)/日志(LOG)"——同一产品的 host 端存在两套产品名与两套信息架构，DESIGN.md 未覆盖这一层（它只规定视觉 Token，未规定产品命名与导航骨架）。

**建议**：DESIGN.md 增补"产品命名与 host 端导航骨架"一节，或在 INDEX 中说明 dashboard 与 combat 的导航关系。

## 4. 缺失项

1. **行动输入/当前事项页（P0 场景）**：Spec 的"当前"页（主事项卡+统一输入框+渐进式确认）没有任何界面稿；PRD-14 的语音优先行动面板同样无稿。
2. **战斗整轮声明与锁定**：无玩家端"声明本轮行动/已声明未锁定/整轮结算进度"稿；无预备动作确认卡（Spec 给了大量文案示例但零视觉稿）。
3. **战术聊天/对讲机**：INDEX 矩阵自认"设计稿待补"。
4. **边界态全面缺失**：21 页无一展示空态（无线索/无物品/未进战斗）、加载/提交中/结算中、错误/拒绝、断线与重连（Spec §1.8 的"重新加入局势"卡、离线重大结果卡均无稿）。Spec §5 也自认"上手引导、空状态、语音输入和无障碍"未设计。
5. **检定结果呈现**：有技能面板但无"结果卡"（Spec §6.1 分层结果卡：公共/仅你可见/判定依据）界面稿。
6. **Spec 自身未完成项**（其 §5 列明）：公共战斗舞台最终线框、追逐是否复用整轮声明、战斗结束/投降/逃跑、角色死亡与永久离场界面、地图/距离/掩体手机交互、桌务无剧透恢复。即 **"Complete_Consolidated_Spec" 名不副实**——它既未覆盖上述场景，也未引用/对齐 stitch 界面稿与 5 份技术方案（全文无一处提及这些资产），建议改名或补齐。
7. **host_database / host_logs 在 Spec 中无对应概念**：Spec 没有"KP 资料库/运行日志"终端定义，这两页面向谁、防剧透边界如何，无据可依。

## 5. 亮点

- **Consolidated Spec 思辨质量高**：冲突优先级规则（"后续明确决定 > 前期建议 > 原型临时表现"）、每轮附"明确否决方案"清单、预备动作/缺席/重连的规则闭环（状态机+审计事件链+防剧透记录）达到了可直接评审实现的深度。
- **INDEX.md 的整理意识**：语义化重命名对照表、版本关系标注（"v2 为最终版本"）、自查列出的待确认事项——虽然未闭环，但自我审计意识好于大多数设计库。
- **bauhaus 视觉规范执行度高**：21 页零圆角、零软阴影、统一偏移色块与色板，视觉一致性确实立住了（界面稿层面最大的优点）。
- **技术方案与 PRD 的映射清晰**：模块 1~5 ↔ PRD-07~11 一一对应，修订说明（v1→v2.0 废弃项）交代明确。

## 6. 结论与行动建议

**结论**：这是一套"规范强、界面弱、彼此打架"的设计库。头脑风暴合并稿是优秀的交互规则文档，Stitch 界面稿是合格的视觉风格稿，但两者分属不同日期、不同交互模型、不同信息架构，且矛盾已沿技术方案渗入 PRD-07~14。当前状态下，任何一端按库开工都会产出需要返工的结果。
