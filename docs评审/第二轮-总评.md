# 第二轮评审总评：代码 ↔ 文档 双向差距分析

> 评审对象：`CodeX-aikeeper/README.md`（代码实现总结）× 上一轮评审过的 docs 全库
> 评审视角：专门找"漏掉的工作"——设计了没实现的、实现了没文档的、验收了没证据的、该有文档却没有的。
> 分报告：同目录三份（代码与平台子系统差距 / 代码与PRD规范差距 / 链路验收与README完备性）

## 一、结论先行

上一轮评审的结论是"三套文档互相打架，不能当唯一事实源"。这一轮把代码拉进来后，结论升级为：

**代码已经投票了。** 在规范 vs PRD 的三面冲突中，代码实际站在了 PRD 一边（语音已落地、PDF 导入已落地、Host 是一等公民），但规范从未被修订，文档也从未追上代码。现在的事实源分裂成**四层**：规范说一套、PRD 说一套、平台施工图说一套、代码做一套。同时，一批高危代码能力（全局重置、迁移、切换）在设计与测试两层都完全裸奔。

## 二、最严重的遗漏（P0 级汇总）

### 1. 安全体系三层断链 —— 本轮最致命发现
M0 必验的"安全与结束"能力（X-card、边界确认、安全暂停、淡出）：
- 规范层：04-M0 列为必验（Gate G5）；
- PRD 层：31 份 PRD **无一份承接**；
- 代码层：README 目录树**零模块**；
- 排期层：40-平台补全把它排到阶段 5 Batch 18。

四方同时失守，M0-Verified 在当前定义下永远无法达成。必须立刻裁决：要么补 PRD+实现拉回 M0，要么开 ADR 正式降级。

### 2. ADR-005 被代码直接违反
规范废止 Host 概念，代码却以 `host/` 路由目录、4 个 Host 页面（HostStage/HostLobby/HostCreate/HostConsole）、`hud_builder.py`、`host_autonomy.py` 为一等公民；规范定义的 RoomOwner/TableSteward 角色在代码中零出现。Gate G0（唯一入口）无法通过。同理 ADR-003（语音 Later）被 `stt.py`/`VoiceInput.tsx` 的既成事实倒逼。规范要么修订，要么代码返工——继续拖只会抬高成本。

### 3. 高危能力零文档零测试
`global_reset.py`（全局重置）、`v2_cutover.py`（V2 切换）、`room_migration.py`（房间迁移）这类**数据销毁/迁移级**能力，在 24 个子系统设计文档中 0 命中（无权限模型、无审计设计），且 `global_reset` 无任何专属测试文件。同类裸奔模块还有：`game_loop/turn_timeout_worker`、`collaboration_contracts`、`solo_runtime/solo_adventure`、`export.py`（50-平台声称已建 `test_export.py`，实际不存在）、`combat_round_planner`、`map_generator` 等 11+ 个。

### 4. 行动状态机三套词汇打架
README 写 6 状态（终态 `resolved`）；代码权威 `action_state.py` 有 14 个状态（终态 `completed`）；PRD-01/09 与 PRD-25 又各说一套。README 的简化状态机漏掉 `awaiting_host_exception` 等 8 个安全关键状态——而"awaiting_host_exception"正是上一轮发现规范未定义的状态，代码却已在用。**三方文档没人跟代码对过账。**

### 5. 验收证据链断裂
- `TEST_COVERAGE.md` 停留在 SQLite 时代（项目已迁 PostgreSQL），完全过期；
- 验收报告声称"已建测试"的文件实际不存在；
- `RagTestPage.tsx` 在全部文档中 0 次出现（开发自留后门页？无设计无验收）；
- 上一轮已发现"全量通过"数字六个版本矛盾——本轮确认部分"通过"对应的测试资产根本不在仓库。

### 6. KP_MCP_Design 恶性设计仍未隔离
20-核心链路的 KP_MCP_Design.md §4.1"先推叙事再掷骰再写库"（无 fact-ref/SpoilerGuard 校验、AI 可直写状态）与代码实际的 State-first 主链直接冲突，文档中无任何"未按此实现"的声明。新人照此文档理解系统会被严重误导。

### 7. 工程文档类型整体缺失
README 之外，整个项目没有：API 参考（REST/WS 端点清单）、数据库 schema 文档（仅一句 `initialize()`）、运维文档（监控/备份/容量）、安全设计文档（威胁模型）、CHANGELOG/版本策略、贡献指南。README 的 docs 目录树也与实际不符（漏 00-路线图、10-现状盘点、40-平台补全、开发文档四处）。另有事实性疑点：`DEEPSEEK_MODEL` 默认值 `deepseek-v4-pro` 是否为真实模型名需核实。

## 三、"设计领先代码"与"代码领先设计"两个方向

**设计了但没实现（纸面系统）**：23-Community 社区生态完全零代码；21-Safety 实质零代码（见 P0-1）；22-Schedule、19-Module 大部分、20-Voice-Media 大部分均为纸面。这些本身不是问题（M0 之后的事），**问题是它们没有统一的"未实现"状态标注**，读者无法分辨哪些能跑。

**代码超前文档（文档欠债）**：至少 5 处代码已超前于文档（19-Module publish_status、08-Clue 事件契约等），09-Scene-Map 与 21-Safety 口径互相矛盾。文档不追代码，下一轮接手的人会再次踩进本轮发现的坑。

## 五、两轮评审的关系

第一轮（纯文档）：发现规范/PRD/施工图三套体系互相矛盾。
第二轮（代码 vs 文档）：确认代码实际选择了其中一套，但没有任何文档记录这个选择；同时暴露出一批代码能力在设计与测试两层的真空。

两轮合并的核心建议没变，只是更紧迫了：**先裁决冲突、再追认现实、然后让验收机制说真话。**
