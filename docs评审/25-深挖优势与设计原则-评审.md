# 25-深挖优势与设计原则 评审报告

## 1. 概述

**定位**：docs/README 将其定义为"战略设计笔记：AI 长期记忆、自然语义理解、线索自动整理、战斗运行时等核心差异点"。实际内容是 13 份 AI 对话式的设计探索文档，每份围绕一个差异化方向给出对象模型、P0/P1 范围和验收清单。

**文件清单**（13 份）：

| 文件 | 主题 | 体量 |

| 第2条：AI 能理解自然语言，但结算透明.md | 可解释裁决链（意图合同/裁决回执/复核事务） | 32KB |
| 第3条：AI 能自动整理线索、人物和时间线，但不替玩家推理.md | 调查工作台 | 33KB |

**整体质量评分：C**

单篇内容质量普遍较高（对象模型具体、有禁止清单、有验收清单），但作为"正式文档库中的一个文件夹"处于治理失控状态：与 M0 现行规范正面冲突且无裁决记录、模块编号撞车、同主题重复建设、含半成品和未编辑的 AI 对话导出物。按项目自己在《验收记录-2026-07-15》建立的文档治理标准，这个文件夹大部分内容应降级为"候选/档案"，而不是与规范文档平级陈列。

## 2. 主要问题

### P0-1：多份文档把 M0 明确的"非目标 / Later"写成 P0，且无任何冲突标注或 ADR 裁决

**证据**：

- `00-产品规范/00-产品宪法.md`（status: normative）"非目标"：*长期战役导演、运行时新 Canon 或自动世界扩写；任意 PDF 的可靠全自动编译和完整模组编辑器；语音、视频、音效、战棋、动态地图……*
- `00-产品规范/04-M0范围、里程碑与指标.md` "Later"：*长期 Campaign Governor、自动世界扩写、运行时新 Canon 和 Host 缺席自治；任意 PDF 的可靠全自动编译、完整模组编辑器和公开市场；完整战斗战棋运行时、连续替补规则……*
- 本文件夹的冲突点：
  - `战斗：应当做成"可插拔的遭遇运行时"….md` "# 三十二、P0 建议范围" 列出 22 项 P0 核心（`EncounterProposal / Confirm / Reject`、`EncounterInstance`、`Host Encounter Console`、`Player Combat Terminal` 等完整遭遇运行时）——正是 M0 的 Later 项"完整战斗战棋运行时"。
  - `AI 主导方向，怎么保证不跑偏.md` "# 二十五、P0 应该做到什么" 14 项含 `CampaignPromise`、`StoryThread`、`WorldClock`、`DirectionCheckpoint`——即 M0 Later 项"长期 Campaign Governor / 自动世界扩写"。
  - `第4条：Host 不在线时仍能继续….md` 通篇设计 Host 缺席自治（`HostPresenceState`、`HostDelegationGrant`）——M0 Later 项"Host 缺席自治"。
  - `把导入系统重新定义….md` "# 二十一、P0 应该实现到什么程度" 含扫描 PDF / 混合 PDF / ZIP 混合包的全自动导入，"# 二十二、建议工程批次 Import-0 ~ Import-8"——M0 Later 项"任意 PDF 的可靠全自动编译"。

**影响**：docs/README 规定"所有新设计和实现任务先引用 `00-产品规范/`；旧文档若冲突，以其中的 ADR 和裁决映射为准"。25 的文档既没有声明自己是 candidate，也没有指向任何 ADR。执行者（DeepSeek 或新人）读到战斗文档的"P0 核心"会认为这是当前必做范围，直接撞穿 M0 边界。这是整个文档库目前最大的口径风险。

**改进建议**：为每份文档补 frontmatter（`status: candidate`、`out_of_scope_for: M0`、`target: M1/Later`）；在 `00-产品规范/06-决策记录 ADR.md` 登记哪些设计被吸收、哪些挂起；或在文档开头加一段"与 M0 的关系"声明。

### P0-2：模块编号"26"三连撞，且与 50 的 24 模块体系脱节

**证据**：

- `自然语义理解.md` "# 九、与现有 01-24 模块怎么接"：链路中插入 **`26-Semantic`**（Grounding + Risk + Clarification + Confirmation）。
- `战斗….md` "# 二、建议新增一个独立模块"：**`26-Combat / Encounter 战斗与遭遇系统`**。
- `把导入系统重新定义….md` "# 二十、建议新增的内部组件"："这**不一定要成为第 26 个用户模块**，可以作为 19-Module 的内部子系统。"
- `第1条….md` "# 十四、是否需要新增一个独立 Memory 模块"：提议新增 **Memory / Knowledge 可信记忆与认知系统**（未编号）。
- 对照 `50-AI-Keeper-Platform/README.md`：模块目录固定为 01–24，无 25/26，无 Semantic/Combat/Memory 独立模块。

**影响**：同一个编号被三份文档赋予三个不同含义，50 的施工图编号体系被架空；后续任何文档引用"模块 26"都产生歧义。

**改进建议**：所有新模块提议统一走 50 的模块登记（新增模块需扩编号并更新 50 README），25 中的编号引用改为指向 50 的正式登记或标记为"未登记提案"。

### P1-3：原则之间冲突未裁决——"人工复核模组真相/结局" vs "用户不读剧本 / 房主无 KP 视角"

**证据**：

- `AI 自动整理线索.md` Stage 9："只让人复核高风险内容：**模组真相、结局**、实体合并、触发器、规则覆盖、可见性……"；同文档"# 十三、人工复核不应该让 Host 看完全部抽取结果"。
- `把导入系统重新定义….md`："用户几乎不需要阅读剧本内容"；"完整策展模式只给愿意阅读剧本的管理员、编辑者或第三方策展员使用。**普通 Host 或玩家不需要进入这个模式**"。
- `PRDs/README.md` 首版核心假设："房主可以作为玩家参与，因此**不能拥有完整 KP 剧透视角**"。

**影响**：三处论述对"谁来复核真相和结局"给出了互不兼容的答案：Host 不能全看、普通 Host 不进策展模式、房主不能看真相、第三方策展员在 M0 根本不存在。这是 25 内部"原则冲突"的典型实例——两篇同主题文档（Module Compiler vs Module Intake Router）在同一文件夹内各自推演，无人裁决。

**改进建议**：在导入主题收敛为一份权威文档，明确"复核人角色矩阵"（房主/不参团 Host/平台策展员分别复核什么），并将该裁决写入 ADR。

### P1-4：半成品与未编辑的 AI 对话导出物留在正式文档库，违反项目已有治理结论

**证据**：

- `想到+待聊.md` 全文仅 7 行（剧本导入 / 角色卡+物品 / 开局状态 / 自然语义的理解 / AI主导方向性问题 / 战斗 / 结局），是个人选题备忘。
- `自然语义理解.md` 含两条死链：`[下载可运行示例代码](sandbox:/mnt/data/semantic_interaction_demo.zip)`、`[查看完整演示输出](sandbox:/mnt/data/semantic_interaction_demo/demo_output.txt)`——sandbox 链接离开原聊天环境即失效，"4 passed"的测试结论无法复核。

- 治理对照：`00-产品规范/验收记录-2026-07-15.md` 记录"将'方向性问题头脑风暴'七份源文件**逐字归档**到 `docs/90-归档/方向性问题头脑风暴/原始材料/`"，并专门指出 sandbox:/mnt/data 死链"不属于仓库可解析链接"、只能留在逐字档案；`90-归档/方向性问题头脑风暴/README.md` 使用规则："档案中的'建议''历史方案''已挂起'**不自动成为 M0 功能承诺**"。

**影响**：项目已经（2026-07-15）为这类素材建立了归档 + 裁决映射的治理通道，25 的同类素材却绕过通道直接进入正式索引（docs/README 推荐阅读顺序第 8 条）。这开创了"聊天记录可以当正式设计文档"的先例，稀释了文档库的可信度。

**改进建议**：`想到+待聊.md` 删除或并入文件夹 README 的 backlog 节；含 sandbox 死链的 `自然语义理解.md` 移入 90-归档；其余文档编辑掉对话口吻（"你们""你指出的是"），补齐 frontmatter。

### P1-5：同主题重复建设，无索引、无权威版本声明

**证据**：

- 自然语义理解主题有三份：`自然语义理解.md`（SemanticRecord + ActionCommand 对象）、`自然语义理解：从"识别一句话"升级为"编译玩家真实意图".md`（Semantic Interaction Protocol 四层模型）、`第2条….md`（意图合同 / 裁决回执 / 复核事务）。三套命名互不兼容，互相无 cross-reference，未声明以谁为准。

## 4. 缺失项

1. **文件夹 README**：无索引、无权威版本声明、无与 M0 关系说明。
2. **"开局状态"与"结局"两份文档**：`想到+待聊.md` 自列 7 个待聊主题，其中"开局状态""结局"始终无对应成文（其余 5 个主题均已有文档）——文件夹自我承诺的完整性未兑现。
3. **每份文档的状态字段**：采纳 / 候选 / 挂起无从分辨。
4. **与 30 任务包、PRD 验收矩阵的落地映射**：100+ 条验收清单无承接登记。
5. **5 条原则的总纲**：为什么是这 5 条、是否完备、与 00-产品宪法"M0 必须证明的五件事"（00-产品宪法.md 第 29–37 行，恰好也是五条）是什么关系——两者条数相同、内容相近但不完全对应，无人做映射。

## 5. 亮点

- 原则本身不是空口号：几乎每个方向都落到了数据对象（`Memory Claim`、`DirectionProposal`、`EncounterInstance`）、硬约束清单（"硬约束必须先过滤，评分不能覆盖硬规则"）和禁止实现方式。
- 安全默认值设计务实："少自动化是可恢复的；错误自动化和剧透往往不可恢复"（把导入文档 "# 十四"）可直接作为设计约束执行。
- 与核心链路既有原则有显式呼应（State 先于 Projection、AI 不写权威状态、Host ACK 不带规则结果），继承关系意识好。
- P0/P1/P2 分层和"明确禁止的实现方式"清单的结构值得保留为模板。
