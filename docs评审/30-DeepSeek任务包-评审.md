# 30-DeepSeek任务包 评审报告

## 1. 概述

**定位**：把 Codex 拆好的方向交给 DeepSeek 执行的第一轮批次包（README："每个 Batch 都必须独立验收，不允许跨批顺手扩功能"）。6 个批次（Batch 0–5）+ 1 份 README，覆盖文档归档、开发态稳定性、状态版本屏障、AI 反幻觉、线索证据链、全量回归。

**文件清单**（7 份）：

| 文件 | 内容 |
|---|---|
| README.md | 执行顺序表 + 6 条通用执行规则 |
| Batch-0-文档归档与索引.md | 建 docs/ 目录结构、归档 plan*.md |
| Batch-1-开发态稳定性与实时闭环.md | WS 崩溃、Host 鉴权、Lobby 同步、日志乱码、MCP/DeepSeek 剧本链路 |
| Batch-2-状态版本屏障与投影时序.md | state version barrier、`executeAfter`、乱序 buffer |
| Batch-3-AI反幻觉与真相锁定.md | AI 输出校验、上下文过滤、Engine 写边界 |
| Batch-4-线索证据链与防剧透.md | 线索归属/分享/摘要/事件引用 |
| Batch-5-验收与回归.md | 全量测试 + 10 步手动主链路 + 5 条安全验收 |

**整体质量评分：B-**

作为执行包，结构是合格的：每批有目标、范围、文件方向、验收命令、手动验收、禁止事项，通用规则（测试库隔离、"通过"结论必须来自本批新运行命令）务实。主要短板是：与 M0 验收范围脱节（安全结束能力无批次承接）、无状态跟踪导致与 60 已有验收证据脱节、批次间文件方向重叠、Batch 1 粒度过大、与 PRDs 的实施批次零映射。

## 2. 主要问题

### P0-1：M0 必须验收的能力域没有对应 Batch——"安全与结束"整域缺席

**证据**：

- `00-产品规范/04-M0范围、里程碑与指标.md` "M0 必须进入验收"表：*安全与结束｜内容提醒、边界确认、X-card、淡出、私密反馈、安全结束｜正常、暂停和中断结束路径*；Gate G5：*安全与 Session 闭环：暂停、淡出、私密反馈与安全结束不依赖 Owner 或 Stage*。
- Batch 0–5 全文检索：无 X-card、淡出、内容提醒、安全结束任何字样。Batch-5 的"安全验收"5 条是另一组内容（防伪造 `characterId`、Host 不写权威状态、房主不见 KP-only 真相、AI 不落库、未发现线索不进上下文）。
- 另外 M0 表中"内容｜一份原创、获授权或内部可合法使用的固定参考短模组"也无 Batch 承接（内容资产准备不在任何批次）。

**影响**：即使 Batch 0–5 全部验收通过，M0 的 G5 Gate 和"内容"域仍然无证据，Batch-5 宣称的"确认系统能真实跑完一条 AI-KP 主流程"不等于 M0 验收。任务包给了执行者"做完这 6 批就完成第一轮"的错误预期。

**改进建议**：新增 Batch（或在 Batch 5 中扩展）覆盖内容提醒/暂停/淡出/私密反馈/安全结束的 M0 最小集；在 README 执行顺序表增加"M0 Gate 映射"列。

### P0-2：无状态跟踪，与 60-验收与测试报告的既有证据脱节

**证据**：

- `60-验收与测试报告/260718_COMPLETION_AUDIT_2026-07-19.md` 已记录：`test_reconnect.py`、`test_resolution_pipeline.py`、`test_host.py`、`test_action_lifecycle_v2.py` 等"189 passed"——其中 `test_reconnect.py`、`test_resolution_pipeline.py` 正是 Batch-2/Batch-3 验收命令中的测试文件；该审计还覆盖了"Host 计划离线与意外离线的保守自治""State-first、统一 ResolutionBundle、公共/私密投影隔离"等与 Batch 2/3 目标重合的项。
- 但 7 份文档均无 status / 执行日期 / 完成记录字段；Batch-5 要求"把实际测试结果补到对应任务记录或测试覆盖文档"，却不说明 60 里已有的 15+ 份报告（含 2026-07-09/07-10/07-19 多份）与本轮验收是什么关系（预演？部分有效？必须重跑？）。
- `10-现状盘点/当前项目状态与风险.md` 仍把"开发态稳定性、实时闭环、Host 状态聚合、状态版本屏障"列为"当前补漏方向"——与 60 的"189 passed"并存，但 30 没有任何文档帮助执行者调和这两个信号。

**影响**：DeepSeek 执行时无法判断每批是"未开始/进行中/已完成"，可能重复修复已验证项，或把历史通过当成新证据（README 通用规则明确禁止后者，但批次文档没给判别依据）。

**改进建议**：每批加 frontmatter（status、started_at、completed_at、证据链接）；README 增加"与 60 报告的关系"一节：历史报告只作参考，每批验收必须重新运行并登记新报告编号。

### P1-3：批次文件方向互相重叠，违反自身"批次独立"规则

**证据**（README 通用规则："只改当前批次列出的文件方向，不做相邻重构"）：

- `src/server/events/events_registry.py` 同时出现在 Batch-1（"事件"行）、Batch-2（"事件契约"行）、Batch-4（"事件日志"行）的文件方向表。
- `src/server/engine/projection.py` 同时出现在 Batch-2（"投影"行）和 Batch-4（"投影"行）。
- `src/server/ai/rag_context.py`、`src/server/ai/spoiler_control.py` 同时出现在 Batch-3（RAG 上下文/剧透控制行）和 Batch-4（AI 上下文行）。
- 验收命令与文件方向表内部不一致：Batch-2 验收命令含 `tests/server/test_player_runtime_state.py`，但其文件方向表的测试行只列了 `test_reconnect.py`、`test_projection.py`、前端 WS 单测；Batch-3 验收命令含 `tests/server/test_ai_kp.py`，文件方向表同样未列。

**影响**：同一文件被多批"认领"，执行时出现两种坏情况：前批顺手改了后批的范围（违反禁止相邻重构），或后批发现前批改动与本批目标冲突时无法定责。文件方向表与验收命令不一致则说明文档未经一次完整的自查。

**改进建议**：为重叠文件声明"主责批次"，其余批次标注"只读/仅联调"；校对每批文件方向表与验收命令的文件集合一致性。

### P1-4：Batch 1 粒度过大，一个批次装 5 个不相关问题域

**证据**：Batch-1 的范围同时包含：①玩家 WS catch-up、②Host WS 鉴权、③开局广播/Lobby snapshot、④HUD 初始推送与状态聚合、⑤日志 UTF-8/ANSI/落盘、⑥AI Gateway provider 顺序、⑦DeepSeek 失败诊断、⑧剧本结构化规范化与质量报告展示。文件方向表横跨 10 个区域约 28 个路径（从 `src/server/main.py`、`router_rooms.py` 到 `log_config.py`、`quality.py` 再到 4 个前端 tsx）。对照：Batch 0 只有文档归档，Batch 5 只有回归——批次间粒度严重不均。

**影响**：8 个子项中任何一项失败，整批不可验收；排障时无法判断是哪项引入的回归。这与 README"每个 Batch 都必须独立验收"形成事实上的自相矛盾——Batch 1 本身就不是一个"独立可验收单元"。

**改进建议**：Batch 1 至少拆成 1a（WS/鉴权/Lobby 实时闭环）、1b（日志与开发态稳定性）、1c（MCP/DeepSeek 剧本链路）三批，各自独立验收命令。

### P1-5：安全场景与手动验收不可验证

**证据**：

- Batch-3"安全场景"4 条（如"玩家猜测凶手身份，AI 不能因为猜对或猜错而改写真相""未发现线索不能出现在玩家提示词、Player event 或公共日志"）——验收命令只有 4 个 pytest 文件，没有说明这 4 条场景由哪个测试、哪个脚本或什么红队流程验证。
- Batch-5"安全验收"5 条（如"Player 不能伪造 `characterId` 操作他人角色"）同样无测试命令映射。
- Batch-1 手动验收"聊天不重复""ready 状态双端同步"无量化判定（重复率？容忍几条？），也无结果记录模板。

**影响**：README 要求"所有'通过'结论必须来自本批新运行的命令输出"，但安全类条目根本没有"命令"可运行，执行者只能以主观判断收尾，安全验收流于打勾。

**改进建议**：为每条安全场景补可执行验证（pytest 用例名或脚本）；手动验收项给出量化判定标准和结果记录表模板。

### P2-6：与 PRDs 的实施批次是两套零映射的体系

**证据**：`PRDs/README.md` 第 8 节"实施建议"：第一批 PRD-00/01/22/23/21（"PDF 到可开房"）、第二批 PRD-12/13/14/15/25、第三批 PRD-24/26/29/30/02/03/04/06/07/09、第四批 PRD-16/17/18/19/20/27/28、第五批 PRD-05/10/11、后续批 PRD-08。这套五批+后续批与 Batch 0–5 互不引用：无法回答"PRD-19 断线重连由哪个 Batch 闭环"（Batch 2 部分覆盖但未声明）、"PRD-05 氛围引擎在哪个 Batch"（无）。

**影响**：PRD 验收矩阵（PRDs/README 第 6 节 12 项验收项）与 Batch 验收各自孤立，第一轮做完后无法系统回答"31 份 PRD 各自被哪个 Batch 实现/验证过"。

**改进建议**：README 增加 Batch ↔ PRD 映射表（多对多，允许标注"部分覆盖/不覆盖"）。

### P2-7：Batch-0 验收标准弱且不可重复

**证据**：Batch-0 验收为 `Get-ChildItem -Recurse docs`（预期"能看到上述新增目录"）和 `Select-String -Path docs\README.md -Pattern "DeepSeek 任务包"`——只验证文件存在，不验证内容质量；且该批显然已执行完毕（docs/ 目录结构已存在），作为常驻文档其验收命令不可再次"通过"，却又没有标记"已完成"。

**改进建议**：Batch-0 标记完成状态并链接执行证据；或将验收改为内容断言（如 README 必须包含哪些锚点）。

## 4. 缺失项

1. **批次状态字段与执行记录**（status/日期/证据链接）。
2. **M0 安全结束批次**：X-card、内容提醒、淡出、私密反馈、安全结束的 M0 最小集无承接。
3. **固定参考短模组的内容准备任务**（M0"内容"域）。
4. **Batch ↔ M0 Gate（G0–G6）映射表、Batch ↔ PRD（00–30）映射表**。
5. **安全场景的可执行验证**（红队脚本/pytest 用例）。
6. **无 Stage 路径与四玩家路径的回归验收**（对应 G6 双路径）。
7. **与 60-验收与测试报告**的登记关系说明。

## 5. 亮点

- 通用执行规则质量高：测试库隔离、不提交密钥/日志/数据库、"通过"结论必须来自本批新运行命令、测试失败先归因再决定修复或回报——这是可直接当团队 SOP 的写法。
- 每批都有"禁止事项"，且禁止项具体（"不用简单延迟计时代替事务节点""不用前端隐藏代替后端权限过滤""不把局部测试通过包装成全量通过"）。
- Batch 2/3/4 的技术目标（版本屏障、`executeAfter` 事务节点、真相锁定、线索证据链）与 20-核心链路、PRD-26/27/29 的原则一致，方向拆解靠谱。

## 6. 结论与行动建议

**结论**：结构合格、方向正确的执行包，但作为一个"任务系统"缺少状态机和映射层：执行者不知道哪些已做、不知道与 M0/PRD 的对应关系，且 M0 的安全结束域整域缺席。评 B-。

**行动建议（按优先级）**：

1. 【P0】补安全结束批次（或扩展 Batch 5），覆盖 M0"安全与结束"最小集 + 无 Stage/四玩家双路径回归。
2. 【P0】每批加 status frontmatter；README 写明 60 历史报告只作参考、每批验收须重跑并登记新证据。
3. 【P1】拆 Batch 1 为 1a/1b/1c；为重叠文件（events_registry.py、projection.py、rag_context.py、spoiler_control.py）声明主责批次；校对文件方向表与验收命令一致性。
4. 【P1】安全场景逐条绑定可执行验证；手动验收给量化标准与记录模板。
5. 【P2】README 增加 Batch ↔ M0 Gate、Batch ↔ PRD 两张映射表。
