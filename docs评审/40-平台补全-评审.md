# 40-平台补全 评审报告

## 1. 概述

**定位**：收纳核心链路之外的平台能力，明确"本目录不是当前实现任务清单"，承接 Batch 5 验收之后的第二至第六阶段规划。4 份文件：索引、能力域矩阵、阶段路线（Batch 6–26 候选）、工程安全运营护栏。

**文件清单**（4 份）：

| 文件 | 内容 |
|---|---|
| README.md | 定位声明、阅读顺序、与 20/30/50/PRDs 的关系、执行边界 |
| 平台能力域与优先级.md | 四层能力分层 + 23 行能力域矩阵 + 第一轮不吸收清单 + 准入条件 |
| 核心链路之后的阶段路线.md | 六轮阶段（Batch 6–26 候选）+ 阶段切换门槛 + 拆批模板 |
| 工程安全运营护栏.md | 工程/权限隐私/AI 安全/跑团安全/运营/成本六组护栏 + 上线前最低门槛 |

**整体质量评分：C+**

三层定位（30 当前执行 / 40 路线边界 / 50 长期施工图）划分清楚，"第一轮不吸收的能力"负向清单和护栏的权限隐私矩阵质量较好。但存在两处与 M0 现行规范的硬冲突（跑团安全边界排期、阶段 1 语音口径）、优先级依据不可追溯、与 50 模块体系数量不对齐且无映射、门槛定义与 M0 发布门槛双轨并行。框架正确、裁决缺失。

## 2. 主要问题

### P0-1：跑团安全边界全部排到"阶段 5"，与 M0 规范的"必须验收"正面冲突

**证据**：

- `工程安全运营护栏.md` "跑团安全护栏"表：内容分级、禁区标签、X-Card/暂停卡、私密反馈、剧情淡出、AI 内容限制 6 项，"推进阶段"列**全部为阶段 5**。
- `平台能力域与优先级.md` 矩阵："跑团安全边界……不进入第一轮实现，但上线前必须补"（P1/P2）；`核心链路之后的阶段路线.md` 把其实体化为阶段 5 的"Batch 18：跑团安全边界"。
- 对照 `00-产品规范/04-M0范围、里程碑与指标.md`（status: normative）"M0 必须进入验收"表：**安全与结束｜内容提醒、边界确认、X-card、淡出、私密反馈、安全结束**；Gate G5："安全与 Session 闭环：暂停、淡出、私密反馈与安全结束不依赖 Owner 或 Stage"。`00-产品宪法.md` 用户表也要求 TableSteward"在不接触幕后真相和玩家私密原文的前提下暂停、恢复和处理安全操作"。

**影响**：M0（当前轮）就要求验收的 X-card/淡出/私密反馈，被 40 排到了第五轮（Batch 18，中间隔着阶段 2/3/4 共 13 个 Batch）。若按 40 执行，M0-Verified 发布门槛（04-M0："任何一项未验证都只能称为'候选能力'"）永远无法达成；若按 M0 执行，40 的阶段路线就是错的。两份"现行"文档给出相反答案，且无 ADR 裁决。这是三份受审文件夹中最严重的一致性问题。

**改进建议**：把 M0 必需的最小安全集（内容提醒、暂停/X-card、私密反馈、安全结束）从"跑团安全边界"中拆出，标为第一轮/M0 范围并与 30 任务包挂钩；完整体系（分级、禁区标签、Session 0）保留在阶段 5；在 ADR 登记此拆分。

### P0-2：阶段 1 验收口径把"语音转写"列为验收结果，与自身矩阵、00-路线图、PRDs 三处冲突

**证据**：

- `核心链路之后的阶段路线.md` 阶段 1 表："玩家行动入口｜**文本、按钮、语音转写后的行动都走统一意图网关**"，且注明"本阶段由 `docs/30-DeepSeek任务包/` Batch 0 到 Batch 5 承接"。
- 对照本文件夹 `平台能力域与优先级.md`："语音 / 视频 / 实时协作……仅保留语音意图占位和文字兜底"。
- 对照 `00-路线图/平台能力分层与MVP边界.md` 第一轮不做清单："语音视频"。
- 对照 `PRDs/README.md` 实施建议："后续批：PRD-08 语音/STT，待浏览器录音与 STT 接入方案稳定后实施"。
- 对照 30 任务包：Batch 0–5 无任何语音转写任务。

**影响**：阶段 1 的"验收结果"在当前批次体系下不可达成——阶段路线给自己定了一个不可能通过的验收项。执行者按阶段 1 验收必然失败，或被迫把语音塞进 Batch（违反"第一轮不吸收"清单）。

**改进建议**：阶段 1 行动入口口径改为"文本、按钮及语音意图占位（文字兜底）走统一意图网关"，语音转写移至对应后续阶段。

### P1-3：优先级依据不充分——"区间优先级"等于没有决策，"附件来源范围"列名不副实

**证据**：

- `平台能力域与优先级.md` 矩阵 23 行的"建议优先级"几乎全是双级区间：房间 P0/P1、NPC P0/P2、地图 P0/P2、时间轴 P0/P2、玩家动作 P0/P2、Host 舞台 P0/P2、模组编辑器 P0/P2、资源素材 P1/P2、插件 P1/P3、后台 P0/P3……只有少数行是单级（语音视频 P2、社区 P2/P3）。
- 同文档"优先级解释"只定义单级 P0–P3，**未定义区间的含义和裁决规则**（何时取 P0、何时取 P2？由谁在什么节点裁决？）。
- "附件来源范围"列填的是功能枚举（如"房间、邀请码、Session、席位、旁观者、归档"），并**不是附件出处引用**——矩阵声称优先级有"附件来源"依据，但全程未指明是哪些附件、哪份清单，依据无法追溯核对。

**影响**：优先级矩阵的核心交付物（"每个能力域是什么优先级"）在多数行上没有给出答案，只给了一个区间；后续拆批时仍需重新决策一次，矩阵的决策价值打折。

**改进建议**：区间拆为"当前级/目标级"两列并写明升级条件；"附件来源范围"列改为真实出处引用或删除。

### P1-4：与 50 的 24 模块体系数量不对齐、无映射，AI-Keeper 核心系统在矩阵中失踪

**证据**：

- `平台能力域与优先级.md` 矩阵为 23 行能力域；`50-AI-Keeper-Platform/README.md` 明确"拆成 24 个……系统模块"（01–24）。两份文档互不引用对方的编号。
- 50 的 `12-AI-Keeper 核心系统`（AI KP、真相锁定、反幻觉、上下文、MCP）在 40 的能力域矩阵中**没有对应行**——矩阵里唯一的 AI 行是"AI 内容生成工具"（NPC/地点/线索生成入库），与 AI KP 核心是两件不同的事。
- 反向地，40 矩阵的"玩家动作 / 交互"行在 50 中也无对应模块（50 将其并入 16-Player-Client）。
- `核心链路之后的阶段路线.md` 批次编号到 Batch 26（商业化），与 24 模块也无映射表。

**影响**：40 自称"承接完整平台清单"、50 自称"完整平台拆 24 模块"，但两边的"完整"不是同一个集合；AI KP 这一产品最核心的系统在平台补全规划里反而没有位置（只在 30/PRD 层出现），长期路线中其演进（反幻觉增强、上下文工程等）无人承接。

**改进建议**：补"能力域 ↔ 50 模块"映射表；在矩阵中补 AI-Keeper 核心行（或显式说明其归属 20-核心链路、不在补全范围）。

### P1-5：两套"门槛"双轨并行且互不引用

**证据**：

- `工程安全运营护栏.md` "上线前最低门槛"7 条（测试可重复、权限边界有记录、快照/重连/日志可用、AI 失败不破坏状态、日志不脱敏、限流报警、备份导出）。
- 对照 `00-产品规范/04-M0范围、里程碑与指标.md` "M0-Verified 发布门槛"：顶层定义无 S0 未决矛盾、Intent/Rule/State/Receipt 链、**无 Shared Stage 可完整结束且其断线不阻塞业务**、私密边界通过**红队检查**、安全操作和恢复可用、失败项逐项披露。
- 两份清单交集约一半：护栏门槛不含 Stage 韧性、红队检查；M0 门槛不含限流、备份导出。"上线前"与"M0-Verified"是否同一节点、谁是谁的子集，均未定义，两份文档互相不引用。

**影响**：发布准入口径分裂，上线评审时两份清单可能被各取所需。

**改进建议**：合并为单一门槛文档（或在护栏中显式声明"M0-Verified 门槛见 04-M0，本文档为公开测试追加项"）。

### P2-6：阶段切换门槛不可测，且存在语病

**证据**（`核心链路之后的阶段路线.md` "阶段切换门槛"表）：

- "4→5：Host/Player 基础体验**不依赖外部 VTT 才能跑**"——语义不通（应为"不依赖外部 VTT 也能跑"）。
- "2→3：多 Session 文字团能**稳定**运行并复盘"——"稳定"无量化（连续几个 Session？允许什么级别的缺陷？）。
- "1→2：权限和投影没有 P0 漏洞"——"P0 漏洞"无定义、无检出方式（什么算 P0？谁来扫？）。

**影响**：门槛不可验证则阶段切换变成主观判断，与 40 README 自己强调的"只有当 Batch-5 验收通过后才拆第二阶段任务"的严谨风格不一致。

**改进建议**：每条门槛给出可观测证据（测试报告编号、手动验收记录、缺陷分级定义引用）。

### P2-7：与 30 的引用单向且稀疏

**证据**：矩阵"第一轮处理"列 23 行中，只有"线索 / 道具 / 情报"行引用了具体批次（"Batch 4 只补线索证据链和防剧透"），其余 22 行的"第一轮处理"（如"骰子/判定/规则：只稳定 COC 主检定和 Engine 权威裁决"）均未注明由哪个 Batch 承接（实际是 Batch 1/3 部分覆盖）。护栏中"测试库隔离""幂等与去重"等工程护栏实际由 Batch 1/2 承接，也未写明。

**影响**：读者无法从 40 反查"第一轮到底做了矩阵中的哪些行"，第一阶段结束时的对账（哪些行的"第一轮处理"已兑现）无法进行。

**改进建议**："第一轮处理"列逐行补 Batch 引用（或标"无承接"）。

## 4. 缺失项

1. **M0 安全最小集与阶段 5 完整体系的拆分**（见 P0-1）。
2. **能力域 ↔ 50 模块映射表**及 AI-Keeper 核心系统的归属说明（见 P1-4）。
3. **区间优先级的裁决规则**（升级条件、决策人、决策节点）。
4. **阶段切换的量化退出指标**（每阶段的可观测证据）。
5. **"上线前最低门槛"与"M0-Verified 发布门槛"的合并或从属声明**。
6. **优先级依据的真实出处**（"附件来源范围"所指的附件清单）。
7. **frontmatter 元数据**（status/owner/date，对齐 00-产品规范治理口径）。

## 5. 亮点

- 三层定位清晰且互相引用：30 管当前执行、40 管路线边界、50 管长期施工图，README 的"与现有文档的关系"表和"执行边界"5 条（尤其"任一平台能力进入实现前必须重新写成独立 DeepSeek Batch"）有效防止了外围功能混入第一轮。
- "第一轮不吸收的能力"负向清单（9 项）明确果断，与 00-路线图口径一致。
- 护栏文档的权限隐私矩阵（每类数据：默认可见范围 + 禁止事项）质量高，可直接作为评审 checklist；拆批模板（目标/范围/不做/数据边界/权限边界/验收命令/手动验收）可直接复用。

## 6. 结论与行动建议

**结论**：框架和边界意识是好的，但作为"规划文档"欠缺裁决：两处与 M0 规范的硬冲突（安全边界、语音）未裁决，优先级大量停留在区间，与 50 模块体系对不齐。评 C+。

**行动建议（按优先级）**：

1. 【P0】拆分跑团安全边界：M0 最小安全集（内容提醒/暂停/私密反馈/安全结束）提前并挂入 30 任务包体系，完整体系留阶段 5；登记 ADR。
2. 【P0】修正阶段 1 语音口径为"语音意图占位 + 文字兜底"。
3. 【P1】优先级矩阵区间改"当前级/目标级"两列并写明升级条件；"附件来源范围"列补真实出处或删除。
4. 【P1】补能力域 ↔ 50 模块映射表，补 AI-Keeper 核心系统行。
5. 【P1】合并"上线前最低门槛"与"M0-Verified 发布门槛"为单一门槛或显式从属。
6. 【P2】阶段切换门槛量化；"不依赖外部 VTT 才能跑"语病修正；矩阵"第一轮处理"列逐行补 Batch 引用；4 份文档补 frontmatter。
